IPC와 POSIX 메시지 큐

fork 뒤에는 메모리가 격리된다는 점에서 IPC의 필요성을 확인하고, POSIX 메시지 큐(mq_open · mq_send · mq_receive)의 우선순위·메시지 경계·블로킹과 요청/응답 큐를 쓰는 서버–클라이언트를 다루는 예제입니다.

실행해 볼 예제

  • isolatedfork 뒤에 자식이 전역 변수와 힙의 값을 고쳐도 부모에게는 보이지 않음을 보여 줍니다. 가상 주소는 같지만 서로 다른 메모리이며, 부모에게 돌아오는 것은 8비트 종료 상태뿐입니다.
  • pmqPOSIX 메시지 큐를 명령 하나씩으로 다룹니다: mq_open(O_CREAT | O_EXCL)으로 만들고, mq_send로 우선순위와 함께 넣고, mq_receive로 꺼내고, mq_getattr로 상태를 보고, mq_unlink로 지웁니다.
  • mqserver요청 큐 /w13_req 하나로 여러 클라이언트의 요청을 받아 대문자로 바꾼 뒤, 클라이언트마다 다른 응답 큐(/w13_rep.PID)로 돌려주는 서버입니다. SIGINT/SIGTERM을 받으면 큐를 지우고 끝납니다.
  • mqclient자기 응답 큐(/w13_rep.PID)를 먼저 만든 뒤 서버의 요청 큐에 요청을 넣고, mq_timedreceive로 최대 3초까지 답을 기다리는 클라이언트입니다. quit을 보내면 서버가 끝납니다.

이번 차시의 주제는 IPC(프로세스 사이의 통신)입니다. 앞의 두 부분에서는 IPC가 왜 필요한지와 어떤 종류가 있는지를 전체 지도로 정리하고, 뒤의 두 부분에서는 그중 POSIX 메시지 큐를 직접 써 봅니다. 예제는 isolated, pmq, mqserver, mqclient 네 개이고, 강의에 나오는 실행 결과는 Ubuntu 24.04 컨테이너에서 얻은 것입니다.

지금까지 온 길

10주차에는 fork, exec, wait로 프로세스를 만들고 바꾸고 거두는 법을 배웠습니다. 만들 줄은 알게 되었지만, 자식이 부모에게 돌려줄 수 있는 것은 종료 상태뿐이어서 "그보다 더 보낼 수는 없는가"라는 질문이 남았습니다. 11주차에는 mmap 공유 매핑으로 메모리를 함께 보았는데, 동시에 쓰면 값이 깨졌고 "순서는 누가 맞추는가"가 남았습니다. 12주차에는 파이프와 FIFO로 바이트를 흘려 보냈지만, 경계가 없고 한 방향이었으며 "서로 모르는 사이라면 어떻게 하는가"가 남았습니다.

이 세 주 동안 쓴 도구는 모두 IPC의 한 종류였습니다. 다만 공유 매핑과 파이프는 둘 다 fork로 이어진 프로세스 사이에서만 썼습니다. 오늘은 이 도구들을 전체 그림 위에 다시 놓고, "서로 모르는 프로세스가 메시지 단위로 주고받으려면 어떻게 하는가"라는 질문에 메시지 큐로 답합니다.

1부 왜 IPC인가

프로세스는 서로의 메모리를 볼 수 없습니다. 그런데도 프로그램을 여러 프로세스로 나누는 이유가 있고, 나눈 프로세스가 함께 일하려면 필요한 것이 있습니다. 1부는 이 두 가지를 다룹니다.

프로세스는 서로의 메모리를 볼 수 없다

주소 공간은 프로세스마다 따로 있습니다. 부모와 자식이 똑같은 가상 주소를 쓰더라도 페이지 테이블이 각자 다르기 때문에, 프로세스가 다르면 그 주소는 다른 물리 메모리를 가리킵니다. fork는 복사입니다. 자식은 부모 메모리의 사본을 받고, 어느 한쪽이 쓰는 순간 그 페이지가 갈라집니다(쓰기 시 복사, copy-on-write). 그래서 자식이 counter를 100에서 101로 고쳐도 부모의 counter는 100 그대로입니다.

같은 이유로 포인터를 넘겨도 소용이 없습니다. 주소는 그 프로세스 안에서만 뜻이 있기 때문입니다.

이 벽은 운영체제가 일부러 만든 것입니다. 한 프로세스의 버그나 악의가 다른 프로세스를 망치지 못하게 하려는 것입니다.

입문 예제 isolated: 같은 주소, 다른 값

isolated는 IPC 함수를 하나도 쓰지 않습니다. IPC가 없으면 어떻게 되는지를 보는 예제입니다. 프로그램은 값 둘을 준비합니다. 데이터 영역의 전역 변수 counter = 100과, malloc으로 얻은 힙의 *heap = 200입니다. 그다음 fork를 부르면 그 줄부터 프로세스가 둘이 되고, 각자 counter와 heap을 따로 갖게 됩니다.

자식은 두 값을 1씩 올리고 값과 주소를 함께 출력한 뒤 42로 끝납니다.

    if (pid == 0) {                     /* 자식: 두 값을 고친다 */
        counter += 1;
        *heap += 1;
        printf("[자식 %d] counter=%d (%p)  *heap=%d (%p)\n", (int)getpid(),
               counter, (void *)&counter, *heap, (void *)heap);
        return 42;                      /* 부모에게 가는 것은 이 8비트뿐 */
    }

부모는 waitpid(pid, &status, 0)으로 자식이 값을 고치고 끝날 때까지 기다린 뒤에 같은 변수의 값과 주소를 출력합니다. 먼저 기다리기 때문에 "부모가 자식보다 먼저 출력해서 그런 것 아닌가" 하는 순서 문제가 없어집니다. 마지막으로 WEXITSTATUS(status)로 자식의 종료 상태를 꺼내 출력합니다.

실행 결과에서 볼 것은 세 가지입니다.

  • 주소는 같습니다. 자식 줄과 부모 줄의 괄호 안 주소가 한 글자도 다르지 않습니다. 출력된 것이 가상 주소이기 때문입니다.
  • 값은 다릅니다. 자식은 101과 201을, 부모는 100과 200을 출력합니다. 자식이 고친 것은 사본이었습니다. 전역 변수든 힙이든 fork 뒤에는 각자의 사본입니다.
  • 돌아온 것은 42뿐입니다. 아무 장치 없이 자식에게서 부모로 돌아오는 정보는 종료 상태 한 바이트가 전부입니다. 그보다 더 보내려면 다른 길이 필요하고, 그 길이 IPC입니다.

그런데 왜 프로세스를 여럿으로 나누나

벽(격리)은 단점이 아니라 프로세스를 나누는 이유입니다. 나누어서 얻는 것은 네 가지입니다.

  1. 고장을 가둡니다. 한 프로세스가 죽어도 다른 프로세스는 계속 돕니다. 브라우저의 탭 하나가 멈춰도 다른 탭이 멀쩡한 것이 그 예입니다.
  2. 권한을 나눕니다. 위험한 입력을 다루는 부분을 권한이 적은 프로세스에 둡니다. 예를 들어 네트워크를 받는 부분과 파일을 쓰는 부분을 가릅니다.
  3. 조합해서 씁니다. 이미 있는 프로그램을 고치지 않고 이어 붙입니다. 12주차 미니 셸에서 다룬 ls | grep | wc가 그 예입니다.
  4. 동시에 일합니다. 코어가 여러 개면 프로세스 여럿이 함께 달립니다. 10주차의 forkpool처럼 요청마다 일꾼 프로세스를 두는 구조입니다.

다만 나누면 벽이 생깁니다. 나눈 프로세스가 함께 일하려면 벽을 넘는 약속된 통로가 있어야 하고, 그것이 IPC입니다.

실제 프로그램은 이미 여러 프로세스다

프로그램프로세스를 나눈 방식주고받는 것쓰는 IPC
셸 파이프라인 ls | grep | wc명령마다 프로세스 하나앞 명령의 출력(바이트)파이프
웹 브라우저탭 · 기능마다 프로세스"이 주소를 열어라" 같은 명령, 그려 낸 화면 데이터소켓(메시지) + 공유 메모리
데이터베이스 서버연결마다 일꾼 프로세스질의와 결과, 모두가 함께 보는 버퍼소켓 + 공유 메모리 + 세마포어
데스크톱 · 시스템 서비스서비스마다 프로세스요청과 알림 메시지유닉스 소켓 위의 메시지 버스(D-Bus)

강의의 실행 결과를 얻은 컨테이너도 docker 명령(클라이언트)이 유닉스 소켓으로 Docker 데몬(서버)에 요청해서 띄운 것입니다.

함께 일하려면 필요한 세 가지

  1. 건넨다 — 전달. A가 가진 것을 B에게 보냅니다. 보낸 뒤에는 각자의 사본입니다. 일상의 편지나 택배에 해당하고, 파이프 · 메시지 큐 · 소켓이 여기에 속합니다.
  2. 함께 본다 — 공유. 같은 데이터를 둘이 봅니다. 한쪽이 고치면 다른 쪽에 바로 보입니다. 같이 쓰는 칠판에 해당하고, 공유 메모리 · 공유 매핑이 여기에 속합니다.
  3. 때를 맞춘다 — 동기화. 한 번에 한 명만 쓰게 하거나, 준비되면 상대를 깨웁니다. 화장실 열쇠나 초인종에 해당하고, 세마포어 · 파일 잠금 · 시그널이 여기에 속합니다.

공유는 빠르지만 동기화 없이는 위험합니다. 11주차 race 실험에서 값이 사라진 이유가 바로 이것입니다. 이 세 가지(통신에 해당하는 전달 · 공유와, 동기화)가 2부 분류 지도의 뼈대가 됩니다.

벽을 넘는 길은 커널을 지난다

프로세스 A가 프로세스 B의 메모리를 직접 읽는 방법은 없습니다. 그래서 커널에 부탁합니다. IPC는 "커널이 관리하는 객체 + 그것을 다루는 시스템 호출"입니다. IPC 객체는 커널 안에 있고, 프로세스는 fd나 식별자로 그것을 가리키며, 시스템 호출로만 커널에 들어갑니다. 한쪽은 보내고 · 붙이고 · 잠그고, 다른 쪽은 받고 · 붙이고 · 기다립니다.

커널이 맡는 일은 권한 검사, 순서, 기다리게 하고 깨우기, 객체의 수명 관리입니다. 객체마다 누가 열 수 있는지(권한)가 정해져 있습니다.

공유 메모리만 조금 다릅니다. 양쪽 주소 공간에 같은 페이지를 한 번 붙이고 나면, 그 뒤로는 시스템 호출 없이 읽고 씁니다.

이미 써 본 IPC 여섯 가지

전달(종료 상태 · 파일 · 파이프 · FIFO), 공유(공유 매핑), 알림(시그널) — 세 종류를 이미 모두 써 보았습니다. 각각의 한계를 정리하면 다음과 같습니다.

방법주차전하는 것한계

시그널9주차"일이 생겼다"는 번호 하나내용을 실을 수 없다. 겹치면 하나로 합쳐진다

파이프로는 안 되는 일

파이프가 나쁘다는 뜻은 아닙니다. 부모와 자식 사이의 한 방향 스트림에는 여전히 파이프가 가장 간단합니다. 다만 파이프로는 메우지 못하는 자리가 다섯 군데 있고, 그 자리마다 다른 IPC가 있습니다.

파이프의 한계구체적으로이것을 메우는 IPC
① 경계가 없다write 세 번이 read 한 번에 붙어 나온다메시지 큐 — 보낸 단위 그대로 (오늘)
② 순서를 바꿀 수 없다급한 것도 줄 맨 뒤에 선다메시지 큐의 우선순위 (오늘)
③ 서로 모르면 못 쓴다fd를 물려받아야 한다 (FIFO는 이름이 있지만 경계가 없다)이름으로 여는 메시지 큐 · 소켓
④ 큰 데이터에 느리다보내는 쪽 → 커널 → 받는 쪽, 복사 두 번공유 메모리 — 복사 없음
⑤ 한 컴퓨터 안에서만커널 하나의 버퍼다소켓 — 다른 컴퓨터까지

1부 정리

  • 프로세스는 격리되어 있습니다. 주소 공간이 따로이고, 이것은 운영체제가 일부러 세운 벽입니다. isolated가 보여 준 것이 이것입니다 — 같은 주소, 다른 값, 그리고 돌아온 것은 종료 상태 42 하나.
  • 그래도 여럿으로 나눕니다. 고장을 가두고, 권한을 나누고, 조합하고, 동시에 일하기 위해서입니다.
  • 나눈 프로세스는 함께 일해야 합니다. 건네고(전달), 함께 보고(공유), 때를 맞춥니다(동기화).
  • 벽을 넘는 문은 커널이 내 줍니다. IPC는 프로세스가 커널의 객체를 통해 데이터를 주고받고 때를 맞추는 일이며, 종류마다 잘하는 일이 다릅니다.

2부 IPC의 지도

IPC는 종류가 많습니다. 함수 이름을 외우기 전에 나누는 기준부터 세웁니다. 전달인가 공유인가, 스트림인가 메시지인가, 어떤 이름으로 만나고 언제까지 남는가입니다.

IPC 분류 지도

분류는 M. Kerrisk의 The Linux Programming Interface 43장의 그림을 따릅니다. IPC는 크게 통신(데이터가 오간다), 동기화(때를 맞춘다), 시그널로 나뉩니다.

  • 통신
    • 데이터 전달 — 바이트 스트림: 파이프 · FIFO(12주차), 스트림 소켓
    • 데이터 전달 — 메시지: 메시지 큐(오늘), 데이터그램 소켓
    • 공유 메모리: POSIX 공유 메모리, mmap 공유 매핑(11주차)
  • 동기화
    • 세마포어: POSIX 세마포어(이름 있는 것 · 이름 없는 것)
    • 파일 잠금: flock, fcntl 레코드 잠금
  • 시그널: kill, sigaction(9주차) — 내용 없이 "일이 생겼다"만 알립니다.

전달과 공유: 복사 횟수가 다르다

전달(파이프 · 메시지 큐 · 소켓)에서는 데이터가 두 번 복사됩니다. 보내는 시스템 호출에서 A의 버퍼가 커널의 버퍼로 복사되고, 받는 시스템 호출에서 커널의 버퍼가 B의 버퍼로 복사됩니다. 그 결과는 다음과 같습니다.

  • 보낸 뒤에는 각자의 사본이므로 서로 방해하지 않습니다.
  • 비어 있으면 받는 쪽이, 가득 차 있으면 보내는 쪽이 기다립니다.
  • 순서와 기다림을 커널이 맡습니다.
  • 데이터가 크면 복사 비용이 커집니다.

공유(공유 메모리 · 공유 매핑)에서는 복사가 0번입니다. A의 포인터와 B의 포인터가 같은 물리 페이지를 가리키므로 둘이 같은 메모리를 봅니다.

  • 한쪽이 쓰면 다른 쪽에 바로 보입니다.
  • 읽고 쓰는 데 시스템 호출이 없어서 가장 빠릅니다.
  • 한 번 붙인 뒤에는 커널이 끼어들지 않으므로, 순서와 기다림을 프로그램이 직접 맞춰야 합니다.
  • 그래서 세마포어 같은 동기화와 짝을 이룹니다.

정리하면, 작은 메시지를 주고받을 때는 전달을, 큰 데이터를 여럿이 볼 때는 공유와 동기화를 함께 씁니다.

바이트 스트림과 메시지

12주차에 본 파이프의 성질 가운데 "바이트 스트림"의 반대편에 있는 것이 오늘의 메시지 큐입니다.

바이트 스트림인 파이프에 write("abc"), write("de"), write("fgh")를 차례로 하면 안에서는 abcdefgh로 이어집니다. 받는 쪽의 read는 예를 들어 "abcde"와 "fgh"로 나올 수 있고, 어디서 끊길지는 알 수 없습니다. 스트림에서는 "한 메시지가 어디까지인가"를 받는 쪽이 직접 알아내야 하므로, 줄바꿈이나 길이 머리표를 써서 프로그램이 끊습니다. 파이프 · FIFO · TCP가 이쪽입니다.

메시지 큐에 send("abc"), send("de"), send("fgh")를 하면 receive는 "abc", "de", "fgh"를 하나씩 돌려줍니다. 보낸 단위 그대로 나오도록 경계를 지켜 줍니다. 메시지 큐 · UDP가 이쪽입니다.

대신 메시지에는 크기 한도가 있습니다. 메시지 하나의 최대 크기가 정해져 있으며, 구체적인 값은 3부의 mq_open에서 다룹니다.

서로를 찾는 법: 약속한 이름

이름이 있으면 fork로 이어지지 않은 프로세스끼리도, 서로 다른 시각에 시작한 프로세스끼리도 만날 수 있습니다. 만드는 쪽이 mq_open("/w13", O_CREAT, …)로 커널 객체에 이름 "/w13"을 붙여 두면, 나중에 온 쪽은 mq_open("/w13", O_WRONLY)로 같은 객체를 엽니다.

종류이름의 모양예만나는 방법

수명: 누가 지울 때까지 남는가

  • 프로세스 수명 — 파이프 · 소켓. 가리키는 fd가 모두 닫히면 사라집니다. 프로세스가 죽으면 커널이 알아서 치웁니다.
  • 커널 수명 — 메시지 큐 · 공유 메모리 · 세마포어. 만든 프로세스가 끝나도 남고, 안의 데이터도 남습니다. 지우거나 재부팅할 때까지입니다. man 7 mq_overview도 "POSIX message queues have kernel persistence"라고 적고 있습니다.
  • 파일 시스템 수명 — 파일 · 파일에 대한 매핑. 재부팅해도 남고, 지울 때까지 디스크에 있습니다.

커널 수명의 좋은 점은 받는 쪽이 아직 없어도 보내 둘 수 있다는 것입니다. 나쁜 점은 지우지 않으면 쌓인다는 것입니다.

둘러보기: 이 시스템의 IPC 객체

커널 수명 객체는 파일 시스템에서 들여다볼 수 있습니다. /dev/mqueue는 POSIX 메시지 큐가 파일처럼 보이는 곳으로, ls · cat · rm이 됩니다. /dev/shm은 POSIX 공유 메모리와 이름 있는 세마포어가 파일로 보이는 곳입니다. 아직 만든 것이 없으므로 지금은 비어 있고, 3부에서 큐를 만들면 여기에 나타납니다.

먼저 가장 단순한 것을 고르고, 그것으로 안 되는 이유가 생기면 다음으로 갑니다. 정답이 하나인 것도 아닙니다. 큰 프로그램은 명령은 메시지로, 큰 데이터는 공유 메모리로 나눠 씁니다. 앞에서 본 브라우저와 데이터베이스 서버가 그 예입니다.

3부 POSIX 메시지 큐

메시지 큐는 커널 안의 우편함입니다. 이름으로 열고, 메시지 단위로 넣고 꺼내고, 다 쓰면 이름을 지웁니다.

메시지 큐: 커널 안의 우편함

여러 프로세스가 mq_send로 같은 큐 "/w13"에 메시지를 넣고, 다른 프로세스가 mq_receive로 꺼냅니다. 보내는 쪽과 받는 쪽이 동시에 떠 있지 않아도 됩니다. 우편함에 넣어 두면 나중에 꺼내 가면 됩니다. 메시지 큐의 성질은 세 가지로 요약됩니다.

  • 메시지 단위. 넣은 덩어리 그대로 하나씩 나옵니다. 길이도 함께 알려 줍니다.
  • 우선순위. 숫자가 큰 것이 먼저 나옵니다. 같으면 먼저 넣은 것이 먼저 나옵니다. 예를 들어 first(우선순위 1) → urgent(5) → second(1) 순서로 보내면, 받는 순서는 urgent(5) → first(1) → second(1)입니다.
  • 이름과 수명. 권한이 맞으면 누구나 "/w13"이라는 이름으로 엽니다. 지울 때까지 남습니다.

파이프와 견주면 경계가 지켜지고, 급한 것이 앞서고, 이름이 있고, 남는다는 점이 다릅니다.

API 한눈에: 파일과 닮았다

헤더는 <mqueue.h>입니다. glibc 2.34 이전에는 -lrt로 링크해야 하며, 예제의 Makefile에 넣어 두었습니다. macOS에는 POSIX 메시지 큐가 없습니다.

함수는 다섯 개가 중심입니다. mq_open은 이름으로 열거나 만들고, mq_send는 메시지 하나를 넣고, mq_receive는 메시지 하나를 꺼내고, mq_close는 내 디스크립터를 닫고, mq_unlink는 이름을 지웁니다. 파일 API와 한 쌍씩 대응합니다.

하는 일파일POSIX 메시지 큐다른 점

넣는다write(fd, buf, n)mq_send(q, buf, n, prio)통째로 들어가거나 실패 · 우선순위가 붙는다

mq_open: 이름 · 플래그 · 속성

mqd_t mq_open(const char *name, int oflag,
              mode_t mode, struct mq_attr *attr);
  • name — "/w13"처럼 "/" 하나로 시작하고, 그 뒤에는 "/"가 없어야 합니다.
  • oflag — 읽기 · 쓰기 방향에 O_CREAT, O_EXCL, O_NONBLOCK을 더합니다.
  • mode — 0600처럼 파일과 같은 권한 비트이며 umask가 적용됩니다.
  • attr — mq_maxmsg는 큐에 쌓을 수 있는 최대 개수, mq_msgsize는 메시지 하나의 최대 바이트입니다.
struct mq_attr attr = { .mq_maxmsg = 10, .mq_msgsize = 128 };
mqd_t q = mq_open("/w13", O_CREAT | O_EXCL | O_RDWR, 0600, &attr);

인자 넷을 모두 쓰는 것은 만들 때뿐입니다. O_CREAT일 때만 mode와 attr을 보고, 이미 있는 큐를 열기만 할 때는 앞의 둘만 줍니다.

용량은 처음에 정합니다. mq_maxmsg와 mq_msgsize는 만든 뒤에 바꿀 수 없고, 바꾸려면 지우고 다시 만들어야 합니다. 큐 하나가 차지하는 커널 메모리가 대략 maxmsg × msgsize이기 때문에 상한도 있습니다. 강의 환경에서는 /proc/sys/fs/mqueue/msg_max가 10, msgsize_max가 8192였고, attr이 NULL이면 기본값 10개 × 8192바이트로 만들어집니다.

실패하면 (mqd_t)-1을 돌려줍니다. 흔한 errno는 EEXIST, ENOENT, EINVAL, EACCES이며, 아래 pmq 실행에서 직접 확인합니다.

mq_send · mq_receive의 규칙

상황결과뜻
send · 자리가 있다0을 반환통째로 들어갔다 — 일부만 들어가는 일은 없다
send · 큐가 가득 찼다잠든다 (O_NONBLOCK: -1, EAGAIN)받는 쪽이 하나 꺼낼 때까지 기다린다
send · msgsize보다 길다-1, errno = EMSGSIZE잘라서 넣어 주지 않는다 — 프로그램이 나눠야 한다
receive · 메시지가 있다받은 길이를 반환우선순위가 가장 높은 것 중 가장 오래된 것 하나
receive · 큐가 비었다잠든다 (O_NONBLOCK: -1, EAGAIN)누군가 넣을 때까지 — EOF라는 것이 없다
receive · 버퍼 < msgsize-1, errno = EMSGSIZE버퍼는 항상 큐의 mq_msgsize 이상으로 잡는다

눈여겨볼 것은 끝 알림이 없다는 점입니다. 파이프의 read는 쓰는 쪽이 모두 닫으면 0(EOF)을 돌려줬지만, 메시지 큐에는 그런 것이 없어서 빈 큐의 mq_receive는 누군가 넣을 때까지 계속 기다립니다. 기다림에 시간 제한을 두려면 mq_timedsend · mq_timedreceive를 씁니다. 4부의 클라이언트가 이것을 씁니다.

파이프 쪽 값은 12주차에 실제로 잰 것이고, 메시지 큐 쪽은 아래 pmq 실행에서 확인합니다.

예제 pmq: 명령 하나에 동작 하나

pmq는 POSIX 메시지 큐를 명령 하나에 동작 하나씩으로 다루는 프로그램입니다.

./pmq create|send|recv|stat|unlink /NAME …

명령을 실행할 때마다 새 프로세스가 뜨므로, 서로 다른 프로세스가 이름 하나로 같은 큐를 쓰는 것을 출력되는 PID로 확인할 수 있습니다.

만들기는 attr에 용량을 적고 O_CREAT | O_EXCL로 엽니다. O_EXCL이 있으므로 같은 이름이 이미 있으면 EEXIST로 실패합니다. 만든 뒤 곧바로 mq_close를 부르지만, 닫아도 큐와 이름은 남고 프로세스가 끝나도 남습니다.

    struct mq_attr attr = { .mq_maxmsg = maxmsg, .mq_msgsize = msgsize };
    /* O_EXCL: 같은 이름이 이미 있으면 EEXIST로 실패한다 */
    mqd_t q = mq_open(name, O_CREAT | O_EXCL | O_RDWR, 0600, &attr);

넣기는 이름만으로 큐를 엽니다. 만든 프로세스가 아니어도 됩니다. 메시지 하나는 "바이트 덩어리 + 우선순위"이고, mq_send의 인자는 큐, 버퍼, 길이, 우선순위 순서입니다. 큐가 가득 차 있으면 기다립니다.

    mqd_t q = mq_open(name, O_WRONLY);  /* 만든 프로세스가 아니어도 된다 */
    …
    if (mq_send(q, text, strlen(text), prio) == -1) die("mq_send");

꺼내기에서는 버퍼 크기가 중요합니다. 버퍼가 큐의 mq_msgsize보다 작으면 EMSGSIZE로 실패하므로, mq_getattr로 msgsize를 물어 그만큼 잡습니다. mq_receive는 메시지 하나를 통째로 돌려주며, 반환값이 길이이고 prio에 우선순위가 담깁니다. recv에 -n을 주면 O_NONBLOCK으로 열어서, 큐가 비었을 때 기다리지 않고 EAGAIN으로 실패합니다.

    mqd_t q = mq_open(name, O_RDONLY | (nonblock ? O_NONBLOCK : 0));
    …
    struct mq_attr attr;
    if (mq_getattr(q, &attr) == -1) die("mq_getattr");
    char *buf = malloc(attr.mq_msgsize + 1);    /* msgsize 이상이어야 한다 */
    …
    unsigned prio;
    ssize_t n = mq_receive(q, buf, attr.mq_msgsize, &prio);

pmq 실행 ①: 넣은 순서와 꺼낸 순서

큐를 만들고 메시지 셋을 넣은 뒤 셋을 꺼내 보면 다음을 확인할 수 있습니다.

  • PID가 모두 다릅니다. 강의의 실행에서는 [275]부터 [281]까지 일곱 개의 서로 다른 프로세스가 이름 하나로 같은 큐에서 만났습니다.
  • 급한 것이 먼저 나옵니다. 나중에 넣은 우선순위 5가 가장 먼저 나왔고, 같은 우선순위 1끼리는 넣은 순서대로 나왔습니다.
  • 경계가 지켜졌습니다. 받은 길이가 6, 10, 11로, 보낸 덩어리 그대로 하나씩 나왔습니다.

pmq 실행 ②: 이름 · 수명 · 기다림

  • 큐가 파일처럼 보입니다. /dev/mqueue/w13이 생기고, 그 큐를 열고 있는 프로세스가 하나도 없어도 남아 있습니다.
  • 쌓인 양을 볼 수 있습니다. 이 파일을 cat으로 보면 QSIZE:10처럼 나옵니다. QSIZE는 쌓인 메시지의 바이트 합으로, "still here"가 10바이트입니다.
  • 빈 큐의 recv는 잠듭니다. 강의의 실행에서는 [346]이 빈 큐에서 기다리다가 [347]이 메시지를 넣자 깨어났습니다. 깨우는 일은 커널이 합니다.

pmq 실행 ③: 흔한 오류 다섯 가지

  • EEXIST — 이미 있는 큐를 또 만들었습니다.
  • ENOENT — 없는 큐를 열었습니다. 이 둘은 파일에서 보던 것과 같은 오류입니다.
  • EAGAIN — 기다리지 않겠다고(O_NONBLOCK) 했는데 큐가 비어 있었습니다.
  • EMSGSIZE — 한도보다 긴 메시지를 보냈습니다.
  • EINVAL 두 가지 — 이름이 "/"로 시작하지 않았거나, maxmsg가 한도 10을 넘었습니다.

3부 정리: 메시지 큐의 한 살이

  1. 만든다 — mq_open + O_CREAT. 용량은 이때 정합니다.
  2. 넣는다 — mq_send. 통째로, 우선순위와 함께.
  3. 꺼낸다 — mq_receive. 하나씩, 충분히 큰 버퍼로.
  4. 닫는다 — mq_close. 큐는 남습니다.
  5. 지운다 — mq_unlink. 잊으면 쌓입니다.

파일의 open · write · read · close · unlink와 한 쌍씩 대응하고, 다른 점은 메시지 단위와 우선순위입니다. 보낸 덩어리 그대로 하나씩 나오고, 우선순위가 높은 것이 먼저, 같으면 넣은 순서입니다. "/이름"으로 누구나 만나고, 프로세스가 끝나도 남으며, /dev/mqueue에서 보입니다. 그리고 EOF도 SIGPIPE도 없으므로, 끝은 메시지로 약속하고 기다림에는 시간 제한을 둡니다.

4부 요청–응답 서버

앞의 다섯 함수로 여러 클라이언트의 요청을 받는 서버를 만듭니다. 프로세스가 여럿이면 실패하는 방법도 여럿이라는 것을 함께 봅니다.

구조: 요청 큐는 하나, 응답 큐는 클라이언트마다

여러 송신자가 한 수신자에게 보내는 일은 큐 하나로 충분합니다. 반대로 한 송신자가 여러 수신자에게 보내려면 받는 쪽마다 큐를 둡니다. 그래서 구조는 다음과 같습니다.

  • 요청 큐 "/w13_req" — 모두가 아는 이름입니다. 서버가 만들고, 클라이언트는 이름만 알면 요청을 넣습니다.
  • 응답 큐 "/w13_rep.PID" — 클라이언트의 PID가 이름에 들어갑니다. 클라이언트가 만들고, 요청 안에 자기 PID를 적어서 돌아올 곳을 알립니다. 편지 봉투에 보내는 사람 주소를 적는 것과 같습니다.

요청은 { 내 PID, 문자열 }이고 응답은 { 순번, 결과 }입니다. 응답 큐를 클라이언트마다 나누는 이유는, 하나를 같이 쓰면 남의 응답을 꺼내 갈 수 있기 때문입니다. 각 응답 큐는 그 클라이언트만 읽습니다.

요청 하나의 여정

  1. 클라이언트가 응답 큐 /w13_rep.PID를 만듭니다.
  2. 클라이언트가 요청을 /w13_req에 넣습니다.
  3. 서버가 요청을 꺼냅니다.
  4. 서버가 처리합니다(대문자로 바꿉니다).
  5. 서버가 응답을 /w13_rep.PID에 넣습니다.
  6. 클라이언트가 응답을 꺼냅니다(3초 이내).
  7. 클라이언트가 응답 큐를 닫고 지웁니다.

서버는 3 → 4 → 5를 한 번에 하나씩 되풀이합니다. 순서대로 처리하는 서버입니다. 이 흐름에서 세 가지 설계 결정에 주목합니다.

  • 1이 2보다 먼저입니다. 요청을 먼저 보내면, 서버가 응답 큐를 열려고 할 때 아직 큐가 없을 수 있습니다.
  • 6에는 시간 제한을 둡니다. 2와 6 사이에 클라이언트는 잠들어 있습니다. 그동안 서버가 죽으면 영원히 기다리게 되므로 3초 뒤에 포기합니다.
  • 7은 만든 쪽이 합니다. 응답 큐는 클라이언트가 만들었으니 클라이언트가 지웁니다.

예제 mqserver · mqclient

mqserver와 mqclient는 문자열을 보내면 대문자로 바꿔 돌려주는 요청–응답 서버와 클라이언트입니다.

./mqserver &
./mqclient TEXT
./mqclient quit

proto.h: 두 프로그램의 약속

두 프로그램이 지켜야 할 약속(프로토콜)은 공용 헤더 proto.h에 적습니다.

#define REQ_QUEUE "/w13_req"            /* 서버의 요청 큐: 모두가 아는 이름 */
#define TEXT_MAX  64

struct request {                        /* 클라이언트 → 서버 */
    pid_t pid;                          /* 응답을 돌려받을 곳 */
    char  text[TEXT_MAX];
};

struct reply {                          /* 서버 → 클라이언트 */
    int  seq;                           /* 서버가 처리한 순번 */
    char text[TEXT_MAX];
};

/* 응답 큐의 이름은 클라이언트마다 다르다: /w13_rep.PID */
static inline void reply_name(char *buf, size_t size, pid_t pid)
{
    snprintf(buf, size, "/w13_rep.%d", (int)pid);
}
  • 요청 큐의 이름. 서버와 클라이언트가 같은 헤더를 포함해 같은 이름을 씁니다.
  • 메시지의 모양. 구조체 하나가 메시지 하나입니다. 메시지 큐가 경계를 지켜 주기 때문에 가능한 방식입니다.
  • 응답 큐의 이름. PID로 이름을 만듭니다. 양쪽이 같은 함수 reply_name을 쓰므로 이름이 어긋나지 않습니다.

mqserver: 준비하고, 받고, 처리하고, 돌려준다

서버는 먼저 SIGINT와 SIGTERM에 처리기를 답니다. Ctrl-C가 오면 처리기가 stop을 세웁니다. 이때 SA_RESTART를 주지 않았기 때문에, 잠들어 있던 mq_receive가 EINTR로 깨어나고 반복문이 stop을 다시 확인할 수 있습니다.

요청 큐는 지난 실행이 남긴 것을 먼저 지우고 새로 만듭니다. mq_msgsize는 요청 구조체의 크기로 잡습니다.

    struct mq_attr attr = { .mq_maxmsg = 10,
                            .mq_msgsize = sizeof(struct request) };
    mq_unlink(REQ_QUEUE);               /* 지난 실행이 남긴 큐를 치운다 */
    mqd_t reqq = mq_open(REQ_QUEUE, O_CREAT | O_EXCL | O_RDONLY, 0622, &attr);

반복문은 한 번에 요청 하나를 받습니다. 받은 문자열의 마지막 칸에는 서버가 직접 널 문자를 넣습니다. 받은 것을 믿지 않기 때문입니다. 내용이 quit이면 반복을 끝냅니다.

        if (mq_receive(reqq, (char *)&req, sizeof req, NULL) == -1) {
            if (errno == EINTR) continue;       /* 시그널: stop을 다시 본다 */
            perror("mq_receive");
            break;
        }
        req.text[TEXT_MAX - 1] = '\0';          /* 받은 것은 믿지 않는다 */
        if (!strcmp(req.text, "quit")) break;

처리는 순번을 매기고 toupper로 대문자로 바꾸는 세 줄이 전부입니다. 서버의 "일"은 이것뿐이고, 나머지는 주고받기와 실패 대비입니다.

응답을 돌려줄 때는 요청에 적힌 PID로 응답 큐의 이름을 만들어 엽니다. 열리지 않으면 클라이언트가 이미 떠난 것이므로, 기록만 남기고 다음 요청으로 넘어갑니다. 응답 큐를 O_NONBLOCK으로 열기 때문에, 응답 큐가 가득 차 있더라도 서버가 거기서 멈추지 않습니다.

        reply_name(name, sizeof name, req.pid);
        mqd_t repq = mq_open(name, O_WRONLY | O_NONBLOCK);
        if (repq == (mqd_t)-1) {                /* 클라이언트가 이미 떠났다 */
            fprintf(stderr, "[서버] #%d PID %d: 응답 큐 없음 (%s)\n", seq,
                    (int)req.pid, strerror(errno));
            continue;
        }
        if (mq_send(repq, (char *)&rep, sizeof rep, 0) == -1)
            perror("mq_send");
        mq_close(repq);

반복이 끝나면 요청 큐를 닫고 mq_unlink(REQ_QUEUE)로 이름을 지웁니다. 이름을 지워야 큐가 사라집니다.

mqclient: 응답 큐를 만들고, 요청을 넣고, 시간 제한을 두고 기다린다

클라이언트는 먼저 자기 PID로 이름을 만들어 응답 큐를 만듭니다. 응답은 하나만 받으면 되므로 mq_maxmsg는 1이면 충분합니다. 요청을 보낸 뒤에 만들면 늦을 수 있으므로 반드시 요청보다 먼저 만듭니다.

    reply_name(name, sizeof name, req.pid);
    struct mq_attr attr = { .mq_maxmsg = 1,
                            .mq_msgsize = sizeof(struct reply) };
    mqd_t repq = mq_open(name, O_CREAT | O_EXCL | O_RDONLY, 0622, &attr);

그다음 서버의 요청 큐를 이름으로 찾습니다. 요청 큐가 없으면 서버가 없는 것이므로, 그 사실(ENOENT)을 알리고 끝냅니다. 큐가 열리면 요청 구조체를 통째로, 길이는 sizeof로 주어 넣습니다. quit을 보낸 경우에는 응답을 기다리지 않습니다.

    mqd_t reqq = mq_open(REQ_QUEUE, O_WRONLY);
    if (reqq == (mqd_t)-1) {
        perror("서버가 없다: mq_open(" REQ_QUEUE ")");
        goto out;
    }
    if (mq_send(reqq, (char *)&req, sizeof req, 0) == -1) {
        perror("mq_send");
        goto out;
    }
    if (quit) { rc = 0; goto out; }

응답은 mq_timedreceive로 기다립니다. 시간 제한은 "몇 초 동안"이 아니라 "언제까지"라는 마감 시각으로 줍니다. 그래서 지금 시각을 얻어 3초를 더합니다. 마감까지 응답이 오지 않으면 ETIMEDOUT으로 실패합니다.

    struct timespec until;
    clock_gettime(CLOCK_REALTIME, &until);
    until.tv_sec += 3;
    struct reply rep;
    if (mq_timedreceive(repq, (char *)&rep, sizeof rep, NULL, &until) == -1) {
        perror("응답 없음: mq_timedreceive");
        goto out;
    }

뒷정리는 out: 표지 아래에 모여 있어서 성공이든 실패든 반드시 지나갑니다. 응답 큐를 닫고 mq_unlink(name)으로 이름을 지웁니다. 내 응답 큐는 내가 지웁니다.

실행 ①: 클라이언트 여럿, 서버 하나

  • 응답이 주인을 찾아갑니다. 강의의 실행에서는 클라이언트 466이 APPLE, 467이 BANANA, 468이 CHERRY를 받았고 서로 섞이지 않았습니다.
  • mqd_t는 fd였습니다. 서버의 fd 3번이 /w13_req를 가리키고 있습니다. 이것은 Linux의 구현 방식입니다.
  • 끝난 뒤 남은 것이 없습니다. 응답 큐는 클라이언트가, 요청 큐는 서버가 지웠습니다.

실행 ②: 서버가 없을 때, 멈췄을 때

  • 서버가 없으면 ENOENT입니다. 요청 큐의 이름이 없으므로, 클라이언트는 기다리지 않고 바로 압니다.
  • 서버가 멈췄으면 3초 뒤에 포기합니다. 요청은 큐에 들어갔지만 응답이 오지 않고, 클라이언트는 ETIMEDOUT으로 끝납니다.
  • 늦은 응답은 갈 곳이 없습니다. 서버가 다시 깨어나 요청을 처리했지만 클라이언트는 이미 떠났고 응답 큐도 없습니다. 그래도 서버는 죽지 않고 다음 요청으로 넘어갑니다.

프로세스가 여럿이면 실패도 여럿이다

아래는 한 프로세스 안에서는 없던 문제들입니다. 함수 호출에서는 상대가 "없거나 멈춰 있는" 일이 없기 때문입니다.

일어날 수 있는 일어떻게 드러나나예제의 대비
서버가 아직 없다요청 큐를 열 때 ENOENT알리고 끝낸다 (mqclient)
서버가 멈췄다 · 죽었다응답이 오지 않는다 (오류도 없다)mq_timedreceive로 3초까지만 (mqclient)
클라이언트가 먼저 떠났다응답 큐를 열 때 ENOENT기록하고 다음 요청으로 (mqserver)
클라이언트가 응답을 안 꺼낸다응답 큐가 가득 찬다O_NONBLOCK — 서버는 멈추지 않는다 (mqserver)
지난 실행의 큐가 남아 있다O_EXCL로 만들 때 EEXIST시작할 때 mq_unlink (mqserver)
이상한 메시지가 온다널 문자가 없다 · 크기가 다르다받은 것을 믿지 않는다 (mqserver)

IPC 코드의 절반은 "상대가 기대대로 움직이지 않을 때"를 위한 것입니다.

4부 정리: 메시지 큐 서버의 한계와 다음

오늘 만든 것은 다음과 같습니다.

  • 요청 큐 하나에 여러 클라이언트가 넣습니다.
  • 요청에 PID를 적어 응답의 주소로 씁니다.
  • 구조체 하나가 메시지 하나입니다(proto.h).
  • 끝은 quit 메시지로 알리고, 기다림에는 3초 제한을 둡니다.
  • 만든 쪽이 지우고, 시작할 때도 지웁니다.

남은 한계는 다음에 배울 것으로 이어집니다.

남은 한계다음에 배울 것
요청마다 응답 큐를 만들고 지운다소켓 — 연결마다 양방향 통로
같은 컴퓨터 안에서만 된다소켓 — 다른 컴퓨터까지
메시지 크기에 한도가 있다공유 메모리 — 큰 데이터도 복사 없이
서버가 한 번에 하나씩 처리한다일꾼 프로세스 여럿 + 세마포어

메시지 큐로 배운 것 — 메시지, 이름, 수명, 프로토콜, 실패 대비 — 은 도구가 바뀌어도 남습니다. 오늘 익힌 설계 질문(이름 · 프로토콜 · 응답의 주소 · 실패 대비)은 소켓 서버에서 그대로 다시 씁니다.

실습 과제와 문제 해결

실습 과제: 예제를 넓힌다

① pmq watch

./pmq watch /w13
  • 큐에서 계속 받아 출력합니다.
  • 내용이 "END"인 메시지가 오면 끝냅니다. EOF가 없으니 끝을 메시지로 약속하는 연습입니다.
  • 다른 터미널에서 send로 우선순위를 바꿔 가며 확인합니다.

② 서버에 명령 추가

./mqclient rev hello
  • struct request에 명령 칸을 넣습니다(upper · rev · len).
  • stat 명령은 지금까지 처리한 요청 수를 돌려줍니다.
  • 모르는 명령에는 오류 응답을 보냅니다.
  • proto.h부터 고칩니다.

③ 급한 요청 먼저 (도전)

./mqclient -p 5 hello
  • 요청을 보낼 때 우선순위를 줄 수 있게 합니다.
  • 서버가 요청마다 1초씩 쉬게 하고 요청을 쌓습니다.
  • 우선순위가 높은 요청이 먼저 처리되는지 확인합니다.
  • "계속 밀리는 요청은 어떻게 되나?"에 대한 답을 적습니다.

제출물은 소스, Makefile, 실행 기록 lab.txt, 그리고 "실패 목록과 대비" 표입니다.

막힐 때 보는 순서

  1. ls -l /dev/mqueue — 큐가 있는지, 남아 있는지 봅니다.
  2. cat /dev/mqueue/이름 — 몇 바이트가 쌓였는지 봅니다.
  3. strace -e trace=mq_open — 어느 호출이 어떤 errno로 실패하는지 봅니다.
  4. rm /dev/mqueue/이름 — 치우고 다시 실행합니다.

strace에서는 mq_send · mq_receive가 mq_timedsend · mq_timedreceive로 보입니다. glibc가 시간 제한을 NULL로 주어 이 호출들을 부르기 때문입니다.

정리

  • 프로세스는 서로의 메모리를 볼 수 없습니다. 운영체제가 일부러 세운 벽이고, 그 덕에 고장과 권한을 가둘 수 있습니다. IPC는 그 벽에 커널이 내 준 문입니다.
  • 함께 일하는 데 필요한 것은 셋입니다 — 건넨다(전달), 함께 본다(공유), 때를 맞춘다(동기화). IPC의 종류는 이 셋으로 나뉩니다.
  • 새 IPC를 만나면 네 가지를 묻습니다 — 전달인가 공유인가, 스트림인가 메시지인가, 어떤 이름으로 만나나, 언제까지 남나.
  • 메시지 큐는 전달 · 메시지 단위 · 이름 · 커널 수명입니다. mq_open → mq_send · mq_receive → mq_close → mq_unlink 순서로 쓰고, 버퍼는 mq_msgsize 이상으로 잡으며, EOF는 없습니다.
  • 프로세스가 여럿이면 실패도 여럿입니다. 상대가 없을 때, 멈췄을 때, 먼저 떠났을 때를 미리 정하고, 만든 것은 만든 쪽이 지웁니다.
