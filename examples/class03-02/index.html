견고한 I/O와 파일 복사

read의 반환 길이를 관찰하고, 부분 쓰기와 EINTR를 처리하는 write_all을 검증한 뒤 이를 이용한 파일 복사 프로그램을 실행한다.

실행해 볼 예제

  • file_copy4096바이트 버퍼로 read한 만큼 write_all로 새 파일에 기록해 복사한다. 목적지는 O_CREAT | O_EXCL로 열기 때문에 기존 파일을 덮어쓰지 않는다.
  • read_chunks4바이트 버퍼로 read를 반복하며 반환값을 stderr에, 읽은 데이터를 stdout에 내보낸다. 짧은 read와 EOF(0)를 구별해 본다.
  • test_write_allwrite를 가짜 함수로 바꿔 부분 쓰기, EINTR, 0 반환, ENOSPC, EAGAIN 등을 재현하고 io_helpers.h의 write_all 완성본을 assert로 검사한다.

이번 수업은 저수준 파일 입출력의 두 번째 시간입니다. 지난 시간에는 open, read, write, lseek, close를 한 번씩 호출해 보았다면, 이번에는 그 호출들을 반복문 안에서 견고하게 쓰는 방법을 다룹니다. read의 세 가지 결과를 구별하고, 지난 시간에 제공받아 쓰기만 했던 write_all을 직접 구현한 다음, 두 반복문을 이어 붙여 파일 복사기를 완성하고 테스트합니다. 마지막에는 보충 내용으로 버퍼의 경계와 표준 입출력(stdio)의 fread/fwrite를 살펴봅니다.

1부 · 지난 시간 복습

파일 프로그램 4개

지난 시간에 만든 프로그램은 네 개였습니다. 각각이 무엇을 했는지 떠올려 봅니다.

  • file_create: 새로운 빈 파일을 만듭니다.
  • file_write: 파일을 덮어쓰거나 끝에 추가로 기록합니다.
  • file_read: EOF까지 읽어서 출력합니다.
  • file_seek: 바이트 위치를 옮겨 그 자리의 내용을 수정합니다.

지난 시간에는 write_all이라는 함수를 제공받아 그대로 사용했습니다. 오늘은 그 함수를 직접 구현합니다.

반환값 복습

오늘의 반복문은 전부 반환값을 보고 분기하므로, 각 호출이 무엇을 돌려주는지부터 정확히 해 둡니다.

  • open: 성공하면 0 이상의 FD를 반환합니다.
  • read / write: 실제로 처리한 바이트 수를 반환합니다. 요청한 길이가 아니라는 점이 중요합니다.
  • read / write는 오류일 때 -1을 반환하므로, 반환값은 부호가 있는 ssize_t로 받습니다.
  • close: 성공하면 0, 실패하면 -1을 반환합니다.

결과 예측

다음 코드는 내용이 ABCDEFGHIJ인 파일을 O_RDWR로 연 뒤의 흐름입니다. 실행하기 전에 읽은 결과, 중간의 현재 위치, 최종 파일 내용을 예측해 봅니다.

/* ABCDEFGHIJ 파일, O_RDWR */
lseek(fd, 3, SEEK_SET);
read(fd, buf, 2);
/* 현재 위치는? */
lseek(fd, 3, SEEK_SET);
write(fd, "XY", 2);

read는 읽은 길이만큼 파일 위치를 옮깁니다. 위치 3에서 2바이트를 읽었으므로 읽은 결과는 DE이고 현재 위치는 5가 됩니다. 그래서 같은 자리를 고쳐 쓰려면 쓰기 전에 위치를 다시 지정해야 합니다. 두 번째 lseek로 위치 3으로 돌아간 뒤 XY를 쓰면 최종 내용은 ABCXYFGHIJ입니다. 참고로 O_APPEND로 연 파일이라면 위치를 어디로 옮겼든 매 write가 파일 끝에 기록됩니다.

위 코드는 흐름만 보여 주는 발췌입니다. 완성된 코드에서는 각 호출의 반환값을 검사합니다.

2부 · read와 오류 처리

이 부분의 목표는 EOF, 짧은 읽기, 오류 세 가지를 서로 구별하는 것입니다.

read의 세 가지 결과

read의 반환값 n은 세 경우로 나뉘고, 경우마다 할 일이 다릅니다.

  • n > 0: n바이트를 읽었습니다. 그 n바이트를 처리하고 계속 읽습니다.
  • n == 0: 일반 파일에서는 EOF입니다. 읽기를 종료합니다.
  • n == -1: 오류입니다. errno를 확인합니다.

이번 실습은 양수 크기를 요청해서 일반 파일을 읽는 경우만 다룹니다. 0이 EOF라는 해석은 이 조건에서 하는 이야기입니다.

짧은 읽기와 EOF

10바이트 파일을 4바이트씩 읽으면 반환값은 4, 4, 2, 0 순서로 나올 것으로 예상합니다. 여기서 세 번째 호출이 2를 반환한 것은 실패가 아니라 성공입니다. 남은 데이터가 2바이트뿐이어서 요청보다 적게 읽었을 뿐입니다. 따라서 "요청보다 적게 읽었다"는 이유로 반복을 끝내면 안 됩니다. 끝났는지는 그다음 호출이 0을 반환하는 것으로 알게 됩니다.

이 숫자들은 인터럽트 같은 방해 없이 일반 파일을 읽는 경우의 예시입니다. 실제로 호출마다 읽히는 길이는 환경에 따라 달라질 수 있으므로, 코드는 특정 길이를 가정하지 말고 반환값을 그대로 따라가야 합니다.

버퍼에서 유효한 범위

read가 n을 반환했다면 이번에 읽은 데이터는 버퍼의 앞쪽 n바이트, 즉 buf[0]부터 buf[n-1]까지입니다. 그 뒤쪽은 이번 호출과 상관없는 내용입니다.

unsigned char buf[4];
ssize_t n = read(fd, buf, sizeof buf);
if (n > 0) {
    /* buf[0]부터 buf[n-1]까지 */
    use_bytes(buf, (size_t)n);
}

read는 읽은 데이터 끝에 NUL 문자를 붙여 주지 않습니다. 그러므로 버퍼를 문자열처럼 다루어 길이를 strlen으로 구하면 안 됩니다. 특히 바이너리 데이터에는 strlen을 쓰지 않습니다. 길이는 언제나 read가 알려 준 n입니다. 코드의 use_bytes는 개념을 설명하기 위한 이름일 뿐이고, 완성된 복사기에서는 이 자리에서 write_all을 호출합니다.

errno와 EINTR

errno는 호출이 실패했다는 것을 반환값으로 확인한 뒤에 읽습니다. 성공한 직후의 errno 값을 보고 성공 여부를 판정하면 안 됩니다.

오류 가운데 EINTR은 따로 취급합니다. EINTR은 데이터를 처리하기 전에 신호 때문에 호출이 중단되었다는 뜻입니다. 아무것도 처리되지 않았으므로 같은 요청을 그대로 다시 시도하면 됩니다. 반대로 일부를 처리한 뒤라면 호출은 -1이 아니라 양수를 반환하며, 이때는 실제 처리량을 그대로 반영해야 합니다. 즉 "데이터 처리 전 중단(-1과 EINTR)"과 "일부 처리 뒤의 양수 반환"을 구분하는 것이 핵심입니다. EINTR이 아닌 그 밖의 오류는 호출자에게 전달합니다. 신호 자체는 이후 수업에서 다룹니다.

읽기 반복문의 분기

지금까지의 내용을 반복문으로 옮기면 다음과 같습니다.

for (;;) {
    ssize_t n = read(fd, buf, sizeof buf);
    if (n == 0) break;
    if (n == -1) {
        if (errno == EINTR) continue;
        return -1;
    }
    /* 읽은 n바이트를 처리 */
}

0과 -1은 둘 다 반복을 끝내지만 서로 다른 종료 경로입니다. 0은 정상적으로 끝까지 읽은 것이고, -1은 실패입니다. EINTR이면 continue로 다시 시도합니다. 이 분기들을 모두 통과한 양수 n만 다음 단계(읽은 데이터의 처리)로 넘어갑니다.

실습 1 · 읽은 길이 관찰

실습 폴더에서 make를 실행한 뒤, read_chunks로 10바이트 파일을 읽어 봅니다.

make
RUN=$(mktemp -d ./run.XXXXXX)
printf ABCDEFGHIJ > "$RUN/in"
./read_chunks "$RUN/in" > "$RUN/out"
cmp "$RUN/in" "$RUN/out"
echo $?

read_chunks는 읽은 데이터를 표준 출력으로, 각 read의 반환값 n을 표준 오류로 내보냅니다. 표준 출력만 파일로 보냈으므로 화면에는 n 값이 남고, 4, 4, 2, 0이 출력됩니다. 이어서 cmp로 입력과 출력의 바이트를 비교합니다. cmp 직후의 종료 상태가 0이면 두 파일이 같다는 뜻입니다. RUN 변수는 이후 실습에서도 같은 셸에서 계속 사용합니다.

3부 · write_all 구현

이 부분에서는 "어디까지 처리했는지"와 "얼마나 남았는지"를 갱신해 가며 요청한 바이트를 전부 기록하는 함수를 만듭니다.

한 번의 write와 전체 기록

write(fd, buf, 10)은 4를 반환할 수 있습니다. 이 경우 호출은 성공한 것이고 앞의 4바이트는 이미 기록되었지만, 요청한 10바이트가 모두 기록된 것은 아닙니다. 나머지를 쓰려면 다음 요청을 buf + 4에서 시작해 6바이트로 해야 합니다. 처음부터 다시 쓰면 앞의 4바이트가 중복됩니다. 결론은, 성공을 뜻하는 양수 반환이라도 그것이 요청 전체의 완료인지 확인해야 한다는 것입니다.

진행 상태 계산

10바이트를 쓰는 동안 write가 4, 2, 4를 차례로 반환했다고 하면 진행 상태는 다음과 같이 바뀝니다.

시점위치남은 길이
시작010
4바이트 성공46
2바이트 성공64
4바이트 성공100

어느 시점에서든 "처리한 길이 + 남은 길이 = 원래 길이"가 성립합니다. 데이터가 ABCDEFGHIJ라면 각 요청의 시작 글자는 A, E, G로 이동합니다.

write_all의 계약

함수를 구현하기 전에 이 함수가 호출자에게 무엇을 약속하는지 정합니다.

  • 성공: 요청한 바이트를 모두 쓰고 0을 반환합니다.
  • 실패: -1을 반환하고 원인은 errno로 전달합니다.
  • 실패하기 전에 일부 바이트를 이미 썼을 수 있습니다.

write_all은 우리가 직접 작성한 함수이지 시스템 호출이 아닙니다. 따라서 "전부 쓰거나 전혀 쓰지 않는" 원자적 동작이나 실패했을 때의 롤백을 보장하지 않습니다. 또한 이번 실습은 작은 버퍼와 blocking FD를 전제로 합니다. 비차단 FD에서 나오는 EAGAIN은 이 함수에서 재시도하지 않습니다.

반복문과 포인터 갱신

진행 상태는 변수 두 개로 표현합니다. p는 다음에 기록할 위치이고, left는 아직 쓰지 않은 길이입니다.

const unsigned char *p = data;
size_t left = count;
while (left > 0) {
    ssize_t n = write(fd, p, left);
    /* 오류와 0 처리: 아래에서 설명 */
    p += (size_t)n;
    left -= (size_t)n;
}

두 값은 write가 양수를 반환했을 때만 바꿉니다. p의 타입이 void *가 아니라 unsigned char *인 이유는 바이트 단위로 포인터 산술을 하기 위해서입니다. 이 코드는 설명을 위해 나누어 놓은 발췌입니다. 오류 분기가 빠져 있으므로 이 상태로 실행해서는 안 됩니다. n이 -1일 때 (size_t)n으로 포인터와 길이를 갱신하면 안 되기 때문입니다.

오류와 진행 없는 반환

다음 분기를 위 반복문의 write 호출 바로 뒤에 넣습니다.

if (n == -1) {
    if (errno == EINTR) continue;
    return -1;
}
if (n == 0) {
    errno = EIO;
    return -1;
}
  • EINTR이면 아무것도 기록되지 않았으므로 p와 left를 그대로 둔 채 같은 요청을 다시 시도합니다.
  • 다른 오류는 -1로 호출자에게 전달합니다. errno에는 write가 설정한 원인이 남아 있습니다.
  • 0이 반환되면 errno를 EIO로 설정하고 -1을 반환해 반복을 끝냅니다.

0을 따로 처리하는 이유는, 양수 길이를 요청했는데 0이 나오면 진행이 전혀 없어서 그대로 두면 반복이 끝나지 않기 때문입니다. 여기서 EIO는 우리 함수가 선택한 정책입니다. write가 0을 반환할 때 반드시 EIO를 설정한다는 뜻이 아닙니다.

처음 받은 상태의 함수는 ENOSYS를 반환하므로, 수정하기 전에 테스트가 실패하는 것은 정상입니다. 완성본은 io_helpers.h에 있습니다. 먼저 스스로 구현한 다음에 비교해 봅니다.

반환값을 정한 테스트

부분 쓰기나 EINTR은 평소의 일반 파일에서는 잘 일어나지 않아 실제로 재현하기 어렵습니다. 그래서 test_write_all은 write 호출을 가짜 함수로 대체하고, 그 가짜 함수가 미리 정해 둔 결과를 차례로 돌려주게 합니다. 예를 들어 가짜 write가 4, -1/EINTR, 2, 4를 순서대로 반환하도록 해 두면 올바른 write_all은 다음과 같이 동작해야 합니다.

  • 요청 길이는 10, 6, 6, 4가 되어야 합니다. 첫 호출에서 4바이트가 처리되어 6이 남고, EINTR에서는 진행이 없으므로 다시 6을 요청하며, 2바이트가 처리된 뒤 4를 요청합니다.
  • EINTR 앞뒤 호출의 포인터는 같아야 합니다.
  • 기록된 결과가 ABCDEFGHIJ인지 검사합니다.

가짜 함수는 커널의 동작을 바꾸는 것이 아닙니다. 테스트가 write 호출을 대체해 분기를 재현하는 것이므로, 이 결과를 실제 신호 실험이나 성능 측정의 결과로 해석해서는 안 됩니다.

4부 · 파일 복사와 테스트

이제 2부의 읽기 반복문과 3부의 write_all을 연결합니다. FD 두 개를 열고, EOF까지 복사한 뒤, 결과를 검증합니다.

file_copy의 구성

file_copy는 다음 순서로 동작합니다.

  • 입력 파일을 O_RDONLY로 엽니다.
  • 출력 파일을 O_WRONLY | O_CREAT | O_EXCL로 엽니다.
  • read로 얻은 n바이트를 write_all로 씁니다.
  • 입력과 출력 FD를 모두 닫습니다.

출력에 O_EXCL을 붙였기 때문에 이 학습용 복사기는 이미 있는 목적지를 덮어쓰지 않고 거부합니다. 같은 이유로 입력과 목적지가 동일한 경로인 경우, 하드 링크인 경우, 목적지가 이미 있는 심볼릭 링크인 경우에도 목적지 생성 단계에서 실패합니다. 또한 이 복사기는 내용만 복사합니다. 권한이나 시간 같은 메타데이터의 복제, 원자적 교체는 다루지 않습니다.

복사 반복문

복사의 핵심인 copy_fd 함수의 반복문은 다음과 같습니다.

for (;;) {
    ssize_t n = read(in, buf, sizeof buf);
    if (n == 0) return 0;
    if (n == -1) {
        if (errno == EINTR) continue;
        return -1;
    }
    if (write_all(out, buf, (size_t)n) < 0)
        return -1;
}

바깥 반복문은 2부에서 본 읽기 반복문 그대로이며 EOF까지 읽습니다. 안쪽에서는 write_all이 이번에 읽은 n바이트를 모두 씁니다. 넘겨주는 길이가 sizeof buf가 아니라 n이라는 점을 확인하십시오. 읽기든 쓰기든 실패하면 -1로 호출자에게 전달합니다. 이 함수는 FD를 빌려 쓰기만 하고, 닫는 일은 FD를 연 main이 맡습니다.

실패 뒤에도 FD 닫기

열어 둔 FD는 실패한 경로에서도 닫아야 합니다.

  • 출력 파일의 open이 실패하면 이미 열어 둔 입력 FD를 닫습니다.
  • 복사가 실패한 경우에도 두 FD를 모두 닫습니다.
  • close의 실패도 프로그램의 종료 상태에 반영합니다.
  • Linux에서는 close가 실패했다고 일괄적으로 재시도하지 않습니다.

재시도하지 않는 이유는, Linux에서는 close가 오류를 반환하더라도 FD가 이미 해제되었을 수 있기 때문입니다. 그 상태에서 다시 close를 호출하면 엉뚱한 다른 FD를 닫을 위험이 있습니다. 그리고 복사가 실패했을 때 목적지에는 일부만 기록된 부분 파일이 남을 수 있으므로, 실패한 복사의 결과물을 성공한 결과처럼 사용해서는 안 됩니다.

실습 3 · 파일 복사

실습 1에서 만든 $RUN/in을 새 목적지 이름으로 복사하고 결과를 비교한 뒤, 같은 목적지로 한 번 더 복사해 봅니다.

./file_copy "$RUN/in" "$RUN/copy"
cmp "$RUN/in" "$RUN/copy"
echo $?
./file_copy "$RUN/in" "$RUN/copy"
echo $?

첫 번째 echo $?는 cmp의 종료 상태로 0이 나와야 합니다. 두 번째 복사는 목적지가 이미 있으므로 실패하고 종료 상태는 1입니다. 이때 기존 목적지의 내용은 그대로 유지됩니다.

경계 조건과 오류 테스트

정상적인 파일 하나가 복사된다고 해서 복사기가 옳다고 할 수는 없습니다. 테스트는 다음과 같은 경계 조건과 오류 상황을 확인합니다.

  • 빈 파일, 그리고 NUL 바이트가 들어 있는 바이너리
  • 버퍼 크기인 4096 바로 앞뒤의 길이
  • 입력 파일이 없는 경우, 목적지가 이미 있는 경우, 입력과 목적지가 동일한 경로인 경우
  • 부분 쓰기, EINTR, 0 반환, 쓰기 오류

make test는 가짜 write에 전달된 호출 인자와 기록된 바이트 결과를 검사하고, 복사기 통합 테스트를 실행합니다. Linux에서 /dev/full이 있으면 실제 쓰기 실패도 확인합니다.

실습 4 · 호출 관찰

Linux에서는 strace로 복사기가 실제로 어떤 read와 write를 호출하는지 추적할 수 있습니다. 이 실습은 Linux에서만 하는 선택 실습입니다.

strace -o "$RUN/trace.log" \
  -e trace=openat,read,write,close \
  ./file_copy "$RUN/in" "$RUN/traced"
cat "$RUN/trace.log"
cmp "$RUN/in" "$RUN/traced"

복사기는 기존 목적지를 거부하므로 traced라는 새 목적지 이름이 필요합니다. 추적 기록에는 동적 로더와 라이브러리 파일에 대한 호출도 섞여 있으므로, 그중에서 실습 파일의 FD에 대한 호출을 찾아 읽어야 합니다. 찾은 호출에서 반환값과 다음 요청 길이를 비교해 봅니다. 정상적인 일반 파일에서는 부분 쓰기가 보이지 않을 수 있는데, 그것은 오류가 아닙니다.

코드 리뷰 · 버그 찾기

다음 세 줄은 얼핏 복사처럼 보이지만 여러 문제가 있습니다. 요청 길이와 실제 길이를 비교하고, 음수 값이 unsigned로 바뀌는 시점을 살펴보고, 부분 쓰기 뒤에 다시 요청해야 할 범위를 설명해 봅니다.

size_t n = read(in, buf, sizeof buf);
if (n > 0)
    write(out, buf, sizeof buf);
  • read의 반환값을 부호 없는 size_t로 받았기 때문에 오류를 뜻하는 -1이 매우 큰 양수로 바뀝니다. 그러면 n > 0 검사가 오류를 걸러 내지 못합니다.
  • 실제로 읽은 n바이트가 아니라 sizeof buf만큼 기록합니다. 짧게 읽은 경우 버퍼 뒤쪽의 무관한 내용까지 출력됩니다.
  • write의 반환값을 보지 않으므로 부분 쓰기와 오류를 처리하지 못합니다.
  • 한 번만 읽고 끝나므로 EOF까지 반복하지 않습니다.

올바른 형태는 반환값을 ssize_t로 받고 앞에서 본 copy_fd처럼 작성하는 것입니다.

정리 퀴즈

  1. 10바이트 write가 4를 반환하면 다음 호출의 인자는 무엇입니까? — buf + 4와 6입니다.
  2. read가 2를 반환하면 EOF입니까? — 아닙니다. 다음 read를 계속합니다.
  3. -1과 EINTR일 때 포인터는 어떻게 바꿉니까? — 바꾸지 않고 그대로 재시도합니다.
  4. write_all이 실패하면 파일은 원래 상태입니까? — 아닙니다. 일부가 이미 기록되었을 수 있습니다.

보충 · 버퍼와 표준 입출력

여기서부터는 본 수업에 덧붙인 보충 내용입니다. 버퍼라는 말의 두 가지 쓰임을 정리하고, fread와 fwrite의 크기 인자, 반환값, 버퍼링을 살펴봅니다.

버퍼의 메모리 경계

char buf[4]에서 유효한 인덱스는 0부터 3까지입니다. buf[4]에 쓰면 배열의 끝을 넘고, buf[-1]에 쓰면 시작 앞을 침범합니다. 두 접근 모두 정의되지 않은 동작입니다.

char buf[4];

buf[0] = 'A';  /* 정상 */
buf[3] = 'D';  /* 정상 */

/* 다음 코드는 실행하지 않는다. */
buf[4] = 'X';  /* overflow */
buf[-1] = 'Y'; /* underwrite */

범위 밖 접근은 방향과 종류에 따라 이름을 구분합니다. 범위 밖을 읽는 것은 over-read 또는 under-read, 범위 밖에 쓰는 것은 overflow 또는 underwrite입니다. 이런 잘못된 접근의 결과는 메모리 손상일 수도, 프로그램 종료일 수도, 겉보기에 정상인 동작일 수도 있습니다. 겉으로 멀쩡해 보인다고 해서 올바른 코드가 아닙니다.

데이터 흐름의 underflow와 overflow

버퍼는 데이터를 잠시 저장해 두는 공간이기도 합니다. 이 문맥에서는 같은 단어가 다른 뜻으로 쓰입니다.

  • Underflow: 소비할 데이터가 부족한 상태입니다. 예를 들어 오디오 데이터의 도착이 늦어 재생이 끊기는 경우입니다.
  • Overflow: 빈 공간보다 더 많은 데이터가 도착한 상태입니다.

이것은 앞에서 본 메모리 경계 침범과는 다른 이야기이므로, 용어를 만나면 어느 문맥인지 확인해야 합니다. 빈 큐에서 읽거나 꽉 찬 큐에 쓰는 상황은 구현에 따라 대기, 실패, 또는 데이터 손실로 처리됩니다. stdio의 입력 버퍼가 비면 라이브러리가 다시 채울 수 있습니다. 따라서 버퍼가 비었다는 사실만으로 EOF나 메모리 오류라고 판단해서는 안 됩니다.

read / write와 stdio

read / writefread / fwrite

대상정수 FDFILE *

fread는 스트림에서 메모리로 읽고, fwrite는 메모리에서 스트림으로 씁니다. stdio는 C 라이브러리 안의 버퍼를 사용할 수 있으므로, stdio 호출 한 번이 시스템 호출 한 번과 항상 대응하지는 않습니다.

fread와 fwrite의 인자

#include <stdio.h>

fread(ptr, size, nmemb, stream);
fwrite(ptr, size, nmemb, stream);

/* 요청 크기 = size * nmemb */
/* stream: FILE * */
/* 두 함수의 반환형: size_t */
  • ptr: 데이터를 담은 메모리 주소입니다. fread에서는 읽은 내용을 받아 적을 쓰기 가능한 메모리이고, fwrite에서는 내보낼 데이터가 있는 곳입니다.
  • size: 항목 하나의 바이트 크기입니다.
  • nmemb: 요청할 항목의 개수입니다.

요청하는 전체 크기는 size * nmemb바이트입니다. 이 크기에 맞는 버퍼를 준비하는 것은 호출자의 책임이며, 이 곱셈이 size_t의 범위를 넘지 않는지도 확인해야 합니다. 위 코드는 호출 형태만 보여 주는 발췌입니다.

반환값의 단위

fread와 fwrite의 반환값은 바이트 수가 아니라 항목 수입니다.

int values[10];
size_t n = fread(values,
                 sizeof values[0], 10, fp);
/* n == 10: int 10개를 읽음 */

unsigned char buf[100];
size_t bytes = fread(buf, 1, sizeof buf, fp);
/* bytes: 실제로 읽은 바이트 수 */

첫 번째 호출의 n은 완전히 읽은 int의 개수입니다. size가 1보다 크면 마지막에 일부만 읽힌 불완전한 항목은 반환 개수에 포함되지 않습니다. 두 번째 호출처럼 size를 1로 주면 항목 하나가 1바이트이므로 반환값이 곧 바이트 수가 됩니다.

어느 경우든 요청한 개수와 반환값을 비교해야 합니다. fread가 요청보다 적게 반환했다면 EOF에 도달했거나 오류가 난 것이므로 feof와 ferror로 확인합니다. fwrite가 요청보다 적은 항목 수를 반환했다면 쓰기 오류입니다.

fread와 버퍼 크기

char text[100];
size_t n = fread(text, 1,
                 sizeof text - 1, fp);
text[n] = '\0';

/* 위험한 요청: 실행하지 않는다. */
char small[10];
fread(small, 1, 100, fp);

read와 마찬가지로 fread도 NUL을 자동으로 붙이지 않습니다. 읽은 내용을 문자열로 다루려면 직접 붙여야 하고, 그 한 바이트를 위한 자리를 남겨 두어야 합니다. 그래서 위 코드는 100바이트 버퍼에 최대 99바이트만 읽고 text[n]에 NUL을 넣습니다. 문자열 ABCD를 담는 데 NUL까지 5바이트가 필요한 것과 같은 이치입니다. 바이너리 데이터라면 NUL을 붙일 것이 아니라 읽은 n바이트 그대로 처리합니다.

마지막 호출은 10바이트 버퍼에 100바이트를 요청하고 있습니다. 입력이 충분히 있으면 버퍼를 넘쳐 쓰게 됩니다. 반대로 fwrite(small, 1, 100, fp)는 버퍼 밖을 읽게 될 수 있습니다. 위 코드는 크기 처리만 보여 주는 발췌이며, 완성된 프로그램에서는 ferror도 확인합니다.

fwrite와 텍스트 출력

int value = 1234;

size_t n = fwrite(&value,
                   sizeof value, 1, fp);
/* 성공한 항목 수 n == 1 확인 */

int rc = fprintf(text_fp, "%d\n", value);
/* 오류이면 rc < 0 */

fwrite는 메모리에 있는 바이트를 그대로 기록하고, fprintf는 값을 텍스트로 변환해서 기록합니다. 같은 1234를 저장해도 두 파일의 저장 형식은 다릅니다. 위 코드는 서로 다른 출력 스트림을 가정하고 두 호출을 비교한 것입니다.

원시 바이트를 그대로 저장하는 방식은 이식성에 주의해야 합니다. int의 크기와 바이트 순서는 환경마다 다를 수 있고, 구조체에는 패딩이 있어서 그대로 저장하면 이식성이 떨어집니다.

EOF와 오류 판별

size_t n = fread(buf, 1, sizeof buf, fp);
/* 먼저 읽은 n바이트를 처리 */

if (n < sizeof buf) {
    if (ferror(fp)) {
        /* 읽기 오류 처리 */
    } else if (feof(fp)) {
        /* 파일 끝 도달 */
    }
}

순서가 중요합니다. 먼저 fread의 반환값을 확인하고 읽은 n바이트를 처리합니다. 요청보다 적게 읽었을 때 ferror가 참이면 읽기 오류이고, feof가 참이면 파일 끝에 도달한 것입니다. (이 코드는 sizeof buf가 양수인 배열이라고 가정합니다.)

feof는 읽기를 시도한 뒤의 EOF 상태를 알려 주는 함수입니다. 그래서 while (!feof(fp)) 형태의 반복문은 다음 읽기가 성공할지를 예측하지 못합니다. 예를 들어 마지막 데이터를 버퍼 크기에 딱 맞게 읽었다면, 그다음 읽기를 한 번 더 시도해야 비로소 EOF 표시가 설정될 수 있습니다.

stdio 파일 복사 반복문

4부의 복사 반복문을 stdio로 쓰면 다음과 같습니다.

unsigned char buf[4096];
size_t n;
int failed = 0;
while ((n = fread(buf, 1, sizeof buf, src)) > 0) {
    if (fwrite(buf, 1, n, dst) != n) {
        failed = 1;
        break;
    }
}
if (ferror(src)) failed = 1;

구조는 같습니다. 읽은 n바이트만 출력하고, fwrite가 반환한 항목 수가 n과 같은지 검사합니다. fread가 0을 반환해 반복이 끝났을 때 그것이 EOF인지 오류인지는 반환값만으로 알 수 없으므로, 반복문 뒤에서 ferror(src)를 확인해 읽기 오류도 실패 결과에 반영합니다. 이 반복문은 src와 dst가 유효하게 열려 있다고 가정한 발췌입니다. 실패한 경우 출력 파일에는 일부 데이터가 남을 수 있습니다.

fopen과 fclose

FILE *src = fopen("input.bin", "rb");
if (!src) return 1;
FILE *dst = fopen("output.bin", "wb");
if (!dst) { fclose(src); return 1; }

/* 앞의 복사 반복문 삽입 */

if (fclose(src) == EOF) failed = 1;
if (fclose(dst) == EOF) failed = 1;
return failed;

이 코드는 main 안에서 앞의 복사 반복문과 결합하는 예시이며, 입력과 출력은 서로 다른 파일이어야 합니다.

  • fopen의 실패는 반환값이 NULL인지로 확인합니다. 두 번째 fopen이 실패하면 먼저 연 src를 닫고 끝냅니다. 4부에서 출력 open 실패 시 입력 FD를 닫은 것과 같은 처리입니다.
  • 모드 rb는 읽기입니다. wb는 파일이 없으면 만들고, 있으면 내용을 삭제합니다. ab는 끝에 추가합니다.
  • fclose의 반환값도 검사합니다. 출력 오류가 fclose에서 드러날 수 있기 때문입니다.
  • fclose한 뒤에는 그 FILE *를 다시 사용하지 않습니다.

wb는 기존 파일을 지우므로, 기존 목적지를 보존하는 본 수업의 O_EXCL 복사기와는 동작이 다릅니다. 모드의 b는 Linux에서는 동작을 바꾸지 않습니다.

출력 버퍼와 fflush

버퍼링되는 출력에서 데이터는 일반적으로 프로그램 메모리, C 라이브러리 버퍼, 커널, 저장 장치의 순서로 이동합니다. 그래서 각 단계의 "성공"이 의미하는 범위가 다릅니다.

  • fwrite가 성공한 뒤에도 데이터는 아직 stdio 출력 버퍼에 남아 있을 수 있습니다.
  • fflush는 stdio 출력 버퍼의 내용을 커널로 내보냅니다.
  • fflush와 fclose는 성공하면 0, 실패하면 EOF를 반환합니다.
  • 디스크에까지 반영되어야 한다면 fsync 등도 고려합니다.
  • fseek는 스트림의 파일 위치를 변경합니다. 성공하면 0, 실패하면 0이 아닌 값을 반환합니다.

fflush만으로는 영구 저장이 보장되지 않습니다. fsync(fileno(fp))를 사용할 때에는 먼저 fflush(fp)가 성공했는지 확인해야 합니다. 라이브러리 버퍼에 남은 데이터가 커널로 넘어가 있어야 하기 때문입니다. 한편 fflush(stdin)을 입력 버퍼를 비우는 방법으로 일반화해서 쓰지 않습니다.

확인 문제

  1. int 10개를 읽었을 때 fread의 반환값은 얼마입니까? — size가 sizeof(int), nmemb가 10이면 10입니다.
  2. char buf[4]에 "ABCD"와 NUL을 담을 수 있습니까? — 담을 수 없습니다. 5바이트가 필요합니다.
  3. fread가 요청보다 적게 읽으면 무엇을 확인합니까? — ferror와 feof입니다.
  4. fwrite의 성공만으로 디스크 저장이 보장됩니까? — 보장되지 않습니다. fflush와 fclose의 오류도 확인해야 하며, 지속성에 대한 요구는 별도로 다룹니다.
