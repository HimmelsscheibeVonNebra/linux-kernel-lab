시스템 정보와 자원 한계

uname·sysconf·sysinfo로 시스템 정보를 조회하고, getrlimit/setrlimit로 자원 한계를 다루며, /proc으로 프로세스 상태를 관찰하는 예제입니다.

실행해 볼 예제

  • sysprobeuname(2)의 필드와 sysconf(3) 값(온라인 CPU 수, 페이지 크기, CLK_TCK, OPEN_MAX, ARG_MAX)을 출력합니다. sysconf의 -1 반환을 errno로 구분하는 계약을 보여 줍니다.
  • limit_showgetrlimit(2)로 nofile, as, stack, fsize, cpu, nproc, core의 soft·hard 한계를 출력하고 RLIM_INFINITY는 unlimited로 표시합니다.
  • nofile_demo/dev/null을 EMFILE이 날 때까지 반복해서 열어 FD 한계를 실험합니다. --raise N을 주면 setrlimit(2)로 soft 한계를 N(hard 이하)으로 바꾼 뒤 측정합니다.
  • proc_probe/proc/self/status에서 VmRSS·Threads 줄을 골라 출력하고, /proc/loadavg 첫 줄과 /proc/self/fd의 항목 수를 셉니다.
  • sysinfo_demoLinux 전용 sysinfo(2)로 uptime, 부하 평균(고정소수점), 프로세스 수, 전체·여유 메모리를 출력합니다. 조건부 컴파일로 플랫폼을 구분하는 예입니다.

지난 두 주 동안은 파일을 중심으로 내용(저수준 입출력), 속성(stat 계열), 이름과 디렉토리를 다뤘습니다. 이번 시간에는 눈을 프로그램 자신에게 돌립니다. 프로그램이 지금 어떤 시스템에서 돌고 있고 어떤 자원까지 쓸 수 있는지를 스스로 알아내는 인터페이스를 배웁니다. uname과 sysconf로 실행 환경을 알아내고, getrlimit으로 자원 한계를 다루며, /proc로 Linux의 상태를 관찰합니다. 전체를 관통하는 문제는 하나입니다. 이식성 있는 표준 API와 Linux 고유의 관찰 창을 구분하는 것입니다.

왜 시스템 정보를 읽는가

프로그램이 실행되는 환경은 매번 다릅니다. 커널, CPU, 메모리, 열 수 있는 파일의 상한이 컴퓨터마다 다르고, 같은 프로그램도 환경에 따라 동작 조건이 달라집니다. 페이지 크기, CPU 수, 열린 파일 상한을 상수로 가정하고 코드를 쓰면 다른 환경에서 실패합니다. 시스템 정보를 읽는 이유는 세 가지로 정리할 수 있습니다.

  • 진단 로그: 오류 보고에 시스템 식별 정보를 함께 남깁니다. 예를 들어 버그 보고서에 uname -a 결과가 붙어 있으면 같은 커널과 아키텍처에서 재현했는지 확인할 수 있어 원인을 좁히기 쉽습니다.
  • 이식성: 값을 컴파일할 때 정하지 않고 실행할 때 얻습니다.
  • 자원 계획: 버퍼 크기나 동시 작업 수를 한계 안에서 정합니다. 작업을 몇 개로 나눌지, 서버가 감당할 동시 접속 수를 얼마로 잡을지 정할 때 CPU 수 같은 값이 필요합니다.

2주차에 uname·sysconf 예제를 잠깐 실행했지만 그때는 출력만 보았습니다. 이번에는 반환값 계약까지 다룹니다. 이번 시간에 배우는 호출은 모두 값을 얻는 조회입니다. 프로그램을 기다리게 만드는 호출은 없고 즉시 답을 주므로, 반환값을 검사하는 것이 곧 프로그램의 첫 단계입니다.

1부 시스템 식별

첫 부분은 시스템을 식별하는 API입니다. 어느 커널에서, 어떤 아키텍처로 돌고 있는지를 문자열로 얻습니다. 식별 정보는 시스템 전체의 정체, 즉 이름·버전·아키텍처를 말합니다.

uname(2)과 struct utsname

uname 함수는 struct utsname 구조체를 채워 줍니다. 헤더는 <sys/utsname.h>이고 성공하면 0, 실패하면 -1을 돌려줍니다. 구조체는 문자열 배열 필드로 이루어져 있습니다.

필드의미
sysname커널 이름
nodename네트워크상의 호스트 이름
release커널 릴리스
version빌드 정보 문자열
machineCPU 아키텍처 이름 (x86_64, aarch64 등)

몇 가지 주의할 점이 있습니다. version 문자열은 형식이 정해져 있지 않아 배포판마다 다릅니다. nodename은 보통 호스트 이름과 같지만 컨테이너처럼 다르게 보이는 환경도 있으므로 항상 일치한다고 가정하지 않습니다. domainname 필드도 있지만 이것은 Linux 확장입니다.

sysprobe: uname 조회

sysprobe의 앞부분은 uname을 호출해 구조체를 채우고, 성공한 뒤에만 필드를 출력합니다.

#include <sys/utsname.h>

struct utsname u;
if (uname(&u) == -1) {
    perror("uname");
    return 1;
}
printf("sysname=%s\n", u.sysname);
printf("nodename=%s\n", u.nodename);
printf("release=%s\n", u.release);
printf("machine=%s\n", u.machine);

읽을 때 볼 점은 세 가지입니다.

  • 호출 결과: 성공 0, 실패 -1입니다. 실패하면 errno를 봅니다. 위 코드는 perror로 errno 메시지를 남기고 종료 상태 1로 끝냅니다.
  • 문자열 필드: 각 필드는 구조체 안에 들어 있는 널 종료 문자열이므로 %s로 바로 출력할 수 있습니다.
  • 출력 시점: 조회에 성공한 뒤에만 필드를 읽습니다. 실패한 뒤의 구조체에는 이번 호출의 결과가 들어 있지 않아 쓰레기 값일 수 있기 때문입니다. 지금까지 반복해 온 "조회 뒤 출력" 순서 그대로입니다.

sysname 값을 보면 운영 체제를 구분하는 코드를 만들 수 있습니다. 완성된 sysprobe는 위 필드에 더해 version 필드와 2부에서 다룰 sysconf 결과까지 함께 출력합니다.

uname(1) 명령과 비교

셸의 uname 명령은 같은 정보를 사람이 읽는 형태로 보여 줍니다. 함수 uname(2)은 프로그램 안에서 로그를 남기거나 환경을 판별할 때 쓰고, 명령 uname(1)은 셸에서 확인할 때 씁니다. uname -a는 전부를 한 줄로, -r은 릴리스만, -m은 아키텍처만 출력합니다.

$ uname -a
Linux lab-ubuntu 6.8.0-49-generic #49-Ubuntu \
SMP ... x86_64 GNU/Linux

# -s Linux             -n lab-ubuntu
# -r 6.8.0-49-generic  -m x86_64

$ uname -r
6.8.0-49-generic
$ uname -m
x86_64

위 출력은 Ubuntu 22.04 환경의 예시입니다. macOS에서는 sysname이 Darwin이고 machine이 arm64처럼 나옵니다. 버전 문자열의 형식도 배포판마다 다릅니다. 그래서 값 자체보다 어떤 필드가 명령 출력의 어느 열에 대응하는지가 중요합니다. 주석 줄이 보여 주듯 -s는 sysname, -n은 nodename, -r은 release, -m은 machine에 해당합니다.

sysinfo(2): 자원 요약

sysinfo는 시스템의 자원 요약을 한 번의 호출로 돌려줍니다. 헤더는 <sys/sysinfo.h>입니다.

  • 구조체 필드: uptime, loads(부하 평균), totalram, freeram, procs(프로세스 수) 등이 있습니다.
  • 단위 환산: 램 필드의 값은 그대로 바이트가 아닙니다. mem_unit을 곱해야 바이트가 됩니다. loads는 65536을 1로 하는 고정소수점 값입니다.
  • Linux 전용: 표준 인터페이스가 아니므로 이식성이 필요한 코드와 구분해야 합니다. 같은 정보의 일부는 표준 API로도 얻을 수 있지만 sysinfo가 주는 묶음 그대로는 없기 때문에 전용으로 분류합니다.

이 구분을 코드로 드러낸 것이 sysinfo_demo입니다. 소스는 #ifdef __linux__ 조건부 컴파일로 작성되어 있어서, Linux가 아니면 안내 문장을 출력하고 실패 상태로 끝납니다. 이식성 있는 코드와 플랫폼 확장을 코드에서 나누는 첫 예시입니다. 참고로 같은 정보는 /proc/meminfo와 /proc/loadavg에서도 읽을 수 있으며, 이 경로들은 4부에서 다시 만납니다.

2부 sysconf와 경계값

두 번째 부분은 경계값입니다. 페이지 크기, CPU 수, clock tick처럼 시스템마다 다른 숫자를 실행 시점에 얻어 옵니다. 헤더 파일에 정의된 상수는 빌드 대상을 가정한 값이라서, 실행 환경이 다르면 틀린 값이 됩니다. 그래서 컴파일 시점 상수 대신 실행 시점 조회를 씁니다.

sysconf(3)의 역할

sysconf는 조회할 항목을 _SC_ 접두사가 붙은 상수로 고르고 그 값을 돌려줍니다. 헤더는 <unistd.h>이고, 인자는 int, 반환은 long입니다. 값을 컴파일할 때 정하지 않고 실행할 때 얻는다는 것이 이 함수의 역할입니다. 조회마다 값이 다를 수 있으므로, 결과를 한 번 저장해 재사용하는 코드와 매번 조회하는 코드가 어떻게 다르게 동작할지도 생각해 볼 만합니다.

단순해 보이지만 반환값에 함정이 있습니다. 반환형이 long인데, 오류와 "무한" 값을 모두 -1로 표현할 수 있기 때문입니다.

sysconf의 반환값 계약

sysconf가 -1을 돌려줄 때는 두 가지 뜻이 있을 수 있습니다. 하나는 조회 자체가 실패한 경우이고, 다른 하나는 한계가 없거나 값을 정할 수 없는 경우입니다. 문제는 sysconf가 실패해도 errno를 바꾸지 않을 수 있다는 점입니다. 호출 뒤에 errno만 봐서는 그 값이 이번 호출이 남긴 것인지 이전 호출에서 남아 있던 것인지 알 수 없습니다. 그래서 다음 순서가 필요합니다.

  1. 호출 직전에 errno를 0으로 만듭니다.
  2. sysconf를 호출합니다.
  3. -1이고 errno가 0이면 한계가 없거나 값을 정할 수 없는 것입니다.
  4. -1이고 errno가 0이 아니면 조회 자체가 실패한 것입니다. 지원하지 않는 name을 넘기면 EINVAL로 실패합니다.

결론적으로 -1 하나를 두 가지 뜻으로 나눠 읽습니다. 그리고 프로그램은 조회에 성공한 값을 얻은 뒤에만 그 값을 사용합니다. 이 읽기법은 -1과 errno의 조합으로 상태를 나누는 대표적인 사례이며, 이렇게 하나의 값으로 두 상태를 표현하는 API에서는 초기화 순서가 계약의 일부입니다.

자주 쓰는 _SC 상수

상수의미와 쓰임
_SC_PAGESIZE메모리 페이지 크기. 정렬과 mmap 계산에 씁니다.
_SC_NPROCESSORS_ONLN지금 사용 가능한 온라인 CPU 수입니다.
_SC_CLK_TCKtimes(2) 값의 초당 틱 수. CPU 시간 환산에 씁니다.
_SC_OPEN_MAXFD의 soft 한계 값입니다. 3부의 FD 한계와 이어집니다.
_SC_ARG_MAXexec 인자와 환경의 총 크기 상한입니다.

x86_64 Linux에서는 PAGESIZE 4096, CLK_TCK 100이 흔합니다. CLK_TCK가 100이라는 것은 times의 틱 하나가 0.01초라는 뜻입니다. 그렇지만 이 숫자들을 코드에 박아 넣지 않고 조회해서 씁니다.

sysprobe: sysconf 읽기

sysprobe의 probe 함수는 방금 본 계약을 그대로 구현합니다.

static int probe(const char *label, int name)
{
    errno = 0;
    long value = sysconf(name);
    if (value == -1) {
        if (errno != 0) {
            perror(label);
            return 1;
        }
        printf("%s=unlimited\n", label);
        return 0;
    }
    printf("%s=%ld\n", label, value);
    return 0;
}
  • 초기화: 호출 직전에 errno를 0으로 만듭니다.
  • 두 갈래: -1이 돌아오면 errno 값으로 실패와 무한을 나눕니다. errno가 0이 아니면 오류를 보고하고 1을 돌려줍니다. errno가 0이면 unlimited를 출력하고 0을 돌려주어 실패로 세지 않습니다.
  • 재사용: 함수로 묶어 두었기 때문에 여러 값을 같은 계약으로 읽을 수 있습니다. 라벨을 인자로 받으므로 오류 메시지가 어느 조회에서 났는지도 알려 줍니다.

완성된 sysprobe는 이 함수로 cpus_online, pagesize, clk_tck, open_max, arg_max 다섯 값을 출력합니다.

페이지 크기와 CLK_TCK가 쓰이는 곳

  • 페이지 크기: 메모리를 다루는 최소 단위입니다. 11주차 mmap에서 다시 만납니다. 페이지 크기를 모르고 버퍼를 정하면 정렬이 어긋나거나 낭비가 생기고, mmap에서는 계산 자체가 틀어질 수 있습니다. 지금은 이 값이 시스템마다 다르다는 것과 조회해서 쓴다는 원칙만 가져가면 됩니다.
  • CLK_TCK: times(2)가 돌려준 틱을 초로 환산할 때 나누는 값입니다. 다음 시간에 배울 시간 처리에서 times와 짝으로 쓰입니다.
  • CPU 수: 작업 분배나 스레드 수를 정하는 근거가 됩니다.

이 값들은 아키텍처와 커널에 따라 다릅니다. x86_64에서는 4096과 100이 흔하지만 Apple Silicon은 16384바이트 페이지를 씁니다. 값의 차이를 만드는 것은 코드가 아니라 환경이며, 같은 프로그램으로 여러 환경의 값을 비교해 보는 것도 과제입니다. 페이지 크기를 얻는 방법으로는 getpagesize()도 있지만 sysconf(_SC_PAGESIZE)가 더 표준적인 방법입니다.

pathconf와 fpathconf

sysconf가 시스템 전체의 경계값을 묻는다면, pathconf와 fpathconf는 파일시스템에 따라 달라지는 경계값을 묻습니다. 같은 상수라도 대상 파일시스템에 따라 값이 다릅니다. 헤더는 <unistd.h>이고 반환값 계약은 sysconf와 같습니다.

  • _PC_NAME_MAX: 그 디렉토리에서 파일 이름의 최대 길이입니다. 이름의 길이 제한은 이름이 속한 파일시스템이 정하기 때문에 디렉토리를 기준으로 묻습니다.
  • _PC_PATH_MAX: 경로 문자열의 최대 길이입니다. 다만 Linux에서는 이 제한보다 긴 경로도 실제로 다루는 경우가 있으므로 문서를 함께 읽어야 합니다.

pathconf는 경로를, fpathconf는 열린 FD를 기준으로 삼습니다. 지난 주의 디렉토리 순회 코드에서 긴 이름을 다룰 때 이 값이 기준이 됩니다.

getconf는 sysconf가 주는 값을 셸에서 확인하는 명령이고, ulimit -Sn은 FD의 soft 한계를 확인합니다. 이 실습의 요점은 같은 값을 서로 다른 문으로 두 번 확인해 맞춰 보는 것입니다. getconf OPEN_MAX와 ulimit -Sn이 같은 숫자인지, sysprobe의 open_max와도 같은지 비교합니다. macOS에서는 일부 기본값이 달라집니다. 값이 다르다면 조회 시점의 soft 한계가 달랐을 수 있으므로 셸 설정이나 시스템 설정 차이를 확인하고, 그 이유를 문서에서 찾습니다. 여기서도 값을 먼저 예측한 뒤 REPORT.md에 기록합니다.

3부 자원 한계

세 번째 부분은 자원 한계입니다. 자원 한계는 프로세스가 쓸 수 있는 자원의 양을 넘지 못하게 하는 커널의 상한입니다. 여기서는 조회에서 한 걸음 나아가, 값을 읽고 조건 안에서 바꾸기까지 합니다.

getrlimit과 setrlimit

헤더는 <sys/resource.h>이고 두 함수 모두 성공하면 0, 실패하면 -1을 돌려줍니다.

  • struct rlimit: 두 값으로 이루어집니다. rlim_cur는 soft 한계, rlim_max는 hard 한계입니다.
  • getrlimit: 현재 값을 구조체로 얻습니다. 드물지만 인자 오류 등으로 실패할 수 있으므로 반환값 검사는 그대로 합니다.
  • setrlimit: 조건을 만족할 때만 값을 바꿉니다. 거부되면 -1과 EPERM입니다.

구조체를 채운 뒤에야 필드를 읽는다는 규칙은 stat과 같습니다. 그리고 값을 바꾼 뒤에는 getrlimit으로 실제 값을 다시 확인합니다.

soft 한계와 hard 한계

  • soft: 지금 강제되는 한계입니다. 넘으면 호출이 실패하거나 시그널이 옵니다.
  • hard: soft가 올라갈 수 있는 상한입니다.
  • 일반 사용자는 soft를 hard까지 올릴 수 있습니다.
  • hard를 낮추면 일반 사용자는 되돌릴 수 없습니다. hard를 올리는 데에는 보통 특권이 필요하기 때문입니다.
  • RLIM_INFINITY는 무제한을 나타내는 특별한 값입니다.

셸에서 실습할 때 주의할 점이 여기서 나옵니다. bash의 ulimit -n은 -S를 붙이지 않으면 soft와 hard를 함께 바꿉니다. hard를 실수로 낮추면 그 셸 안에서는 되돌릴 수 없고 새 셸을 열어야 합니다. 그래서 실습에서는 soft만 바꾸는 ulimit -Sn을 씁니다. 또 프로그램이 바꾼 한계는 그 프로세스와 이후에 만들어지는 자식에만 적용됩니다.

세부 의미는 getrlimit(2) 매뉴얼의 표에서 확인합니다.

limit_show: getrlimit 출력

limit_show는 여러 자원의 soft·hard 한계를 한 번에 표로 보여 줍니다. 핵심 부분은 다음과 같습니다.

struct rlimit rl;
if (getrlimit(RLIMIT_NOFILE, &rl) == -1) {
    perror("getrlimit");
    return 1;
}
printf("%-7s", "nofile");
if (rl.rlim_cur == RLIM_INFINITY)
    printf(" soft=unlimited");
else
    printf(" soft=%ju", (uintmax_t)rl.rlim_cur);
/* hard도 같은 방식으로 출력한다 */
  • 무제한 표시: 값을 RLIM_INFINITY와 비교해서 같으면 숫자 대신 unlimited로 표시합니다.
  • 자료형: rlim_t의 크기는 시스템마다 다를 수 있습니다. printf 형식을 맞추기 위해 uintmax_t로 변환하고 %ju로 출력합니다. 정수형을 printf 형식에 맞추는 이 패턴은 지난 주에도 반복했습니다.
  • 비교 표: 완성된 limit_show는 일곱 종류의 자원(nofile, as, stack, fsize, cpu, nproc, core)을 한 줄씩 출력합니다. 출력의 두 열이 각각 soft와 hard입니다.

한계에 도달하면 무슨 일이 생기나

초과한 한계결과
FD 개수open이 -1을 돌려주고 errno는 EMFILE입니다.
파일 크기write가 EFBIG이고 SIGXFSZ가 갈 수 있습니다.
CPU 시간SIGXCPU가 먼저 오고, 계속 쓰면 SIGKILL입니다.
주소 공간mmap이나 메모리 할당이 ENOMEM으로 실패합니다.

즉 한계 초과의 결과는 오류 반환과 시그널이라는 두 형태로 함께 존재합니다. 시그널을 다루는 방법은 9주차 주제이므로, 지금은 기본 시그널 처리로 프로그램이 끝나는 경우도 있다는 것만 알아 둡니다. 이번 시간에는 한계 초과가 호출 실패로 나타나는 경우, 그중에서도 EMFILE을 직접 관찰합니다.

nofile_demo: FD 한계 실험

nofile_demo는 FD 한계를 직접 밟아 보는 실험입니다. /dev/null을 열 수 있을 때까지 open을 반복하고, EMFILE을 만나면 멈춥니다.

int fd = open("/dev/null", O_RDONLY);
if (fd == -1) {
    if (errno == EMFILE)
        break;            /* 한계 도달 */
    perror("open");
    return 1;
}
fds[opened++] = fd;

/* 실험 뒤 정리 */
while (opened > 0)
    close(fds[--opened]);
  • 실험 설계: open이 실패했을 때 errno가 EMFILE이면 한계에 도달한 것이므로 반복을 끝냅니다. 그 밖의 오류는 진짜 실패로 보고합니다.
  • 열린 개수: 표준 입력·출력·오류 FD 세 개가 이미 열려 있으므로 opened는 soft 값보다 약간 작습니다. 연 FD를 담는 배열의 크기는 soft 한계에 맞춰 확보합니다.
  • 자원 반환: 실험이 끝나면 열린 FD를 모두 닫습니다. 실패해도 연 FD는 모두 닫습니다.

EMFILE을 만났다고 프로그램이 반드시 끝나야 하는 것은 아닙니다. 상황에 따라 기존 FD를 닫고 다시 시도할 수도 있습니다. 이 예제는 관찰이 목적이라 거기서 멈춥니다.

setrlimit로 soft 한계 바꾸기

nofile_demo에 --raise 옵션을 주면 실험 전에 soft 한계를 바꿉니다.

struct rlimit rl;
if (getrlimit(RLIMIT_NOFILE, &rl) == -1) {
    perror("getrlimit");
    return 1;
}
/* hard를 넘는 요청은 hard로 제한한다 */
rlim_t target = want > rl.rlim_max
              ? rl.rlim_max : want;
struct rlimit next = { target, rl.rlim_max };
if (setrlimit(RLIMIT_NOFILE, &next) == -1) {
    perror("setrlimit");
    return 1;
}
  • 상향 범위: 일반 사용자는 hard를 넘어 올릴 수 없습니다. 그래서 먼저 getrlimit으로 hard를 읽고, 요청이 hard를 넘으면 hard 값으로 제한합니다. hard 자체(rl.rlim_max)는 그대로 둡니다.
  • 적용 범위: 바꾼 한계는 이 프로세스와 이후 자식들에만 적용됩니다. 자원 한계는 프로세스별 속성이고 부모로 전파되지 않으므로, 프로그램이 한계를 바꿔도 그 프로그램을 실행한 부모 셸은 그대로입니다.
  • 변경 확인: 바꾼 뒤에는 getrlimit으로 실제 값을 다시 읽어 출력합니다.

셸에서는 ulimit -Sn N이 같은 역할을 합니다. 한 가지 차이가 있습니다. hard를 넘는 상향 요청이 조용히 hard로 잘리는 것은 이 예제 프로그램이 그렇게 작성되었기 때문이고, 셸에서 같은 시도를 하면 오류로 나타납니다.

실습 3: FD 한계 관찰

./limit_show | head -1
./nofile_demo
./nofile_demo --raise 64
./nofile_demo --raise 4096

# 셸에서 soft만 바꿔 비교 (hard 이하)
bash -c 'ulimit -Sn 64 && ./nofile_demo'
bash -c 'ulimit -Sn 4096; ./nofile_demo'
  • 측정: 기본 상태에서 opened가 soft 값 근처에서 멈추는지 확인합니다. 셸이나 라이브러리가 이미 연 FD가 더 있을 수 있으므로 정확히 3만큼 작지 않아도 근처 값이면 됩니다.
  • 변경 실험: --raise 64와 --raise 4096으로 soft를 바꿔 비교합니다. 환경에 따라 기본 soft가 이미 클 수 있는데, 그럴 때 --raise 64는 하향 실험이 됩니다. 4096이 hard보다 크면 hard 값으로 잘리는 것도 관찰합니다. 변화의 방향보다 측정 값이 soft를 따라가는지가 중요합니다.
  • 셸 비교: 새 bash 안에서 ulimit -Sn으로 soft를 바꾸고 실행해 같은 결과가 나오는지 봅니다. 이 실험의 목적은 한계가 그 새 bash 안에서만 바뀌는지 확인하는 것입니다.

여기서도 값을 예측한 뒤 REPORT.md에 기록합니다.

4부 /proc 관찰 창

마지막 부분은 /proc입니다. 표준 API 바깥에서 Linux의 상태를 파일처럼 읽는 방법입니다.

/proc 파일시스템

/proc는 커널과 프로세스 상태를 파일처럼 읽게 해 주는 가상 파일시스템입니다. 내용은 디스크에 저장되어 있는 것이 아니라, 읽을 때마다 커널이 그 순간의 상태를 만들어 줍니다. 그래서 /proc의 파일 크기는 보통 0으로 표시되지만 읽어 보면 내용이 있습니다. /proc 안에는 파일과 숫자 이름의 디렉토리가 섞여 있는데, 각 숫자는 프로세스 ID이고 그 안에 해당 프로세스의 정보가 들어 있습니다.

중요한 것은 /proc가 표준이 아니라 Linux 고유의 관찰 창이라는 점입니다. 다른 Unix에도 비슷한 메커니즘이 있지만 구조가 다릅니다. 그래서 프로그램의 판단 근거보다는 진단과 스크립트에 씁니다. 이식성이 필요한 판단은 표준 API로, 진단은 /proc로 나누는 것이 이번 시간의 원칙입니다.

읽는 데 새로운 API가 필요하지는 않습니다. 지난 주에 배운 opendir·fgets 조합으로 그대로 읽을 수 있습니다.

/proc의 주요 경로

경로내용
/proc/cpuinfo, /proc/meminfoCPU와 메모리의 전체 요약 정보
/proc/loadavg1, 5, 15분 부하 평균과 작업 수를 한 줄로 줍니다.
/proc/self/...이 프로세스의 상태, 한계, 열린 FD

self는 그 경로를 읽고 있는, 실행 중인 프로세스 자신으로 풀립니다. self 자리에 PID를 직접 쓰면 다른 프로세스도 관찰할 수 있습니다. /proc/self/fd 안의 항목들은 FD 번호를 이름으로 하는 심볼릭 링크입니다. 자세한 목록은 proc(5) 매뉴얼에 있습니다.

proc_probe: /proc/self 관찰

proc_probe는 /proc/self/status를 열어 필요한 줄만 걸러 출력합니다.

FILE *f = fopen("/proc/self/status", "r");
if (f == NULL) {
    fprintf(stderr, "/proc/self/status: %s\n",
            strerror(errno));
    return 1;
}
char line[256];
while (fgets(line, sizeof line, f) != NULL)
    if (strncmp(line, "VmRSS:", 6) == 0 ||
        strncmp(line, "Threads:", 8) == 0)
        fputs(line, stdout);
fclose(f);
  • 읽기 방법: 3주차에 배운 stdio 함수로 일반 파일처럼 읽습니다.
  • 필터: 줄의 앞부분을 비교해 VmRSS:와 Threads:로 시작하는 줄만 화면에 남깁니다. VmRSS의 단위는 kB입니다.
  • fd 세기: 완성된 proc_probe는 /proc/loadavg의 첫 줄도 출력하고, /proc/self/fd를 opendir로 읽어 항목 개수를 셉니다.

fd 개수를 해석할 때 주의할 점이 하나 있습니다. /proc/self/fd를 여는 순간 그 디렉토리 스트림 자체가 FD 하나를 추가합니다. 세는 행위가 세는 대상을 하나 늘리는 셈입니다. macOS 실습 환경에는 /proc가 없으므로 안내 오류가 나오는데, 이것도 관찰로 기록합니다.

표준 API와 /proc의 역할 분담

  • 표준 API: uname·sysconf·getrlimit는 이식성 있는 근거입니다.
  • /proc: Linux의 진단·관찰 창입니다. 더 많은 정보를 담고 있습니다.
  • 선택 기준: 프로그램의 판단은 표준 API로, 진단 스크립트는 /proc로 합니다. 기준은 이식성이 필요한지 여부이므로, 목적이 진단이라면 /proc도 합리적인 선택입니다.

같은 값을 두 창에서 확인하는 것이 이번 시간의 관점입니다. 예를 들어 /proc/self/limits는 getrlimit이 주는 값과 같은 정보를 사람이 읽는 형태로 보여 줍니다. 두 값이 어긋나 보이면 단위나 대상 프로세스를 먼저 확인합니다.

확인 문제와 실습 정리

확인 문제

  1. sysconf가 -1을 돌려줄 때 두 경우는 무엇이고 어떻게 구분하는가? 조회 실패와 무한·미정의입니다. 호출 전에 errno를 0으로 만든 뒤, -1일 때 errno로 나눕니다.
  2. 일반 사용자가 soft 한계와 hard 한계에서 바꿀 수 있는 범위는? soft는 hard까지 올릴 수 있고, hard를 낮추면 되돌릴 수 없습니다.
  3. RLIMIT_NOFILE에 도달한 open의 errno 값은? EMFILE입니다.
  4. sysconf(_SC_OPEN_MAX)가 알려주는 값은 무엇과 같은가? RLIMIT_NOFILE의 soft 한계 값입니다.
  5. 프로그램의 판단 근거로 /proc 대신 표준 API를 쓰는 이유는? /proc는 Linux 고유이므로 이식성이 없기 때문입니다.

실습 정리와 제출

  • sysprobe 결과를 uname·getconf 출력과 항목별로 비교합니다.
  • limit_show의 soft·hard를 ulimit·/proc/self/limits와 비교합니다.
  • nofile_demo로 EMFILE까지의 개수와 한계 변경 전후를 기록합니다.
  • proc_probe 결과를 셸 명령 출력과 줄 단위로 대조합니다.

이번 실습의 값은 환경마다 다른 것이 당연합니다. 그래서 기준은 숫자의 일치가 아니라, 두 문에서 같은 값을 얻었는지와 변화의 방향을 설명했는지입니다. 한 곳에서만 확인한 값은 환경의 특수성일 수 있으므로 교차 확인이 근거가 됩니다. 선택 확장 과제는 sysprobe에 pathconf(_PC_NAME_MAX) 항목을 추가하는 것입니다.

새 API를 읽을 때는 반환값과 오류 표시 방식부터 확인합니다. 조회마다 대상, 반환값, 자료형, 실패 조건을 함께 확인하는 습관을 들입니다. 이번 시간에 참고한 매뉴얼은 uname(2), sysinfo(2), getpagesize(2), sysconf(3), pathconf(3), times(2), getrlimit(2), open(2), signal(7), proc(5)이며, 수업은 Ubuntu 일반 사용자 환경을 기준으로 합니다.
