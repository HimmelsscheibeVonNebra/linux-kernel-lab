Linux Lab/6주차 1차시

프로세스 정체성·인자·환경

프로세스의 PID·PPID·PGID·SID, 명령행 인자, 환경 변수, 작업 디렉토리, 자격 증명을 조회하고 ps·/proc과 교차 확인하는 예제입니다.

실행해 볼 예제

  • id_probegetpid·getppid·getpgrp·getsid로 프로세스 정체성을 출력하고 ttyname으로 표준 입력에 연결된 터미널을 확인합니다.
  • arg_showargc와 argv 배열을 출력하고 argv[argc]가 NULL임을 보여 줍니다. argv[0]은 호출 쪽이 정하는 값이라 프로그램 판별에 쓸 수 없음을 확인합니다.
  • env_dumpenviron 배열을 순회해 환경 전체를 출력하고, --find/--set/--unset으로 getenv·setenv·unsetenv의 동작과 변경 범위(이 프로세스 안)를 관찰합니다.
  • cwd_probegetcwd를 버퍼 전달 방식과 (NULL, 0) 할당 방식 두 가지로 호출하고, 인자가 있으면 chdir(2) 후 다시 조회합니다. 실패 경로(ENOENT·ENOTDIR)도 확인합니다.
  • procinfo정체성(pid·ppid·pgid·sid·tty), 자격 증명(uid·euid·gid·egid), 작업 디렉토리, 인자, 환경 요약을 한 번에 출력하는 종합 보고서입니다. --argv, --env로 전체 목록을 볼 수 있습니다.

이번 수업의 주제는 프로세스의 실행 문맥입니다. 5주차에는 uname·sysconf·getrlimit으로 프로세스 바깥의 시스템을 물었다면, 이번에는 처음으로 프로세스 자신에 대해 묻습니다. 프로세스 하나를 설명하는 정보는 네 묶음으로 나눌 수 있습니다. 정체성(PID·PPID·PGID·SID), 입력(argc·argv·environ), 자격 증명과 위치(uid·euid·gid·egid·작업 디렉터리), 그리고 이것들을 밖에서 관찰하는 도구(ps·id·pwd·/proc/PID)입니다. 번호와 관계, 입력, 문맥을 모두 합친 것이 실행 문맥입니다.

수업 전체에서 같은 동작을 반복합니다. 프로그램이 스스로 보고한 값을, ps·id·pwd·/proc가 밖에서 관찰한 값과 맞춰 보는 것입니다. 오늘 다루는 조회는 모두 즉시 답을 주는 호출이므로, 프로그램 쪽에서 신경 쓸 일은 반환값 검사가 전부입니다.

1부 프로세스 정체성

PID·PPID·PGID·SID 네 값이 각각 무엇을 뜻하고 서로 어떤 관계인지 확인합니다.

PID: 프로세스 번호

PID는 커널이 프로세스를 구분하는 데 쓰는 양의 정수입니다. 같은 순간에는 두 프로세스가 같은 PID를 갖지 않습니다. 새 프로세스가 만들어지면 새 PID가 배정되고, 프로세스가 종료하면 그 번호는 회수됩니다. 회수된 번호는 나중에 다른 프로세스에 다시 쓰일 수 있습니다. 예를 들어 PID 8230을 받은 프로세스가 끝나면, 이후에 전혀 다른 프로세스가 8230을 받을 수 있습니다.

그래서 PID는 자원이 아니라 이름이라고 이해해야 합니다. "같은 순간에 유일하다"는 것만 보장되므로, 오래된 PID를 저장해 두었다가 나중에 그 번호가 여전히 같은 프로세스를 가리킨다고 가정하면 안 됩니다.

pid_t pid = getpid();   /* 반환값 검사 없음 */
printf("pid=%ld\n", (long)pid);

getpid는 <unistd.h>에 선언되어 있고 pid_t를 돌려줍니다. 실패 경로가 정의되지 않은 드문 호출이어서 반환값을 검사하지 않습니다.

PPID와 프로세스 트리

PPID는 나를 실행한 프로세스, 곧 부모 프로세스의 PID입니다. 터미널에서 프로그램을 실행했다면 부모는 대개 셸입니다. 셸이 fork로 자식을 만들기 때문입니다. 예를 들어 터미널 프로그램(PID 7399) 아래에 셸 zsh(PID 7412)가 있고, 그 셸에서 실행한 ./id_probe(PID 8230)의 PPID는 7412가 됩니다.

모든 프로세스는 부모를 거슬러 올라가면 PID 1에 닿습니다. PID 1은 Linux에서는 init/systemd, macOS에서는 launchd입니다. 이렇게 부모-자식 관계가 이어져 하나의 트리를 이룹니다.

부모가 자식보다 먼저 종료하면 자식은 고아 프로세스가 되고, PID 1 아래로 재수용됩니다. 이때 자식의 PPID는 1이 됩니다. 부모-자식 관계는 프로세스가 만들어진 시점의 사실이라는 점을 기억해 둡니다. 트리는 Linux에서는 pstree -p, 또는 ps -ef로 확인합니다.

id_probe: 정체성 조회

id_probe는 네 가지 정체성 값을 같은 서식으로 출력하는 예제입니다.

printf("pid=%ld\n", (long)getpid());
printf("ppid=%ld\n", (long)getppid());
printf("pgid=%ld\n", (long)getpgrp());
printf("sid=%ld\n", (long)getsid(0));
const char *tty = ttyname(STDIN_FILENO);
if (tty == NULL) {
    printf("tty=(none)\n");
} else {
    printf("tty=%s\n", tty);
}

네 조회 모두 pid_t를 돌려줍니다. getsid(0)의 0은 "자기 자신"을 뜻합니다. 네 조회는 실패를 정의하지 않으며, getsid도 0을 넘기는 오늘의 용법에서는 안전합니다. 그래서 반환값 검사 없이 곧바로 출력합니다. pid_t의 크기는 시스템마다 다를 수 있으므로 출력하기 전에 (long)으로 변환하고 %ld로 찍습니다. 이 조회들은 모두 unistd.h에 선언되어 있습니다.

ttyname(STDIN_FILENO)는 표준 입력에 연결된 터미널의 이름을 묻습니다. 표준 입력이 터미널이 아니면(입력 리다이렉션이나 크론 등) NULL을 돌려주는데, 이것은 오류가 아니라 관찰 결과입니다. 그래서 프로그램은 "없다"는 결과도 tty=(none)으로 출력에 남깁니다.

프로그램의 앞부분은 인자 검사입니다. 인자를 받지 않는 프로그램이므로 argc != 1이면 사용법을 표준 오류로 알리고 종료 상태 2로 끝냅니다.

if (argc != 1) {
    fprintf(stderr, "usage: %s\n", argv[0]);
    return 2;
}

뒷부분에서는 밖에서 같은 값을 확인할 수 있도록 ps 비교 명령을 프로그램이 직접 알려 줍니다. Linux에서는 여기에 sid 열을 더해 볼 수 있습니다. 마지막으로 fflush의 결과를 검사해 출력이 실제로 나갔는지 확인한 뒤 종료 상태를 정합니다.

printf("compare: ps -o pid,ppid,pgid,tty,stat,command -p %ld\n",
       (long)getpid());
if (fflush(stdout) == EOF) {
    perror("stdout");
    return 1;
}
return 0;

PGID와 세션: 작업 제어의 축

PGID(프로세스 그룹 ID)와 SID(세션 ID)는 작업 제어를 위한 값입니다. 대화형 셸은 작업(job)마다 새 프로세스 그룹을 만듭니다. 그룹의 대표, 곧 그 그룹의 첫 프로세스의 PID가 그 그룹의 PGID가 됩니다.

예를 하나 따라가 봅니다. 로그인 셸 zsh의 PID가 7412라면, 이 셸이 세션 대표이므로 세션의 SID는 7412이고, 세션에는 제어 터미널(예: /dev/pts/0)이 하나 연결됩니다. 셸 자신은 그룹 7412에 속합니다(PID 7412, PGID 7412). 여기서 cat f | grep x | wc를 실행하면 세 프로세스(PID 8300, 8301, 8302)가 하나의 작업이 되어 모두 PGID 8300을 갖습니다. 첫 프로세스 cat의 PID가 그룹 번호가 된 것입니다. sleep 30 &로 백그라운드 작업을 띄우면 그것은 또 다른 그룹(PID 8310, PGID 8310)이 됩니다.

이렇게 묶는 이유는 신호를 작업 단위로 보내기 위해서입니다. Ctrl+C(SIGINT)는 프로세스 하나가 아니라 포그라운드 그룹 전체에 전달됩니다. 위의 예에서는 파이프라인의 세 프로세스가 함께 받고, 백그라운드 그룹과 셸은 받지 않습니다.

두 축: 트리와 작업 제어

부모-자식 관계(PPID)와 그룹·세션(PGID·SID)은 서로 다른 축입니다. 앞의 예에서 cat, grep, wc, sleep 네 프로세스는 모두 셸이 만든 자식이므로 PPID가 전부 7412입니다. 트리만 보면 이 넷은 구분되지 않습니다. 반면 그룹으로 보면 앞의 셋은 포그라운드 그룹 8300, sleep은 백그라운드 그룹 8310으로 나뉘고, 넷 모두 같은 세션 7412와 같은 제어 터미널에 속합니다. PPID는 "태어난 관계"를, PGID·SID는 "작업 제어의 관계"를 말해 줍니다.

ps로 교차 확인

프로그램이 보고한 값은 ps의 같은 열과 맞춰 확인합니다. 셸에서 $$는 셸 자신의 PID, $!는 직전 백그라운드 작업의 PID입니다. 아래는 Linux(procps)·bash 환경의 출력 예시입니다.

$ ps -o pid,ppid,pgid,sid,tty,stat,cmd -p $$
    PID    PPID    PGID     SID TT       STAT CMD
   7412    7399    7412    7412 pts/0    Ss -bash
$ sleep 30 &
$ ps -o pid,ppid,pgid,sid,tty,stat,cmd -p $!
    PID    PPID    PGID     SID TT       STAT CMD
   8310    7412    8310    7412 pts/0    S    sleep 30

두 번째 출력에서 sleep 30은 셸이 만든 자식이므로 PPID가 셸의 PID(7412)입니다. 그리고 작업마다 새 그룹이 생기므로 PGID는 자기 PID(8310)와 같습니다. SID는 셸과 같은 7412입니다.

macOS의 ps에는 sid·cmd 열이 없습니다. 대신 tty·command를 쓰고, SID는 id_probe의 출력끼리 비교합니다.

직접 확인 1: 정체성

./id_probe
./id_probe < /dev/null     # 표준 입력이 터미널이 아니면 tty=(none)

ps -o pid,ppid,pgid,sid,tty,stat,cmd -p $$    # Linux
ps -o pid,ppid,pgid,tty,stat,command -p $$    # macOS

sleep 30 &
ps -o pid,ppid,pgid,command -p $!
kill %1

pstree -p | less    # Linux · macOS는 ps -ef

확인할 것은 세 가지입니다. 첫째, id_probe의 출력과 ps의 같은 열을 비교합니다. 둘째, & 실험에서 백그라운드 자식의 PPID가 셸의 PID이고 PGID가 자기 PID인지 봅니다. sleep 30이 살아 있는 동안 ps로 확인하고, 끝나면 kill %1로 정리합니다. 셋째, pstree 또는 ps -ef의 출력에서 자기 셸과 그 부모를 찾아봅니다.

2부 인자와 환경

프로세스가 시작할 때 받는 두 입력, argc·argv와 environ의 구조와 수명을 다룹니다.

argc·argv의 구조

argv는 널 종료 문자열을 가리키는 포인터의 배열입니다(char *argv[]). ./arg_show one two three를 실행하면 argc는 4이고, argv[0]부터 argv[3]까지가 각각 "./arg_show", "one", "two", "three"를 가리키며, argv[4]는 NULL입니다.

각 문자열은 \0으로 끝나고, 배열 자체는 NULL로 끝납니다. argv[argc] == NULL은 보장되는 사실입니다. 따라서 배열의 끝을 알리는 표시가 개수(argc)와 NULL 두 가지인 셈이고, 두 번째 끝 표시 덕분에 argc 없이도 배열을 순회할 수 있습니다. 인덱스의 의미로 보면 argv[0]은 관례상 프로그램 이름이지만, 뒤에서 보듯이 보증된 것은 아닙니다.

arg_show: 인자 순회

arg_show는 이 구조를 그대로 출력해 보는 예제입니다.

printf("argc=%d\n", argc);
for (int i = 0; i < argc; i++) {
    printf("argv[%d]=%s\n", i, argv[i]);
}
printf("argv[%d]=%p\n", argc, (void *)argv[argc]);

argc를 먼저 확보하면 반복의 범위가 명확해집니다. 마지막 줄은 argv[argc]를 포인터로 출력해서 그것이 NULL임을 직접 관찰합니다. 인자로 받은 문자열은 외부에서 들어온 값이므로, 길이와 형식은 사용하기 전에 검증해야 합니다. 소스의 주석은 exec -a 등으로 argv[0]을 바꾼 실행과 비교할 때 문자열 길이도 함께 출력해 보면 길이 검증의 출발점이 된다는 힌트를 남기고 있습니다.

argv는 어디서 오는가

argv는 프로그램을 실행하는 쪽이 만듭니다. 부모인 셸이 명령줄을 쪼개 배열을 만들고, execve(path, argv, envp)를 호출하면 커널이 그 배열을 새 프로그램에 전달하며, 새 프로그램은 그것을 main(argc, argv)로 받습니다.

이 과정에서 실행하는 쪽은 어떤 문자열이든 넣을 수 있습니다. 셸은 보통 실행한 경로를 argv[0]에 넣지만, exec -a로 얼마든지 바꿀 수 있습니다.

$ bash -c 'exec -a fake-name ./arg_show x'
argc=2
argv[0]=fake-name
argv[1]=x
argv[2]=0x0       (Linux: argv[2]=(nil))

실행한 파일은 ./arg_show인데 argv[0]은 fake-name으로 나옵니다. argv[0]은 관례일 뿐 보증이 아니라는 뜻입니다. 따라서 argv[0]은 로그와 오류 메시지의 표기에만 쓰고, 프로그램을 판별하는 근거로는 쓰지 않습니다.

함께 알아 둘 점이 두 가지 있습니다. 첫째, ps도 argv를 봅니다. 관리자가 ps로 보는 명령줄이 바로 argv이므로, 인자로 넘긴 비밀은 그대로 드러납니다. 둘째, 인자와 환경의 총 크기에는 상한 ARG_MAX가 있으며, 이것은 5주차에 sysconf로 조회했던 값입니다.

environ: 같은 모양의 배열

환경은 "NAME=value" 형태 문자열의 널 종료 포인터 배열입니다. 예를 들어 "HOME=/home/u", "PATH=/usr/bin:/bin", "LANG=ko_KR.UTF-8"이 차례로 들어 있고 마지막 칸이 NULL입니다. argv와 모양이 같으므로 순회하는 코드도 같습니다.

extern char **environ;
for (char **e = environ; *e != NULL; e++)
    printf("%s\n", *e);

extern char **environ;은 프로그램이 직접 선언합니다. 헤더의 선언은 조건부이기 때문입니다. glibc에서는 _GNU_SOURCE를 정의할 때만 unistd.h가 environ을 선언합니다. main의 세 번째 인자 envp로 받는 방법도 있지만 이것은 POSIX 표준이 아닙니다. 프로세스의 환경은 부모 프로세스 환경의 복사본으로 시작합니다.

env_dump: 환경 순회와 변경

env_dump는 environ을 순회하고, getenv·setenv·unsetenv로 조회·변경하는 계약을 관찰하는 예제입니다. stdlib.h는 getenv·setenv를 위해, string.h는 strcmp·strchr를 위해 포함합니다. 런타임이 정의한 전역 배열 environ은 extern으로 가져다 씁니다.

extern char **environ;

static int count_env(void)
{
    int n = 0;
    for (char **e = environ; *e != NULL; e++) {
        n++;
    }
    return n;
}

count_env는 argv와 같은 널 종료 순회로 항목 수를 셉니다. 각 요소는 "이름=값" 문자열 하나입니다. dump_env는 같은 순회로 *e를 한 줄씩 출력하기만 합니다. 개수를 따로 세는 이유는 setenv·unsetenv 뒤에 개수가 어떻게 변하는지 비교하기 위해서입니다.

static int find_env(const char *name)
{
    const char *value = getenv(name);
    if (value == NULL) {
        printf("%s=(unset)\n", name);
    } else {
        printf("%s=%s\n", name, value);
    }
    return 0;
}

find_env는 이름 하나를 getenv로 조회합니다. getenv가 돌려주는 것은 내부 저장소를 가리키는 포인터입니다. 값이 없으면 NULL이 오는데, 이것은 오류가 아니라 "설정되지 않음(unset)"이라는 정상 결과이므로 오류와 구분해 (unset)이라는 기본 표기로 처리합니다.

main은 하위 명령을 나눠 처리합니다. 인자가 너무 많으면(argc > 3) 사용법을 안내하고 종료 상태 2로 끝냅니다. 인자 없이 실행하면 개수(env_count=)와 전체 환경을 출력합니다. --find NAME은 이름 하나를 조회합니다. 어느 하위 명령에도 맞지 않으면 마지막에 다시 사용법 오류로 끝냅니다.

if (argc > 3) {
    fprintf(stderr, "usage: %s [--find NAME | --set NAME=VALUE"
                    " | --unset NAME]\n", argv[0]);
    return 2;
}
if (argc == 1) {
    printf("env_count=%d\n", count_env());
    dump_env();
    return 0;
}
if (strcmp(argv[1], "--find") == 0 && argc == 3) {
    return find_env(argv[2]);
}

--set NAME=VALUE 블록은 입력 검증, 이름 분리, 변경과 재조회의 세 단계로 이루어집니다.

if (strcmp(argv[1], "--set") == 0 && argc == 3) {
    char *eq = strchr(argv[2], '=');
    if (eq == NULL || eq == argv[2]) {
        fprintf(stderr, "--set expects NAME=VALUE\n");
        return 2;
    }
    size_t name_len = (size_t)(eq - argv[2]);
    char name[name_len + 1];
    memcpy(name, argv[2], name_len);
    name[name_len] = '\0';
    if (setenv(name, eq + 1, 1) == -1) {
        perror("setenv");
        return 1;
    }
    printf("env_count=%d\n", count_env());
    return find_env(name);
}

eq는 NAME=VALUE에서 =의 위치입니다. 등호가 없거나 맨 앞에 있으면(이름이 비어 있으면) 형식 오류이므로 종료 상태 2로 끝냅니다. 그다음 = 앞부분만 널 종료 문자열로 복사해 이름을 분리합니다. setenv의 세 번째 인자 1은 같은 이름이 이미 있으면 덮어쓴다는 뜻입니다. setenv는 실패해 -1을 돌려줄 수 있으므로 반환값을 검사합니다. 바꾼 뒤에는 개수와 값을 다시 조회해 결과를 확인합니다. 이 변경은 이 프로세스 안에서만 일어나며 부모 셸에는 영향을 주지 않습니다.

if (strcmp(argv[1], "--unset") == 0 && argc == 3) {
    if (unsetenv(argv[2]) == -1) {
        perror("unsetenv");
        return 1;
    }
    printf("env_count=%d\n", count_env());
    return find_env(argv[2]);
}

--unset NAME도 같은 모양입니다. 삭제도 실패 경로를 가지므로 반환값을 검사하고, 지운 뒤에는 (unset) 표기와 개수 변화로 결과를 확인합니다.

getenv·setenv·unsetenv 계약

세 함수는 <stdlib.h>에 선언되어 있습니다. 각각의 성공과 실패는 다음과 같습니다.

호출성공실패 또는 없음
getenv("HOME")값 포인터. 내부 저장소를 가리키므로 수정하거나 free하면 안 됩니다.NULL = unset. 오류가 아니라 정상 결과입니다.
setenv("PROBE", "1", 1)0. overwrite가 1이면 덮어씁니다.-1, errno = EINVAL. 이름이 비었거나 =를 포함한 경우입니다.
unsetenv("PROBE")0. 없는 이름이어도 성공입니다.-1, errno = EINVAL. 이름이 비었거나 =를 포함한 경우입니다.

변경은 이 프로세스와 이후에 만들어지는 자식에만 적용됩니다. 여기서 나오는 안전한 사용 패턴은 세 가지입니다. getenv의 NULL은 오류와 구분해 기본 표기로 처리하고, setenv는 실패할 수 있으므로 반환값을 검사하며, 바꾼 뒤에는 개수와 값을 다시 조회해 확인합니다. 이 세 가지가 env_dump의 find_env와 --set 블록에 그대로 들어 있습니다.

환경 변경의 전파 범위

환경은 부모에서 자식으로, 한 방향으로만 흐릅니다. 부모 셸(PID 7412)이 환경 A(HOME, PATH 등)를 갖고 있을 때, fork와 exec로 실행된 ./env_dump(PID 8230)는 환경 A의 복사본을 받습니다. 자식이 setenv("PROBE", "1", 1)을 호출하면 자식 안의 환경은 A + PROBE=1이 되지만, 그것은 복사본을 고친 것이므로 부모는 그대로입니다. 자식은 부모를 고칠 수 없습니다. 실제로 부모 셸에서 env | grep PROBE를 실행하면 아무것도 나오지 않습니다. 반대로 그 자식이 다시 자식을 만들면, 새 자식은 A + PROBE=1을 상속합니다.

셸의 동작도 이 규칙으로 설명됩니다.

  • export: 셸의 export는 셸이 실행할 자식으로의 상속을 뜻합니다. 스크립트를 자식 프로세스로 실행해서는 현재 셸의 환경을 바꿀 수 없으므로, 현재 셸에 적용하려면 source가 필요한 이유이기도 합니다.
  • 명령 앞 붙이기: MESSAGE=hi ./env_dump처럼 명령 앞에 붙인 변수는 그 명령의 프로세스에만 적용됩니다.
  • env -i: 빈 환경으로 자식을 실행하는 실험 도구입니다. 빈 환경도 유효한 환경입니다.

직접 확인 2: 인자·환경

./arg_show one two three
bash -c 'exec -a fake-name ./arg_show x'
./env_dump | head -3
./env_dump --find HOME
./env_dump --find NO_SUCH_NAME
MESSAGE=hi ./env_dump --find MESSAGE
./env_dump --set PROBE=1
env | grep PROBE                 # 부모 셸은 그대로
env -i PATH=/usr/bin ./env_dump

exec -a 실험에서는 argv[0]만 바뀐 실행을 관찰합니다. MESSAGE=hi 실험에서는 명령 앞 붙이기가 그 명령에만 적용되는 것을, --set PROBE=1 뒤의 env | grep PROBE에서는 부모 셸이 그대로인 것을 확인합니다. env -i 뒤에는 PATH처럼 직접 넘긴 항목만 남습니다. 아무것도 넘기지 않은 env -i ./env_dump도 동작합니다. 빈 환경도 유효한 환경이기 때문입니다.

3부 사용자와 작업 디렉터리

UID·GID와 작업 디렉터리(CWD)까지 더해 실행 문맥을 완성합니다.

자격 증명: uid·euid·gid·egid

프로세스는 사용자 ID를 두 가지로 갖습니다. getuid는 실제(real) 사용자 ID를, geteuid는 유효(effective) 사용자 ID를 돌려줍니다. 파일 접근 허가는 대부분 유효 ID를 기준으로 결정됩니다. 예를 들어 ./procinfo를 일반 실행해서 uid=501, euid=501, gid=20, egid=20인 프로세스가 소유자 501, 권한 rw-r--r--인 파일 data.txt에 접근할 때, 허가 여부는 euid·egid를 기준으로 판단됩니다. 그룹에 대해서도 getgid·getegid가 같은 계약을 제공합니다.

일반적인 수업 환경에서는 uid와 euid가 같습니다. 그런데도 둘을 개념적으로 나누는 이유는 set-user-ID 실행처럼 유효 ID만 바뀌는 경우가 있기 때문입니다. 소유자가 root이고 set-user-ID 비트가 켜진 /usr/bin/passwd를 사용자 501이 exec하면, 실행 중인 프로세스는 uid=501, euid=0이 됩니다. 유효 ID만 바뀌는 것입니다.

이 조회들은 <unistd.h>와 <sys/types.h>를 사용합니다. 더 자세한 내용은 credentials(7)에 있고, 14주차 IPC 권한에서 이어집니다.

procinfo: 자격 증명과 문맥

procinfo는 오늘 배운 실행 문맥을 한 프로그램으로 종합한 예제입니다. 정체성(pid·ppid·pgid·sid), 자격 증명(uid·euid·gid·egid), 작업 디렉터리, 인자, 환경 요약을 같은 조회-출력 규칙으로 출력합니다. --env를 주면 환경 전체를, --argv를 주면 인자 전체를 나열합니다.

printf("uid=%ld euid=%ld\n",
       (long)getuid(), (long)geteuid());
printf("gid=%ld egid=%ld\n",
       (long)getgid(), (long)getegid());
char cwd[4096];
if (getcwd(cwd, sizeof cwd) == NULL) {
    perror("getcwd");
    return 1;
}
printf("cwd=%s\n", cwd);

uid·euid와 gid·egid 두 쌍을 같은 서식으로 출력한 다음 작업 디렉터리를 조회합니다. 앞의 조회들과 달리 getcwd는 결과를 담을 버퍼를 인자로 받습니다. 그리고 실패 경로가 있습니다. 버퍼가 짧으면 ERANGE, 경로가 사라졌으면 ENOENT로 실패하므로 NULL 반환을 검사합니다. CWD까지 출력되면 실행 문맥 보고서가 완성됩니다.

나머지 부분은 앞에서 본 코드의 재사용입니다. count_env는 env_dump와 같은 함수를 그대로 가져왔고, show_env_var는 getenv의 NULL을 (unset)으로 출력하는 패턴 그대로이며 HOME과 PATH 두 조회를 한 함수로 처리합니다. 정체성 부분은 id_probe와 같은 조회를 두 값씩 한 줄에 묶어(pid=… ppid=…, pgid=… sid=…) 보고서의 행 수를 줄였고, tty가 NULL인 경우도 (none)으로 남깁니다.

옵션 파싱은 인자 검증의 예입니다.

int show_env = 0;
int show_argv = 0;
for (int i = 1; i < argc; i++) {
    if (strcmp(argv[i], "--env") == 0) {
        show_env = 1;
    } else if (strcmp(argv[i], "--argv") == 0) {
        show_argv = 1;
    } else if (strncmp(argv[i], "--", 2) == 0) {
        fprintf(stderr, "usage: %s [--env] [--argv]"
                        " [args...]\n", argv[0]);
        return 2;
    }
    /* --로 시작하지 않는 인자는 명령행 입력으로 그대로 두고
       --argv로 관찰한다. argv는 검증 대상이지 거부 대상이 아니다. */
}

두 플래그를 0으로 초기화하고 해당 옵션을 만나면 켭니다. 모르는 --옵션은 사용법을 안내하고 종료 상태 2로 끝냅니다. 반면 --로 시작하지 않는 일반 인자는 거부하지 않고 관찰 대상으로 남깁니다. 끝부분에서는 argc를 항상 출력하고 --argv가 켜졌을 때만 인자 전체를 나열하며, 환경도 개수(env_count=)는 항상, 전체 나열은 --env를 줄 때만 출력합니다. 마지막으로 HOME·PATH를 조회하고, 출력 버퍼를 정리한 뒤 종료 상태를 확정합니다.

CWD와 상대 경로

작업 디렉터리(CWD)는 상대 경로를 절대 경로로 푸는 기준입니다. CWD가 /home/u/lab일 때 open("data.txt")는 /home/u/lab/data.txt를 엽니다. chdir("/tmp")로 CWD를 /tmp로 바꾼 뒤의 open("data.txt")는 /tmp/data.txt를 엽니다. 같은 문자열 "data.txt"가 다른 파일을 가리키게 되는 것입니다. 그래서 로그에 getcwd 값을 남겨 두면 나중에 어디서 실행했는지 재현할 수 있습니다.

getcwd의 호출 형태는 두 가지입니다. 호출자가 버퍼를 넘기는 형태가 POSIX 기본형입니다. getcwd(NULL, 0)은 glibc·BSD 확장으로, 라이브러리가 알아서 할당해 주며 호출자가 free해야 합니다. 실패 경로는 getcwd가 ERANGE·ENOENT, chdir이 ENOENT·ENOTDIR입니다. CWD는 프로세스별 속성이어서 chdir은 그 프로세스 안에서만 유효합니다.

cwd_probe: chdir 실험

cwd_probe는 getcwd의 두 형태와 chdir의 성공·실패 경로를 관찰하는 예제입니다. 먼저 호출자 버퍼 형태입니다. 호출자가 준 버퍼에 결과를 담고, 실패는 perror로 보고합니다.

static int show_cwd(const char *label)
{
    char buf[4096];
    if (getcwd(buf, sizeof buf) == NULL) {
        perror(label);
        return 1;
    }
    printf("%s=%s\n", label, buf);
    return 0;
}

다음은 할당 형태입니다. (NULL, 0)을 주면 라이브러리가 알아서 할당합니다. NULL 반환을 검사해 perror와 종료 상태 1로 처리하고, 할당받은 메모리는 출력한 뒤 free로 반환합니다. stdlib.h를 포함하는 이유가 이 free입니다.

static int show_cwd_alloc(const char *label)
{
    char *p = getcwd(NULL, 0);
    if (p == NULL) {
        perror(label);
        return 1;
    }
    printf("%s=%s\n", label, p);
    free(p);
    return 0;
}

main은 선택 인자를 하나까지만 받으며, 그 이상이면 사용법을 알리고 종료 상태 2로 끝냅니다. 그다음 show_cwd("cwd")와 show_cwd_alloc("cwd_alloc")으로 같은 값을 서로 다른 호출 형태로 두 번 읽어 비교합니다. 인자가 있으면 chdir 실험으로 넘어갑니다.

if (argc == 2) {
    if (chdir(argv[1]) == -1) {
        perror(argv[1]);
        return 1;
    }
    if (show_cwd("after_chdir") != 0) {
        return 1;
    }
}

chdir은 없는 경로를 주면 ENOENT, 디렉터리가 아닌 파일을 가리키면 ENOTDIR로 실패합니다. perror(argv[1])이므로 오류 메시지 앞에 경로 이름이 찍힙니다. 성공했을 때는 "바뀌었을 것"이라고 가정하지 않고, show_cwd가 getcwd로 실제 값을 다시 읽어 after_chdir=로 출력합니다. 바뀐 CWD는 이 프로세스 안에서만 유효하고 부모 셸은 그대로입니다. 프로그램은 출력 버퍼를 밀어낸 뒤 종료 상태를 확정하며 끝납니다.

상속과 교체의 규칙

지금까지 본 문맥이 새 프로세스로 어떻게 넘어가는지는 fork와 exec의 규칙으로 정리됩니다.

  • fork는 복제입니다. 부모(PID 7412)가 fork()를 호출하면 자식은 새 PID(예: 8230)를 받고, 환경·CWD·자격 증명·열린 파일 디스크립터를 모두 복사본으로 갖습니다.
  • exec는 교체입니다. execve()를 호출하면 PID는 유지된 채 프로그램이 새것으로 바뀝니다. 코드·데이터·힙·스택이 바뀌고, argv와 (새 배열을 넘기면) environ도 바뀝니다. CWD·자격 증명·열린 FD(기본)는 유지됩니다.

정리하면 환경·CWD·자격 증명·열린 FD는 유지되는 쪽이고, exec에서는 PID도 유지됩니다. 셸의 cd가 서브셸 밖에 영향을 주지 않는 이유는 서브셸이 CWD의 복사본을 가진 별도 프로세스이기 때문이고, execve에 새 환경 배열을 넘기면 환경을 통째로 바꿀 수 있는 이유는 exec가 그 배열로 환경을 교체하기 때문입니다. fork·exec의 상세는 10주차에서 완성합니다.

직접 확인 3: 문맥

./procinfo one
./procinfo --argv one
id                      # uid·gid를 procinfo와 맞춘다
pwd

(cd /tmp && "$OLDPWD/procinfo" | grep cwd)
pwd                      # 부모 셸은 그대로

./cwd_probe /tmp
./cwd_probe /no/such/dir; echo "status=$?"
./cwd_probe /etc/hosts; echo "status=$?"

procinfo 하나로 오늘의 조회 전체를 다시 확인합니다. id 명령이 보여 주는 uid·gid와 procinfo의 출력이 같은지 맞춥니다. 괄호로 만든 서브셸 안에서 cd /tmp를 하고 procinfo를 실행하면 cwd는 바뀌어 나오지만, 서브셸 밖의 pwd에는 영향이 없습니다. cwd_probe의 실패 실험에서는 없는 경로가 ENOENT, 파일 경로가 ENOTDIR로 실패하는 것과 그때의 종료 상태를 확인합니다.

4부 관찰 창과 보안

/proc와 ps로 문맥을 밖에서 확인하고, 인자와 환경을 어느 수준까지 신뢰할지 정합니다.

/proc/PID 관찰 창

Linux에서는 /proc/PID/ 디렉터리가 그 프로세스의 실행 문맥을 들여다보는 창입니다. 프로그램 안에서 표준 API로 얻던 값들이 파일 형태로 대응됩니다.

항목내용
statusPid·PPid·Uid·Gid. getpid·getppid·getuid·getgid에 대응합니다.
cmdlineargv. 널 바이트로 구분된 문자열입니다.
environexecve 시점의 초기 환경. setenv 이후의 변경은 반영되지 않습니다.
cwdgetcwd에 대응합니다. 작업 디렉터리로 가는 심볼릭 링크입니다.
fd/열린 파일 디스크립터 표(0, 1, 2, …). readlink로 대상을 확인합니다.
maps주소 공간 구역. 다음 주제인 코드·데이터·힙·스택으로 이어집니다.

/proc/self는 자기 자신을 가리킵니다. 이 창은 Linux 전용이므로 역할을 나눠 씁니다. 프로그램의 판단은 표준 API로 하고, /proc는 진단에 씁니다.

셸 관찰 명령 (Linux)

grep -E '^(Name|Pid|PPid|Uid|Gid)' /proc/$$/status
tr '\0' ' ' < /proc/$$/cmdline; echo
readlink /proc/$$/cwd          # pwd·getcwd 값과 맞춘다
sleep 30 & P=$!
grep -E '^(Name|Pid|PPid)' /proc/$P/status
tr '\0' ' ' < /proc/$P/cmdline; echo
ls -l /proc/$P/fd
kill $P

status의 Pid·PPid·Uid는 procinfo와 id의 출력과 같습니다. cmdline은 argv를 그대로 보여 주는데, 인자가 널 바이트로 구분되어 있으므로 tr '\0' ' '로 바꿔 읽습니다. readlink /proc/$$/cwd의 결과는 pwd·getcwd 값과 맞춥니다. 권한도 확인해 둘 만합니다. 다른 사용자 프로세스의 environ은 열리지 않습니다.

인자·환경은 입력이다

관찰 창을 알고 나면 인자와 환경이 어디로 노출되는지도 보입니다.

  • 명령줄 argv는 ps와 /proc/PID/cmdline으로 드러나며, 같은 머신의 모든 사용자가 볼 수 있습니다. 따라서 비밀번호나 토큰을 인자로 넘기지 않습니다.
  • 환경 변수 environ은 /proc/PID/environ으로 드러나며, 같은 uid 또는 관리자가 볼 수 있습니다. 프로그램은 getenv 결과를 검증하고 기본값을 둡니다.
  • PATH·LD_PRELOAD가 오염되면 엉뚱한 프로그램이나 라이브러리가 실행됩니다. 그리고 민감한 값을 로그에 통째로 남기지 않습니다.

외부에서 들어오는 값은 범위와 형식을 검증한 뒤 씁니다. 노출 경로를 알면 무엇을 인자·환경에 넣으면 안 되는지도 알 수 있습니다. 오늘의 원칙은 한 문장입니다. argv와 environ은 신뢰가 아니라 입력입니다.

두 창의 교차 확인

오늘 다룬 다섯 항목은 모두 "안에서 보고하는 표준 API"와 "밖에서 관찰하는 도구"의 짝으로 정리됩니다.

항목안에서 보고 · 표준 API밖에서 관찰 · 도구
정체성getpid · getppid · getpgrp · getsid(0)ps -o pid,ppid,pgid,sid · /proc/PID/status
인자argc · argvps -o cmd (macOS: command) · /proc/PID/cmdline
환경environ · getenvenv · /proc/PID/environ (초기 환경)

두 창의 값이 일치하는지가 신뢰의 근거입니다. procinfo 하나로 전체를 다시 확인할 수 있습니다.

정리

  • 정체성: PID·PPID·PGID·SID로 프로세스를 식별합니다. 트리와 작업 제어는 서로 다른 축입니다.
  • 입력: argc·argv와 environ은 같은 모양의 배열이며 프로그램의 입력입니다.
  • 계약: getenv의 NULL은 unset이고, 환경 변경은 이 프로세스와 자식에만 적용됩니다.
  • 문맥: 자격 증명과 작업 디렉터리까지가 실행 문맥입니다. chdir은 프로세스 안에서만 유효합니다.
  • 확인: 프로그램의 조회를 ps·id·pwd·/proc와 교차 검증합니다.

더 읽을 자료는 man 7 environ과 man 7 credentials입니다. 이어지는 주제는 프로세스 상태·주소 공간·자원이고, 9주차 시그널과 10주차 fork·exec로 연결됩니다.

이것으로 할 수 있는 일

  • 로그와 장애 추적: 로그 줄마다 PID·PPID·CWD를 남기면(getpid·getppid·getcwd) "누가, 어디서" 실행했는지 재현됩니다.
  • 환경 변수로 설정 받기: PORT, LOG_LEVEL 같은 설정을 getenv로 읽고, NULL이면 기본값을 씁니다. 값은 범위와 형식을 검증한 뒤 사용합니다.
  • 명령줄 도구 만들기: argv를 검증하고 usage와 종료 상태 2를 돌려주는 관례를 따릅니다. argv[0]은 표기용이고, 비밀은 인자가 아니라 파일이나 FD로 전달합니다.
  • 미니 셸(캡스톤): 작업마다 새 프로세스 그룹을 만들고 Ctrl+C를 포그라운드 그룹에 보냅니다. cd가 내장 명령이어야 하는 이유도 chdir이 그 프로세스 안에서만 유효하기 때문입니다.
  • 데몬·서비스: setsid로 세션을 분리하고 chdir("/")와 환경 정리로 터미널에서 독립합니다. 부모가 끝나면 PID 1 아래로 재수용됩니다.
  • 프로세스 관찰·점검 도구: /proc/PID를 읽어 미니 ps·top을 만들고, 인자에 비밀을 노출하는 프로그램이나 PATH 오염을 점검합니다.

이 내용은 9주차 시그널, 10주차 fork·exec, 캡스톤 미니 셸로 이어집니다. 오늘의 조회가 그 모든 코드의 첫 줄입니다.
