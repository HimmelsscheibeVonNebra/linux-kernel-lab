파일 속성

stat/lstat으로 파일 속성을 조회하고 권한(umask·fchmod), 희소 파일의 크기와 할당량, 시간 속성(futimens), unlink 이후의 열린 FD를 관찰하는 예제입니다.

실행해 볼 예제

  • file_attr기본은 lstat, --follow를 주면 stat으로 종류, inode, 링크 수, 권한(rwx 문자열), 소유자, 크기·블록 수, 나노초 단위 atime/mtime/ctime을 출력합니다.
  • mode_demoumask를 바꿔 가며 openat(O_CREAT|O_EXCL)·mkdirat으로 파일과 디렉토리를 만들고, fchmod 전후의 권한을 fstat으로 확인합니다.
  • sparse_demo새 파일에서 lseek로 1MiB 위치로 이동한 뒤 1바이트를 써서 희소 파일을 만들고, 논리적 크기(st_size)와 할당 블록 수(st_blocks)를 비교합니다.
  • time_attrsfutimens(2)로 atime·mtime을 지정한 값(2024-01-01, 2024-01-02 UTC)으로 바꾸고, fchmod 뒤에도 그 값이 유지되며 ctime만 현재 시각임을 보여 줍니다.
  • fd_unlink_demomkstemp로 만든 임시 파일을 unlink한 뒤에도 열린 FD로 fstat(links=0)과 read가 가능함을 보여 줍니다. 이름과 inode의 수명이 다르다는 예제입니다.

이번 시간에는 파일의 내용이 아니라 파일 속성을 집중해서 다룹니다. 파일 내용을 읽고 쓰는 일과, 파일의 종류·권한·소유권·크기·시간을 확인하는 일은 서로 다른 작업입니다. 속성을 조회하는 방법을 먼저 익힌 뒤 권한을 바꿔 보고, 크기와 시간을 비교하고, 마지막에는 파일 이름을 지운 뒤에도 열린 파일 디스크립터(FD)로 속성을 조회해 봅니다. 실습에서는 inode 번호 같은 숫자 자체보다 작업 전후에 무엇이 같고 무엇이 달라졌는지를 비교하는 것이 핵심입니다.

복습: 내용·속성·이름과 디렉토리

파일 내용과 파일 속성, 파일 이름

하나의 파일을 이야기할 때는 세 가지를 구별해야 합니다.

  • 파일 내용: read와 write로 읽고 쓰는 바이트입니다.
  • 파일 속성: 종류, 권한, 소유자, 크기, 시간 등의 정보입니다. stat 계열 함수가 다루는 대상입니다.
  • 파일 이름: 디렉토리가 관리하는, 이름과 대상 사이의 연결입니다.

내용이 완전히 같은 두 파일이라도 inode와 소유자, 수정 시각은 다를 수 있습니다. 파일을 복사하면 바이트 내용은 같지만 별도의 inode를 가진 다른 객체가 만들어지기 때문입니다. 반대로 내용이 없는 0바이트 파일도, 존재하는 이상 종류·권한·소유자 같은 속성을 가집니다.

파일 이름은 struct stat의 필드가 아니라는 점도 기억해 둡니다. 이름은 디렉토리 쪽 정보입니다. 또한 inode 번호는 같은 파일시스템 안에서만 의미가 있으므로, 두 파일이 같은 파일인지 비교할 때는 st_dev와 st_ino를 함께 봅니다.

디렉토리 트리와 경로 해석

디렉토리 구조는 루트 /에서 시작합니다. 디렉토리 안에는 파일과 다른 디렉토리가 있고, 경로는 각 이름을 차례로 찾아 가며 해석합니다. 예를 들어 루트에서 usr, local을 차례로 선택하면 /usr/local이라는 경로가 됩니다. 이때 중간의 usr은 다음 이름을 검색할 수 있는 디렉토리여야 합니다.

디렉토리도 inode를 가집니다. 디렉토리의 데이터에는 이름과 inode 번호의 연결이 들어 있습니다.

절대 경로의 탐색

절대 경로는 루트부터 해석합니다. /usr/bart/git/gui.py라면 /에서 usr, bart, git을 차례로 검색하고, 마지막 이름 gui.py에 연결된 파일을 찾습니다. 각 디렉토리의 이름 엔트리에서 다음 inode를 찾아 가는 과정이므로, 전체 경로 문자열이 파일 inode의 "이름 필드"에 저장되어 있다고 생각하면 안 됩니다.

현재 작업 디렉토리를 바꾸어도 절대 경로의 시작점은 프로세스가 보는 루트 디렉토리입니다. 여기서의 설명은 마운트나 심볼릭 링크 같은 세부 동작을 생략한 것입니다.

상대 경로와 현재 디렉토리

상대 경로는 현재 작업 디렉토리를 기준으로 해석합니다. 현재 디렉토리가 /usr/bart일 때 다음 호출은 /usr/bart/prog.c를 찾습니다.

open("prog.c", O_RDONLY)

같은 prog.c라는 문자열도 현재 디렉토리가 바뀌면 다른 파일을 가리킬 수 있습니다. 현재 디렉토리가 /usr/bart/git이라면 그 디렉토리에서 prog.c를 새로 검색합니다. 이것은 일반 open의 상대 경로에 대한 설명이며, openat 계열은 지정한 디렉토리 FD를 기준으로 삼을 수 있습니다.

디렉토리·inode·데이터 블록

open("/a/b/c.c", O_RDONLY)와 그 뒤의 read가 이름 검색과 내용 읽기를 어떻게 연결하는지 순서대로 따라가 보면 다음과 같습니다.

  1. 루트 디렉토리의 inode를 읽습니다.
  2. 루트 디렉토리의 데이터에서 a를 검색합니다.
  3. a의 inode를 읽습니다.
  4. a의 데이터에서 b를 검색합니다.
  5. b의 inode를 읽습니다.
  6. b의 데이터에서 c.c를 검색합니다.
  7. 일반 파일 c.c의 inode를 읽습니다.
  8. 그 inode가 가리키는 실제 파일 데이터를 읽습니다.

여기서 강조할 차이는 디렉토리 데이터는 이름과 inode의 연결을 담고, 일반 파일 데이터는 내용 바이트를 담는다는 점입니다. 위의 번호는 각 디렉토리가 한 블록에 들어가고 필요한 정보가 캐시되어 있지 않다고 가정한 설명용 읽기 순서입니다. 실제 Linux가 항상 여덟 번의 물리 디스크 입출력을 한다는 뜻은 아니며, 실제 횟수는 캐시와 파일시스템 등에 따라 달라집니다. 이렇게 찾아낸 inode의 속성을 읽는 것이 바로 다음에 다룰 stat입니다.

1부 파일 속성 조회

속성 조회에서는 어떤 객체를 조회하는지와 반환값을 먼저 확인합니다. 넘긴 것이 이름인지 FD인지, 심볼릭 링크를 따라가는지를 확인하고, 반환값을 검사한 뒤에야 구조체 필드를 읽습니다.

ls -l의 각 열과 파일 속성

ls -l의 한 줄은 여러 파일 속성을 모아서 보여 줍니다.

$ ls -l note.txt
-rw-r----- 2 student lab 4 Sep 22 09:00 note.txt

# -           파일 종류
# rw-r-----   기본 접근 권한
# 2           하드 링크 수
# student lab 소유자와 그룹
# 4           일반 파일의 바이트 크기
# Sep 22 ...  기본 표시: 수정 시각
  • 권한과 종류: 첫 문자(종류)와 그다음 9개 문자(권한)를 나누어 읽습니다.
  • 소유권: 실제로 저장된 것은 UID와 GID라는 숫자이며, ls가 이를 이름으로 변환해 표시할 수 있습니다.
  • 이름: note.txt는 디렉토리 엔트리의 이름입니다. 화면에 함께 보인다고 해서 inode 안에 저장된 필드로 혼동하면 안 됩니다.

위 화면은 설명용 예시이며 계정 이름과 시각은 환경에 따라 달라집니다. ls -n은 숫자 ID를 표시하고, ls -ld는 디렉토리 안의 목록이 아니라 디렉토리 자체의 속성을 보여 줍니다. 크기 열은 일반 파일을 기준으로 설명한 것입니다. 디렉토리의 크기가 4096으로 보인다고 해서 파일이 4096개 들어 있다는 뜻은 아닙니다. 디렉토리 크기를 내부 파일 개수로 해석할 수 없습니다.

stat, lstat, fstat의 조회 대상

세 함수는 모두 <sys/stat.h>에 선언되어 있고 결과를 struct stat에 저장합니다. 차이는 무엇을 조회하느냐에 있습니다.

함수조회 대상
stat(path, &st)경로가 가리키는 파일을 조회합니다. 마지막 요소가 심볼릭 링크여도 따라갑니다.
lstat(path, &st)마지막 경로 요소가 심볼릭 링크이면 링크 자체를 조회합니다.
fstat(fd, &st)이름 대신, 이미 열린 파일 디스크립터가 참조하는 파일을 조회합니다.

세 함수 모두 성공하면 0, 실패하면 -1을 반환하며, 실패했을 때는 errno를 확인합니다. lstat이 경로의 모든 링크를 무시하는 것은 아닙니다. 링크 자체를 조회하는 것은 마지막 요소에 한해서이고, lstat("dir-link/file")처럼 경로 중간에 있는 심볼릭 링크는 여전히 해석합니다. 또한 속성 조회에서는 파일 내용의 읽기 권한과, 경로에 있는 디렉토리의 검색 권한을 구분해야 합니다.

struct stat의 주요 필드

필드 이름을 그대로 외우기보다 역할별로 묶어 보는 것이 좋습니다.

필드의미
st_dev / st_ino파일시스템 장치 식별과 inode 번호 — 파일을 식별합니다.
st_mode / st_nlink종류·권한 비트와 하드 링크 수
st_uid / st_gid소유 사용자와 그룹의 숫자 ID
st_size / st_blocks / st_blksize크기와 할당·입출력 정보
st_atim / st_mtim / st_ctim접근·내용 수정·상태 변경 시각

inode 번호는 파일시스템마다 겹칠 수 있으므로 st_ino만으로는 서로 다른 파일시스템의 파일을 비교할 수 없고, st_dev를 함께 비교해야 합니다. st_dev는 그 파일이 들어 있는 파일시스템의 장치를 뜻하며, 장치 파일 자체가 나타내는 장치인 st_rdev와는 다릅니다. 시각 필드는 Linux의 POSIX 필드명을 사용했고, st_atime 같은 이름은 그 초 부분에 접근하는 호환 이름으로 볼 수 있습니다. 마지막으로, 모든 필드가 하나의 원자적인 시점을 찍은 스냅샷이라는 보장은 없습니다.

file_attr: 조회 후 필드 출력

예제 file_attr는 경로 하나를 조회해 필드를 출력하는 프로그램입니다.

  • 기본 동작: 기본적으로 lstat을 호출합니다.
  • --follow 옵션: 옵션을 주면 stat으로 바꾸어 대상 파일을 따라갑니다. --follow는 이 예제에서 정의한 옵션입니다.
  • 출력 자료형: st_ino나 st_size 같은 정수형을 printf에 맞추기 위해 uintmax_t와 intmax_t로 명시적으로 변환해 %ju와 %jd로 출력합니다.
struct stat st;
int rc = follow ? stat(path, &st)
                : lstat(path, &st);
if (rc == -1) {
    perror(path);
    return 1;
}
printf("inode=%ju links=%ju\n",
       (uintmax_t)st.st_ino,
       (uintmax_t)st.st_nlink);
printf("size=%jd\n", (intmax_t)st.st_size);

조회에 실패하면 구조체를 출력하지 않고 바로 오류로 끝난다는 점을 확인합니다. 실패한 호출 뒤의 st에 들어 있는 값은 이번 조회의 결과가 아니므로 읽어서는 안 됩니다. 완성된 소스는 여기에 더해 인자 검사, 종류·권한 해석, 나노초 단위 시각 출력도 포함합니다.

파일 종류와 권한 비트 분리

st_mode에는 권한뿐 아니라 파일 종류도 함께 들어 있습니다. 그래서 두 정보를 분리해서 읽어야 합니다.

  • 파일 종류: S_ISREG, S_ISDIR 등의 판정 매크로를 사용합니다.
  • 기본 rwx: 0777 마스크로 소유자·그룹·기타 권한을 추출합니다.
  • 특수 비트 포함: 07777은 set-ID와 sticky 비트까지 포함합니다.
if (S_ISREG(st.st_mode)) puts("regular");
else if (S_ISDIR(st.st_mode)) puts("directory");
else if (S_ISLNK(st.st_mode)) puts("symlink");
else if (S_ISFIFO(st.st_mode)) puts("fifo");

printf("permissions=%04jo\n",
       (uintmax_t)(st.st_mode & 07777));

st_mode == 0644처럼 st_mode 전체를 권한 값과 직접 비교하면, 종류 비트가 함께 들어 있기 때문에 잘못된 판정이 됩니다. 권한을 보려면 마스크로 권한 부분만 추출하고, 종류를 보려면 S_ISREG 같은 매크로를 씁니다. 완성 예제는 문자·블록 장치와 소켓도 구별합니다.

링크와 inode의 관계

  • 하드 링크: 같은 파일시스템의 동일한 inode를 가리키는 또 다른 이름입니다. 같은 파일의 다른 이름이므로 inode와 내용을 공유하고, 하드 링크를 추가하면 그 파일의 st_nlink가 증가합니다.
  • 심볼릭 링크: 대상 경로를 저장하는 별도의 객체입니다. 링크 자체의 속성은 lstat으로 읽습니다. 심볼릭 링크를 만든다고 해서 대상 파일의 하드 링크 수가 늘어나지는 않습니다.
  • 파일 동일성: 두 이름이 같은 파일인지는 st_dev와 st_ino를 함께 비교해서 판단합니다. 이것은 "내용이 일치하는가"와는 다른 질문입니다.

inode 번호는 파일이 제거된 뒤 재사용될 수 있으므로 영구적인 식별자로 저장해 두어서는 안 됩니다.

실습 1: 링크의 속성 비교

같은 임시 폴더 안에 원본, 하드 링크, 심볼릭 링크를 만들고 file_attr로 각각 조회합니다. 숫자를 따로따로 적기보다 무엇이 같고 무엇이 다른지를 표시해 봅니다.

RUN=$(mktemp -d)
printf 'ABC\n' > "$RUN/note.txt"
ln "$RUN/note.txt" "$RUN/hard.txt"
ln -s note.txt "$RUN/soft.txt"

./file_attr "$RUN/note.txt"
./file_attr "$RUN/hard.txt"
./file_attr "$RUN/soft.txt"
./file_attr --follow "$RUN/soft.txt"
ln -s missing "$RUN/broken.txt"
./file_attr --follow "$RUN/broken.txt"
  • 하드 링크: note.txt와 hard.txt의 device와 inode가 같고 links가 2인지 비교합니다.
  • 심볼릭 링크: 기본 조회(lstat)와 --follow(stat)의 종류·크기를 비교합니다. soft.txt를 기본 조회하면 크기는 저장된 경로 문자열 note.txt의 길이인 8바이트입니다. --follow로 대상을 보면 ABC와 개행으로 이루어진 내용의 크기인 4바이트가 나옵니다.
  • 깨진 링크: lstat은 가능하지만 stat은 실패할 수 있습니다. 링크 객체 자체는 여전히 있으므로 기본 조회는 되지만, 대상을 따라가려는 조회는 없는 대상을 찾으려다 실패합니다. 조회 함수가 어느 대상을 찾으려 했는지가 중요합니다.

마지막 명령이 실패한 뒤에는 기본 조회 ./file_attr "$RUN/broken.txt"도 실행해 차이를 확인합니다. 값을 먼저 예측한 뒤 실제 결과를 REPORT.md에 기록합니다. RUN 변수는 이후 실습에서도 계속 쓰므로 같은 터미널을 유지합니다. 의도적으로 실패하는 명령이 있으므로 명령은 한 줄씩 실행합니다.

조회 실패와 조회 이후의 변화

조회가 실패하는 대표적인 원인은 다음과 같습니다.

  • ENOENT / ENOTDIR: 경로가 없거나, 경로의 중간 요소가 디렉토리가 아닌 경우입니다. 예를 들어 일반 파일 이름 뒤에 /child를 붙인 경로가 후자에 해당합니다.
  • EACCES: 경로에 있는 디렉토리에서 검색 권한이 부족할 수 있습니다.

또 하나 주의할 점은 조회와 사용 사이의 시간입니다. stat이 성공한 뒤에도 이름이나 권한은 바뀔 수 있습니다. stat이 성공했다고 그 파일의 내용을 반드시 읽을 수 있는 것도 아닙니다. 내용 읽기 권한과 경로 검색 권한은 다르고, 그 사이에 상태가 바뀔 수도 있기 때문입니다. 마찬가지로 먼저 access를 호출해 보아도 그 뒤의 open 성공이 보장되지는 않습니다. 따라서 미리 조회한 결과에 의존하지 말고, 실제로 하려는 호출의 반환값을 검사해야 합니다.

이미 열린 객체를 다룰 때는 fstat으로 그 FD의 속성을 조회합니다. 다만 fstat이 파일 내용이나 속성을 고정하거나 잠그는 것은 아닙니다.

2부 권한과 소유권

이제 속성을 바꾸어 봅니다. 접근 권한 비트를 읽는 법을 먼저 정리하고, 파일을 만들 때 적용되는 umask와 이미 있는 파일의 권한을 바꾸는 chmod를 구분해 결과를 비교합니다.

기본 권한과 8진수 표현

권한은 소유자(u), 그룹(g), 기타 사용자(o)의 세 범주에 각각 rwx를 부여합니다. r = 4, w = 2, x = 1을 더해 범주마다 8진수 한 자리로 표현합니다.

0640 = rw-r-----     0755 = rwxr-xr-x

C 코드에서 0640은 앞의 0 때문에 8진수 상수이고, 모양이 비슷한 640은 전혀 다른 값인 10진수 상수입니다. 그리고 앞에서 본 것처럼 파일 종류와 기본 권한은 st_mode에서 분리해 해석합니다.

권한 판정은 해당하는 범주 하나를 적용합니다. 프로세스가 파일 소유자와 일치하면 소유자 권한 비트를 적용하며, 소유자 권한이 없다고 해서 더 허용적인 기타 사용자 권한으로 다시 시도하지 않습니다. 실제 접근 판단에는 보조 그룹, ACL, capability 등도 영향을 줍니다.

권한 비트로 rwx 문자열 만들기

아홉 개의 권한 비트를 하나씩 검사하면 ls -l에서 보던 권한 문자열을 직접 만들 수 있습니다.

  • 비트 검사: 각 비트와 AND 연산을 해서 권한이 있는지 확인합니다.
  • 문자 선택: 켜진 비트는 r, w, x로, 꺼진 비트는 -로 표시합니다.
  • 문자열 끝: 9개의 권한 문자 뒤에 널 문자가 들어갈 공간을 둡니다. 출력 문자가 9개인데 배열이 10칸인 이유입니다.
const mode_t bits[9] = {
    S_IRUSR, S_IWUSR, S_IXUSR,
    S_IRGRP, S_IWGRP, S_IXGRP,
    S_IROTH, S_IWOTH, S_IXOTH
};
char out[10];
for (int i = 0; i < 9; i++)
    out[i] = (mode & bits[i]) ? "rwx"[i % 3] : '-';
out[9] = '\0';

위 코드는 기본 rwx 부분만 발췌한 것입니다. 완성된 file_attr는 set-user-ID·set-group-ID·sticky 비트를 실행 문자 자리에 s/S/t/T로 표시하는 처리도 합니다. 예를 들어 set-user-ID가 켜져 있을 때 실행 비트가 없으면 S, 있으면 s입니다.

일반 파일과 디렉토리의 권한

같은 rwx라도 일반 파일과 디렉토리에서 의미가 다릅니다.

  • 일반 파일의 r / w / x: 내용 읽기, 내용 쓰기, 프로그램 실행을 허용합니다.
  • 디렉토리의 r / x: r은 이름 목록을 읽는 권한이고, x는 파일 실행이 아니라 알고 있는 이름을 검색하고 경로를 통과하는 권한입니다.
  • 디렉토리의 w와 x: 디렉토리 안에 이름을 만들거나 지우는 것은 디렉토리를 변경하는 일이므로, 일반적으로 두 권한이 함께 필요합니다.

파일 내용 쓰기와 파일 이름 삭제는 서로 다른 동작입니다. 그래서 파일에 w 권한이 없다고 그 이름을 절대로 지울 수 없는 것은 아닙니다. 이름 삭제는 부모 디렉토리의 권한에 따라 결정되며, 읽기 전용 파일도 부모 디렉토리 권한에 따라 이름을 지울 수 있습니다. 여기에 sticky bit, ACL, capability, 읽기 전용 파일시스템 같은 추가 조건이 있을 수 있습니다. 실습은 root가 아닌 일반 사용자로, 자신이 만든 임시 디렉토리에서 진행합니다.

chmod와 fchmod

chmod는 경로를, fchmod는 열린 FD를 대상으로 권한을 설정합니다.

/* 경로가 가리키는 파일의 권한 변경 */
if (chmod(path, 0640) == -1) {
    perror("chmod");
    return 1;
}

/* 이미 열린 파일의 권한 변경 */
if (fchmod(fd, 0600) == -1) {
    perror("fchmod");
    return 1;
}
  • 지정한 mode: 넘긴 값 그대로 권한을 설정합니다. 기존 비트에 자동으로 추가하는 호출이 아닙니다.
  • 변경 주체: 일반적으로 파일 소유자나 적절한 권한이 있는 프로세스만 바꿀 수 있습니다.
  • 변경 결과: 파일 내용은 그대로여도 inode 상태가 바뀌므로 ctime이 갱신될 수 있습니다.

두 함수 모두 성공하면 0, 실패하면 -1을 반환합니다. chmod는 마지막 심볼릭 링크를 따라가 대상의 권한을 바꿉니다. Linux에서 일반 심볼릭 링크의 권한은 링크 자체의 접근 제어로 해석하지 않습니다. 그리고 umask는 파일을 만들 때만 적용되므로, chmod에 0640을 넘길 때 umask가 그 값에 다시 적용되지는 않습니다.

umask와 생성 권한

umask는 파일을 새로 만들 때 요청한 권한에서 특정 비트를 제거하는 값입니다.

  • 생성 시 적용: 요청한 mode에서 mask에 해당하는 비트를 제거합니다.
  • 비트 연산: 결과는 mode & ~umask이며 단순한 뺄셈이 아닙니다.
  • 적용 범위: 이미 존재하는 파일의 권한은 바꾸지 않습니다. umask를 바꾸어도 앞에서 만든 note.txt의 권한은 그대로입니다.
/* 기본 ACL이 없는 디렉토리의 예 */
requested = 0666;
mask      = 0022;
result    = 0644;   /* 0666 & ~0022 */

requested = 0666;
mask      = 0077;
result    = 0600;   /* 0666 & ~0077 */

/* umask는 없는 권한 비트를 추가하지 않는다. */

위 블록은 계산을 설명하기 위한 것이며 완성된 C 프로그램이 아닙니다. 뺄셈처럼 보일 때가 있어도 실제로는 비트 마스크 연산이라서, 단순히 빼는 계산은 항상 맞지 않습니다. 예를 들어 요청이 0600이고 mask가 0002인 경우를 뺄셈으로 계산하면 틀린 답이 나옵니다. 요청에 원래 없던 비트는 제거할 것도 없고, umask가 요청에 없는 실행 권한 같은 비트를 더해 주지도 않습니다.

또한 Linux에서 부모 디렉토리에 기본 ACL이 있으면 생성 권한을 정할 때 그 ACL이 사용되므로 이 단순한 공식을 그대로 적용할 수 없습니다. 이번 실습은 기본 ACL이 없는 환경을 가정합니다.

생성 후 fstat으로 권한 확인

예제 mode_demo는 umask를 임시로 바꾸어 파일을 만든 다음, 실제로 어떤 권한으로 만들어졌는지 fstat으로 확인합니다.

mode_t old = umask(0077);
int fd = open(path, O_WRONLY | O_CREAT | O_EXCL,
              0666);
int saved = errno;
umask(old);
if (fd == -1) {
    errno = saved;
    perror("open"); return 1;
}
struct stat st;
if (fstat(fd, &st) == -1) {
    perror("fstat"); close(fd); return 1;
}
close(fd);
  • 원래 mask 보관: umask 함수는 이전 mask를 반환하므로 old에 받아 둡니다.
  • 생성 실패도 처리: O_EXCL 때문에 이미 있는 이름이면 실패하며, 기존 파일을 덮어쓰지 않습니다.
  • 원상 복구: open이 성공하든 실패하든 프로세스의 mask를 복원합니다. 이때 open 실패의 errno는 복원하기 전에 saved에 보관해 두었다가, 오류를 출력하기 전에 되돌려 놓습니다.

이 코드는 발췌이며, 완성된 mode_demo는 close 실패도 검사합니다. umask는 프로세스 범위의 값이므로 다중 스레드 프로그램에서는 임시로 바꾸는 것에도 주의가 필요합니다. 반대로, 이 프로그램은 셸의 자식 프로세스로 실행되므로 여기서 umask를 바꾸어도 부모 셸의 mask는 바뀌지 않습니다.

소유 사용자와 그룹 변경

  • st_uid와 st_gid: 파일의 소유 사용자와 그룹을 숫자 ID로 저장합니다.
  • chown(path, uid, gid): 지정한 소유권을 변경합니다. 인자가 -1이면 UID나 GID를 -1로 바꾸라는 뜻이 아니라 해당 값을 기존대로 유지하라는 특별한 표시입니다. 예를 들어 chown(path, (uid_t)-1, gid)는 소유 사용자는 그대로 두고 그룹만 바꿉니다.
  • 일반 사용자의 제한: 소유 사용자를 바꾸는 데는 보통 특권이 필요하고, 그룹 변경도 제한됩니다. 일반 사용자가 임의의 사용자에게 파일 소유권을 넘길 수 있다고 가정하면 안 됩니다.

소유권 변경도 성공하면 0, 실패하면 -1을 반환합니다. Linux에서 파일 소유자는 자신이 속한 그룹으로는 파일의 그룹을 바꿀 수 있습니다. chown은 심볼릭 링크의 대상을, lchown은 링크 자체를 변경합니다. 소유권을 변경하면 set-ID 비트가 지워질 수 있다는 점도 알아 둡니다. 이번 수업에서는 소유권을 조회하고 권한 조건을 이해하는 데 집중하며, 임의 계정으로의 변경은 요구하지 않습니다.

실습 2: 생성 권한과 chmod

mkdir "$RUN/modes"
./mode_demo "$RUN/modes"
./file_attr "$RUN/modes/mask022.txt"
./file_attr "$RUN/modes/mask077.txt"
./file_attr "$RUN/modes/groupdir"

chmod 600 "$RUN/note.txt"
./file_attr "$RUN/note.txt"
./file_attr "$RUN/hard.txt"
  • 예상 권한: 요청 0666과 mask 022는 0644, mask 077은 0600입니다. 디렉토리 groupdir는 0777 요청과 mask 0027로 0750이 예상됩니다.
  • 생성 후 변경: mode_demo는 첫 파일을 만든 직후의 권한을 먼저 출력하고, 이어서 fchmod로 0640으로 바꿉니다. 그래서 mode_demo의 출력에는 생성 직후의 0644와 fchmod 후의 0640이 각각 나오고, 나중에 file_attr로 mask022.txt를 조회하면 0640이어야 합니다. 이 값이 0644가 아니라고 umask 계산이 틀린 것이 아니므로, 두 출력 시점을 구분해서 기록합니다.
  • 하드 링크: note.txt라는 이름으로 권한을 바꾸면 hard.txt로 조회해도 같은 변경이 보입니다. 권한은 이름이 아니라 두 이름이 공유하는 파일의 속성이기 때문입니다.

mode_demo를 같은 디렉토리에 두 번째로 실행하면 기존 이름 때문에 실패하는데, 이것이 정상입니다.

3부 파일 크기와 시간 속성

파일의 "크기"에도 서로 다른 값이 있습니다. 프로그램이 보는 논리적 크기와 파일시스템이 실제로 할당한 공간을 구분하고, 시간 역시 하나의 날짜로 묶지 않고 세 종류로 나누어 봅니다.

st_size, st_blocks, st_blksize

필드의미
st_size일반 파일의 논리적 크기입니다. 단위는 바이트입니다.
st_blocksLinux에서는 파일에 할당된 공간을 512바이트 단위로 나타냅니다.
st_blksize효율적인 파일 입출력을 위한 권장 블록 크기입니다.

이름이 비슷하지만 st_blksize는 st_blocks의 단위가 아니므로 둘을 곱하면 안 됩니다. 예를 들어 st_blocks가 8이고 st_blksize가 4096이라면 할당량은 8×4096이 아니라 8×512바이트입니다. 그리고 st_blocks × 512와 st_size는 서로 다른 질문에 답하는 값입니다. 앞의 것은 "얼마나 할당되었는가", 뒤의 것은 "논리적으로 얼마나 긴가"입니다. 압축, 희소 파일, 파일시스템 정책 등에 따라 할당량은 달라집니다. 디렉토리의 크기 역시 내부 파일 크기의 합이나 파일 개수가 아닙니다.

실습 3: 희소 파일의 크기

예제 sparse_demo는 새 파일의 1 MiB 위치로 이동한 뒤 한 바이트만 써서, 논리적 크기와 할당 공간이 다를 수 있음을 보여 줍니다.

./sparse_demo "$RUN/sparse.bin"
./file_attr "$RUN/sparse.bin"

# Ubuntu GNU coreutils 명령
stat -c 'size=%s blocks=%b unit=%B' \
  "$RUN/sparse.bin"
du -B1 "$RUN/sparse.bin"

# 코드 핵심: 1 MiB 위치에서 한 바이트 쓰기
# lseek(fd, 1024 * 1024, SEEK_SET);
# write(fd, "X", 1);
  • 논리적 크기: 1,048,576 위치에 한 바이트를 썼으므로 크기는 1 MiB가 아니라 1,048,577바이트가 됩니다.
  • 비어 있는 구간: 기록하지 않은 앞부분을 읽으면 0 값의 바이트가 나옵니다.
  • 할당 공간: 논리적 크기와 할당량을 실제 파일시스템에서 비교합니다. 파일시스템이 희소 파일을 지원하면 실제 할당 공간은 논리적 길이보다 작을 수 있습니다.

lseek는 위치만 옮길 뿐이므로 그것만으로는 파일 크기가 늘지 않습니다. 그 뒤에 실제로 쓰기를 해야 크기가 늘어납니다. 실습 파일은 O_EXCL로 새로 만들기 때문에 기존 파일을 덮어쓰지 않습니다. 완성된 sparse_demo는 open, lseek, write, fstat, close의 반환값을 모두 검사합니다. 할당량은 파일시스템에 따라 달라지므로, 특정 숫자가 나와야 하거나 반드시 작은 값이어야 한다고 보지 않습니다. 중요한 것은 단위와 두 크기의 의미를 정확히 설명하는 것입니다.

atime, mtime, ctime

시각의미
atime (접근 시각)파일 데이터 접근과 관련됩니다. 마운트 정책에 따라 갱신을 줄일 수 있습니다.
mtime (내용 수정 시각)파일 데이터 쓰기 등 내용 변경과 관련됩니다.
ctime (상태 변경 시각)권한·소유권·링크 수 등 inode 상태 변경과 관련됩니다.

가장 흔한 오해는 ctime의 c를 creation으로 외우는 것입니다. ctime은 생성 시각이 아닙니다. chmod만 했는데 ctime이 바뀌었다면 새로 만들어진 파일이 아니라 같은 파일의 상태가 변경된 것입니다. 내용 쓰기는 일반적으로 mtime과 ctime 모두에 영향을 줍니다. atime은 noatime·relatime 같은 조건 때문에 읽을 때마다 증가한다고 가정할 수 없습니다. 파일시스템마다 시각을 저장하는 해상도도 다릅니다.

작업과 시간 속성의 변화

작업시간 속성의 변화
파일 읽기atime 갱신 여부는 마운트 정책 등의 영향을 받습니다.
파일 내용 쓰기일반적으로 mtime과 ctime을 갱신합니다.
chmod내용은 그대로여도 ctime을 갱신합니다. mtime은 유지됩니다.
utimensat / futimensatime과 mtime을 지정할 수 있습니다.

ctime은 이 API로 임의의 과거 시각을 직접 지정하지 않습니다. 또한 짧은 간격으로 일어난 두 작업은 시각 해상도 때문에 같은 숫자로 보일 수 있습니다. 표시된 값이 같다고 해서 작업이 일어나지 않았다고 판단하면 안 되며, 작업의 성공 여부는 반환값과 실제 권한으로 확인합니다. 이번 실습은 과거의 고정된 atime·mtime을 지정한 뒤 권한을 바꾸어 세 시각의 의미를 구분합니다.

futimens로 atime과 mtime 지정

struct timespec ts[2] = {
    {1704067200, 0},  /* atime: UTC 2024-01-01 */
    {1704153600, 0}   /* mtime: UTC 2024-01-02 */
};
if (futimens(fd, ts) == -1) {
    perror("futimens");
    return 1;
}

/* ts[0]: atime, ts[1]: mtime */
/* tv_nsec: UTIME_NOW / UTIME_OMIT도 가능 */
  • FD 또는 경로: futimens는 FD를, utimensat은 경로를 기준으로 합니다. 헤더는 <sys/stat.h>입니다.
  • 배열의 순서: timespec 배열의 첫 항목이 atime, 두 번째가 mtime입니다. ctime은 세 번째 항목으로 넣을 수 있는 값이 아닙니다.
  • 특수 지정: tv_nsec에 UTIME_NOW를 넣으면 현재 시각, UTIME_OMIT을 넣으면 기존 값 유지입니다. 예를 들어 atime은 그대로 두고 mtime만 바꾸려면 atime 항목의 tv_nsec에 UTIME_OMIT을 씁니다.
  • 권한 조건: 임의의 시각을 지정하는 것은 보통 파일 소유자나 특권이 필요합니다. 두 값을 지금 시각으로 갱신하는 경우와 임의 값을 지정하는 경우의 권한 조건은 서로 다릅니다.

실습은 자신이 새로 만든 파일에 수행합니다. utimensat에 AT_SYMLINK_NOFOLLOW를 주면 마지막 링크 자체를 대상으로 삼을 수 있습니다. 완성 예제는 time_attrs입니다.

실습 4: 시간 속성의 의미

./time_attrs "$RUN/times.txt"
./file_attr "$RUN/times.txt"

# Ubuntu에서 이름과 시간을 함께 확인
stat -c 'atime=%X mtime=%Y ctime=%Z' \
  "$RUN/times.txt"

# 프로그램의 두 출력 단계
# after_futimens: atime과 mtime을 과거로 설정
# after_fchmod:   권한만 0640으로 변경

time_attrs는 두 단계로 출력합니다. 첫 단계에서 atime과 mtime을 고정하고, 두 번째 단계에서는 권한만 바꿉니다.

  • 고정한 시각: atime은 1704067200, mtime은 1704153600입니다.
  • 권한 변경 후: fchmod 뒤에도 atime과 mtime이 그대로 유지되는지 확인합니다.
  • ctime 해석: ctime은 지금 일어난 상태 변경을 반영합니다. 과거의 파일 생성 시각으로 해석하지 않습니다.

연속된 두 출력의 ctime이 같은 숫자여도 틀린 결과가 아닙니다. 또한 time_attrs는 파일 내용을 읽지 않고 futimens와 fchmod 뒤에 fstat만 수행하므로, 그 때문에 atime이 갱신되리라고 기대하지 않습니다. 이 실습의 핵심은 각 시각의 의미와, 변하지 않아야 할 값이 무엇인지입니다.

4부 이름과 열린 파일의 속성

마지막 주제는 이름과 열린 파일의 관계입니다. "이름이 사라졌다"는 사실과 "열린 객체를 더는 사용할 수 없다"는 사실은 같지 않습니다. 이름을 지운 뒤에도 열린 FD에서 속성을 조회해 봅니다.

unlink 이후의 fstat

  • 이름 삭제: unlink는 디렉토리에서 이름 하나를 제거합니다.
  • 열린 참조: 마지막 하드 링크가 없어져도 열린 FD가 파일에 대한 참조를 유지할 수 있습니다.
  • 관찰할 속성: unlink 전후로 같은 inode와 크기를 읽고, 하드 링크 수가 0이 된 것을 확인할 수 있습니다.

하드 링크가 하나뿐인 파일을 unlink하면 링크 수는 0이 됩니다. 그 뒤로 경로를 통한 조회는 ENOENT로 실패하지만, 이미 열려 있는 FD를 통한 fstat과 읽기는 가능합니다. st_nlink는 파일을 열어 둔 FD의 개수가 아니라 파일을 가리키는 이름, 즉 하드 링크의 수입니다. 이름의 수와 열린 참조의 수는 같은 값이 아닙니다. 파일의 공간이 최종적으로 회수되려면 열린 참조를 포함한 파일 수명 조건이 모두 해소되어야 합니다.

실습 5: 이름 삭제 후 속성 조회

./fd_unlink_demo

# 프로그램 내부의 실행 순서
# mkstemp: 전용 임시 파일 생성
# write:   "hello" 5바이트 기록
# fstat:   inode, links=1, size=5 출력
# unlink:  방금 만든 이름 제거
# fstat:   같은 inode, links=0, size=5
# read:    열린 FD로 "hello" 읽기
# close:   열린 참조 정리
  • 전용 임시 파일: fd_unlink_demo는 명령 인자를 받지 않고, mkstemp로 만든 자기 임시 파일만 대상으로 생성·삭제합니다. 다른 파일을 건드리지 않습니다.
  • 속성 비교: before와 after의 inode와 크기가 같은지, 링크 수가 1에서 0으로 바뀌는지 비교합니다.
  • 결과 설명: 이름이 없는데도 마지막 read에서 hello가 나오는 이유를, 이름의 존재와 열린 객체의 수명을 구별해서 설명합니다. 열린 FD가 같은 파일을 계속 참조하고 있기 때문에 내용을 읽을 수 있습니다.

프로그램이 출력한 임시 경로가 정상 종료 뒤에 남아 있지 않은지도 확인합니다. 이 설명은 Linux 로컬 파일시스템을 기준으로 하며, NFS 같은 특수한 환경은 별도의 해석이 필요합니다.

확인 문제

값만 답하지 말고 어떤 대상을 조회했고 어떤 비트를 보았는지 함께 설명해 봅니다.

  1. 깨진 심볼릭 링크에서 stat과 lstat은 어떻게 다른가? — stat은 없는 대상을 따라가다 실패하고, lstat은 링크 자체를 조회합니다.
  2. st_mode 전체를 0644와 직접 비교하면 왜 안 되는가? — st_mode에는 종류와 특수 비트도 포함되므로 목적에 맞는 마스크가 필요합니다.
  3. 기본 ACL이 없을 때 0666과 umask 0027의 결과는? — 0640입니다.
  4. chmod로 ctime이 바뀌면 파일 내용도 바뀐 것인가? — 아닙니다. ctime은 상태 변경 시각입니다.
  5. unlink 뒤 fstat에서 links=0이 나와도 읽을 수 있는 이유는? — 열린 FD가 참조를 유지하기 때문입니다.

정리

  • file_attr가 출력하는 필드를 종류·권한·소유권·크기·시간으로 나누어 설명할 수 있어야 합니다.
  • 링크 종류(하드 링크, 심볼릭 링크, 깨진 링크)에 따른 조회 결과와 실패하는 경로를 기록합니다.
  • umask와 chmod 전후의 권한 변화를 비교합니다. umask는 생성 시점에, chmod는 이미 있는 파일에 적용됩니다.
  • 논리적 크기와 할당 공간, mtime과 ctime을 구별합니다.
  • 제출물은 C 소스, REPORT.md, 실행 로그입니다. inode 번호나 할당 블록 수를 다른 사람과 같게 만들 필요는 없으며, 작업 전후의 관계를 설명하는 것이 중요합니다.
  • 선택 확장 과제는 이전 시간의 mini_ls에 파일 속성 열(rwx 문자열, UID/GID, 크기, mtime)을 추가하는 것입니다. 재귀 탐색 등으로 범위를 넓히지 않고 파일 속성 해석에 집중합니다.

새 API를 읽을 때는 함수 이름과 예제만 보지 말고 대상, 반환값, 자료형, 권한 조건과 실패 조건을 함께 확인합니다.
