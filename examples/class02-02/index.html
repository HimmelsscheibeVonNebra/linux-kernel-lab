while 반복 서비스와 Makefile

while(1)·printf·fflush·sleep으로 2초마다 출력하는 반복 프로그램을 실행하고, 백그라운드 실행과 kill로 프로세스를 관찰·종료한다.

실행해 볼 예제

  • helloworldwhile (1) 안에서 Hello, world!를 출력하고 fflush한 뒤 sleep(2)로 쉬는 무한 반복 프로그램이다. 스스로 끝나지 않으므로 신호로 종료한다.
  • helloworldcount를 1씩 증가시키며 2초마다 count=N을 출력하는 GDB 연습용 반복 프로그램이다. 여기서는 실행 결과와 시스템 콜만 관찰한다.

이번 수업은 1차시에 만든 Hello World를 while 반복문으로 계속 실행되는 프로그램으로 바꾸고, Makefile로 빌드한 뒤 systemd 서비스로 등록해 로그를 확인하는 흐름으로 진행합니다. 순서는 while 반복 서비스, Makefile 빌드, 서비스 실행과 로그, 코드 수정과 실습 정리, GDB 기본 디버깅입니다.

1부. while 반복 서비스

한 번 실행과 반복 실행

1차시의 프로그램은 문자열을 한 번 출력하고 곧바로 종료했습니다. 그래서 서비스로 등록할 때 Type=oneshot을 썼고, 실행을 마친 뒤의 상태는 inactive (dead)였습니다. 이번에는 같은 코드에 while문을 추가해 프로그램이 끝나지 않고 계속 실행되도록 만듭니다. 계속 실행하는 프로그램은 Type=simple로 등록하며, 정상 상태는 active (running)입니다. 즉 이번 수업에서 바뀌는 것은 세 가지입니다. 코드에 반복문이 들어가고, 서비스 설정의 유형이 바뀌고, 상태를 볼 때 "실행을 마쳤는가"가 아니라 "계속 실행 중인가"를 확인합니다. 서비스 이름과 설치 경로는 1차시와 동일합니다.

1단계: 한 번 출력하는 코드에서 출발

출발점은 1차시의 helloworld.c입니다.

#include <stdio.h>
int main(void)
{
    // 한 번 출력한 뒤 종료
    printf("Hello, world!\n");
    return 0;
}

프로그램은 main 안의 명령을 위에서 아래로 차례로 실행합니다. 이 코드가 몇 번 출력하고 언제 종료하는지를 먼저 말해 본 뒤, 완성 코드를 보기 전에 기존 코드에서 어느 부분을 바꿔야 할지 찾아봅니다.

2단계: while 조건과 반복 범위

while (1) {
    // 중괄호 안의 작업을 반복
}
// 조건이 참이면 본문 실행
// 본문 끝에서 조건을 다시 확인

while은 조건이 참이면 본문을 실행하고, 본문 끝에 도달하면 조건을 다시 확인합니다. C에서는 0이 거짓이고 0이 아닌 값은 모두 참입니다. 따라서 while (1)은 조건이 항상 참이어서 반복을 계속합니다. 반복할 명령은 중괄호 안에 넣어야 하며, 중괄호가 곧 반복 범위입니다. 위의 빈 반복문은 구조를 읽기 위한 것이므로 실행하지는 않습니다.

3단계: 출력과 대기를 반복

while (1) {
    printf("Hello, world!\n");
    fflush(stdout);
    sleep(2);
}

본문은 세 줄입니다. 문자열을 출력하고, 그 내용을 전달한 다음, 2초간 대기합니다. sleep도 반복문 안에 있어야 매 반복마다 대기합니다. sleep을 생략하거나 반복문 밖에 두면 어떻게 되는지 스스로 설명해 보십시오. printf와 fflush는 stdio.h, sleep은 unistd.h가 필요합니다.

반복 실행 예제 전체 코드

완성된 helloworld의 소스는 다음과 같으며, 파일 이름은 그대로 helloworld.c입니다.

#include <stdio.h>
#include <unistd.h>
int main(void)
{
    while (1) {                 // 계속 반복
        printf("Hello, world!\n");
        fflush(stdout);         // 바로 출력
        sleep(2);               // 2초 대기
    }
}

while (1)의 조건이 항상 참이므로 계속 반복하고, sleep(2)가 반복 사이에 2초간 대기합니다. 프로그램이 스스로 끝나지 않으므로, 직접 실행한 프로그램은 Ctrl+C로 끝냅니다.

작업 폴더와 소스 확인

pwd
ls -l
cat helloworld.c
# 수정이 필요할 때
vim helloworld.c

작업은 Codes/class02-02 폴더에서 합니다. pwd로 현재 위치를 확인하고, ls -l로 helloworld.c와 Makefile이 있는지 봅니다. 현재 폴더가 다르면 같은 명령을 입력해도 다른 파일을 대상으로 실행되므로, 위치 확인이 먼저입니다. 수정이 필요하면 Vim에서 i로 입력 모드에 들어가 고치고, Esc를 누른 뒤 :wq로 저장하고 종료합니다.

직접 컴파일과 실행

gcc -std=c17 -Wall -Wextra -g \
    helloworld.c -o helloworld
./helloworld
# 2초마다 출력 확인
# Ctrl+C로 실행 종료

컴파일하면 실행 파일 helloworld가 만들어집니다. 실행하면 같은 문자열을 2초마다 출력하고, Ctrl+C를 누르면 별도 종료 메시지 없이 실행이 끝납니다. Docker 환경에서도 여기부터 Makefile 실습까지는 진행할 수 있습니다.

서비스로 등록하기 전에 이렇게 직접 실행해서 출력과 대기를 먼저 확인합니다. 관찰할 항목은 네 가지입니다.

  • 첫 출력이 나오는 시점: 첫 출력은 sleep보다 먼저 실행되므로 시작하자마자 나옵니다.
  • 다음 출력까지의 간격: 대기는 2초지만 실제 출력 간격은 조금 더 길 수 있습니다.
  • 프로그램이 스스로 끝나는지 여부.
  • Ctrl+C 이후 셸 프롬프트가 돌아오는지: 직접 실행한 프로그램은 Ctrl+C로 끝냅니다.

출력과 대기: 세 함수의 역할

while (1) {
    printf("Hello, world!\n");
    fflush(stdout);   // 출력 내용 전달
    sleep(2);         // 2초 대기
}

printf는 문자열과 줄바꿈을 출력합니다. fflush는 출력 내용을 바로 전달해, 서비스로 실행했을 때 로그에서도 곧바로 확인할 수 있게 합니다. sleep은 프로그램이 대기 없이 반복하면서 CPU를 계속 쓰는 것을 막습니다. 출력 간격을 5초로 바꾸려면 어느 줄을 수정해야 하는지 생각해 보십시오(4부에서 실제로 바꿉니다).

무한 루프를 백그라운드에서 실행

./helloworld > loop.log 2>&1 &
loop_pid=$!
printf "PID=%s\n" "$loop_pid"
ps -o pid,ppid,user,stat,args -p "$loop_pid"
tail -n 5 loop.log

명령 끝의 &는 프로그램을 백그라운드로 실행하고, $!는 방금 실행한 작업의 PID입니다. 이 값을 loop_pid 변수에 담아 두면 이후 명령에서 같은 프로세스를 정확히 가리킬 수 있습니다. > loop.log 2>&1은 표준 출력과 표준 오류를 모두 loop.log에 기록합니다. ps 출력에서는 그 PID가 정말 내가 실행한 helloworld인지 확인하고, tail로 로그 파일의 마지막 다섯 줄을 봅니다. 이 실습은 일반 사용자로 class02-02 폴더에서 실행하며, 변수를 계속 쓰기 위해 이후에도 같은 Bash를 사용합니다.

kill로 반복 실행 종료

kill "$loop_pid"
wait "$loop_pid"
ps -p "$loop_pid"
# 종료되었다면 해당 PID 행이 없음

kill은 기본적으로 종료 요청(SIGTERM)을 보냅니다. 현재 예제에는 별도의 신호 처리 코드가 없으므로 이 요청을 받으면 그대로 종료됩니다. wait로 종료를 기다리고, ps에서 해당 PID 행이 사라졌는지 확인합니다. 이때 wait와 마지막 ps의 종료값은 0이 아닐 수 있습니다. 이번 수업에서는 신호 처리 함수를 작성하지 않습니다.

다른 터미널에서 실행한 프로그램 종료

ps -u "$USER" -o pid,ppid,stat,args
# 본인이 실행한 helloworld의 PID 확인
# 예: PID가 12345인 경우에만
kill 12345
ps -p 12345

다른 터미널에는 loop_pid 변수가 전달되지 않습니다. 그래서 그 터미널에서는 프로세스 목록에서 명령과 소유자를 확인한 뒤 실제 PID를 직접 써야 합니다. 12345는 예시일 뿐입니다. No such process라는 오류는 프로세스가 이미 종료되었거나 PID가 틀린 경우일 수 있습니다. 다른 사람이 실행한 프로세스나 systemd가 관리하는 프로세스는 이 방법으로 종료하지 않습니다.

kill과 강제 종료의 구분

kill PID
# 먼저 일반 종료 요청
kill -KILL PID
# 같은 의미: kill -9 PID
# 응답하지 않는 프로세스에만 사용

순서가 중요합니다. 먼저 일반 kill로 종료를 요청하고 상태를 확인합니다. SIGKILL은 프로그램이 종료 전에 정리 작업을 수행할 수 없게 하므로, 응답하지 않는 프로세스에만 사용합니다. 현재 while 예제는 일반 kill로 종료되므로 강제 종료는 명령의 의미만 알아 둡니다. 그리고 서비스로 등록한 프로그램은 kill이 아니라 systemctl stop helloworld.service로 중지합니다.

2부. Makefile 빌드

이 부에서는 GCC 옵션의 의미를 정리하고, Makefile을 작성해 재빌드 조건을 확인합니다.

GCC 옵션과 출력 파일

gcc -std=c17 -Wall -Wextra -g \
    helloworld.c -o helloworld
./helloworld

-std=c17은 C17 문법 기준으로 컴파일하라는 뜻이고, -Wall -Wextra는 여러 종류의 경고를 표시합니다. -g는 디버깅 정보를 넣고, -o는 출력 파일 이름을 정합니다. helloworld.c는 소스이고 helloworld는 그것을 컴파일한 실행 파일이라는 점을 구분합니다.

표준과 경고 옵션

-std=c17
# C17 문법 기준
-Wall -Wextra
# 여러 경고 그룹 활성화
-Wpedantic
# 선택한 표준 관련 진단 추가

-std로 사용할 C 언어 표준을 지정합니다. -Wall은 이름과 달리 "모든 경고"라는 뜻이 아니며, -Wextra로 더 보강합니다. -Wpedantic은 선택한 표준과 관련된 진단을 추가합니다. 이 수업에서는 -std=c17 -Wall -Wextra를 기본으로 사용합니다. 다만 경고 없이 빌드되었다고 해서 프로그램의 모든 오류가 사라진 것은 아닙니다.

경고와 오류 비교

// 별도 파일 warning.c
int main(void)
{
    int unused = 1;
    return 0;
}
gcc -Wall warning.c -o warning
gcc -Wall -Werror warning.c -o warning

첫 번째 명령에서는 사용하지 않는 지역 변수에 대한 경고를 확인합니다. 두 번째 명령의 -Werror는 경고를 오류로 취급하여 빌드를 실패하게 합니다. 빌드가 실패한 뒤에도 이전에 만든 실행 파일이 남아 있을 수 있으므로, 파일이 있다는 것만으로 이번 빌드가 성공했다고 판단하면 안 됩니다. 이 비교는 실습 소스와 별도의 파일에서 하며, -Werror는 이번 비교에만 사용합니다.

디버깅과 최적화 옵션

-g
# 디버거용 정보 포함
-O0 : 최적화 끔
-Og : 디버깅을 고려한 최적화
-O2 : 실행 성능을 위한 최적화
# 개발용 조합 예시
-g -Og

-g는 실행 파일에 디버깅 정보를 넣는 옵션이지, 디버거를 실행하는 옵션이 아닙니다. 최적화 옵션을 주면 컴파일러가 실행 코드를 바꾸며, 그 결과와 효과는 프로그램마다 다릅니다. 이번 예제는 실행 시간의 대부분이 sleep 대기이므로 최적화 수준에 따른 속도를 비교하는 용도로는 적절하지 않습니다. 디버거 사용법은 5부에서 다루고, 여기서는 각 옵션의 목적을 구분하는 데 집중합니다.

컴파일 단계 선택

gcc -E helloworld.c -o helloworld.i
# 전처리 결과
gcc -S helloworld.c -o helloworld.s
# 어셈블리 코드
gcc -c helloworld.c -o helloworld.o
# 오브젝트 파일
gcc helloworld.o -o helloworld
# 링크하여 실행 파일 생성

-E는 전처리 결과까지만 생성하고, -S는 어셈블리 코드에서, -c는 오브젝트 파일 생성에서 멈춥니다. -o는 어느 단계에서든 그 단계의 출력 파일 이름을 정합니다. 마지막 명령은 오브젝트 파일을 링크하여 실행 파일을 만듭니다. 위 명령들은 각각 별도의 예시이며, .o 파일은 직접 실행하는 프로그램이 아닙니다.

Makefile에 옵션 반영

make clean
make CFLAGS="-std=c17 -Wall -Wextra -g -Og"
# 기본 옵션으로 복귀
make clean
make

make 명령행에 CFLAGS=...를 적으면 이번 빌드에서 사용할 컴파일 옵션을 지정할 수 있습니다. 그런데 이 수업의 Makefile은 옵션이 바뀐 것만으로는 재빌드가 필요하다고 판단하지 않습니다. 그래서 먼저 make clean으로 기존 파일을 지워, 새 옵션으로 빌드하게 만듭니다. 기본 옵션으로 돌아갈 때도 같은 이유로 다시 make clean 후 make를 실행합니다. 기본 옵션 자체를 계속 바꿔 쓰려면 Makefile 안의 CFLAGS를 수정합니다.

직접 작성하는 최소 Makefile

helloworld: helloworld.c
	gcc -std=c17 -Wall -Wextra -g \
	helloworld.c -o helloworld
# 명령 앞에는 탭 사용

Makefile의 규칙은 세 부분으로 읽습니다. 콜론 왼쪽은 타깃, 즉 만들 파일 helloworld입니다. 콜론 오른쪽은 의존 파일로, 재빌드가 필요한지 판단하는 데 사용할 소스입니다. 그 아래 줄은 실행 명령으로, 필요할 때 이 gcc 명령이 실행됩니다. 명령 앞에는 반드시 탭을 사용합니다. 이 최소 구조를 이해한 뒤, 제공된 Makefile의 변수와 작업 타깃을 읽습니다.

Makefile의 기본 구조와 변수

# 컴파일러와 빌드 옵션
CC = gcc
CFLAGS = -std=c17 -Wall -Wextra -g
TARGET = helloworld
.PHONY: all run clean
all: $(TARGET)
$(TARGET): helloworld.c
	$(CC) $(CFLAGS) $< -o $@

타깃은 만들 실행 파일일 수도 있고 수행할 작업일 수도 있습니다. $(TARGET): helloworld.c는 helloworld.c가 바뀌면 다시 빌드한다는 뜻이며, 그 아래 명령 줄의 들여쓰기는 탭입니다. 위 코드는 빌드 부분만 발췌한 것이고, 실습에서는 제공된 Makefile을 그대로 사용합니다.

변수는 반복되는 내용을 한곳에 모으기 위한 것입니다. $(이름)으로 변수에 지정한 값을 사용합니다. $<와 $@는 자동 변수로, $<는 첫 번째 의존 파일이고 $@는 현재 타깃입니다. 따라서 위 명령 줄은 최소 Makefile의 gcc 명령과 같은 내용이 됩니다. 공통 컴파일 옵션을 바꾸고 싶을 때는 CFLAGS 한 곳만 수정하면 됩니다. 제공 파일에는 추가 빌드 옵션 변수도 있지만, 먼저 이 핵심 구조를 읽습니다.

all, run, clean과 .PHONY

.PHONY: all run clean
all: helloworld
run: helloworld
	./helloworld
clean:
	rm -f helloworld

이 예제에서 make만 입력하면 all이 선택됩니다. all과 run은 둘 다 helloworld를 필요로 하므로, make run은 필요하면 먼저 빌드한 뒤 실행합니다. make clean은 로컬 실행 파일을 지웁니다. .PHONY는 all, run, clean이 파일이 아닌 작업 이름임을 표시하며, 같은 이름의 파일이 있어도 작업을 수행하도록 합니다.

제공 Makefile에서는 같은 타깃이 변수로 적혀 있습니다.

# 빌드 후 실행
run: $(TARGET)
	./$(TARGET)
# 로컬 실행 파일 정리
clean:
	rm -f $(TARGET)
# $@ : 현재 타깃
# $< : 첫 번째 의존 파일

run은 무한 반복 프로그램을 실행하므로 계속 실행됩니다. Ctrl+C로 종료한 뒤에 다음 명령을 입력합니다. 또한 clean은 작업 폴더의 실행 파일만 지울 뿐, 설치된 서비스를 제거하지 않습니다.

install 타깃과 install 명령

install: $(TARGET)
	install -d ...
	install -m 0755 ...
	install -m 0644 ...
# 실행 방법
sudo make install

여기에는 install이라는 이름이 두 가지 의미로 나옵니다. 콜론 앞의 install은 Make가 수행할 작업 이름(타깃)이고, 명령 줄의 install은 디렉토리를 만들거나 파일을 복사하면서 권한을 설정하는 리눅스 명령입니다. install 타깃은 TARGET인 helloworld에 의존하므로, 필요하면 먼저 빌드가 수행됩니다. 위 코드는 구조 설명을 위한 축약이며, 실제 실행은 제공 Makefile을 사용합니다.

설치 경로 변수

TARGET = helloworld
PREFIX = /usr/local
UNITDIR = /etc/systemd/system
# DESTDIR 기본값: 빈 문자열
$(DESTDIR)$(PREFIX)/bin/$(TARGET)
# 변수 치환 후
/usr/local/bin/helloworld
# 서비스 설정 경로
/etc/systemd/system/helloworld.service

TARGET은 만들고 설치할 실행 파일 이름입니다. PREFIX는 프로그램 설치의 기준 경로이고 UNITDIR은 서비스 설정을 두는 경로입니다. DESTDIR은 패키징을 위해 임시 설치 경로를 앞에 붙일 때 사용하며 기본값은 빈 문자열입니다. 그래서 $(DESTDIR)$(PREFIX)/bin/$(TARGET)은 기본 상태에서 /usr/local/bin/helloworld가 됩니다. 이번 서비스 실습은 기본 경로를 그대로 사용합니다. PREFIX를 바꾸면 실행 파일이 놓이는 위치가 달라지므로 서비스 설정의 ExecStart도 그에 맞춰야 합니다.

install -d: 설치 디렉토리 준비

# Makefile의 변수 표기
install -d \
    "$(DESTDIR)$(PREFIX)/bin" \
    "$(DESTDIR)$(UNITDIR)"
# 변수 치환 후
install -d \
    "/usr/local/bin" \
    "/etc/systemd/system"

-d는 필요한 디렉토리를 생성하며, 상위 경로도 함께 만듭니다. 디렉토리가 이미 있으면 새로 만들 필요 없이 그대로 사용합니다. 경로를 따옴표로 감싼 것은 경로에 공백이 있어도 하나의 인자로 전달하기 위해서입니다. $(...)는 Makefile의 변수 표기이므로, 셸에 직접 입력할 때는 실제 경로를 써야 합니다.

install -m 0755: 실행 파일 복사

# Makefile의 변수 표기
install -m 0755 $(TARGET) \
    "$(DESTDIR)$(PREFIX)/bin/$(TARGET)"
# 변수 치환 후
install -m 0755 helloworld \
    "/usr/local/bin/helloworld"
# 권한: rwxr-xr-x

현재 폴더의 helloworld를 시스템 실행 경로로 복사합니다. -m 0755는 복사한 파일의 권한을 지정합니다. 소유자는 읽기·쓰기·실행이 가능하고, 그룹과 기타 사용자는 읽기·실행이 가능합니다. cp와 chmod로 나눠 하던 복사와 권한 설정을 install 하나로 함께 수행하는 것입니다.

install -m 0644: 서비스 설정 복사

# Makefile의 변수 표기
install -m 0644 helloworld.service \
    "$(DESTDIR)$(UNITDIR)/helloworld.service"
# 변수 치환 후
install -m 0644 helloworld.service \
    "/etc/systemd/system/helloworld.service"
# 권한: rw-r--r--

이 줄은 systemd가 읽을 서비스 설정 파일을 설치합니다. -m 0644는 소유자에게 읽기·쓰기, 그룹과 기타 사용자에게 읽기만 허용합니다. 설정 파일은 실행하는 것이 아니라 읽어서 해석하는 파일이므로 실행 권한을 주지 않습니다. 실행 파일의 0755와 설정 파일의 0644가 왜 다른지 비교해 보십시오.

파일 설치와 서비스 실행의 구분

make
sudo make install
sudo systemctl daemon-reload
sudo systemctl start helloworld.service
systemctl status helloworld.service \
    --no-pager

이 다섯 줄은 서로 다른 일을 합니다. make로 빌드하고, make install로 시스템 경로에 복사합니다. daemon-reload는 변경된 서비스 설정을 systemd가 다시 읽게 하고, start가 설치한 프로그램을 실제로 실행합니다. 즉 파일을 설치했다고 서비스가 시작되는 것이 아닙니다. 기존 서비스가 실행 중이라면 설치 전에 stop합니다. 부팅 시 실행되도록 등록하는 일은 enable로 별도로 수행합니다.

Makefile 명령 미리 보기

make -n
make -n clean
# 이어서 실제 작업 실행
make

제공 Makefile에서 -n은 명령을 실행하지 않고 실행할 예정인 명령을 출력합니다. 특히 clean처럼 파일을 삭제하는 작업은 실행 전에 삭제 대상을 읽어 볼 수 있습니다. 실행 파일이 이미 최신 상태이면 make -n에 컴파일 명령이 나오지 않을 수 있는데, 이것은 재빌드 조건에 따른 정상적인 결과입니다. 이 확인은 이 수업의 단순한 Makefile을 대상으로 합니다.

Makefile 오류 메시지 읽기

missing separator
# 명령 앞 탭을 확인
No rule to make target ...
# 파일 이름과 의존 파일을 확인
make: command not found
# make 설치와 명령 경로를 확인

missing separator가 나오면 명령 앞의 탭을 확인합니다. 탭과 공백은 겉으로는 비슷해 보여도 Makefile에서는 다르게 처리됩니다. No rule to make target ...은 파일 이름과 의존 파일을 확인하라는 신호이며, 이름은 대소문자와 확장자를 포함해 정확히 적어야 합니다. make: command not found는 make가 설치되어 있는지와 명령 경로를 확인해야 하는 경우로, command -v make로 셸이 명령을 찾는지 볼 수 있습니다. 오류가 나면 문구를 기록하고 원인을 한 가지씩 수정합니다.

재빌드 조건 관찰

make clean
make
make
touch helloworld.c
make
make run

이 순서로 실행하면 Make가 언제 컴파일하는지 볼 수 있습니다. 첫 번째 make는 실행 파일이 없어서 컴파일합니다. 두 번째 make는 변경이 없으므로 컴파일하지 않습니다. touch helloworld.c로 소스의 수정 시각을 바꾼 뒤의 make는 다시 컴파일합니다. 마지막 make run은 Ctrl+C로 끝내고, 각 단계의 실행 결과를 기록합니다.

make 명령 요약

빌드와 직접 실행. 이 명령들은 Codes/class02-02의 Makefile이 있는 폴더에서 실행합니다.

make              # 기본 빌드
make all          # 기본 빌드와 동일
make run          # 빌드 후 반복 실행
make clean        # 로컬 실행 파일 삭제
make -n           # 실행 예정 명령 확인

make run으로 실행한 무한 루프는 Ctrl+C로 끝냅니다. 편집과 빌드는 관리자 권한 없이 일반 사용자로 수행합니다. make clean은 소스 코드와 설치된 서비스를 삭제하지 않습니다.

실제 예제 서비스 설치.

make
sudo make install
sudo systemctl daemon-reload
sudo systemctl start helloworld.service
# 실습 종료 후 제거
sudo systemctl disable --now helloworld.service
sudo make uninstall
sudo systemctl daemon-reload

install은 helloworld 실행 파일과 서비스 설정을 설치합니다. 실제 예제 서비스의 시작과 중지는 Makefile이 아니라 systemctl로 수행합니다. uninstall은 설치한 파일을 제거하며, 그 전에 먼저 서비스를 중지합니다. 이미 실행 중인 서비스를 교체하는 경우에는 sudo make install 전에 systemctl stop을 실행합니다.

테스트 서비스 전체 실행.

make service-test
# 위 타깃이 내부에서 실행하는 명령
sudo make -f service-test.mk test
# 테스트 순서
load / enable / start / status
stop / disable / unload

이 타깃은 고유한 이름의 테스트 서비스를 만들고 load, enable, start, status, stop, disable, unload 순서로 각 상태를 자동으로 확인합니다. 타깃 안에서 sudo를 호출하므로 비밀번호를 요구할 수 있습니다. 테스트가 끝나면 서비스를 제거하며, 오류가 났을 때에도 정리를 시도합니다. 이 테스트 서비스는 sleep을 실행하는 것으로, 실제 helloworld.service와는 별개입니다.

테스트 서비스 단계별 실행.

make load
sudo make -f service-test.mk enable
sudo make -f service-test.mk start
sudo make -f service-test.mk status
sudo make -f service-test.mk stop
sudo make -f service-test.mk disable
make unload

load는 테스트 설정을 등록하고 읽기만 하며 자동으로 시작하지는 않습니다. -f 옵션은 서비스 제어 타깃이 들어 있는 service-test.mk를 Makefile로 선택합니다. unload는 중지, 부팅 등록 해제, 설정 삭제를 수행합니다. 단계별 실습에서 서비스 이름은 week02-make-test.service이며, load는 아직 등록되지 않은 상태에서 실행합니다.

상황별 make 명령 선택

코드를 수정한 뒤 직접 실행해 보려면 다음 한 줄이면 됩니다.

make run

코드를 수정한 뒤 서비스에 반영하려면 중지, 빌드, 설치, 시작을 차례로 수행합니다.

sudo systemctl stop helloworld.service
make
sudo make install
sudo systemctl start helloworld.service

서비스 등록과 해제 과정만 확인하려면 테스트 서비스를 사용합니다.

make service-test

정리하면, 코드를 수정했을 때는 저장한 뒤 make로 다시 빌드합니다. 컴파일 옵션을 수정했을 때는 제공 Makefile에서는 make clean 후 빌드합니다. unit 파일도 바꾸었다면 start 전에 daemon-reload를 실행합니다. GDB 실습은 gdb 폴더에서 별도로 빌드하고 GitHub Pages는 웹 화면에서 게시하므로, 이 둘을 위한 전용 make 타깃은 없습니다.

3부. 서비스 실행과 로그

이 부에서는 1차시의 서비스를 반복 프로그램으로 교체하고, 시작·중지와 로그를 확인합니다.

작업 파일과 설치 파일

./helloworld.c
# 편집하는 C 소스
./helloworld
# make가 만든 실행 파일
/usr/local/bin/helloworld
# 서비스가 실행할 설치 파일
/etc/systemd/system/helloworld.service

파일이 놓이는 곳은 두 종류입니다. 작업 폴더에서는 일반 사용자로 소스를 편집하고 빌드합니다. 설치 단계에서는 실행 파일을 공통 실행 경로에 복사하고, unit 파일을 systemd가 읽는 위치에 둡니다. 서비스가 실행하는 것은 작업 폴더의 파일이 아니라 설치된 파일이므로, 작업 폴더에서 빌드만 해서는 설치된 실행 파일이 바뀌지 않습니다.

반복 서비스 설정

[Unit]
Description=Week02 Looping Hello World
[Service]
Type=simple
ExecStart=/usr/local/bin/helloworld
DynamicUser=yes
StandardOutput=journal
StandardError=journal
[Install]
WantedBy=multi-user.target

Type=simple은 계속 실행되는 프로그램을 관리하는 유형입니다. ExecStart에는 설치한 실행 파일의 절대 경로를 적습니다. StandardOutput=journal과 StandardError=journal은 표준 출력과 표준 오류를 로그(journal)로 기록하게 합니다. 실습에서는 제공된 helloworld.service를 그대로 사용합니다.

make install이 수행하는 작업

make
sudo make install
ls -l /usr/local/bin/helloworld
ls -l \
    /etc/systemd/system/helloworld.service

먼저 일반 사용자로 make를 실행해 빌드합니다. 시스템 경로에 파일을 설치하는 단계에서만 sudo를 사용합니다. 설치 후 ls -l로 보면 실행 파일은 0755, unit 파일은 0644 권한으로 설치되어 있습니다. 제공 Makefile의 install은 파일만 설치하며, 서비스 시작은 별도의 단계입니다.

서비스 교체와 시작

u=helloworld.service
sudo systemctl stop "$u"
make
sudo make install
sudo systemctl daemon-reload
sudo systemctl enable --now "$u"
systemctl status "$u" --no-pager

1차시에 등록한 서비스를 먼저 중지한 다음 교체합니다. 이어서 빌드하고, 실행 파일과 unit 설정 파일을 설치하고, daemon-reload로 설정을 다시 읽은 뒤 enable --now로 등록과 시작을 함께 수행합니다. 마지막으로 상태에서 active (running)을 확인합니다. 서비스를 처음 등록하는 경우에는 첫 stop 명령을 생략합니다. 이 실습은 Ubuntu에서 수행합니다.

서비스 제어 명령 구분

systemctl start helloworld.service
systemctl stop helloworld.service
systemctl restart helloworld.service
systemctl enable helloworld.service
systemctl daemon-reload

명령별 역할을 구분해야 합니다. start, stop, restart는 지금 실행하거나, 중지하거나, 다시 실행하는 명령입니다. enable은 지금의 실행 여부와 별개로 부팅 시 실행하도록 등록합니다. daemon-reload는 변경한 unit 설정을 다시 읽습니다. 시스템 서비스를 제어할 때는 명령 앞에 sudo를 붙입니다.

등록한 서비스 설정 확인

u=helloworld.service
systemctl cat "$u"
sudo journalctl -u "$u" \
    --since today --no-pager

systemctl cat은 unit 파일과 추가 설정의 내용을 보여 줍니다. 여기서 ExecStart가 설치한 실행 파일을 가리키는지 확인합니다. journalctl의 --since today는 오늘 기록부터 로그를 보여 줍니다. 설정 파일을 변경했다면 daemon-reload 후 서비스를 다시 시작해야 합니다.

반복 로그 확인

u=helloworld.service
sudo journalctl -u "$u" -f
# Ctrl+C로 로그 보기 종료
systemctl is-active "$u"
sudo journalctl -u "$u" \
    -n 20 --no-pager

-f는 새로 들어오는 로그를 계속 보여 주므로 2초마다 메시지가 쌓이는 것을 실시간으로 볼 수 있습니다. 여기서 Ctrl+C를 누르면 로그 보기만 끝나고 서비스는 유지됩니다. 바로 이어서 systemctl is-active로 이를 확인합니다. -n 20은 최근 로그 20개를 보여 줍니다. 직접 실행한 프로그램을 끝내는 Ctrl+C와 로그 보기를 끝내는 Ctrl+C는 같은 키지만 대상이 다르다는 점을 구분해야 합니다.

프로세스 관찰: ps, top, htop

ps -C helloworld -o pid,comm,stat,%cpu,%mem
top
# Ubuntu에서 htop 설치
sudo apt update
sudo apt install htop
htop

세 도구는 보는 방식이 다릅니다. ps는 현재 상태를 한 번 출력합니다. top은 CPU·메모리와 프로세스 목록을 주기적으로 갱신합니다. htop은 색상과 검색·정렬 기능으로 프로세스를 찾아보기 쉽게 해 줍니다. top과 htop 같은 관찰 프로그램은 q로 종료합니다. 이번 실습에서는 이 도구들의 프로세스 종료 기능을 사용하지 않습니다.

top 화면에서 읽을 항목

열의미
PID프로세스 번호
USER실행 사용자
S프로세스 상태
%CPUCPU 사용률
%MEM물리 메모리 대비 비율
RES상주 메모리
COMMAND명령 이름

화면 상단은 시스템 전체의 요약이고 하단은 프로세스별 값이므로 둘을 구분해서 읽습니다. CPU 사용률은 멀티코어 환경과 표시 방식에 따라 개별 프로세스가 100%를 넘을 수도 있습니다. 메모리는 RES와 %MEM을 함께 보고, VIRT를 실제 RAM 사용량으로 해석하지 않습니다. 값은 측정 시점과 단위에 따라 달라지므로 특정 숫자를 정답으로 삼지 않습니다.

top 정렬과 화면 조작

top
# 실행 중 누르는 키
P : CPU 사용률 순
M : 메모리 사용량 순
1 : CPU별 표시 전환
h : 도움말
q : 종료

P와 M으로 정렬 기준을 CPU와 메모리 사이에서 바꾸며, 두 키는 대문자입니다. 숫자 1을 누르면 CPU별 상태를 볼 수 있습니다. q는 top 화면만 끝내며, 관찰하던 서비스는 계속 실행됩니다. 환경에 따라 기능이 다를 수 있으므로 h 또는 man top에서 확인합니다.

htop 검색과 정렬

htop
F3 또는 / : 이름 검색
F4 : 목록 필터
F6 : 정렬 항목 선택
F1 : 도움말
F10 또는 q : 종료

검색으로 helloworld를 찾아 선택할 수 있고, 필터를 쓰면 이름에 맞는 프로세스만 목록에 표시됩니다. 노트북에서는 기능키에 Fn을 함께 눌러야 할 수 있습니다. htop의 색상과 열 구성은 설정에 따라 다르므로, PID와 명령 이름을 기준으로 프로세스를 찾습니다.

실습: 내 서비스의 CPU 관찰

u=helloworld.service
systemctl is-active "$u"
# active일 때 계속 진행
service_pid=$(systemctl show "$u" \
    --property=MainPID --value)
top -p "$service_pid"

관찰 대상은 systemd가 관리하는 서비스의 MainPID입니다. 이 값을 변수에 담아 top -p로 그 프로세스만 봅니다. 프로그램은 대부분의 시간을 sleep으로 보내므로, CPU 사용률이 낮고 대기 상태로 보일 수 있습니다. PID, %CPU, RES와 관찰 시각을 기록합니다. 비활성 서비스의 MainPID는 0일 수 있으므로, 먼저 is-active로 확인하고 active 상태에서만 top을 실행합니다.

서비스 중지와 다시 시작

u=helloworld.service
sudo systemctl stop "$u"
systemctl is-active "$u"
# inactive
sudo systemctl start "$u"
systemctl is-active "$u"
# active

stop은 실행 중인 서비스를 중지하고, start는 중지한 서비스를 다시 실행합니다. 각 명령 뒤에 is-active로 inactive와 active를 비교합니다. inactive일 때 is-active의 종료값은 0이 아닙니다.

4부. 코드 수정과 실습 정리

이 부에서는 메시지와 출력 간격을 바꿔 다시 설치하고, 결과를 제출합니다.

메시지와 출력 간격 수정

// 아래 두 줄을 수정
printf("Hello, Linux!\n");
sleep(5);
// while문 안의 fflush(stdout)는 유지

출력 문자열을 원하는 내용으로 바꾸고, sleep(2)를 sleep(5)로 바꿉니다. while문 안의 fflush(stdout)는 그대로 둡니다. 실행하기 전에 다음 실행에서 어떤 결과가 나올지 먼저 적어 봅니다. 소스를 수정한 뒤에는 다시 빌드하고 설치해야 서비스에 반영됩니다.

컴파일 오류와 실행 오류

gcc: error: helloworld.c: ...
# 현재 위치와 파일 이름 확인
error: expected ...
# 표시된 줄과 바로 앞줄 확인
./helloworld: No such file or directory
# 컴파일 성공 여부와 실행 파일 확인

첫 번째는 파일 오류입니다. pwd와 ls -l로 현재 위치에 소스가 있는지 확인합니다. 두 번째는 문법 오류로, 표시된 줄과 그 바로 앞줄에서 세미콜론, 따옴표, 중괄호를 확인합니다. 세 번째는 실행 파일이 없는 경우이므로, 컴파일에 성공했는지 확인하고 성공한 뒤에 실행 파일을 실행합니다. 반대로 컴파일이 실패했는데도 이전 실행 파일이 남아 있을 수 있어서, 실행이 된다고 해서 방금 고친 코드가 실행된 것이라고 단정할 수 없습니다.

변경한 코드 반영

u=helloworld.service
sudo systemctl stop "$u"
make
sudo make install
sudo systemctl start "$u"
sudo journalctl -u "$u" -f

서비스를 중지한 뒤, make로 수정한 소스에서 실행 파일을 만들고, make install로 서비스가 실행할 경로에 반영한 다음 다시 시작합니다. 로그에서 새 메시지와 5초 간격을 확인합니다. unit 설정도 바꾸었다면 start 전에 daemon-reload를 실행합니다.

수정했는데 결과가 같을 때

코드를 바꿨는데 로그가 그대로라면 다음 순서로 확인합니다.

  1. 소스를 저장했는가?
  2. make가 성공했는가?
  3. 새 실행 파일을 설치했는가?
  4. 서비스를 다시 시작했는가?
  5. 새 로그를 보고 있는가?

먼저 작업 폴더에서 ./helloworld를 직접 실행해 수정한 메시지가 출력되는지 확인합니다. 다음으로 systemctl cat으로 ExecStart가 가리키는 설치 경로를 확인합니다. 마지막으로 journalctl -f에서 새로 들어오는 로그를 봅니다. 예전 로그가 남아 있는 것과 새 코드가 반영되지 않은 것은 서로 다른 상황이므로 구분해야 합니다.

종합 실습: 내 메시지 서비스

수정 조건은 다음과 같습니다.

  • 메시지: 자신의 실습용 문구
  • 출력 간격: 5초
  • 파일 이름: helloworld.c
  • 빌드: make
  • 실행 방식: systemd 서비스

구현은 while문 안의 문자열과 sleep 인자를 수정하는 것입니다. 반영은 중지, 빌드, 설치, 시작 순서로 수행합니다. 제출할 때는 변경한 코드와 새 로그를 함께 기록합니다. 메시지에는 이름·학번 같은 개인정보 대신 자유로운 실습 문구를 사용합니다.

짝과 함께 확인할 항목

다음 내용을 서로 설명해 봅니다.

  • while (1)의 의미
  • sleep이 반복문 안에 있는 이유
  • make와 make install의 차이
  • start와 enable의 차이
  • 로그 보기 종료와 서비스 중지의 차이

코드는 한 줄씩 실행 순서를 설명하고, 명령은 각 명령이 어떤 파일이나 서비스를 바꾸는지 말해 봅니다. 그리고 상대방이 바꾼 메시지와 간격을 로그에서 확인합니다. 정답 명령을 외우는 것보다 실행 결과를 설명할 수 있는지가 중요합니다.

제출과 확인 문제

제출할 기록은 네 가지입니다.

  1. make의 재빌드 전후 출력
  2. active와 inactive 상태
  3. 2초 간격의 반복 로그
  4. 메시지와 간격 수정 결과

명령 실행 결과와 그 이유를 함께 적습니다. 확인 문제와 답은 다음과 같습니다.

  • Q1. while (1)은 왜 계속 실행되나요? 조건이 항상 참이기 때문입니다.
  • Q2. 소스만 수정하면 실행 중인 서비스도 바뀌나요? 바뀌지 않습니다. 빌드와 설치 후 서비스를 다시 시작해야 합니다.
  • Q3. 로그 보기에서 Ctrl+C를 누르면 서비스도 끝나나요? 로그 보기만 끝나고 서비스는 유지됩니다.

실습 정리

u=helloworld.service
sudo systemctl disable --now "$u"
sudo make uninstall
sudo systemctl daemon-reload
make clean

disable --now로 서비스를 중지하고 부팅 등록을 해제합니다. make uninstall로 수업용 서비스의 설치 파일을 제거하고, daemon-reload와 make clean으로 마무리합니다. helloworld.c와 Makefile은 지우지 않고 보관합니다. 시스템 신호 처리는 이후 수업에서 다룹니다.

5부. GDB 기본 디버깅

이 부에서는 중단점에서 프로그램을 멈추고, 한 줄씩 실행하며 변수 값을 확인합니다.

GDB 실습용 Hello World

#include <stdio.h>
#include <unistd.h>
int main(void)
{
    int count = 0;              // 반복 횟수 초기화
    while (1) {
        count++;                // 이 줄에 중단점 설정
        printf("count=%d\n", count);
        fflush(stdout);
        sleep(2);
    }
}

관찰할 대상이 있도록 반복 횟수를 세는 변수 count를 추가한 예제입니다. 앞의 서비스 예제와 섞이지 않도록 별도 폴더인 Codes/class02-02/gdb의 helloworld.c를 사용합니다. 중단점은 제공 소스의 8행인 count++에 둡니다. 이 예제는 GDB에서 직접 실행하며 서비스에 설치하지 않습니다.

GDB 설치와 디버깅 빌드

sudo apt update
sudo apt install gdb
# class02-02/gdb 폴더에서 실행
gcc -std=c17 -Wall -Wextra -g -O0 \
    helloworld.c -o helloworld
gdb ./helloworld

-g는 소스 줄과 변수 정보를 실행 파일에 포함시켜, 디버거가 줄 번호와 변수 이름을 알 수 있게 합니다. -O0은 최적화를 꺼서 소스에 적힌 순서대로 실행을 관찰할 수 있게 합니다. 셸에서 gdb ./helloworld를 실행하면 (gdb) 프롬프트가 나오고, 이후 명령은 그 프롬프트에 입력합니다. 실습은 Ubuntu PC 또는 VM에서 일반 사용자로 진행하며, 약 15분을 배정합니다.

중단점과 한 줄 실행

(gdb) break helloworld.c:8
(gdb) run
(gdb) list
(gdb) print count
# 예상값: 0
(gdb) next
(gdb) print count
# 예상값: 1

break로 중단점을 설정하고 run으로 프로그램을 시작하면 8행에서 멈춥니다. 이때 중요한 점은, 멈춘 줄은 아직 실행하기 전이라는 것입니다. 그래서 처음 print count의 값은 증가 전인 0입니다. next로 증가문을 실행한 뒤 다시 print count를 하면 1이 됩니다. (gdb) 표시는 프롬프트이므로 입력하지 않습니다. 줄 번호는 제공된 소스를 기준으로 한 것입니다.

다음 반복 관찰과 종료

(gdb) continue
(gdb) print count
# 다음 반복의 증가 전: 1
(gdb) next
(gdb) print count
# 증가 후: 2
(gdb) quit
# 종료 확인 질문이 나오면 y

continue는 다음 중단점까지 실행합니다. 그 사이에 sleep을 지나므로 잠시 기다릴 수 있습니다. 다시 같은 줄에서 멈추면 count는 다음 반복의 증가 전 값인 1이고, next 뒤에는 2가 됩니다. 같은 줄에서 count만 달라지는지 확인하는 것이 이 관찰의 목적입니다. quit은 GDB와 GDB가 실행한 예제를 함께 종료하며, 종료 확인 질문이 나오면 y를 입력합니다. 요약하면 next는 한 줄 진행이고 continue는 다음 중단점까지 진행입니다.

GDB 확인 문제와 오류 해결

실습을 마치면 다음을 확인합니다.

  • 중단점에서 아직 실행 전인 줄이 어디인지
  • next 전후의 count 값
  • next와 continue의 차이
  • 소스 수정 후 다시 빌드했는지

변수를 표시할 때 오류가 나면 -g로 빌드했는지, 그리고 main 안에 멈춰 있는지 확인합니다. 소스에 줄을 추가해 줄 번호가 바뀌었다면 list로 count++의 새 줄 번호를 찾아 중단점을 다시 지정합니다. 제출할 내용은 처음 두 반복의 변수 값과 그 해석이며, 관찰 결과는 이어지는 GitHub Pages 홈페이지의 학습 기록에 추가합니다.
