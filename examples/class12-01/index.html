파이프 (pipe · dup2 · popen · FIFO)

pipe로 만든 익명 파이프의 읽기·쓰기 끝과 EOF, SIGPIPE/EPIPE, 용량을 확인하고, 셸의 CMD1 | CMD2 를 pipe · fork · dup2 · exec로 직접 만들며, popen과 FIFO(이름 있는 파이프)를 써 보는 예제입니다.

실행해 볼 예제

  • pipe_basic한 프로세스 안에서 pipe()로 파이프를 만들고 쓰기 끝에 쓴 뒤, 쓰기 끝을 닫고 읽기 끝에서 EOF까지 읽습니다.
  • pipemsg부모가 파이프로 두 줄을 보내고 자식이 읽습니다. 쓰지 않는 끝점 닫기와 EOF의 관계(ok/leak), 읽는 쪽이 없을 때의 SIGPIPE와 EPIPE, 파이프 용량(cap)을 모드별로 확인합니다.
  • pipe2셸의 CMD1 | CMD2 > FILE 을 pipe · fork · dup2 · execvp로 직접 만듭니다. -o FILE은 CMD2의 표준 출력을 파일로 돌리고, -k는 부모가 쓰기 끝을 닫지 않아 EOF가 오지 않는 상황을 재현합니다.
  • pipeio파이프를 쓰는 다른 두 방법을 보여 줍니다. popen은 셸 명령의 출력을 FILE*로 읽고 pclose로 종료 코드를 받으며, recv/send는 mkfifo로 만든 FIFO를 통해 서로 무관한 두 프로세스가 통신합니다.

파이프는 한 프로세스가 쓴 바이트를 다른 프로세스가 읽게 해 주는 커널 안의 통로입니다. 셸에서 ls | wc -l을 칠 때의 세로 막대가 바로 파이프입니다. 새로 배울 함수는 pipe, dup2, mkfifo, popen 넷뿐이고, 나머지는 3주차에 배운 read · write · close를 그대로 씁니다. 대신 이 수업에서는 "누가 어느 끝을 열어 두고 있는가"를 정확히 따지는 연습을 합니다. 전체를 꿰는 한 문장은 "끝나지 않으면 쓰기 끝을 의심한다"입니다.

도입: 파이프가 놓이는 자리

10 · 11주차에서 이어지는 질문

10주차에는 fork를 하면 자식이 부모의 fd 테이블을 복사해 받고, 두 프로세스의 같은 번호 fd가 같은 열린 파일을 가리킨다고 배웠습니다. 11주차에는 MAP_SHARED|MAP_ANONYMOUS 공유 매핑으로 부모와 자식이 같은 메모리를 보게 했는데, 동시에 ++를 하자 값이 사라졌습니다. 순서와 동시 접근을 프로그램이 직접 맞춰야 한다는 숙제가 남았습니다.

파이프는 이 둘을 잇습니다. fork로 물려받은 fd로 데이터를 주고받되, 번거로운 세 가지를 커널이 맡아 줍니다.

  • 순서: 먼저 쓴 바이트가 먼저 나옵니다.
  • 기다림: 파이프가 비면 read가, 가득 차면 write가 잠듭니다.
  • 끝 알림: 상대가 사라지면 EOF나 SIGPIPE로 알려 줍니다.

커널 안의 버퍼

파이프의 실체는 커널 안의 작은 버퍼입니다. 프로세스 A가 write(fd[1], buf, n)으로 넣은 바이트는 사용자 공간에서 커널 버퍼로 한 번 복사되고, 프로세스 B가 read(fd[0], buf, n)으로 꺼낼 때 커널에서 B의 버퍼로 한 번 더 복사됩니다. 복사가 두 번이고, read와 write마다 시스템 호출이 일어납니다. 버퍼의 크기는 페이지 16개, 곧 65536바이트입니다.

파일과 비교하면 다음 세 가지가 다릅니다.

  • 디스크에 없습니다. 데이터는 커널 메모리에만 있고 저장 장치는 관여하지 않습니다. 한 번 읽으면 버퍼에서 사라지고, 두 끝이 모두 닫히면 버퍼도 사라집니다.
  • 파일처럼 다룹니다. read · write · close를 그대로 씁니다. 다만 위치를 옮기는 lseek는 ESPIPE로 실패합니다.
  • 커널이 조율합니다. 비면 읽는 쪽을 재우고 차면 쓰는 쪽을 재우므로 흐름 제어가 따라옵니다.

Linux에서 파이프는 pipefs라는 내부 파일 시스템의 inode이고, /proc/PID/fd에서 pipe:[inode 번호]로 보입니다. 이 표시는 뒤에서 멈춘 프로그램을 진단할 때 씁니다.

입문 예제 pipe_basic

pipe_basic은 가장 작은 파이프 프로그램입니다. fork 없이 프로세스 하나가 파이프를 만들고, 한 줄을 쓰고, 다시 읽습니다. 실제로 이렇게 쓸 일은 없지만 두 fd의 역할과 EOF가 생기는 시점을 다른 것에 방해받지 않고 볼 수 있습니다.

int fd[2];                  /* fd[0]: 읽기 끝, fd[1]: 쓰기 끝 */

if (pipe(fd) == -1) {       /* 성공 0, 실패 -1 */
    perror("pipe");
    return 1;
}
...
if (write(fd[1], msg, strlen(msg)) == -1) {   /* 커널 버퍼에 들어간다 */
    ...
}
close(fd[1]);               /* 쓰기 끝이 모두 닫혀야 EOF가 생긴다 */

while ((n = read(fd[0], buf, sizeof buf)) > 0)    /* 0이면 EOF */
    fwrite(buf, 1, (size_t)n, stdout);
close(fd[0]);

pipe가 배열에 번호 두 개를 채워 줍니다. fd[0]이 읽기 끝, fd[1]이 쓰기 끝입니다. "hello pipe\n" 11바이트를 쓰기 끝에 쓰면 그 순간 데이터는 커널 버퍼에 들어가 있습니다. 쓰기 끝을 닫은 뒤 read를 반복하면 처음에는 11을, 다음 호출에서는 0을 돌려줍니다. read가 0을 돌려주는 것이 파이프의 EOF입니다.

./pipe_basic

실행하면 두 줄이 나옵니다. 첫 줄의 fd 번호는 3과 4입니다. 0 · 1 · 2는 표준 입력 · 출력 · 오류가 쓰고 있으므로 그다음 가장 작은 빈 번호 둘이 배정된 것입니다. 둘째 줄은 쓴 문장이 그대로 읽혀 나온 것입니다. 그리고 프로그램이 멈추지 않고 끝납니다. 쓰기 끝을 닫았기 때문에 read가 0을 돌려줬기 때문입니다. close(fd[1])을 지우면 첫 read는 11을 돌려주지만 둘째 read가 영원히 기다립니다. 쓰기 끝을 자기 자신이 쥐고 있어서 커널은 "더 올 수도 있다"고 판단합니다.

1부. pipe와 EOF

파이프는 fork와 함께 써야 의미가 있습니다. 1부에서는 fork 뒤에 끝점이 몇 개가 되는지, 그중 무엇을 닫아야 하는지, 그리고 read와 write가 언제 기다리고 언제 끝나는지를 정리합니다. 핵심 문장은 "쓰기 끝을 가리키는 fd가 모두 닫혀야 EOF"입니다.

파이프의 성질 네 가지

  • 한 방향: 쓰기 끝으로 넣고 읽기 끝으로 꺼냅니다. 반대로는 흐르지 않습니다. 양방향이 필요하면 파이프를 두 개 만듭니다.
  • 바이트 스트림: 메시지 경계가 없습니다. write를 세 번 해서 a, b, c를 따로 써도 read 한 번에 "abc"로 합쳐져 나올 수 있습니다. 이것은 버그가 아니라 정상 동작이므로 읽는 쪽은 항상 루프로 읽어야 합니다. 경계가 필요하면 줄바꿈이나 길이 머리표를 프로그램이 정합니다. 3주차의 "부분 읽기 루프"가 여기서도 필요합니다.
  • 먼저 쓴 것이 먼저: 순서가 뒤바뀌지 않고, 건너뛰어 읽을 수도 없습니다(lseek 불가).
  • 이름이 없다: fd로만 가리키므로 fork로 물려받은 프로세스끼리만 쓸 수 있습니다. 이름이 필요하면 3부의 FIFO를 씁니다.

pipe()와 fd 두 개

#include <unistd.h>

int pipe(int fd[2]);

크기 2인 int 배열을 받아 fd 둘을 채우고, 성공하면 0, 실패하면 -1을 돌려줍니다. 가장 작은 빈 번호 두 개가 배정되므로 보통 3과 4가 됩니다. fd[0]은 읽기 끝이어서 read만 되고, fd[1]은 쓰기 끝이어서 write만 됩니다. 0은 표준 입력 번호, 1은 표준 출력 번호와 같다고 외우면 헷갈리지 않습니다. fd가 모자라면 EMFILE로 실패하는데, 7주차의 ulimit -n 한도에 걸린 경우입니다. Linux의 pipe2(fd, O_CLOEXEC)는 exec 때 자동으로 닫히는 끝점을 만듭니다.

호출 직후에는 한 프로세스가 양 끝을 모두 갖고 있습니다. 이 상태로는 쓸모가 없고, fork로 나눠 갖는 것이 다음 단계입니다.

fork 뒤에는 끝점이 네 개

fork는 fd 테이블을 복사하고 열린 파일은 공유합니다. 파이프도 같은 규칙을 따르므로, pipe 다음에 fork를 하면 부모도 3번과 4번, 자식도 3번과 4번을 갖습니다. fd는 네 개인데 파이프는 여전히 하나입니다. 쓰기 끝을 가리키는 fd가 둘, 읽기 끝을 가리키는 fd가 둘인 이 상태에서는 누가 보내고 누가 받는지 정해지지 않았습니다.

pipe가 fork보다 먼저여야 합니다. 먼저 만들어야 자식이 같은 파이프를 물려받습니다. 순서를 바꾸면 부모와 자식이 서로 다른 파이프를 하나씩 만들게 되어 둘은 이어지지 않습니다.

방향 정하기: 쓰지 않는 끝을 닫는다

부모가 자식에게 보내는 방향으로 쓰려면 부모는 읽기 끝을, 자식은 쓰기 끝을 닫습니다. 그러면 쓰기 끝 fd는 부모에게 하나, 읽기 끝 fd는 자식에게 하나만 남습니다. 그리고 부모가 다 보낸 뒤 자기 쓰기 끝을 닫는 순간 쓰기 끝이 0개가 되어 자식의 read가 0(EOF)을 돌려줍니다.

여기서 가장 중요한 점은 파이프에서 close가 뒷정리가 아니라 신호라는 것입니다. 쓰기 끝을 닫는 것이 상대에게 "다 보냈다"를 알리는 유일한 방법입니다. 그래서 close가 세 번 필요합니다.

  1. 부모: close(fd[0]) — 부모는 보내기만 하므로 읽기 끝이 필요 없습니다.
  2. 자식: close(fd[1]) — 자식은 받기만 합니다. 이 close를 빼먹으면 EOF가 오지 않습니다.
  3. 부모: 다 보낸 뒤 close(fd[1]) — 이것을 해야 자식의 read가 0이 됩니다.

자식은 받기만 하는데도 쓰기 끝을 닫아야 하는 이유는, 쓰기 끝 fd가 하나라도 남아 있으면 EOF가 오지 않는데 자식이 쥔 쓰기 끝도 그 하나로 세어지기 때문입니다.

read의 규칙

파이프의 상태read(fd[0], buf, n)의 결과뜻
데이터가 들어 있다바로 반환: 들어 있는 만큼(최대 n바이트)요청보다 적게 올 수 있으므로 루프로 읽는다
비어 있고 쓰기 끝이 열려 있다잠든다(block)누군가 쓰거나, 쓰기 끝이 모두 닫힐 때까지
비어 있고 쓰기 끝이 모두 닫혔다0을 반환EOF — 더 올 데이터가 없다. 루프를 끝낸다
비어 있고 O_NONBLOCK-1, errno = EAGAIN기다리지 않고 돌아온다(기본은 블로킹)

둘째 줄과 셋째 줄의 차이는 "쓰기 끝을 가리키는 fd가 하나라도 남았는가" 하나뿐입니다. 파일의 EOF는 offset이 크기에 닿는 것이었지만 파이프의 EOF는 쓰는 쪽이 없다는 뜻입니다. 쓰기 끝이 모두 닫혔더라도 버퍼에 데이터가 남아 있으면 read는 남은 데이터를 먼저 다 돌려주고, 0은 그다음 호출에서 나옵니다. 읽는 루프는 while ((n = read(…)) > 0) 형태로 쓰고, 0이면 끝, -1이면 오류로 구분합니다.

write의 규칙

파이프의 상태write(fd[1], buf, n)의 결과뜻
빈 공간이 있다쓴 바이트 수를 반환4096바이트(PIPE_BUF) 이하는 한 덩어리로 들어간다
가득 찼고 읽기 끝이 열려 있다잠든다(block)읽는 쪽이 꺼내 갈 때까지 — 속도가 느린 쪽에 맞춰진다
읽기 끝이 모두 닫혔다SIGPIPE를 받는다(기본 동작: 종료)시그널을 무시하거나 처리하면 -1, errno = EPIPE
가득 찼고 O_NONBLOCK-1, errno = EAGAIN예제 pipemsg의 cap 모드가 이 방법으로 용량을 잰다

가득 차면 쓰는 쪽이 잠들기 때문에 빨리 쓰는 프로세스가 느리게 읽는 프로세스의 속도에 저절로 맞춰집니다. 셋째 줄은 받을 프로세스가 없는데 계속 쓰는 것은 낭비이므로 커널이 쓰는 쪽을 멈춰 주는 규칙입니다. yes | head -2가 끝나는 이유가 이것입니다. SIGPIPE는 13번 시그널이고 기본 동작은 종료이므로(9주차), 셸이 보는 종료 코드는 128 + 13 = 141입니다.

용량 65536바이트와 PIPE_BUF 4096바이트

두 숫자를 구분해야 합니다. 65536은 용량입니다. 파이프 버퍼는 4096바이트 페이지 16개이고, 아무도 읽지 않으면 여기까지 들어간 뒤 다음 write가 기다립니다. Linux의 기본값이며 F_GETPIPE_SZ로 확인한 값도 65536입니다. 크기 상한 pipe-max-size는 1048576입니다.

4096은 PIPE_BUF입니다. 한 번의 write가 이 크기 이하이면 쪼개지지 않고 통째로 들어갑니다(원자적). 그래서 여러 프로세스가 같은 파이프에 써도 덩어리 단위로만 번갈아 들어가고, 한 줄이 중간에 끊기지 않습니다. 4096바이트를 넘는 write는 다른 프로세스의 데이터가 사이에 끼어들 수 있습니다. 읽는 쪽이 하나, 쓰는 쪽이 하나이면 PIPE_BUF는 신경 쓰지 않아도 됩니다. 로그처럼 여러 프로세스가 한 파이프에 쓸 때 한 번에 4096바이트 이하로 쓰라는 규칙입니다. 두 숫자는 Linux의 값이고 macOS에서는 다릅니다.

EOF는 "쓰기 끝 fd가 0개"일 때만 온다

세는 대상은 프로세스가 아니라 쓰기 끝을 가리키는 fd의 수입니다.

  1. fork 직후: 부모의 4번과 자식의 4번이 모두 열려 있어 쓰기 끝 fd가 2개입니다. read는 기다립니다.
  2. 부모만 close: 자식의 4번이 남아 쓰기 끝 fd가 1개입니다. read는 영원히 기다립니다.
  3. 자식도 close: 쓰기 끝 fd가 0개가 되어 read가 0(EOF)을 돌려줍니다.

둘째 상태가 까다로운 이유는 읽고 있는 자식 자신이 그 쓰기 끝을 쥐고 있기 때문입니다. 자기 자신도 세어지므로 자기 때문에 EOF를 못 받습니다. 게다가 증상은 "멈춤"뿐입니다. 오류 메시지가 없고 그냥 끝나지 않으며, ps로 보면 S 상태입니다. 그래서 규칙은 이렇습니다. pipe를 만든 뒤 fork를 했다면 모든 프로세스에서 "내가 쓰지 않는 끝"을 닫았는지 하나씩 확인합니다. 읽는 쪽은 fd[1]을, 쓰는 쪽은 fd[0]을 닫습니다.

예제 pipemsg

pipemsg는 부모가 파이프로 두 줄을 보내고 자식이 EOF까지 읽는 프로그램에, 일부러 잘못된 경우를 만드는 모드를 붙인 것입니다. 사용법은 ./pipemsg ok | leak | sigpipe | epipe | cap이고, 다섯 모드가 앞의 규칙 표의 줄 하나씩에 대응합니다. ok는 정상, leak은 read가 기다리는 경우, sigpipe와 epipe는 읽기 끝이 없는 경우, cap은 가득 찬 경우입니다.

ok 모드의 흐름은 다음과 같습니다. 부모는 pipe → fork → close(fd[0]) → "첫 번째 줄" 쓰기 → 0.2초 쉼 → "두 번째 줄" 쓰기 → close(fd[1]) → waitpid 순서로 움직입니다. 자식은 fd 3과 4를 물려받아 close(fd[1])을 하고, read로 15바이트를 두 번 받은 뒤 read가 0을 돌려주면 exit(0)합니다. 두 프로세스 사이에는 서로 다른 세 통로가 있습니다. 데이터는 write로, 끝은 close로, 종료는 wait로 전해집니다.

자식 쪽 코드의 핵심은 다음 부분입니다.

if (!leak)
    close(fd[1]);           /* 내가 쓰지 않는 쓰기 끝을 닫는다 */
while ((n = read(fd[0], buf, sizeof buf)) > 0)
    printf("[자식] read %zd바이트: %.*s", n, (int)n, buf);
if (n == -1)
    die("read");
printf("[자식] read 0 → EOF, 종료\n");

leak 모드는 close(fd[1]) 한 줄만 건너뛰고 다른 코드는 완전히 같습니다. %.*s는 길이를 정해 찍는 서식입니다. read가 채운 buf에는 문자열 끝 표시가 없으므로 n바이트만 찍도록 지정한 것입니다. 루프가 끝난 뒤에는 -1(오류)과 0(EOF)을 구분합니다.

부모 쪽은 pipe 다음에 fork를 하고, close(fd[0])으로 읽기 끝을 닫은 뒤 두 줄을 쓰고 close(fd[1])을 합니다. 마지막 close가 "다 보냈다"는 신호이며, 이 줄 뒤에 자식의 read가 0을 받습니다. 이 close는 waitpid보다 반드시 먼저 와야 합니다. 순서가 바뀌면 부모는 자식의 종료를, 자식은 EOF를 기다리며 서로 멈춥니다.

sigpipe · epipe 모드는 읽는 쪽이 없는 파이프에 씁니다.

close(fd[0]);               /* 읽기 끝이 하나도 남지 않는다 */
if (ignore)
    signal(SIGPIPE, SIG_IGN);   /* 시그널 대신 오류 값으로 받는다 */
printf("읽는 쪽 없이 write를 시도한다\n");
if (write(fd[1], "x", 1) == -1) {
    printf("write 실패: %s (errno %d)\n", strerror(errno), errno);
    return 1;
}
printf("이 줄은 출력되지 않는다\n");

sigpipe 모드에서는 write에서 SIGPIPE를 받아 그 자리에서 죽으므로 아래 줄들은 실행되지 않습니다. epipe 모드에서만 SIG_IGN으로 시그널을 무시해 두므로 죽지 않고 write가 -1과 EPIPE를 돌려줍니다.

pipemsg 실행 결과

./pipemsg ok

자식이 15바이트를 두 번 읽습니다. 한글 4자 × 3바이트 + 공백 2 + 줄바꿈 1 = 15입니다. 부모의 "쓰기 끝을 닫고" 줄 다음에야 자식의 "read 0"이 나오는 순서를 확인합니다. 닫은 뒤에 EOF가 오고, 자식은 EOF를 보고 스스로 끝나 종료 코드가 0입니다. 두 줄이 따로 읽힌 것은 경계가 보존되어서가 아니라 부모가 0.2초 간격을 두었기 때문입니다. usleep을 지우면 두 줄이 read 한 번에 30바이트로 올 수 있습니다.

./pipemsg leak &
ps -o pid,ppid,stat,cmd
ls -l /proc/$(pgrep -n pipemsg)/fd | grep pipe
pkill pipemsg

leak 모드에서는 두 줄을 읽고 부모가 닫았다는 줄까지 나오지만 "read 0 → EOF" 줄이 나오지 않습니다. 오류 메시지도 없이 멈춥니다. 진단 순서는 세 단계입니다. 먼저 ps로 멈춘 프로세스를 찾으면 둘 다 S(잠듦) 상태입니다. 다음으로 자식의 fd 목록을 보면 3번과 4번이 같은 번호의 파이프를 가리킵니다(pipe:[…] 뒤의 숫자가 같으면 같은 파이프입니다). 마지막으로 권한을 보면 3번은 lr-x(읽기), 4번은 l-wx(쓰기)입니다. 범인은 4번입니다. 자식이 같은 파이프의 쓰기 끝을 아직 쥐고 있어서, 자식은 EOF를, 부모는 자식의 종료를 서로 기다리며 끝나지 않습니다.

./pipemsg sigpipe; echo "종료 코드 $?"
./pipemsg epipe; echo "종료 코드 $?"
./pipemsg cap

sigpipe 모드는 안내문 한 줄만 내고 끝나며 "write 실패" 줄이 없습니다. 종료 코드 141 = 128 + 13으로, SIGPIPE로 죽은 것입니다. epipe 모드는 죽지 않고 write가 -1을 돌려주어 EPIPE(errno 32)를 출력합니다. 같은 상황을 시그널 대신 오류 값으로 받은 것이며, 서버 프로그램은 보통 이렇게 SIGPIPE를 무시하고 EPIPE를 검사합니다. cap 모드는 아무도 읽지 않는 파이프에 계속 써서 65536바이트에서 멈추고, 그다음 write는 EAGAIN이 됩니다. 블로킹이었다면 그 자리에서 잠들었을 것입니다.

1부 정리

  • 만드는 순서: pipe → fork → 쓰지 않는 끝 close. close는 세 번입니다. 부모가 읽기 끝을 닫고, 자식이 쓰기 끝을 닫고, 부모가 다 보낸 뒤 쓰기 끝을 닫습니다.
  • 끝나는 조건: 쓰기 끝 fd가 0개이면 read가 0(EOF)을 돌려주고, 읽기 끝이 0개이면 write가 SIGPIPE를 받습니다(무시하면 EPIPE).
  • 기다리는 조건: 비면 read가, 65536바이트가 차면 write가 잠듭니다.

2부. dup2와 파이프라인

2부에서는 프로그램을 고치지 않고 표준 입력 · 표준 출력을 파이프나 파일로 바꿔 끼우는 dup2를 배우고, 셸의 CMD1 | CMD2를 직접 만듭니다.

프로그램은 파이프를 모른다

ls -l만 실행하면 ls는 1번 fd에 쓰고, 1번은 터미널입니다. ls -l | wc -l에서도 ls의 코드는 한 글자도 바뀌지 않습니다. 바뀐 것은 "1번 fd가 가리키는 곳"뿐이어서, 1번은 파이프 쓰기 끝을, wc의 0번은 파이프 읽기 끝을 가리킵니다. ls는 터미널이든 파이프든 파일이든 같은 코드로 1번에 쓰고(3주차의 약속), wc는 read(0, …)이 0을 돌려줄 때까지 셉니다. 그래서 wc에는 EOF가 꼭 와야 합니다.

파이프를 만들고 끼워 넣는 것은 ls도 wc도 아닌 셸입니다. 셸은 fork와 exec 사이에서 1번과 0번이 가리키는 곳을 바꿉니다. exec를 해도 열린 fd는 그대로 남으므로(10주차) exec 전에 바꿔 놓은 연결이 새 프로그램에도 이어집니다. 이를 위해 fd 번호를 다른 열린 파일로 바꾸는 함수가 필요하고, 그것이 dup2입니다.

dup2(oldfd, newfd): 번호를 바꿔 끼운다

#include <unistd.h>

int dup2(int oldfd, int newfd);

성공하면 newfd, 실패하면 -1을 돌려줍니다. 인자 순서를 자주 틀리므로 "oldfd를 newfd 자리에", 곧 "무엇을, 어느 자리에"로 읽습니다. 참고로 dup(oldfd)는 가장 작은 빈 번호로 복제합니다.

dup2(fd[1], STDOUT_FILENO);   close(fd[1]);

4번이 파이프 쓰기 끝일 때 dup2(4, 1)을 하면 1번이 파이프 쓰기 끝을 가리키게 되고, 원래 가리키던 터미널과의 연결은 끊어집니다. 이 뒤로 printf와 write(1, …)는 모두 파이프로 갑니다. 세 가지를 기억합니다.

  • newfd가 oldfd와 같은 열린 파일을 가리키게 만듭니다.
  • newfd가 열려 있었으면 커널이 먼저 닫고 나서 복제합니다. 이 둘은 한 번에 일어납니다.
  • oldfd는 그대로 남아 둘이 같은 것을 가리킵니다. 원래 번호는 직접 close해야 합니다. 이 close를 빼먹으면 쓰기 끝 fd가 하나 더 남으므로, 1부의 EOF 규칙과 다시 만나게 됩니다.

리다이렉션은 open + dup2

파일로 가든 파이프로 가든 방법은 같습니다. 원하는 열린 파일을 만들고, dup2로 0 · 1 · 2번 자리에 놓고, 원래 번호를 닫습니다. 자식 프로세스가 fork 뒤 exec 전에 open → dup2 → close를 하는 것입니다. 이 작업을 부모인 셸에서 하면 셸 자신의 출력이 파일로 가 버리므로 반드시 자식에서 합니다.

셸 문법자식 프로세스가 exec 전에 하는 일결과
cmd > FILEfd = open(FILE, O_WRONLY|O_CREAT|O_TRUNC, 0644); dup2(fd, 1); close(fd);표준 출력이 파일로(덮어씀)
cmd >> FILEfd = open(FILE, O_WRONLY|O_CREAT|O_APPEND, 0644); dup2(fd, 1); close(fd);표준 출력이 파일 끝에 붙음
cmd < FILEfd = open(FILE, O_RDONLY); dup2(fd, 0); close(fd);표준 입력이 파일에서
cmd 2> FILEfd = open(FILE, O_WRONLY|O_CREAT|O_TRUNC, 0644); dup2(fd, 2); close(fd);표준 오류만 파일로
cmd 2>&1dup2(1, 2);2번이 1번과 같은 곳으로

파이프라인 조립: 프로세스 셋, 파이프 하나

ls | wc에는 부모(셸)와 자식 둘, 그리고 파이프 하나가 등장합니다. 순서는 pipe → fork → (자식) dup2 → close → exec, (부모) close → wait입니다.

  1. 부모가 pipe를 만듭니다.
  2. fork를 두 번 합니다. 이 시점에 세 프로세스가 모두 3번과 4번을 갖고, 끝점은 여섯 개입니다.
  3. 왼쪽 자식은 4를 1 자리에, 오른쪽 자식은 3을 0 자리에 놓고, 둘 다 3과 4를 닫습니다.
  4. 자식들은 exec합니다.
  5. 부모도 3과 4를 닫고 둘을 wait합니다.

결과적으로 남은 쓰기 끝 fd는 ls의 1번 하나, 남은 읽기 끝 fd는 wc의 0번 하나입니다. 그래서 ls가 끝나 1번이 닫히면 쓰기 끝 fd가 0개가 되고, wc의 read가 0(EOF)을 받아 결과를 출력하고 끝납니다.

닫기 장부: 누가 무엇을 닫아야 하나

파이프 하나에 close는 여섯 번입니다. 프로세스마다 읽기 끝과 쓰기 끝을 하나씩 확인합니다.

프로세스fd[0] 읽기 끝fd[1] 쓰기 끝닫지 않으면
CMD1 (왼쪽 자식)닫는다dup2(fd[1], 1) 뒤 닫는다읽기 끝이 남는다 → CMD2가 먼저 끝나도 CMD1이 SIGPIPE를 받지 못한다
CMD2 (오른쪽 자식)dup2(fd[0], 0) 뒤 닫는다닫는다쓰기 끝이 남는다 → 자기 자신 때문에 EOF가 오지 않는다(1부 leak과 같다)
부모닫는다닫는다쓰기 끝이 남는다 → CMD2가 EOF를 못 받고 부모의 wait도 끝나지 않는다(pipe2의 -k)

가장 흔한 실수는 셋째 줄입니다. 부모는 파이프를 쓰지도 않으니 닫는 것을 잊기 쉽습니다. 또한 exec를 해도 fd는 남으므로, exec 전에 닫지 않은 fd는 ls와 wc 안에서도 열린 채로 있습니다. 파이프가 N개이면 프로세스마다 2N개를 모두 살펴야 합니다.

yes | head -2: 뒤쪽이 먼저 끝나면

yes는 "y" 줄을 끝없이 쓰는데도 이 파이프라인은 끝납니다. head가 두 줄을 읽고 exit(0)하면 읽기 끝 fd가 0개가 되고, yes의 다음 write가 SIGPIPE를 받아 yes가 시그널 13으로 종료합니다. 받는 쪽이 없어지면 보내는 쪽도 끝나므로 무한 루프가 정리됩니다.

yes | head -2; echo "${PIPESTATUS[@]}"

파이프라인의 $?는 마지막 명령의 값입니다. yes가 시그널로 죽어도 $?는 head의 0입니다. 앞쪽 상태를 보려면 bash의 ${PIPESTATUS[@]}를 쓰며 여기서는 141 0이 나옵니다. set -o pipefail을 켜면 $?가 141이 됩니다.

예제 pipe2

pipe2는 셸의 CMD1 | CMD2 > FILE을 pipe · fork · dup2 · exec로 만든 프로그램입니다. 사용법은 ./pipe2 [-k] [-o FILE] CMD1 [ARG...] -- CMD2 [ARG...]입니다. --가 세로 막대 자리입니다(진짜 세로 막대를 쓰면 셸이 가로챕니다). -o는 > FILE이고, -k는 부모가 쓰기 끝을 닫지 않게 하는 실험용 옵션입니다.

부모는 argv를 --에서 둘로 자르고, pipe를 만들고, fork를 두 번 한 뒤 close(fd[0]) · close(fd[1])을 하고 두 자식을 waitpid로 거두어 마지막 명령의 상태로 종료합니다. 부모의 close 두 번이 waitpid보다 먼저여야 합니다. 순서가 바뀌면 CMD2가 EOF를 못 받아 waitpid가 끝나지 않습니다.

왼쪽 자식은 표준 출력을 파이프에 연결합니다.

if (p1 == 0) {                      /* 왼쪽 명령: 표준 출력 → 파이프 */
    dup2(fd[1], STDOUT_FILENO);
    close(fd[0]);
    close(fd[1]);                   /* 1번이 대신하므로 닫는다 */
    execvp(left[0], left);
    perror(left[0]);
    _exit(127);
}

쓰기 끝을 1번 자리에 놓고 원래 번호 둘을 닫습니다. 1번이 쓰기 끝을 대신 가리키므로 fd[1]을 닫아도 연결은 유지되고, 실행될 프로그램에 필요 없는 fd를 넘기지 않게 됩니다. execvp는 성공하면 돌아오지 않고, 실패하면 perror 뒤 _exit(127)로 끝냅니다(10주차 관례).

오른쪽 자식은 표준 입력을 파이프에 연결하고, -o가 있으면 표준 출력을 파일로 돌립니다.

if (p2 == 0) {                    /* 오른쪽 명령: 표준 입력 ← 파이프 */
    dup2(fd[0], STDIN_FILENO);
    close(fd[0]);
    close(fd[1]);
    if (out != NULL) {              /* > FILE: 표준 출력을 파일로 */
        int o = open(out, O_WRONLY | O_CREAT | O_TRUNC, 0644);
        ...
        dup2(o, STDOUT_FILENO);
        close(o);
    }
    execvp(right[0], right);
    ...
}

여기서 close(fd[1])이 닫기 장부의 "CMD2 · 쓰기 끝" 칸입니다. 이 줄을 빼면 자기 때문에 EOF가 오지 않습니다. -o FILE 부분은 open한 fd를 1번 자리에 놓는 것으로, 리다이렉션 표의 첫 줄과 같습니다. 이 명령은 0번은 파이프, 1번은 파일인 채로 실행됩니다.

부모의 마지막 부분은 짧지만 2부에서 가장 중요합니다.

close(fd[0]);                       /* 부모는 파이프를 쓰지 않는다 */
if (!keep)
    close(fd[1]);                   /* 안 닫으면 CMD2에 EOF가 안 온다 */
report(left[0], p1);
return report(right[0], p2);        /* 마지막 명령의 상태로 끝난다 */

부모는 파이프를 만들기만 하고 쓰지 않으므로 둘 다 닫습니다. -k를 주면 close(fd[1])을 건너뛰어 쓰기 끝 fd가 부모에게 하나 남습니다. report는 waitpid로 자식을 거두고 상태를 출력하며, 셸처럼 마지막 명령의 상태가 프로그램의 종료 코드가 됩니다.

pipe2 실행 결과

./pipe2 ls -l -- wc -l
ls -l | wc -l
./pipe2 -o out.txt cat /etc/passwd -- grep root
cat out.txt

직접 만든 파이프라인과 셸의 |가 같은 숫자를 냅니다. [pipe2]로 시작하는 보고 줄은 표준 오류(2번)로 나가므로 파이프에도 파일에도 섞이지 않습니다. -o를 준 실행에서는 grep의 출력이 화면에 없고 out.txt에 있습니다.

./pipe2 ls -l /proc/self/fd -- cat
./pipe2 true -- ls -l /proc/self/fd

/proc/self는 그 경로를 여는 프로세스 자신을 가리키므로 자식의 fd 테이블을 직접 볼 수 있습니다. ls를 왼쪽에 두면 1번이 파이프이고 권한이 l-wx(쓰기 전용)입니다. dup2(fd[1], 1)의 결과입니다. 오른쪽에 두면 0번이 파이프이고 lr-x(읽기 전용)이며 dup2(fd[0], 0)의 결과입니다. 그 밖에는 0 · 1 · 2와 ls가 /proc/…/fd를 읽으려고 연 3번뿐입니다. 파이프의 원래 fd는 exec 전에 닫혔습니다.

./pipe2 yes -- head -2; echo "종료 코드 $?"
./pipe2 nosuch -- wc -l; echo "종료 코드 $?"
timeout 3 ./pipe2 -k ls -- wc -l; echo "종료 코드 $?"

첫째 실행에서 head가 끝나자 yes는 시그널 13으로 끝나고 전체 상태는 head의 0입니다. 둘째 실행의 없는 명령은 exec 실패로 127이고, wc는 바로 EOF를 받아 0줄을 셉니다. 셋째 -k 실행에서는 ls의 보고는 나오지만 wc의 숫자가 끝내 나오지 않습니다. ls는 끝났고 wc는 자기 쓰기 끝을 닫았지만 부모 pipe2가 쓰기 끝을 쥐고 있어서 wc가 EOF를 못 받습니다. timeout이 3초 뒤 그룹 전체에 SIGTERM을 보내 끝냈고 그 표시가 124입니다. 닫기 장부의 셋째 줄이 실제로 일어난 것입니다.

2부 정리

자식은 pipe(fd) → fork() → dup2(fd[i], 0 또는 1) → close(fd[0]) · close(fd[1]) → execvp(…)의 순서를 밟고, 부모는 close 둘 뒤에 wait합니다. dup2(fd[1], 1)은 쓰기 끝을 표준 출력 자리에, dup2(fd[0], 0)은 읽기 끝을 표준 입력 자리에 놓습니다. 리다이렉션도 open한 fd를 dup2로 0 · 1 · 2 자리에 놓는 같은 방법입니다. 파이프라인이 끝나지 않을 때는 다음을 점검합니다.

  • 자식마다 dup2 뒤에 fd[0]과 fd[1]을 모두 닫았는가
  • 부모가 fork를 마친 뒤 fd[0]과 fd[1]을 모두 닫았는가
  • 부모의 close가 waitpid보다 먼저인가
  • exec 실패 경로에서 _exit를 불렀는가

그래도 끝나지 않으면 ls -l /proc/PID/fd에서 남은 pipe 쓰기 끝을 찾습니다.

3부. popen과 FIFO

3부는 두 질문에 답합니다. 매번 다섯 단계를 다 써야 하는가에 대한 답이 popen이고, 부모와 자식이 아니면 파이프를 못 쓰는가에 대한 답이 FIFO입니다.

popen · pclose: 다섯 단계를 한 번에

#include <stdio.h>

FILE *popen(const char *command, const char *type);
int   pclose(FILE *stream);

popen("ls | sort", "r")이 안에서 하는 일은 2부에서 직접 한 것과 같습니다. glibc 2.39에서 실측하면 pipe2(O_CLOEXEC) → clone(CLONE_VFORK)(fork 역할) → 자식의 dup3(4, 1, 0)(쓰기 끝을 1번에) → execve("/bin/sh", ["sh", "-c", "--", cmd]) 순서입니다. 부모는 읽기 끝을 FILE *로 받아 fgets(line, n, fp)로 읽습니다.

  • "r"과 "w": "r"은 명령의 출력을 읽고, "w"는 명령의 입력에 씁니다. 한 방향만 됩니다.
  • FILE *를 돌려줍니다: fgets · fprintf를 쓰며, 4주차의 stdio 버퍼가 그대로 적용됩니다.
  • pclose로 닫습니다: fclose가 아닙니다. pclose(fp)는 fclose에 자식에 대한 wait4를 더한 것으로, 자식을 기다려 종료 상태를 돌려주며 그 반환값을 WEXITSTATUS로 풉니다. fclose로 닫으면 아무도 wait하지 않은 자식, 곧 좀비가 남습니다.

명령 문자열은 셸(/bin/sh -c)이 해석합니다. 그래서 |와 >와 *를 쓸 수 있지만, 대신 사용자 입력을 그대로 넣으면 위험합니다.

FIFO: 이름이 있는 파이프

#include <sys/stat.h>

int mkfifo(const char *path, mode_t mode);

성공하면 0, 실패하면 -1이며 이미 있으면 EEXIST입니다. 셸 명령 mkfifo PATH도 같은 일을 합니다. FIFO를 만들면 파일 시스템에 이름이 하나 생기고, ls -l에서 파일 종류가 p로 보입니다(예: prw-------, 5주차의 파일 종류 문자). 크기는 늘 0이고 데이터는 커널의 파이프 버퍼에 있습니다.

이름은 만나는 장소일 뿐입니다. 프로세스 A가 open(path, O_WRONLY)로, 프로세스 B가 open(path, O_RDONLY)로 같은 경로를 열면 커널 안의 같은 파이프에 연결됩니다. fork로 물려받지 않아도 되므로 A와 B는 서로 다른 터미널에서 따로 실행한 프로그램이어도 되고, 약속할 것은 경로 하나뿐입니다. 연결된 뒤의 규칙은 파이프와 같아서 EOF · SIGPIPE · 65536 · PIPE_BUF가 모두 그대로 적용됩니다. 이름은 unlink로 지웁니다.

FIFO open의 만남 규칙

보통의 파일 open은 기다리지 않지만 FIFO는 open이 잠들 수 있습니다. 기본(블로킹) open은 읽는 쪽과 쓰는 쪽이 모두 올 때까지 양쪽을 재웁니다. 둘이 "만나야" 시작됩니다.

open의 플래그상대가 아직 없으면메모
O_RDONLY쓰는 쪽이 open할 때까지 잠든다예제 recv가 "쓰는 쪽을 기다림" 줄에서 멈춘다
O_WRONLY읽는 쪽이 open할 때까지 잠든다예제 send — recv가 떠 있으면 바로 지나간다
O_RDONLY | O_NONBLOCK바로 성공한다read는 쓰는 쪽이 없으면 0을 돌려준다
O_WRONLY | O_NONBLOCK-1, errno = ENXIO받을 쪽이 없다는 것을 기다리지 않고 안다
O_RDWR바로 성공한다(Linux)자신이 쓰는 쪽이기도 해서 EOF가 오지 않는다

양방향은 파이프 두 개, 그리고 교착

파이프는 한 방향이므로 대화하려면 두 개를 만듭니다. 부모가 요청 파이프 A에 쓰고 응답 파이프 B에서 읽으며, 자식(예: sort, bc)은 A에서 읽고 B에 씁니다. 끝점은 여덟 개이고 닫을 것은 넷입니다. 이때 두 가지 교착을 조심해야 합니다.

  • 교착 ① 순서: 부모가 read(B)부터, 자식이 read(A)부터 하면 아무도 쓰지 않아 영원히 기다립니다.
  • 교착 ② 용량: 자식이 응답을 쓰다가 B가 가득 차 멈추면 자식은 A를 읽지 않게 되고, 부모는 응답을 읽지 않고 쓰기만 하다가 A도 가득 차 멈춥니다. 65536에서 양쪽이 함께 멈추는 것으로, 작은 입력에서는 잘 되다가 큰 입력에서 멈추는 전형적인 버그입니다. 이것이 popen으로 양방향을 하지 못하게 한 이유입니다.

규칙은 누가 먼저 쓰고 누가 먼저 읽는지(프로토콜)를 정하고, 다 쓴 쪽은 쓰기 끝을 닫아 끝을 알리는 것입니다. 해결 방법으로는 조금씩 쓰고 읽기, 읽는 프로세스를 따로 두기, 13–14주차에 배울 다른 IPC를 쓰는 것이 있습니다.

예제 pipeio

pipeio는 popen으로 명령의 출력을 읽는 모드와, FIFO로 다른 터미널의 프로세스와 만나는 모드를 가진 프로그램입니다. 사용법은 ./pipeio popen "COMMAND" | recv FIFO | send FIFO TEXT입니다. popen 모드는 혼자 실행하고, recv와 send는 터미널 둘로 실행합니다.

popen 모드는 세 줄이 전부입니다.

FILE *fp = popen(cmd, "r");         /* "r": 명령의 표준 출력을 읽는다 */
...
while (fgets(line, sizeof line, fp) != NULL)
    printf("%2d: %s", ++count, line);
int st = pclose(fp);              /* fclose가 아니다. 자식을 기다린다 */
...
printf("줄 수 %d, 명령의 종료 코드 %d\n", count, WEXITSTATUS(st));

popen은 실패하면 NULL을 돌려줍니다. 명령이 끝나 쓰기 끝이 닫히면 EOF가 와서 fgets가 NULL을 돌려줍니다. pclose의 반환값은 wait의 상태와 같은 형식이라 WEXITSTATUS로 풉니다. 2부 pipe2에서 길게 쓴 조립이 여기서는 세 줄입니다.

recv 모드는 FIFO를 만들고, 쓰는 쪽이 열 때까지 기다렸다가 EOF까지 읽습니다.

if (mkfifo(path, 0600) == -1 && errno != EEXIST)
    die("mkfifo");
printf("[recv] %s 를 연다 (쓰는 쪽을 기다림)\n", path);
int fd = open(path, O_RDONLY);      /* 상대가 열 때까지 여기서 멈춘다 */
...
while ((n = read(fd, buf, sizeof buf)) > 0)
    printf("[recv] %zd바이트: %.*s", n, (int)n, buf);
...
close(fd);
unlink(path);                       /* 이름을 지운다 */

FIFO가 이미 있으면(EEXIST) 그대로 씁니다. open에서 쓰는 쪽이 올 때까지 멈추고, 그 뒤의 read 루프는 pipemsg의 자식과 같습니다. 마지막에 unlink로 이름을 지웁니다.

send 모드는 FIFO를 만들지 않고 open(path, O_WRONLY)로 보통의 파일처럼 엽니다. FIFO가 없으면 ENOENT로 끝나고, 읽는 쪽이 없으면 기다립니다. 한 줄을 만들어 쓰는데 4096바이트 이하라 다른 쓰기와 섞이지 않습니다. close하면 쓰기 끝이 0개가 되어 recv가 EOF를 받습니다. recv와 send의 본문은 1부 pipemsg의 자식 · 부모와 같고, 달라진 것은 pipe + fork 대신 mkfifo + open으로 만난다는 점뿐입니다. 만남(open이 함께 풀린다), 데이터(write → read), 끝(close → EOF)의 세 단계도 그대로입니다.

pipeio 실행 결과

./pipeio popen "ls *.c | sort -r"
./pipeio popen "exit 3"

첫 명령에는 *와 |가 들어 있는데도 동작합니다. 명령 문자열을 /bin/sh가 해석했기 때문이며, 파이프 안의 파이프가 된 셈입니다. 줄 번호는 fgets로 받은 줄에 프로그램의 printf가 붙인 것입니다. 둘째 명령 exit 3은 출력이 없지만 pclose가 자식의 상태를 돌려주어 종료 코드 3이 나옵니다. 출력이 없어도 상태는 옵니다.

# 터미널 1

# 터미널 2
ls -l /tmp/chan
./pipeio send /tmp/chan hello
ls /tmp/chan

recv는 첫 줄만 내고 open에서 멈춰 있습니다. 다른 터미널에서 ls -l로 보면 파일 종류가 p이고 크기가 0입니다. 데이터는 파일 시스템에 저장되지 않습니다. send를 실행하는 순간 양쪽 open이 풀리고 recv가 6바이트를 받습니다. send가 닫고 끝나자 recv가 EOF를 받고 unlink로 FIFO를 지웁니다. 두 프로그램은 부모 · 자식이 아니며 서로 아는 것은 /tmp/chan이라는 경로뿐입니다. send 대신 echo hi > /tmp/chan으로 보내도 됩니다. 셸의 리다이렉션이 그대로 쓰기 쪽 open이 되기 때문입니다.

파이프는 복사가 두 번인 대신 순서, 기다림, 끝 알림을 커널이 맡습니다. 그래서 한쪽이 만들고 다른 쪽이 차례로 쓰는 일, 곧 필터 · 로그 · 작업 전달에 맞습니다.

부록. strace 사용법

strace는 프로그램이 커널에 무엇을 부탁하는지, 곧 시스템 호출을 한 줄씩 보여 주는 도구입니다. 파이프가 멈추거나 이상할 때 가장 먼저 꺼냅니다.

strace가 보여 주는 것

strace는 ptrace(2)로 대상 프로세스를 멈춰 가며 시스템 호출 경계에서 일어나는 일을 받아 적습니다. 그래서 대상이 느려집니다.

시작하는 법쓰는 때
strace CMD [ARG...]프로그램을 처음부터 추적한다
strace -p PID이미 실행 중인(멈춰 있는) 프로세스에 붙는다
strace -o FILE CMD기록을 파일에 저장한다(출력이 많을 때)
  • 시스템 호출만 보입니다. printf · strlen 같은 라이브러리 함수는 보이지 않고 write는 보입니다.
  • 출력은 stderr로 나갑니다. 프로그램의 출력과 섞이지 않게 하려면 -o FILE이나 2>를 씁니다.
  • 고치지 않고 봅니다. 소스도, 다시 컴파일도 필요 없으므로 ls나 bash도 볼 수 있습니다.

한 줄 읽는 법

종류출력의 모습읽는 법
보통의 줄write(4, "hello pipe\n", 11) = 11이름(인자들) = 반환값
실패한 줄execve("/bin/nosuch", ...) = -1 ENOENT (No such file or directory)-1 뒤에 errno 이름과 설명
멈춰 있는 줄read(3,괄호가 안 닫혔다 = 지금 이 호출에서 기다리는 중
시그널--- SIGCHLD {si_signo=SIGCHLD, si_pid=761, ...} ------ 사이: 받은 시그널
종료+++ exited with 0 +++ / +++ killed by SIGPIPE ++++++ 사이: 끝난 방식

-f로 볼 때는 줄 앞의 숫자가 PID이고, <unfinished ...>와 <... resumed>는 같은 호출의 앞뒤 사이에 다른 프로세스의 줄이 끼었다는 표시입니다. 문자열 인자는 32바이트까지만 보이고 한글은 \354\262\253처럼 8진수로 나오며, -s 200으로 길이를 늘릴 수 있습니다.

자주 쓰는 옵션

옵션하는 일파이프에서의 쓰임
-ffork · clone으로 생긴 자식도 따라간다필수. 없으면 부모의 호출만 보인다
-e trace=a,b,c적은 이름의 호출만 보여 준다로더와 libc가 부르는 수십 줄을 걸러 낸다
-o FILE기록을 FILE에 쓴다프로그램의 출력과 섞이지 않는다
-p PID실행 중인 프로세스에 붙는다멈춘 프로세스가 어느 호출에 있는지 본다
-yfd 옆에 대상을 붙인다: 3<pipe:[123]>어느 fd가 어느 파이프인지 바로 보인다
-c호출별 횟수 · 오류 수 · 시간을 표로close를 몇 번 했는지 센다
-tt, -T시각(마이크로초) · 호출에 걸린 시간어디서 오래 기다렸는지 본다
-s N문자열을 N바이트까지 보여 준다(기본 32)주고받은 내용을 더 길게 본다

파이프를 볼 때의 기본형은 다음과 같습니다.

strace -f -e trace=pipe2,dup3,close,clone,execve,wait4 -o t.txt ./prog

예제에 적용해 보기

strace -e trace=pipe2,read,write,close ./pipe_basic > /dev/null

pipe_basic을 추적하면 맨 위 세 줄은 로더가 libc.so를 여는 과정이고, 그 아래가 소스와 한 줄씩 대응합니다. pipe → write → close → read 11 → read 0 → close의 순서입니다. read(3, "", 64) = 0 줄이 EOF입니다. printf와 fwrite의 출력은 모였다가 끝날 때 write(1, …, 32) 한 번으로 나갑니다.

-y를 붙이면 3번과 4번의 꺾쇠 안 pipe:[번호]가 같아서 한 파이프의 양 끝임이 바로 보이고, > /dev/null로 돌린 1번은 1</dev/null>로 보입니다. ls -l /proc/PID/fd의 정보를 호출마다 붙여 주는 셈입니다.

-f -o로 pipe2를 추적하면 줄 앞의 숫자가 PID여서 부모와 두 자식의 호출이 함께 보입니다. 왼쪽 자식의 dup3(4, 1)은 쓰기 끝을 1번에, 오른쪽 자식의 dup3(3, 0)은 읽기 끝을 0번에 놓은 것입니다. -f가 없으면 부모만 보입니다.

./pipemsg leak > /dev/null &
timeout 2 strace -p $(pgrep -n pipemsg)
pkill pipemsg

leak으로 멈춘 자식에 -p로 붙으면 read(3,에서 괄호가 닫히지 않은 채 멈춰 있습니다. 자식이 3번에서 read를 기다리는 중이라는 뜻입니다. 3번이 무엇인지는 ls -l /proc/PID/fd로 보고, 같은 파이프의 쓰기 끝을 누가 쥐었는지 찾습니다. 붙었다 떼도 안전합니다. Ctrl-C나 timeout으로 strace만 끝나고 대상은 계속 실행됩니다.

-c로 pipe2를 세면 pipe2 1번, clone 2번, dup3 2번으로 파이프 하나, 자식 둘, 바꿔 끼우기 두 번이라는 그림과 숫자가 맞습니다. close는 21번인데, 우리 코드의 6번에 로더 · ls · wc가 연 파일의 close가 더해진 것입니다. 시간은 대부분 wait4에서 보냅니다. 부모가 자식을 기다린 시간입니다.

파이프 문제에 쓰는 세 가지 방법과 주의할 점

  • 끝나지 않는다 — strace -p PID. read(N,에서 멈췄으면 EOF를 기다리는 것이고 쓰기 끝이 남았다는 뜻입니다. wait4(이면 자식을 기다리는 중이고, write(N,이면 파이프가 가득 찼고 읽는 쪽이 없다는 뜻입니다.
  • 누가 닫지 않았나 — strace -f -y -e trace=pipe2,dup3,close CMD. PID별로 close(N<pipe:[…]>)를 세어 닫기 장부와 비교합니다.
  • 왜 실행이 안 되나 — strace -f -e trace=execve CMD. = -1 ENOENT(없는 명령)나 EACCES(권한)가 보이고, 인자 배열이 생각대로 넘어갔는지도 보입니다.

주의할 점은 네 가지입니다. 출력은 stderr이므로 프로그램 출력과 섞이면 -o FILE을 씁니다. 대상이 느려지므로 시간을 재는 실험과 함께 쓰지 않습니다. 자기 프로세스만 볼 수 있으며, Ubuntu는 기본 설정(/proc/sys/kernel/yama/ptrace_scope가 1이면 자기 자식만)에서 -p로 붙는 것도 막아 "Operation not permitted"가 나옵니다. 이때는 strace로 직접 실행하거나 sudo를 씁니다. 마지막으로 시스템 호출만 보이므로 변수 값과 함수 흐름은 gdb로 봅니다.

정리

  • pipe(fd)는 읽기 끝 fd[0]과 쓰기 끝 fd[1]을 만듭니다. pipe 다음에 fork, 그리고 각자 쓰지 않는 끝을 닫습니다.
  • 쓰기 끝 fd가 모두 닫혀야 read가 0(EOF)을 돌려줍니다. 읽기 끝 fd가 모두 닫히면 write는 SIGPIPE(무시하면 EPIPE)를 받습니다.
  • 비면 read가, 65536바이트가 차면 write가 잠듭니다. 4096바이트(PIPE_BUF) 이하의 write는 섞이지 않습니다.
  • dup2(old, new)로 파이프나 파일을 0 · 1번 자리에 놓으면 프로그램을 고치지 않고 연결을 바꿉니다. 셸의 |와 >가 이것입니다.
  • popen은 이 과정을 한 번에 해 주고(sh -c를 거칩니다), FIFO는 이름으로 만나게 해 줍니다. 규칙은 모두 같습니다.

파이프 프로그램이 오류 없이 멈춰 있다면 가장 먼저 ls -l /proc/PID/fd로 같은 파이프의 쓰기 끝(l-wx)을 누가 쥐고 있는지 봅니다.
