시그널: 종료 상태·처리·관찰

종료 상태 워드 해석, sigaction으로 시그널 잡기·무시하기, alarm과 EINTR·SA_RESTART, /proc의 시그널 마스크, 시그널 번호·이름 표를 다룬다.

실행해 볼 예제

  • exit_how자식을 exit·abort·SIGSEGV·SIGTERM 등으로 끝내고 부모가 waitpid의 status를 WIFEXITED/WIFSIGNALED/WIFSTOPPED/WIFCONTINUED로 해석해 raw 값과 함께 출력한다.
  • catch_intsigaction으로 SIGINT는 잡아서 세고(3번이면 종료), SIGTERM은 정리 후 종료, SIGQUIT은 무시하며, SIGKILL은 바꿀 수 없음(EINVAL)을 보여 준다.
  • timeout_readalarm으로 read에 시간 제한을 걸고, 핸들러 없음(기본 동작 종료)·핸들러 있음(EINTR)·SA_RESTART(read 재시작) 세 경우를 비교한다.
  • sigmask_show/proc/PID/status의 SigPnd·ShdPnd·SigBlk·SigIgn·SigCgt 비트마스크를 시그널 이름으로 풀어 보여 준다(인자가 없으면 자기 자신).
  • sig_names시그널 번호 1~31의 이름, strsignal 설명, 기본 동작(Term·Core·Stop·Cont·Ignore)을 표로 보여 주는 참조 도구다.

이 차시는 시그널의 기본을 다룹니다. 시그널이 어떻게 발생해서 전달되는지, 처분을 바꾸지 않았을 때 커널이 무엇을 하는지, sigaction으로 잡거나 무시하면 무엇이 달라지는지, 그리고 알람으로 기다림에 시간 제한을 거는 방법을 차례로 봅니다. 전체를 관통하는 방법은 하나입니다. 프로그램이나 셸이 스스로 보고한 값을 kill -l, /proc/PID/status, $?처럼 밖에서 보이는 값과 맞춰 보는 것입니다. 본문에 인용한 실행 결과는 Ubuntu 24.04(x86-64, 커널 6.8) 실습 서버에서 얻은 것입니다.

1부 시그널이란

폴링과 인터럽트

어떤 사건이 일어났는지 알아내는 방법은 크게 둘입니다. 첫째는 폴링으로, 사건이 있는지 반복해서 확인하는 방식입니다. 프로그램이나 드라이버가 상태를 읽어 보고 준비되었으면 처리합니다. 이 방식에서는 확인하는 쪽이 실행 순서를 정합니다. 대신 비용이 따릅니다. 쉬지 않고 확인하면(바쁜 대기) CPU를 계속 쓰고, 확인 사이에 잠들면 그 간격만큼 사건을 늦게 발견할 수 있습니다. 그렇다고 폴링이 항상 나쁜 것은 아닙니다. 사건이 매우 자주 오거나 짧은 지연이 중요하면 반복 확인이 오히려 유리할 수 있습니다.

둘째는 인터럽트로, 장치가 CPU에 사건을 통지하는 방식입니다. 키보드 입력이나 장치의 작업 완료가 하드웨어 IRQ를 발생시키면, CPU는 허용된 인터럽트를 받아 실행 문맥을 보존하고 커널의 인터럽트 처리 경로로 들어갑니다. 커널은 필요한 처리를 하거나 뒤로 미룬 뒤 복귀하고, 실행은 이어집니다. 기본 흐름은 하던 작업으로 돌아오는 것이지만 스케줄링 때문에 다른 작업이 실행될 수도 있습니다. 저장할 상태와 진입·복귀 절차는 CPU 아키텍처마다 다릅니다.

둘을 비교하면 다음과 같습니다.

  • 사건을 발견하는 주체: 폴링은 확인하는 쪽이 상태를 읽고, 인터럽트는 장치가 CPU에 처리 요청을 알립니다.
  • CPU 사용과 응답 지연: 폴링 간격을 줄이면 확인 비용이 늘어납니다. 인터럽트에는 진입·복귀 비용과 사건마다 드는 처리 비용이 있습니다.
  • 사건 빈도에 맞춘 조합: 드문 사건에는 통지가 유리한 경우가 많고, 고빈도 처리에서는 인터럽트와 폴링을 함께 쓰기도 합니다.

하드웨어 인터럽트와 시그널의 관계

시그널은 인터럽트와 닮았지만 놓인 계층이 다릅니다. 하드웨어 인터럽트는 CPU와 커널 사이의 경계에서 일어납니다. 장치 사건을 커널이 처리하며, 장치의 IRQ 처리기는 커널 코드입니다. 시그널은 커널과 프로세스 사이의 경계에서 일어납니다. 커널이 프로세스에 사건을 알리는 수단이고, 프로그램이 등록한 시그널 처리기는 사용자 코드입니다.

또 시그널에서는 발생 원인과 전달 시점을 구분해야 합니다. 시그널은 장치 사건뿐 아니라 kill이나 alarm으로도 발생합니다. 그리고 발생한 시그널은 보류되거나 블록될 수 있으므로 처리기가 즉시 실행된다는 보장이 없습니다.

프로그램 관점에서 폴링은 다음과 같은 모양입니다.

for (;;)
    if (이벤트가 있나?)
        처리();
    /* 없으면 다시 물어본다 */

통지 방식에서는 기다리는 동안 pause로 잠들어 있고, 이벤트가 오면 커널이 깨워서 처리하게 합니다. 이때의 이벤트가 시그널입니다. 시그널은 커널이 다른 프로세스(또는 자기 자신)에게 보내는 번호 하나짜리 사건이며, 도착하는 순간에 코드가 대기 중이어야 하는 것도 아닙니다. 그래서 시그널을 비동기 사건이라고 합니다. 폴링의 값은 순서를 내가 정한다는 데 있고, 통지의 값은 반복 확인을 줄인다는 데 있습니다. 대신 통지에서는 사건이 언제 오는지를 코드가 알지 못합니다.

시그널이 필요한 상황

  • 터미널에서 실행 중인 작업을 멈추고 싶을 때: Ctrl+C를 누르면 터미널 드라이버가 SIGINT를 발생시킵니다. 전달 대상은 포그라운드 프로세스 그룹에 속한 각 프로세스입니다. 각 프로세스의 반응은 제각각일 수 있습니다. 기본은 종료이지만 처리기를 등록했다면 처분이 달라집니다.
  • 서비스를 정리한 뒤 종료하고 싶을 때: 운영자가 kill -TERM PID를 실행하면 커널에 시그널 전달을 요청하는 것입니다. SIGTERM 처리기를 둔 서버는 이 요청에 맞춰 정리할 수 있습니다. 이때 핸들러는 종료 플래그만 기록하고 빠르게 돌아오고, 메인 흐름이 새 작업 받기를 멈추고 진행 중인 작업과 자원을 정리합니다.
  • 시간 만료나 자식의 상태 변화를 알고 싶을 때: alarm(5)는 SIGALRM 발생을 예약합니다. 자식이 종료하면 커널이 부모에게 SIGCHLD를 알립니다. 다만 SIGCHLD를 받는 것과 waitpid로 상태를 회수하는 것은 별개의 일입니다.
  • 응용 프로그램끼리의 약속: SIGHUP을 설정 다시 읽기에 쓰는 프로그램이 있습니다. 이것은 그 프로그램이 SIGHUP 처리기를 구현했을 때에만 가능한 사용법입니다. SIGUSR1·SIGUSR2로 상태 출력을 요청하는 것도 마찬가지로, 보내는 쪽과 받는 쪽이 의미를 약속한 것이며 커널이 용도를 정해 주지 않습니다. 그래서 기본 처분을 먼저 확인해야 합니다. SIGHUP·SIGUSR1·SIGUSR2의 기본 처분은 프로세스 종료입니다.

정리하면 시그널에는 두 측면이 있습니다. 하나는 발생 원인, 즉 누가 어떤 사건을 알렸는가입니다(키 입력, 다른 프로세스의 요청, 커널 타이머, 자식의 상태 변화). 다른 하나는 수신 측의 처분, 즉 프로그램이 어떻게 반응하는가입니다(기본 동작, 무시, 등록한 핸들러 실행 중 하나). 시그널은 사건의 통지에 적합한 수단입니다. 표준 시그널은 같은 종류의 보류가 하나로 합쳐지므로, 횟수를 세거나 대량의 데이터를 전달해야 한다면 별도의 IPC를 써야 합니다.

시그널의 생애: 발생 → 보류 → 전달 → 처분

  1. 발생(generated): 키보드, kill(2), 커널(오류), alarm 등이 시그널을 만듭니다.
  2. 보류(pending): 전달을 기다리는 상태입니다. 시그널마다 비트 한 칸으로 기록됩니다.
  3. 전달(delivered): 블록이 풀리는 순간 커널이 처분을 실행합니다. 블록 마스크가 전달의 관문 역할을 합니다.
  4. 처분(disposition): 기본 동작, 무시, 핸들러 실행 가운데 하나입니다.

여기서 두 가지를 기억해야 합니다. 첫째, 보류는 한 칸입니다. 같은 표준 시그널이 여러 번 와도 pending 비트는 한 칸이므로 하나로 합쳐지고(큐잉되지 않음), 몇 번 왔는지는 남지 않습니다. 실시간 시그널은 이 과목의 범위를 넘어섭니다. 둘째, 블록은 폐기가 아니라 지연입니다. 블록된 시그널은 버려지지 않고 보류 상태로 남아 있다가 마스크를 풀면 전달됩니다.

이 상태들은 /proc/PID/status의 다섯 줄로 관찰할 수 있습니다. SigPnd·ShdPnd(보류), SigBlk(블록), SigIgn(무시), SigCgt(잡음)입니다.

번호와 이름: kill -l

kill -l은 셸이 아는 시그널 번호와 이름의 표를 보여 줍니다. 실습 프로그램 sig_names가 같은 표를 C로 만듭니다.

  • 코드에서는 항상 SIGINT 같은 이름 매크로를 씁니다. 번호는 아키텍처마다 다를 수 있기 때문입니다.
  • 1–31이 표준 시그널입니다. 34 이후의 SIGRTMIN+는 실시간 시그널이며, 표준 시그널과 달리 큐잉됩니다.
  • 셸에서 번호와 이름을 서로 바꿔 볼 수 있습니다. kill -l 11은 SEGV를, kill -l TERM은 15를 돌려줍니다. 뒤에서 비트를 관찰할 때 매우 유용합니다.

키보드가 보내는 시그널과 $?

시그널로 끝난 명령에 대해 셸은 $?에 128 + 시그널 번호를 남깁니다.

  • Ctrl-C는 SIGINT(2)를 보내므로 $?는 130(128+2)입니다.
  • Ctrl-\는 SIGQUIT(3)을 보내므로 131입니다. 이때 셸이 출력하는 Quit (core dumped)는 이 시그널의 기본 동작이 Core라는 뜻입니다.
  • Ctrl-Z 뒤에는 148이 보입니다. 다만 Ctrl-Z로 정지한 작업은 종료된 것이 아닙니다. kill %1이 보내는 SIGTERM이 그 작업을 끝내고, 셸은 Terminated라고 알립니다.

$? 규칙과 wait status의 대응

같은 끝남을 셸과 커널은 서로 다르게 표현합니다. 셸의 규칙은 정상 종료면 종료 코드 그대로, 시그널 종료면 128+n입니다. 예를 들어 exit(3)으로 끝나면 3, Ctrl-C면 130, Ctrl-\면 131입니다. 커널은 같은 사실을 wait status라는 비트 묶음으로 기록합니다. wait status는 int이지만 하위 16비트만 정의되어 있습니다(man 2 wait).

끝남raw status읽는 법
exit(3)0x0300종료 코드 3이 상위 8비트에 있습니다.
SIGQUIT + core0x0083시그널 번호 3에 코어 비트 0x80이 더해진 값입니다.
SIGTERM0x000f15 = 0x0f입니다.

이 raw 값은 waitpid가 채워 주는 int 하나입니다. 비트 배치를 직접 세지는 않습니다. WIFEXITED 같은 매크로로 판정하는 것이 표준입니다. 또 코어 비트 0x80은 "코어를 남기려 했다"는 보고일 뿐이고, 파일이 실제로 남는지는 2부에서 볼 별개의 조건이 결정합니다.

exit_how: raw status 직접 보기

exit_how는 부모가 자식을 만들고, 자식이 끝난 방식을 waitpid가 준 status로 읽어 0x%04x 형식으로 출력하는 관찰 도구입니다.

  • 0x0300: exit(3). 종료 코드 3이 상위 8비트에 있는 정상 종료입니다.
  • 0x0086: abort()가 자기에게 SIGABRT(6)를 보낸 경우입니다. 0x80 자리의 8은 코어 비트가 켜졌다는 뜻입니다.
  • 0x000f: raise(SIGTERM). 코어 비트가 없는, Term 동작의 모습입니다.

순서가 중요합니다. 먼저 WIF*로 어떤 끝남인지 판정하고, 그 판정이 참일 때에만 짝이 되는 매크로로 값을 읽습니다. 순서를 섞으면 의미 없는 값을 읽게 됩니다. 그리고 정지는 종료가 아닙니다. WIFSTOPPED는 프로세스가 아직 살아 있다는 보고이고, WIFCONTINUED는 다시 달린다는 보고입니다. 이 두 보고는 waitpid에 WUNTRACED와 WCONTINUED를 켰기 때문에 볼 수 있습니다.

처분을 바꾸지 않으면 이 표의 동작이 일어나고, 처분을 바꾸는 도구가 3부의 sigaction입니다. Core는 종료에 더해 디버깅 재료를 저장하는 동작입니다. Ignore는 단순한 버림이 아닙니다. CHLD의 Ignore처럼 커널이 알아서 처리하는 종류도 있습니다.

코어 파일이 남는 조건

코어는 프로세스가 죽은 순간의 메모리 사진이고, gdb로 열어 원인을 살피는 재료입니다. 코어 파일은 다음 세 조건이 모두 갖춰져야 남습니다.

  1. 시그널의 기본 동작이 Core여야 합니다. QUIT(3)·ABRT(6)·SEGV(11)·FPE(8)·ILL(4)·BUS(7) 등이 그렇습니다.
  2. RLIMIT_CORE가 0보다 커야 합니다. 셸에서는 ulimit -c로 봅니다. 0이면 코어가 남지 않고, unlimited면 제한이 없습니다.
  3. 기록 경로가 정해져 있어야 합니다. /proc/sys/kernel/core_pattern에 파일 이름 템플릿 또는 |로 시작하는 파이프(수집기)가 적혀 있습니다.

core_pattern이 파일 이름 템플릿이면 core.%p 같은 규칙으로 현재 디렉터리에 코어가 남습니다. 파이프면 수집기가 정한 곳에 남습니다. 실습 서버인 Ubuntu는 파이프 방식입니다. 프로세스가 Core 시그널로 죽으면 커널이 core_pattern을 읽어 apport에 파이프로 넘기고, apport가 /var/lib/apport/coredump에 기록합니다. 관찰한 실행에서는 307200바이트의 코어가 남았고, 파일 이름에는 원래 실행 파일의 경로가 들어 있었습니다.

ulimit -c 0으로 코어를 닫아 두면 abort로 죽어도 코어 파일은 만들어지지 않습니다. 그런데도 "core dumped" 문구는 그대로 붙습니다. WCOREDUMP 비트는 "코어를 남기려 했다"는 보고이고, 파일이 실제로 남는지는 위 조건들이 결정하기 때문입니다. 코어를 열 때는 다음처럼 서브셸 안에서만 제한을 풀면 나머지 셸은 그대로 닫혀 있습니다.

(ulimit -c unlimited; ./exit_how abort)

$?로 확인하는 시그널 종료: TERM과 KILL

  • 143 = 128 + 15. SIGTERM(15)으로 종료된 자식에 대한 셸의 보고입니다. exit_how가 보여 준 raw 0x000f와 같은 사실을 가리킵니다.
  • 137 = 128 + 9. SIGKILL(9)입니다. 잡을 수 없는 시그널이므로 기본 동작이 반드시 일어납니다.
  • 셸이 출력하는 Terminated 줄은 셸이 자식의 상태 변화를 통지받았다는 뜻입니다. 이 통지를 맡는 SIGCHLD는 다음 차시의 주제입니다.

정지와 재개의 보고: WUNTRACED · WCONTINUED

정지와 재개는 waitpid에 WUNTRACED|WCONTINUED를 켜야 보고가 들어옵니다. exit_how wait로 자식을 대기시켜 놓고 밖에서 시그널을 보내면 다음을 볼 수 있습니다.

  • SIGSTOP을 보내면 "stopped by signal 19" 보고와 함께 raw 0x137f가 나옵니다. 이 값에는 정지 시그널 번호 19(0x13)가 담겨 있습니다.
  • SIGCONT를 보내면 "continued" 보고가 나오고 raw는 0xffff입니다. 이것은 어떤 값이 아니라 "계속됨"을 나타내는 표시의 모양이며, 시그널 번호를 담지 않습니다.
  • SIGUSR1을 보내면 기본 동작이 Term이므로 자식이 종료합니다. 종료 보고가 나와야 비로소 부모는 대기 루프를 끝냅니다.

시그널을 보내는 네 가지 길

kill이라는 이름은 "죽이기"가 아니라 "시그널을 보낸다"는 뜻입니다. 보내는 쪽이 누구든 받는 쪽은 같은 번호를 받습니다.

  • 터미널 드라이버: Ctrl-C → INT, Ctrl-\ → QUIT, Ctrl-Z → TSTP, 창 닫기 → HUP.
  • kill(1) 명령: kill -TERM 3356658, kill %1, pkill, killall.
  • C 함수: kill(2), raise(3). abort()는 자기 자신에게 ABRT를 보냅니다.
  • 커널: 오류에 따른 SEGV·FPE·ILL·BUS, alarm 만료에 따른 ALRM, 그리고 CHLD.

kill(2)는 pid로 대상을 정하며, 성공하면 0, 실패하면 -1을 반환하고 errno(EPERM, ESRCH 등)를 설정합니다. raise(3)는 자기 자신에게 보내는 kill(getpid(), sig)입니다. 받는 쪽은 기본적으로 누가 보냈는지 알 수 없습니다. 필요하다면 SA_SIGINFO 핸들러가 받는 siginfo를 쓰는데, 이것은 다음 차시에서 다룹니다.

3부 잡기 · 무시 · 마스크

sigaction으로 처분을 바꾸고, 그 결과를 /proc/PID/status로 확인합니다.

처분 세 가지와 struct sigaction

sigaction(2)은 시그널 처분을 다루는 POSIX 표준 인터페이스입니다. 처분은 프로세스마다, 시그널마다 한 칸씩 있습니다. 그 칸에 들어갈 수 있는 것은 셋입니다.

  • SIG_DFL: 기본 동작(2부의 다섯 동작)으로 돌아갑니다.
  • SIG_IGN: 전달되어도 아무 일도 하지 않습니다. 뒤에서 볼 상속 규칙의 주인공입니다.
  • 핸들러: 시그널이 오면 지금 흐름을 잠깐 멈추고 실행되는 함수입니다.
int sigaction(int sig,
              const struct sigaction *act,
              struct sigaction *oldact);

성공하면 0, 실패하면 -1을 반환하고 errno를 설정합니다. sig에는 SIGINT 같은 이름 매크로를 씁니다. oldact가 NULL이 아니면 이전 처분을 돌려주므로 저장했다가 복원할 수 있습니다. struct sigaction의 주요 필드는 다음과 같습니다.

  • sa_handler: SIG_DFL, SIG_IGN, 또는 함수 포인터.
  • sa_mask: 핸들러가 실행되는 동안 추가로 블록할 시그널 집합(sigset_t). 이와 별개로, 핸들러 실행 동안에는 그 시그널 자신이 자동으로 블록됩니다.
  • sa_flags: SA_RESTART, SA_SIGINFO 등의 조정 비트.

signal()이 아니라 sigaction()을 쓰는 이유

signal(SIGINT, on_int);  /* 의미가 시스템마다 다르다 */

signal()은 시스템마다 의미가 다릅니다. System V 계열에서는 핸들러가 끝난 뒤 시스템 호출이 깨어나 -1, EINTR로 돌아올 수 있고, BSD 계열은 자동으로 재시작하는 경향이 있습니다. 같은 코드가 플랫폼에 따라 다르게 흐르면 재현하고 설명하기가 어렵습니다. sigaction은 "어느 쪽이냐"를 묻던 것을 "내가 정한다"로 바꿉니다.

struct sigaction sa;
memset(&sa, 0, sizeof sa);
sa.sa_handler = on_int;
sigemptyset(&sa.sa_mask);
sa.sa_flags = SA_RESTART; /* 원하는 것만 명시 */
sigaction(SIGINT, &sa, NULL);

재시작 여부(SA_RESTART), 핸들러 형태(SA_SIGINFO), 추가 블록(sa_mask)을 코드가 직접 정하므로 계약이 명시됩니다. 또 POSIX 표준이므로 시스템이 바뀌어도 같은 계약으로 읽힙니다. 이 수업의 모든 예제는 sigaction으로 통일합니다.

catch_int: 잡고, 무시하고, 거절당하고

catch_int는 네 시그널에 서로 다른 처분을 시도합니다. SIGINT는 잡아서 세고 세 번째에 끝납니다. SIGTERM은 잡아서 정리 메시지를 내고 끝납니다. SIGQUIT는 무시하므로 Ctrl-\를 눌러도 아무 일이 없습니다. SIGKILL은 바꾸려 해 보지만 거절당합니다.

  • 시작하자마자 나오는 sigaction(SIGKILL): Invalid argument 한 줄은 SIGKILL을 SIG_IGN으로 바꾸려는 호출이 -1과 EINVAL로 거절된 결과입니다. 처분 변경 자체가 금지되어 있습니다.
  • [handler] SIGINT 줄은 핸들러가 write로 찍은 것입니다. printf를 쓰는 출력(main: SIGINT #n)은 핸들러가 아니라 main이 맡습니다.
  • 세 번 세고 나면 종료 코드 0으로 정상 종료합니다. 시그널을 받았더라도 직접 다뤘다면 종료 코드는 프로그램이 정합니다. kill -TERM을 받았을 때도 정리 메시지를 내고 0으로 끝납니다.

이 프로그램은 처분 등록을 작은 래퍼 함수 하나로 모읍니다. 구조체를 memset으로 0부터 채워 필드 누락 버그를 막고, 빈 마스크와 sa_flags = 0(재시작하지 않음)을 지정한 뒤 sigaction의 반환값을 그대로 돌려주어 호출한 쪽이 성공 여부를 판정하게 합니다. 핸들러와 main이 함께 쓰는 변수는 다음처럼 선언합니다. 이것이 비동기적으로 읽고 쓰는 공유 변수의 최소 요건입니다.

static volatile sig_atomic_t ints = 0;
static volatile sig_atomic_t got_term = 0;

SIGINT 핸들러는 write 한 줄과 ints++만 하고, SIGTERM 핸들러는 got_term = 1만 합니다. main은 pause()로 잠들었다가 핸들러가 끝나 돌아오면, 핸들러가 센 횟수(ints)와 자기가 출력한 횟수(seen)의 차이만큼 출력합니다.

while (!got_term && ints < 3) {
    pause();                /* 잡은 시그널의 핸들러가 끝나면 돌아온다 */
    while (seen < ints)
        printf("main: SIGINT #%ld\n", ++seen);
    fflush(stdout);
}

플래그 검사와 pause 사이에 생기는 경쟁은 다음 차시(sigsuspend)에서 다룹니다.

핸들러 작성 규칙: 비동기라는 전제

핸들러 안에서 해도 되는 것은 제한적입니다.

  • write(STDOUT_FILENO, msg, len). write(2)는 안전한 함수 목록(man 7 signal-safety)에 있습니다.
  • volatile sig_atomic_t 플래그를 0과 1 사이에서 바꾸거나 ++하는 것.
  • errno를 저장했다가 복원하는 것(saved = errno; … errno = saved;).
  • 핸들러 안에서 다시 시그널을 기다리지는 않습니다.

하지 말아야 할 것(비동기 안전하지 않은 것)은 다음과 같습니다.

  • printf / fprintf: stdio의 내부 상태와 잠금을 건드립니다.
  • malloc / free: 힙 할당자의 상태를 건드립니다.
  • exit: atexit 핸들러와 stdio 정리를 실행합니다.
  • 그 밖에 잠금을 기다리는 모든 코드.

이유는 핸들러가 main의 어느 명령 중간에라도 끼어들어 실행될 수 있기 때문입니다. main이 printf의 내부 버퍼를 고치고 있는 도중에 핸들러가 printf를 또 실행하면 그 상태는 정의되지 않습니다. 그래서 이 수업의 예제는 "핸들러는 플래그만, 출력은 main"이라는 패턴을 고정해서 씁니다.

/proc/PID/status의 Sig* 다섯 줄

/proc/PID/status의 Sig* 줄은 커널이 프로세스마다 유지하는 시그널 상태를 들여다보는 창입니다.

줄기록하는 것관찰한 예
SigPnd · ShdPnd보류 중(전달 대기)인 시그널백그라운드 catch_int: 0 — 아직 사건 없음
SigBlk블록 마스크(전달 지연)bash: CHLD / catch_int: 0
SigIgn처분이 SIG_IGN인 시그널catch_int: QUIT / nohup: HUP
SigCgt핸들러를 세운 시그널catch_int: INT TERM / bash: 다수

값은 0x0000000000004002처럼 16자리 16진수로 적힌 64비트 마스크입니다. 왼쪽이 큰 번호이고 오른쪽 끝이 비트 0이며, 비트 n-1이 시그널 n에 해당합니다. SigPnd는 스레드별 보류, ShdPnd는 프로세스 전체의 보류이고, 지금은 ShdPnd 위주로 봅니다.

catch_int를 백그라운드로 띄우고 이 줄들을 읽으면 프로그램의 sigaction 호출과 비트가 그대로 일치합니다.

  • SigIgn이 0x04입니다. QUIT이 3번이므로 1<<(3-1)입니다. SIG_IGN으로 설정한 것이 그대로 보입니다.
  • SigCgt가 0x4002입니다. INT(2)의 비트 1과 TERM(15)의 비트 14를 합친 값입니다. kill -l로 번호를 대응해 보면 됩니다.
  • SigBlk는 0입니다. 지금은 블록한 것이 없고, 핸들러가 실행되는 순간에만 그 시그널 자신이 잠시 블록됩니다.

이 비트를 이름으로 풀어 주는 도구가 sigmask_show입니다. 인자로 PID를 주면 /proc/PID/status를, 인자가 없으면 /proc/self/status를 열어 Name·Pid 줄과 Sig* 다섯 줄만 골라 읽습니다. 각 줄에서 이름과 마스크를 뽑은 뒤 1번부터 64번까지 비트를 하나씩 검사합니다.

for (int sig = 1; sig <= 64; sig++) {
    if (!(mask & (1ULL << (sig - 1))))
        continue;
    if (sig < 32)
        printf(" %s", names[sig]);
    else
        printf(" RT%d", sig);
}

이름 표는 x86-64 Linux 번호 기준이고, 32 이상은 RT(실시간)로 적습니다. /proc가 없는 환경(macOS)에서는 파일 열기가 실패해 오류 메시지를 내고 끝나는데, 이것은 정상적인 실패 경로입니다.

셸의 마스크: bash가 무엇을 잡고 무시하나

sigmask_show를 인자 없이 실행하면(자기 자신 조회) 모든 줄이 0입니다. 아무 처분도 바꾸지 않은 프로세스는 기본 동작이 그대로라는 뜻입니다. 반면 ./sigmask_show $$로 bash를 조회하면 모습이 다릅니다. bash는 CHLD를 블록해 두고(SigBlk) 자기가 준비된 때에만 받는데, 이는 작업 제어를 위한 준비입니다. 그리고 INT·CHLD·WINCH 등 많은 시그널을 핸들러로 잡고 있습니다(SigCgt). 셸이 대화형 서비스라는 증거입니다.

처분의 상속: fork와 exec의 경계

  • fork에서는 처분 표가 전부 복사됩니다. SigIgn·SigCgt·SigBlk가 모두 유지됩니다.
  • exec에서는 SIG_IGN은 유지되고, 핸들러는 기본 동작으로 초기화됩니다. 블록 마스크와 보류는 유지됩니다.

이렇게 나뉘는 이유는 분명합니다. 핸들러는 이전 프로그램의 코드 주소인데, 새 프로그램에는 그 코드가 존재하지 않습니다. 반면 무시는 "받지 않겠다"는 의도이므로 프로그램이 바뀌어도 살아남습니다.

이 규칙의 흔적을 sigmask_show로 볼 수 있습니다.

  • 그냥 실행한 sleep은 전부 0입니다. 처분 변경이 없습니다.
  • nohup sleep 30은 SigIgn에 HUP 비트(1<<(1-1))가 켜져 있습니다. nohup이 HUP를 SIG_IGN으로 세워 두고 exec했고, 그 비트가 살아남은 것입니다.
  • 셸에서 trap '' INT로 무시해 둔 INT도 exec 후에 유지됩니다(1<<(2-1)).

막을 수 없는 두 시그널

SIGKILL(9)과 SIGSTOP(19)은 처분을 바꿀 수 없습니다. sigaction(SIGKILL, …)은 항상 EINVAL이며, 블록도 무시도 불가능합니다. 어떤 프로세스든 반드시 멈출 수 있어야 시스템이 관리 가능하다는 설계이기 때문입니다. SIGSTOP은 사용자가 잡을 수 없는 정지이고, Ctrl-Z가 보내는 TSTP는 잡을 수 있는 정지라는 점이 다릅니다. 성격이 다른 제어 시그널도 있습니다. CONT(18)는 Stop된 프로세스에만 작동합니다.

한 줄로 줄이면, 처분은 sigaction으로 세우고(잡기·무시) 그 결과는 /proc/PID/status의 비트로 교차 확인합니다. SigBlk를 프로그램이 직접 다루는 sigprocmask와 sigsuspend는 다음 차시의 주제입니다.

4부 알람과 재시작

기다림에 시간 제한을 걸고, 시그널 때문에 깨어난 시스템 호출을 어떻게 다루는지 봅니다.

alarm: 일정 시간 뒤에 SIGALRM

alarm(2)는 초 단위로 SIGALRM 발생을 예약합니다. alarm(3)을 호출하면 3초 뒤에 SIGALRM이 도착합니다. 더 정밀한 예약 수단으로 timer_create와 timerfd가 있지만 여기서는 이름만 소개합니다.

  • 프로세스당 하나: 알람은 한 프로세스에 하나뿐입니다. 예약이 남아 있을 때 다시 호출하면 이전 예약을 갈아 끼우고 남은 초를 반환합니다.
  • 핸들러가 없으면: SIGALRM의 기본 동작은 Term이므로 알람이 프로그램을 죽입니다. 핸들러가 있으면 핸들러가 실행된 뒤 원래 흐름으로 복귀합니다.
  • alarm(0)은 취소: 남은 예약을 지웁니다. 작업이 먼저 끝났을 때 호출하는 정리 코드입니다.

느린 시스템 호출과 EINTR, SA_RESTART

read·write·accept처럼 길게 기다릴 수 있는 호출을 느린 시스템 호출(slow syscall)이라고 합니다. 이런 호출에서 대기하는 중에 시그널이 오면 호출이 깨어납니다. 그 뒤의 일은 처분을 세울 때의 플래그에 따라 둘로 갈립니다.

  1. 플래그 0: 핸들러가 실행된 뒤 read()가 -1을 반환하고 errno는 EINTR이 됩니다. 처분을 새로 세울 때 플래그를 주지 않으면 이것이 기본입니다.
  2. SA_RESTART: 핸들러가 실행된 뒤 커널이 read()를 다시 시작하게 하여, 호출이 계속 기다리다가 나중에 성공합니다. 단, 이 플래그가 모든 호출에 적용되지는 않습니다.

EINTR은 "인터럽트되어 아직 아무것도 하지 않았다"는 뜻입니다. 형식상 실패이지만 다시 시도하면 됩니다.

timeout_read: 세 모드의 대비

timeout_read는 alarm으로 read에 시간 제한을 겁니다. 같은 알람(2초), 같은 입력(4초 뒤에 도착하는 파이프 입력)을 두고 처분 하나만 바꿔 세 번 실행합니다.

(sleep 4; echo hello) | ./timeout_read default 2; echo "exit=$?"
(sleep 4; echo hello) | ./timeout_read norestart 2; echo "exit=$?"
(sleep 4; echo hello) | ./timeout_read restart 2; echo "exit=$?"
  • default → 142: 핸들러가 없으므로 SIGALRM의 기본 동작(Term)으로 죽습니다. 142 = 128 + 14입니다.
  • norestart → EINTR: 시그널을 잡았지만 read가 -1, EINTR로 돌아옵니다. 알람이 울린 2.00초에 깨어나 타임아웃으로 보고합니다.
  • restart → 성공: 핸들러는 똑같이 실행되지만 read가 재개되어 4초 뒤에 입력 6바이트를 받습니다.

세 모드의 차이는 소스에서 한 줄입니다. default 모드만 sigaction 호출을 건너뛰어 처분을 바꾸지 않은 대조군이 되고, 나머지 두 모드는 다음 플래그만 다릅니다.

sa.sa_flags = strcmp(argv[1], "restart") == 0 ? SA_RESTART : 0;

알람을 예약하고 읽는 부분은 다음과 같습니다. read에서 돌아오자마자 errno를 saved에 옮기고, alarm(0)으로 남은 예약을 지웁니다. 경과 시간은 CLOCK_MONOTONIC으로 잽니다.

alarm((unsigned)sec);
ssize_t n = read(STDIN_FILENO, buf, sizeof buf);
int saved = errno;
alarm(0);                   /* 남은 알람 취소 */

EINTR을 다루는 표준 패턴

ssize_t n;
do {
    n = read(fd, buf, sizeof buf);
} while (n == -1 && errno == EINTR);   /* 깨었으면 다시 기다린다 */
if (n == -1) {                          /* EINTR 외의 진짜 실패 */
    int saved = errno;
    fprintf(stderr, "read fd=%d: %s\n", fd, strerror(saved));
    return 1;
}
  • EINTR은 진짜 실패가 아니라 "아무것도 하지 않고 깼다"는 뜻이므로, 루프로 다시 호출하면 원래 의미가 유지됩니다.
  • errno는 저장해서 씁니다. 호출 뒤에 다른 호출이 errno를 덮어쓸 수 있으므로 판정하고 출력하기 전에 saved에 옮겨 둡니다.
  • SA_RESTART를 켰다면 이 루프는 돌지 않습니다. 두 방법은 함께 써도 안전합니다.

5부 정리

질문별 관찰 창

사건은 순간에 지나가므로, 커널이 남긴 기록(비트와 status)을 읽는 것이 관찰의 핵심입니다.

질문프로그램 안(표준 API)밖에서 관찰
무엇이 왔나waitpid의 WIF* · WTERMSIG셸 $?(=128+n) · ps STAT
어떤 처분인가sigaction 조회(oldact)/proc/PID/status의 SigCgt · SigIgn
지금 보류인가sigpending (다음 차시)status의 SigPnd · ShdPnd
무엇을 막았나sigprocmask (다음 차시)status의 SigBlk
어떻게 끝났나wait status 매크로echo $? · Quit (core dumped)

이것으로 할 수 있는 일

순서는 관찰이 먼저이고 처분 변경은 그다음입니다.

  • Ctrl-C를 무시하는 도구: 긴 작업을 하는 도구가 INT를 SIG_IGN으로 세워 두면 실수로 죽지 않습니다.
  • 정리 종료를 갖춘 서비스: TERM을 잡아 "정리 후 exit 0"으로 끝냅니다. catch_int가 보여 준 패턴입니다. KILL은 잡을 수 없다는 점을 함께 기억합니다.
  • 타임아웃 걸기: alarm과 EINTR로 기다림에 시간을 겁니다. timeout_read의 norestart 모드가 바로 그것입니다.
  • 정지·좀비 자식 진단: $?, waitpid 보고, ps STAT의 T·Z로 자식이 무슨 사건을 겪었는지 판정합니다. 10주차의 기초가 됩니다.
  • 시그널 상태 진단: sigmask_show처럼 /proc status의 Sig*를 읽어 누가 무엇을 잡고, 무시하고, 막았는지 봅니다.
  • 코어 덤프 준비: ulimit -c와 core_pattern을 확인해 두면 충돌을 재현했을 때 gdb로 원인을 볼 수 있습니다.

참조 도구 sig_names

sig_names는 kill -l에 대응하는 번호·이름·기본 동작 표를 C로 만든 참조 도구입니다. 인자가 없으면 1–31을 표로 출력하고, 번호 하나를 주면 그 번호의 이름, strsignal(3)이 주는 설명, 기본 동작을 한 줄로 출력합니다. strsignal은 번호를 시스템이 제공하는 설명 문자열로 바꾸는 함수입니다. 이름 표는 sigmask_show와 같은 것을 쓰고, 기본 동작 표는 man 7 signal의 표를 T(Term)·C(Core)·S(Stop)·c(Cont)·I(Ignore) 글자로 옮긴 것입니다. 두 표 모두 x86-64 Linux 번호 기준이며 같은 번호가 환경마다 다른 시그널을 가리킬 수 있으므로, kill -l, strsignal 열, signal(7) 매뉴얼과 서로 대조해 보라는 것이 이 도구의 취지입니다. 32–64의 실시간 범위는 이 과목에서 다루지 않습니다.

확인 문제

  1. Ctrl-C로 끝난 프로그램의 $?는 몇이고, 그 규칙은 무엇입니까? — 130이며, 규칙은 128 + 시그널 번호입니다.
  2. exit_how segv의 raw status 0x008b에서 코어 비트와 시그널 번호를 각각 찾으십시오. — 코어 비트 0x80이 켜져 있고, 하위 7비트가 0x0b = 11(SEGV)입니다.
  3. sigaction(SIGKILL, …)이 실패하는 이유를 시스템 관리 관점에서 설명하십시오. — 어떤 프로세스든 반드시 종료·정지시킬 수 있어야 시스템이 관리 가능하기 때문입니다.
  4. nohup sleep 30의 SigIgn에 HUP 비트가 남아 있는 이유를 exec 규칙으로 설명하십시오. — exec 후에도 SIG_IGN은 유지되는데, nohup이 HUP를 SIG_IGN으로 세워 두었기 때문입니다.
  5. 같은 알람에서 norestart와 restart 모드가 다르게 끝나는 이유는 무엇입니까? — norestart에서는 read가 -1·EINTR로 깨어 타임아웃이 되고, restart에서는 커널이 read를 재개해 입력을 받습니다.

정리

  • 시그널은 커널이 프로세스에 보내는 번호 하나짜리 비동기 사건입니다.
  • 생애는 발생 → 보류(비트 한 칸) → 전달 → 처분이고, 표준 시그널은 합쳐집니다.
  • 기본 동작은 Term·Core·Stop·Cont·Ignore 다섯 가지입니다.
  • 종료는 셸에서는 $? = 128+n으로, 프로그램에서는 wait status를 매크로로 판정해 읽습니다.
  • 처분은 sigaction으로 세우고, 결과는 /proc/PID/status의 Sig* 비트로 교차 확인합니다.

더 읽을 자료는 man 7 signal, man 2 sigaction, man 5 proc_pid_status, man 7 signal-safety입니다. 다음 차시에서는 sigprocmask로 블록과 보류를 다루고, 검사와 대기 사이의 틈을 sigsuspend가 어떻게 없애는지, SIGCHLD를 잡아 waitpid(WNOHANG)으로 자식을 수거하는 방법, 두 프로세스가 kill로 SIGUSR1·SIGUSR2를 주고받는 실험을 봅니다.
