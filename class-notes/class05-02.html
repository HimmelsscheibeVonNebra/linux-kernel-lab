지난 시간에는 프로그램이 바깥을 보았습니다. 시스템 이름, 페이지 크기, 열린 파일 한계를 조회했습니다. 이번 시간의 주제는 시간입니다. 지금이 몇 시인지 알아내고, 코드가 얼마나 걸렸는지 재고, 그 둘을 로그 한 줄에 함께 남기는 방법을 다룹니다. 수업 전체를 관통하는 질문은 하나입니다. 이 시간은 보여 줄 용도인가, 잴 용도인가.

왜 시간을 다루는가

시간이 들어가는 코드는 생각보다 많습니다. 대표적인 용도는 네 가지입니다.

  • 로그: 사건에 타임스탬프를 남겨 두었다가 나중에 일어난 순서를 재구성합니다.
  • 측정: 코드가 얼마나 오래 걸리는지 초나 밀리초로 잽니다.
  • 판정: 타임아웃, 만료, 유효 기간을 시각과 비교해 결정합니다.
  • 정렬: 파일과 기록을 시각 순서로 세웁니다.

문제는 이 용도들이 서로 다른 시계를 요구한다는 점입니다. 벽시계와 스톱워치가 다른 물건인 것과 같습니다. 벽시계는 절대 시각을 보여 주는 도구이고, 스톱워치는 흐른 시간을 재는 도구입니다. 사람이 읽는 시각은 벽시계에서 얻어야 하고, 짧은 구간의 측정은 거꾸로 가지 않는 시계에서 얻어야 합니다. 그래서 이번 시간의 원칙은 표시할 때는 달력 시간, 잴 때는 단조 시계입니다. 달력 시간은 "언제"에 답하고 경과 시간은 "얼마나"에 답합니다. 지난 시간에 잠깐 본 CLK_TCK도 이 이야기와 이어집니다.

수업은 달력 시간(1부), 경과 시간(2부), 둘을 합친 타임스탬프 로그(3부), 시계 선택과 남은 함정(4부) 순서로 진행합니다. 여기서 나오는 호출은 모두 <time.h> 하나에 모여 있습니다.

1부 달력 시간

1부에서는 지금이 몇 년 몇 월 며칠 몇 시인지를 숫자로 얻고, 그 숫자를 사람이 읽는 문자열로 바꿉니다. 등장하는 자료형은 time_t와 struct tm 두 가지입니다.

time(2)과 time_t

time_t는 에포크, 곧 1970-01-01 00:00:00 UTC부터 지난 초를 담는 정수입니다. 해상도는 초 단위입니다. 달력 시간의 용도는 날짜와 시각을 나타내는 것이지 정밀 측정이 아니므로 이 정도면 충분하고, 더 세밀한 측정은 2부의 struct timespec이 맡습니다.

  • time(&t) 또는 time(NULL)은 현재 시각의 time_t를 돌려줍니다. 실패하면 (time_t)-1입니다.
  • difftime(3)은 두 time_t의 차를 초 단위 실수로 돌려줍니다.

time_t는 산술형이고 보통 64비트 정수입니다. 32비트 time_t는 2038년에 넘칩니다. 두 시각을 직접 빼도 되지만, 오버플로 없이 비교하는 공식적인 방법은 difftime입니다.

calendar_demo: 시각 조회와 출력

calendar_demo의 앞부분은 달력 시간을 다루는 기본 흐름을 그대로 보여 줍니다. time으로 초를 얻고, localtime으로 연·월·일·시·분·초로 분해한 뒤, strftime으로 사람이 읽는 문자열을 만듭니다. 이 가운데 화면에 바로 쓸 수 있는 문자열을 주는 함수는 strftime 하나뿐입니다. 나머지는 숫자나 구조체를 주므로 문자열로 바꾸는 마지막 단계가 반드시 필요합니다.

time_t now = time(NULL);
if (now == (time_t)-1) { perror("time"); return 1; }

struct tm *tm = localtime(&now);
if (tm == NULL) { perror("localtime"); return 1; }

char buf[64];
size_t n = strftime(buf, sizeof buf,
        "%Y-%m-%d %H:%M:%S %Z", tm);
if (n == 0)             /* 버퍼가 작으면 0 */
    return 1;
printf("local=%s\n", buf);

세 호출 모두 실패 경로가 있고, 실패를 알리는 값이 서로 다릅니다. time은 -1, localtime은 NULL, strftime은 0입니다. strftime은 결과가 버퍼보다 길면 아무것도 쓰지 않고 0을 돌려주고, 성공하면 0이 아닌 길이를 돌려줍니다. 따라서 0인지 확인하는 것이 곧 오류 검사입니다. gmtime은 같은 변환을 UTC 기준으로 수행합니다. 완성된 calendar_demo는 UTC 문자열과 difftime 결과까지 출력합니다.

date(1) 명령과 비교

셸의 date 명령은 같은 정보를 다른 형식으로 보여 줍니다. date도 내부에서는 같은 변환 함수들을 쓰기 때문에, 프로그램의 출력과 명령의 출력을 맞대어 교차 확인할 수 있습니다.

$ date +%s
1790493335
$ date
2026. 09. 27. (일) 16:15:35 KST
$ date -u
Sun Sep 27 07:15:35 UTC 2026

# TZ 환경변수로 시간대를 바꿔 본다
$ TZ=Asia/Seoul date
2026. 09. 27. (일) 16:15:35 KST
$ TZ=UTC date
Sun Sep 27 07:15:35 UTC 2026
  • date +%s는 에포크 초를 그대로 출력합니다. calendar_demo가 출력하는 epoch 값과 같은 숫자여야 합니다.
  • TZ 환경변수는 프로세스의 시간대를 정합니다. date가 보여 주는 시각이 바뀌는 것과 같은 방식으로, 프로그램 안의 localtime도 이 값을 봅니다.

TZ를 바꾼다고 시각 자체가 달라지는 것은 아닙니다. 같은 순간을 어느 시간대로 보여 주느냐가 달라질 뿐입니다. 출력 형식은 로캘에 따라 달라지므로(위 예시는 Ubuntu 22.04 환경입니다), 글자 모양이 아니라 값의 구조를 비교합니다.

struct tm과 변환 함수

struct tm은 시각을 연·월·일·시·분·초 필드로 쪼개 담는 구조체입니다. time_t와 struct tm 사이를 오가는 함수는 방향에 따라 나뉩니다.

  • localtime / gmtime: time_t를 각각 지역 시간대와 UTC 기준의 struct tm으로 분해합니다. struct tm 포인터를 돌려주며 실패하면 NULL입니다.
  • mktime: 반대로 struct tm을 time_t로 되돌립니다. 범위를 벗어난 값은 다음 달로 넘기는 식으로 정규화해 줍니다.

주의할 필드가 두 개 있습니다. tm_mon은 0부터 세므로 0이 1월이고 11이 12월입니다. tm_mon이 9라면 10월입니다. 월 이름표 같은 배열의 인덱스로 바로 쓰기 좋게 한 설계입니다. tm_year는 1900년 기준 오프셋이라 1900을 더해야 실제 연도가 됩니다.

asctime과 ctime은 고정된 형식의 문자열을 주지만 로캘과 정적 버퍼의 제약이 있어 strftime이 더 안전합니다. localtime도 정적 버퍼를 돌려주므로 멀티스레드 프로그램에서는 localtime_r을 씁니다.

실습 1: 달력 시간 관찰

TZ=Asia/Seoul ./calendar_demo
TZ=UTC ./calendar_demo

./tm_normalize

# 같은 시각을 다른 문으로 확인
date; date -u; date +%s

값을 먼저 예측한 뒤 실행해 확인합니다. 살펴볼 것은 세 가지입니다.

  • 시간대 차이: 서울과 UTC로 실행한 local 문자열이 정확히 9시간 차이인지 봅니다.
  • 정규화: tm_normalize에서 1월 32일, 2월 29일이 mktime을 거친 뒤 어떻게 바뀌는지 적습니다. 2025년은 평년이라 2월 29일이 없으므로 2025-02-29는 3월 1일로 정규화되지만, 윤년인 2024-02-29는 그대로 남습니다. 이 비교가 윤년 규칙을 관찰하는 지점입니다. 12월 32일이 다음 해 1월 1일이 되는 것도 확인합니다.
  • 교차 확인: epoch 값이 date +%s와 같은 초인지 확인합니다.

코드 읽기: calendar_demo.c

파일 맨 위 주석이 호출 흐름(조회 → 분해 → 문자열)을 먼저 밝혀 둡니다. 이 프로그램은 명령행 인자를 받지 않으므로 인자가 있으면 usage를 남기고 종료 상태 2로 끝납니다. 관례상 2는 사용법 오류이고 1은 실행 실패입니다.

  • time(NULL)의 결과를 printf("epoch=%lld\n", (long long)now)로 출력합니다. time_t의 크기는 시스템마다 다르므로 long long으로 바꿔 %lld로 찍습니다.
  • localtime이 NULL이 아닌지 확인한 뒤에만 포인터를 읽습니다. 시각 문자열 버퍼 64바이트는 이 형식에 넉넉한 크기입니다.
  • UTC 문자열도 gmtime과 strftime으로 같은 방식으로 만듭니다. 다만 형식에서 %Z 대신 UTC라는 고정 표기를 붙입니다. 이 줄은 TZ와 무관합니다.
  • difftime을 보여 주려면 두 번째 time 판독이 첫 판독과 달라야 합니다. time(2)는 초 단위 해상도이므로 1.2초를 기다려 차이를 만듭니다. 이 대기는 CLOCK_MONOTONIC을 반복해 읽으면서, 나노초로 환산한 차가 1.2초에 닿을 때까지 도는 do-while 반복입니다. 조건을 뒤에서 검사하므로 판독을 최소 한 번은 하고, 차는 같은 시계에서 읽은 값끼리만 냅니다.
  • 두 번째 time 판독도 첫 번째와 같은 방식으로 실패를 검사한 뒤 difftime(later, now)를 출력합니다.
  • 마지막에 fflush(stdout)의 결과까지 확인하고, 실패하면 종료 상태 1로 끝냅니다.

코드 읽기: tm_normalize.c

이 프로그램은 struct tm을 직접 채워 mktime에 넘기는 실험을 normalize라는 함수 하나로 묶고, main에서 네 번 호출합니다. 함수는 라벨과 연·월·일을 받습니다.

  • struct tm을 만든 뒤 memset으로 0을 채워 쓰레기 값이 섞이지 않게 합니다.
  • tm_in.tm_year = year - 1900; — 1900년 기준 오프셋이므로 2026년은 126을 넣습니다.
  • tm_mon에는 인자를 그대로 넣어 0부터 센다는 함정을 드러냅니다. 입력을 출력할 때는 mon + 1이 사람이 아는 월 번호입니다. tm_mday는 1부터 세며, 32처럼 범위 밖 값도 그대로 넣습니다.
  • 시·분·초는 정오(12:00:00)로 고정합니다. 자정 경계를 피하기 위해서입니다.
  • tm_isdst = -1로 두어 서머타임 여부를 mktime이 판단하게 맡깁니다.
  • mktime은 표현할 수 없는 시각이면 (time_t)-1로 실패합니다. 성공하면 넘겨준 struct tm 자체가 정규화되어 있으므로 그것을 strftime으로 문자열로 만듭니다. mktime은 tm_wday까지 채워 주며, tm_wday는 0이 일요일입니다.

main의 네 실험은 다음과 같습니다. 각 호출의 결과를 status |= ...로 모아, 한 번이라도 실패했으면 0이 아닌 종료 상태가 되게 합니다.

status |= normalize("1월 32일", 2026, 0, 32);
status |= normalize("12월 32일", 2026, 11, 32);
status |= normalize("2025-02-29", 2025, 1, 29);   /* 평년 2월 29일 */
status |= normalize("2024-02-29", 2024, 1, 29);   /* 윤년 2월 29일 */

1월 32일은 2월 1일이 되고, 12월 32일은 다음 해 1월 1일로 넘어갑니다. 연도를 넘기는 것까지 정규화가 처리합니다. 평년인 2025-02-29는 3월 1일이 되고, 윤년인 2024-02-29는 그대로 살아 있습니다.

2부 경과 시간

2부에서는 코드 구간이 얼마나 걸렸는지를 잽니다. 달력 시간으로도 초 단위의 차는 잴 수 있지만 두 가지 문제가 있습니다. 해상도가 초라는 점, 그리고 벽시계는 수정되면 거꾸로 갈 수 있다는 점입니다. 그래서 측정에는 clock_gettime과 단조 시계를 씁니다.

clock_gettime(2)과 struct timespec

clock_gettime은 시계를 하나 골라 그 시계의 현재 값을 struct timespec으로 돌려줍니다.

  • struct timespec은 tv_sec(초)와 tv_nsec(나노초) 두 필드로 초와 나노초를 함께 담습니다. 1.5초라면 tv_sec이 1이고 tv_nsec이 5억입니다.
  • 클럭 아이디로 CLOCK_REALTIME, CLOCK_MONOTONIC 등을 고릅니다. CLOCK_* 상수도 <time.h>에 있습니다.
  • 성공하면 0, 실패하면 -1을 돌려줍니다. 시스템에 없는 시계를 요청하면 EINVAL로 실패합니다.

나노초 필드가 있다고 해서 항상 나노초까지 정확한 것은 아닙니다. 필드는 그릇일 뿐이고, 실제 눈금은 시계마다 다르며 clock_getres로 조회합니다.

두 시계: REALTIME과 MONOTONIC

  • CLOCK_REALTIME은 벽시계입니다. 달력 시각의 기준이고 NTP가 조금씩 수정합니다. 과거로 점프할 수 있기 때문에 측정에 쓰면 음수 간격이 나올 수 있습니다.
  • CLOCK_MONOTONIC은 단조 시계입니다. 거꾸로 가지 않습니다. 대신 기준점이 부팅 이후라서 시각 표시에는 쓸 수 없습니다. 원점이 부팅 시각이면 절대 시각과의 관계가 시스템마다 다르기 때문입니다.

여기서 원칙이 나옵니다. 측정은 MONOTONIC, 표시는 REALTIME입니다. 이 밖에 절전 중에도 멈추지 않는 변형(CLOCK_BOOTTIME)이나 NTP 보정을 받지 않는 변형(CLOCK_MONOTONIC_RAW)도 있지만, 수업에서는 두 표준 시계만 다루고 나머지는 clock_show로 관찰만 합니다.

timespec 차이 계산

두 판독의 차를 낼 때는 초와 나노초를 나노초 정수 하나로 합친 뒤에 뺍니다.

static long long ts_ns(const struct timespec *ts)
{
    return (long long)ts->tv_sec * 1000000000LL
         + ts->tv_nsec;
}

long long start = now_ns(CLOCK_MONOTONIC);
/* ... 재려는 코드 ... */
long long elapsed =
    now_ns(CLOCK_MONOTONIC) - start;
printf("%lldns\n", elapsed);

double로 바꿔서 빼면 값이 클 때 아래 자리가 떨어져 나갑니다. 정수로 빼면 오차가 생기지 않습니다. 그래서 계산은 나노초 정수로 하고, 밀리초로 보여 주고 싶을 때처럼 표시 직전에만 1e6으로 나눕니다. long long을 쓰는 이유는 초 값에 10의 9승을 곱하면 int 범위를 훌쩍 넘기 때문입니다. 1.5초는 나노초 정수로 15억입니다.

elapsed_demo: 측정 흐름

elapsed_demo는 배열을 훑는 작업을 재는 프로그램이며, 측정의 기본 흐름 세 가지를 담고 있습니다.

  • 시작·끝 기록: 작업 앞뒤로 CLOCK_MONOTONIC을 읽어 차를 구합니다.
  • 반복 측정: 5번 재고 min·median·max를 뽑아 노이즈를 가려냅니다.
  • 워밍업: 첫 측정 전에 한 번 돌려 캐시 효과를 줄입니다. 첫 측정이 보통 가장 느린 것은 캐시가 아직 차오르지 않았고 페이지가 아직 할당되지 않았을 수 있기 때문입니다.

측정 예제에서는 컴파일러의 최적화도 적이 됩니다. 결과를 쓰지 않는 반복은 컴파일러가 통째로 지워 버릴 수 있으므로, 배열을 volatile로 선언하고 작업의 결과(sink)를 출력합니다.

정밀도와 함정

  • 해상도와 정밀도는 다릅니다. 나노초 필드가 있어도 실제 오차는 더 큽니다. 해상도는 눈금일 뿐 보장된 정밀도가 아닙니다.
  • 측정 자체도 시간을 씁니다. clock_gettime 호출 비용이 결과에 섞입니다. 1나노초 해상도의 시계로 1나노초를 재기 어려운 것은 호출 자체가 그보다 오래 걸리기 때문입니다.
  • 계산은 정수 나노초로 하고, 나눗셈과 실수 표현은 표시할 때만 씁니다.
  • clock_getres로 시계의 해상도를 조회할 수 있습니다.
  • 한 번의 측정보다 여러 번 잰 값의 최솟값이 안정적입니다.

이 수업의 예제는 마이크로초에서 밀리초 규모의 작업만 잽니다. 그보다 정밀한 측정은 하드웨어 카운터 이야기로 이어지며 수업 범위 밖입니다.

반복 측정과 노이즈

한 번만 재면 스케줄링, 캐시, 인터럽트가 값을 흔듭니다. 이 조건들은 실행할 때마다 다릅니다. 다섯 번 재면 통계값을 고를 수 있습니다. min은 방해가 가장 적었던 최상 조건의 값이고, median은 전형적인 값입니다. 최댓값을 대표값으로 쓰지 않는 것은, 방해 요소가 반영된 값이라 코드 자체의 성격보다 환경을 더 많이 말해 주기 때문입니다.

코드를 고치기 전후를 비교할 때는 같은 조건에서 얻은 같은 통계값끼리 비교해야 공정합니다. 값은 매번 달라지더라도 min ≤ median ≤ max라는 관계는 유지되는지가 관찰할 점입니다.

실습 2: 경과 시간 측정

./elapsed_demo
./elapsed_demo --clocks
./clock_show

# 나노초를 밀리초로 환산
python3 -c 'print(3492000/1e6, "ms")'
  • run1부터 run5까지의 나노초 값과 min·median을 적습니다.
  • --clocks로 REALTIME과 MONOTONIC의 now와 res를 봅니다.
  • 두 now 값의 규모가 다른 이유를 설명해 봅니다. REALTIME의 now는 에포크 초라서 date +%s와 규모가 같고, MONOTONIC의 now는 부팅 후 초라서 훨씬 작습니다.

res가 0.000001000(마이크로초 눈금)처럼 나오는지는 환경에 따라 다릅니다.

코드 읽기: elapsed_demo.c

이 파일의 계약은 "timespec을 나노초 정수로 바꾸고 빼기를 정수로 처리한다"입니다. 작은 도우미 함수들이 그 계약을 나눠 맡습니다.

  • ts_ns: timespec을 나노초 정수 하나로 바꿉니다. 초에 10의 9승을 곱해 나노초를 더하며, long long으로 오버플로를 피합니다.
  • now_ns: 지정한 시계의 현재 값을 나노초로 돌려주는 래퍼입니다. clock_gettime이 -1로 실패하면 바로 종료합니다.
  • cmp_ll: qsort에 넘길 비교 함수입니다. void 포인터를 long long으로 되돌려 읽고 return x < y ? -1 : x > y;로 대소를 판정합니다.
  • workload: 측정 대상 작업입니다. static volatile int a[1000000]; 배열을 네 번 훑어 합을 구하는, 밀리초 안팎의 작업입니다. volatile이라 컴파일러가 반복을 지우지 못하고, 합을 반환하는 것도 최적화를 막기 위해서입니다.
  • spin_ns: 약속한 나노초만큼 바쁘게 기다립니다. 경과가 목표에 닿을 때까지 몸통이 빈 반복을 돕니다.
  • show_clock: 시계 하나의 현재 값과 해상도를 한 줄로 출력합니다. 값 조회가 실패하면 미지원으로 표시하고 계속하지만, 해상도 조회 실패는 이 프로그램에서 치명적으로 보고 종료합니다.

main은 측정 모드와 --clocks 모드를 나눕니다. 인자가 없거나 --clocks 하나만 있는 경우가 아니면 usage와 종료 상태 2입니다. --clocks 모드에서는 CLOCK_REALTIME과 CLOCK_MONOTONIC을 찍고, CLOCK_MONOTONIC_RAW와 CLOCK_PROCESS_CPUTIME_ID는 #ifdef로 매크로가 정의되어 있을 때만 컴파일합니다.

측정 모드의 핵심은 다음 몇 줄입니다.

spin_ns(2000000);   /* 워밍업: 첫 측정의 캐시 효과를 줄인다 */
for (int i = 0; i < RUNS; ++i) {
    long long start = now_ns(CLOCK_MONOTONIC);
    sink += workload();
    ns[i] = now_ns(CLOCK_MONOTONIC) - start;
    printf("run%d=%lldns\n", i + 1, ns[i]);
}

2ms 워밍업으로 첫 측정의 캐시·페이지 효과를 줄인 뒤 측정을 다섯 번(enum { RUNS = 5 }) 반복합니다. 작업의 반환값을 sink에 더해 두어 작업이 지워지지 않게 합니다. 반복이 끝나면 다섯 값을 qsort로 오름차순 정렬합니다. 정렬 뒤에는 첫 값 ns[0]이 min, 가운데 ns[RUNS / 2]가 median, 끝 ns[RUNS - 1]이 max입니다.

3부 시간 기록

3부에서는 앞에서 배운 두 시간을 한 줄로 합쳐 타임스탬프 로그를 만듭니다. 좋은 로그 한 줄에는 언제 일어났는지, 시작부터 얼마나 지났는지, 무엇이 일어났는지 세 가지가 있어야 합니다.

로그 한 줄의 설계

  • 달력 시각: 사건의 절대 시각입니다. 다른 기록과 비교할 수 있습니다.
  • 경과 시간: 프로그램 시작부터의 흐름입니다. 단계 사이의 간격이 바로 보입니다.
  • 메시지: 무엇이 일어났는지 사람이 읽는 한 줄입니다.

형식의 예는 2026-09-27 16:15:35 KST +00.0125s read config입니다. 두 시간은 겹치는 정보처럼 보이지만 역할이 다릅니다. 경과 시간 열은 MONOTONIC 시계에서 얻은 값이라 거꾸로 가지 않고 단조 증가합니다.

tslog: 로그 한 줄 쓰기

tslog에서는 log_line 함수가 로그 한 줄을 씁니다.

static int log_line(FILE *out, const char *message)
{
    time_t now = time(NULL);
    struct tm *tm = localtime(&now);
    char stamp[32];
    strftime(stamp, sizeof stamp,
             "%Y-%m-%d %H:%M:%S %Z", tm);
    struct timespec mono;
    clock_gettime(CLOCK_MONOTONIC, &mono);
    double elapsed =
        (double)(ts_ns(&mono) - ts_ns(&start)) / 1e9;
    fprintf(out, "%s +%07.4fs %s\n",
            stamp, elapsed, message);
    return fflush(out) == EOF ? -1 : 0;
}

앞부분은 calendar_demo와 같은 세 단계(time → localtime → strftime)로 달력 시각 문자열을 만듭니다. 그 뒤에 MONOTONIC으로 잰 경과 시간을 붙입니다. start는 main에서 MONOTONIC으로 딱 한 번 기록해 둔 시작 판독입니다.

  • 한 줄 조립: fprintf 호출 하나가 로그 한 줄이고, 줄바꿈까지 직접 넣습니다. 서식은 시각 문자열, +%07.4fs, 메시지 순서입니다. %07.4f는 초를 소수 네 자리로 찍으면서 폭을 고정해 줄이 어긋나지 않게 합니다.
  • 즉시 flush: 쓰자마자 fflush로 밀어냅니다. 그러지 않으면 프로그램이 비정상 종료할 때 버퍼에 남아 있던 줄이 사라져 마지막 순간의 기록을 잃습니다.

위 발췌에는 오류 검사가 빠져 있고, 완성 소스에는 모두 들어 있습니다.

로그 파일과 버퍼

FILE *out = fopen("run.log", "a");
if (out == NULL) {
    perror("fopen");
    return 1;
}
if (log_line(out, "start") == -1)
    return 1;

/* "a"는 파일 끝에 붙인다.
   이전 실행의 기록이 사라지지 않는다. */

if (fclose(out) == EOF) {
    perror("fclose");
    return 1;
}
  • 추가 모드: "a"는 파일 끝에 붙이므로 이전 실행의 기록이 사라지지 않습니다. "w"는 실행할 때마다 파일을 비웁니다. 로그에서는 거의 항상 추가 모드가 맞습니다. tslog에서는 -o 옵션이 이 방식으로 파일을 엽니다.
  • 버퍼링: stdio는 출력을 모았다가 씁니다. 그래서 로그는 줄마다 fflush합니다.
  • 닫기: fclose도 실패할 수 있으므로 반환값을 확인합니다.

줄마다 fflush하면 느려질 수 있지만 수업 예제는 안전한 쪽을 택했습니다. 시스템 크래시까지 대비하려면 fsync가 필요하다는 점만 알아 둡니다.

로그에서 시간의 역할

  • 순서: 두 사건 가운데 어느 것이 먼저였는지를 타임스탬프로 재구성합니다.
  • 간격: 경과 시간의 차로 각 단계가 얼마나 걸렸는지 잽니다.
  • 병합: 다른 프로그램의 로그와 달력 시각으로 시선을 맞춥니다. 두 서버의 로그를 합쳐 보려면 같은 시간대 기준의 달력 시각이 필요하고, 그래서 시각에 시간대를 함께 남깁니다.

로그의 가치는 나중에 원인을 찾을 때 나옵니다. 그래서 로그는 고치지 않고 이어 쓰기만 합니다. 시스템의 syslog(3)나 통합 로그 시스템도 같은 관심사를 다루지만 이 수업의 범위 밖이며, 여기서는 직접 만들어 보는 것이 목적입니다.

두 시간을 함께 남기는 이유

  • 달력 시각만 남기면 다른 기록과 비교는 되지만 짧은 간격이 잘 보이지 않습니다.
  • 경과 시간만 남기면 간격은 보이지만 절대 시점을 모릅니다. "시작한 지 3.2초에 오류가 났다"는 기록만 있으면 그것이 몇 시 몇 분인지 알 수 없어 다른 기록과 합치기 어렵습니다.
  • 둘 다 남기면 "언제"와 "얼마나"를 한 줄에서 동시에 답합니다.

tslog 실행 예시

$ TZ=Asia/Seoul ./tslog --demo
2026-09-27 16:15:35 KST +00.0004s start
2026-09-27 16:15:35 KST +00.0125s read config
2026-09-27 16:15:35 KST +00.0245s process data
2026-09-27 16:15:35 KST +00.0365s write result
2026-09-27 16:15:35 KST +00.0486s done

출력 값은 예시입니다. 다섯 줄 모두 같은 초 안에서 일어났기 때문에 달력 시각 열은 전부 같습니다. 전체 48ms는 1초보다 짧아 초 단위 시각이 바뀌지 않습니다. 이렇게 짧은 간격은 경과 시간 열에서 읽어야 합니다.

  • 간격 읽기: 인접한 두 줄의 경과 차가 그 단계의 지속 시간입니다. read config와 process data 사이는 24.5 − 12.5 = 12밀리초입니다. 간격이 약 12ms인 것은 데모가 줄 사이에 그만큼 기다리도록 만들어져 있기 때문입니다.
  • 정렬: 경과 시간은 단조 증가하므로 줄 순서가 곧 사건 순서입니다.
  • 형식 고정: 폭을 고정했기 때문에 눈으로 줄을 맞춰 읽을 수 있습니다.

시간을 잘못 쓰는 사례

다섯 가지 흔한 실수입니다. 각각이 이번 시간 원칙의 한 조각씩과 대응합니다.

  • 측정에 time(2) 쓰기: 초 단위 해상도라 1초 미만의 짧은 작업은 0초로 잽니다. clock_gettime의 timespec을 써야 합니다.
  • 측정에 REALTIME 쓰기: 측정 도중 시각이 수정되면 음수나 튄 값이 나옵니다.
  • tm_mon을 1부터 세기: 3월을 고르려면 2를 넣어야 합니다.
  • 시간대 없이 시각 남기기: 나중에 그 시각이 KST인지 UTC인지 알 수 없습니다.
  • fflush 없이 남기기: 크래시 직전의 줄이 사라집니다.

실습 3: 로그 실행과 확인

TZ=Asia/Seoul ./tslog --demo
./tslog -o run.log --demo
./tslog -o run.log 'second run'
cat run.log

# read config와 process data의 간격
python3 -c 'print(24.5-12.5, "ms")'
  • 화면(stderr)으로 내보내는 실행과 -o로 파일에 쓰는 실행의 출력을 비교합니다.
  • 같은 파일을 지정해 다시 실행하고 줄이 이어지는지 봅니다. 데모 다섯 줄에 이어 쓴 한 줄이 붙어 모두 여섯 줄이 되면 추가 모드가 확인된 것입니다. cat 대신 tail을 써도 됩니다.
  • 경과 시간 열을 이용해 각 단계의 지속 시간을 계산합니다.

코드 읽기: tslog.c

프로그램 시작 시점의 단조 시계 판독은 전역 변수 static struct timespec start;에 저장합니다. ts_ns는 elapsed_demo의 것과 같고, spin_ns는 CLOCK_MONOTONIC을 반복해 읽으며 두 판독의 나노초 차가 목표에 닿을 때까지 기다립니다.

완성된 log_line은 위 발췌와 흐름이 같지만 단계마다 실패를 검사해 호출자에게 -1로 알립니다. time의 -1, localtime의 NULL, strftime의 0(버퍼 부족), clock_gettime의 -1, fprintf의 음수 반환, fflush의 EOF가 모두 실패 경로입니다.

main은 옵션 해석, 메시지 결정, 기록의 순서로 진행합니다. 사용법은 usage: %s [-o FILE] [--demo | MESSAGE...]입니다.

  • 기본 출력은 stderr입니다. 화면에 보이는 로그는 표준 오류로 남깁니다.
  • 대시로 시작하는 인자를 앞에서부터 읽습니다. -o는 뒤에 파일 이름이 없거나 중복으로 주어지면 usage와 종료 상태 2입니다. 파일은 fopen(argv[i + 1], "a"), 곧 추가 모드로 열고, 실패하면 경로와 errno 메시지를 남기고 종료 상태 1로 끝납니다. --demo는 플래그만 기록합니다. 모르는 대시 인자를 만나면 옵션 해석을 멈추고 그 뒤를 메시지로 봅니다.
  • 데모 모드는 "start", "read config", "process data", "write result", "done" 다섯 메시지를 씁니다. 데모와 메시지를 함께 주거나, 데모가 아닌데 메시지가 없으면 usage입니다. 이때 이미 열어 둔 파일은 닫고 나갑니다.
  • 메시지를 쓰기 직전에 clock_gettime(CLOCK_MONOTONIC, &start)로 시작 판독을 기록합니다. 이것이 경과 시간 0의 기준점입니다.
  • 메시지마다 log_line을 호출하고, 한 줄이라도 실패하면 알린 뒤 반복을 중단합니다. 마지막 줄이 아니면 spin_ns(12000000)으로 약 12ms 간격을 만듭니다.
  • 파일에 썼다면 fclose의 실패를, 표준 오류에 썼다면 fflush(stderr)의 실패를 종료 상태에 반영합니다.

4부 시계 선택과 함정

마지막 부분에서는 목적에 따라 어느 시계를 고를지 정리하고 남은 함정을 확인합니다. 한 문장으로 줄이면 표시는 달력 시간, 측정은 단조 시계, 기록은 둘 다입니다.

벽시계가 거꾸로 가는 경우

벽시계는 고쳐지는 시계입니다.

  • NTP가 시각을 과거 방향으로 보정할 수 있습니다. 그러면 REALTIME 판독 값이 줄어듭니다.
  • 관리자가 직접 시각을 고쳐도 같은 일이 생깁니다.
  • 가상 머신의 일시정지나 이동도 벽시계를 점프시킵니다.

그래서 간격 측정에는 MONOTONIC을 씁니다. 단조 시계에는 이런 점프가 원천적으로 없습니다. 그렇다고 REALTIME이 필요 없는 것은 아니며, 달력 시각 표시에는 여전히 REALTIME이 필요합니다. 로그에서 달력 시각이 어긋나 보이더라도 간격은 경과 시간 열에서 얻도록 설계한 이유가 여기에 있습니다. 달력 시각은 다른 기록과 맞추는 용도로 씁니다.

정밀도와 단위 선택

  • 초: 사람이 읽는 기록과 만료 판정에 충분한 단위입니다.
  • 밀리초: 작업 지속 시간과 타임아웃에 흔히 쓰는 단위입니다.
  • 나노초: 구간 측정의 계산 단위입니다. 표시할 때 환산합니다.

단위는 계산과 표시에서 각각 고릅니다. 정수 나노초는 오차 없이 뺄 수 있고 실수로의 변환은 표시 직전에 한 번만 하면 되므로, 계산은 나노초 정수로 하고 표시할 때 단위를 바꿉니다. timespec은 항상 나노초 필드를 갖지만 실제 해상도는 clock_getres 값으로 확인합니다.

clock_show: 시계별 값과 해상도

clock_show는 REALTIME, MONOTONIC, RAW, CPU 시간 등 여러 시계를 차례로 돌며 각 시계의 현재 값과 해상도를 표처럼 출력합니다.

static int show(const char *name, clockid_t clock)
{
    struct timespec now, res;
    if (clock_gettime(clock, &now) == -1) {
        printf("%-24s unsupported\n", name);
        return 0;           /* 없는 시계는 표시만 */
    }
    if (clock_getres(clock, &res) == -1) {
        perror("clock_getres");
        return 1;
    }
    printf("%-24s now=%lld.%09ld res=%ld\n",
           name, (long long)now.tv_sec,
           now.tv_nsec, res.tv_nsec);
    return 0;
}
  • 미지원 처리: 시스템마다 있는 시계가 다릅니다. 없는 시계는 호출이 실패로 알려 오므로 unsupported로 표시하고 지나갑니다.
  • 해상도: res가 그 시계의 최소 눈금입니다. res가 0.000001000이라면 눈금이 1마이크로초라는 뜻이고, 필드가 나노초여도 값은 눈금 단위로 움직입니다.

CLOCK_PROCESS_CPUTIME_ID는 그 프로세스가 쓴 CPU 시간을 잽니다. 다음 주에 다루는 times(2)·CLK_TCK와 같은 관심사입니다.

달력 시간과 경과 시간의 역할 분담

구분답하는 질문쓰는 곳
달력 시간언제로그 시각, 만료 판정, 기록 정렬
경과 시간얼마나구간 측정, 타임아웃, 간격 비교

선택 기준은 보여 주고 비교할 때는 달력, 잴 때는 단조 시계입니다. 예를 들어 타임아웃은 남은 시간을 재는 일이므로 단조 시계가 어울립니다. 벽시계가 점프하면 타임아웃이 사라지거나 늘어날 수 있습니다. 자료형도 이 구분을 그대로 반영합니다. time_t(초)와 struct tm(분해된 달력 시각)이 달력 쪽이고, struct timespec(초와 나노초)이 경과 쪽입니다. CPU 시간은 다음 주 times(2)에서 세 번째 축으로 추가됩니다.

실습 4: 시계 비교 관찰

./clock_show
./elapsed_demo --clocks
date +%s

# 시간대 확인
TZ=Asia/Seoul date; TZ=UTC date

# (Linux 선택) 부팅 후 시간 규모 비교
cat /proc/uptime
  • now의 단위: REALTIME의 now는 date +%s와 같은 에포크 초입니다.
  • MONOTONIC의 기준: 부팅 이후 초이므로 /proc/uptime과 규모가 비슷합니다. macOS에는 /proc/uptime이 없으므로 이 줄은 Linux에서만 하는 선택 관찰입니다.
  • res 비교: 시계마다 눈금이 다른 것을 표로 정리합니다.

같은 순간에 두 시계의 now를 읽어도 값이 다른 것은 원점이 다르기 때문입니다. 하나는 1970년부터, 다른 하나는 부팅부터 셉니다. clock_show와 elapsed_demo --clocks가 출력하는 같은 시계의 값이 크게 다르지 않은지도 확인합니다.

코드 읽기: clock_show.c

완성 소스의 show 함수는 위 발췌와 구조가 같습니다. clock_gettime이 실패하면 그 시계가 없다는 뜻으로 보고 strerror(errno)와 함께 미지원이라고 표시한 뒤 0을 돌려주어 계속 진행합니다. clock_getres 실패는 치명적으로 보고 1을 돌려줍니다. 출력에서는 %-24s가 이름 열의 폭을 맞춥니다.

main은 여섯 시계를 차례로 조사하고, 시계별 결과를 status |= show(...)로 모아 종료 상태로 돌려줍니다.

  • CLOCK_REALTIME: 벽시계이며 달력 시각의 기준입니다.
  • CLOCK_MONOTONIC: 단조 시계이며 부팅 후의 흐름입니다. 구간 측정에 씁니다.
  • CLOCK_MONOTONIC_RAW: 표준이 아니어서 #ifdef로 매크로를 확인한 뒤 컴파일합니다.
  • CLOCK_BOOTTIME: Linux 확장이며 절전 시간을 포함한 흐름입니다.
  • CLOCK_PROCESS_CPUTIME_ID: 이 프로세스가 쓴 CPU 시간을 잽니다.
  • CLOCK_THREAD_CPUTIME_ID: 이 스레드가 쓴 CPU 시간을 잽니다.

확인 문제

  1. 경과 시간을 잴 때 CLOCK_MONOTONIC을 쓰는 이유는 무엇입니까? REALTIME은 점프할 수 있어 음수 간격이 나올 수 있기 때문입니다.
  2. time_t에서 화면용 문자열까지 만드는 호출 순서는 무엇입니까? time → localtime(또는 gmtime) → strftime입니다.
  3. struct tm의 tm_mon이 9라면 몇 월입니까? 10월입니다.
  4. strftime의 반환값이 0이면 무엇을 뜻합니까? 버퍼가 작아 아무것도 쓰지 못했다는 뜻입니다.
  5. 로그 한 줄에 달력 시각과 경과 시간을 함께 남기는 이유는 무엇입니까? 절대 시점과 흐름의 간격을 한 줄에서 동시에 알 수 있기 때문입니다.

새 API를 읽을 때는 반환값과 자료형부터 확인합니다. 이번 시간처럼 같은 헤더 안에서도 용도별로 다른 시계와 자료형이 함께 있습니다. 여기서 배운 시간 다루기는 다음 주의 프로세스 정보와 times(2)·CLK_TCK로 이어집니다.
