이번 차시의 주제는 부모 프로세스가 자식 프로세스를 제어하는 방법입니다. 방법은 두 가지입니다. 하나는 fork와 waitpid만 쓰는 방법으로, 자식을 만들 때 일을 정해 주고 자식이 끝난 뒤에 결과를 받습니다. 다른 하나는 시그널을 쓰는 방법으로, 자식이 도는 중에 끼어듭니다. 앞의 방법은 예제 forkpool로, 뒤의 방법은 예제 sigctl로 살펴봅니다.

새로운 시스템 콜을 배우는 시간이 아니라, 이미 배운 것을 부모 쪽에서 묶는 시간입니다. 10주차 1·2차시에서는 fork로 자식을 만들고 waitpid로 거두었으며, status는 매크로로 먼저 판정한 다음 값을 꺼낸다는 것을 배웠습니다. 2차시의 runcmd는 status를 셸의 $?로 바꾸었고, multiwait는 wait가 자식을 끝난 순서대로 돌려준다는 것을 보여 주었습니다. 9주차에서는 kill로 시그널을 보내고 sigaction으로 받으며, 핸들러는 깃발만 세운다는 규칙과 SIGCHLD를 배웠습니다. 오늘은 이 둘을 합쳐 자식을 제어합니다.

1부. fork와 waitpid로 제어하기

1부에서는 시그널을 쓰지 않습니다. 자식을 만들 때 할 일을 정해 주고, 자식이 끝난 뒤 종료 코드를 읽어 다음 행동을 정합니다. 예제는 작업 풀 forkpool입니다.

부모가 쥔 손잡이 네 개

자식의 일생은 fork → 자식이 일함 → exit(code) → 부모가 waitpid로 회수하는 순서로 흘러갑니다. 이 흐름에서 부모가 정할 수 있는 것은 네 가지입니다.

손잡이정하는 방법forkpool에서
① 언제 만드나fork를 부르는 시점start()
② 무슨 일을 시키나fork 전의 변수 값, 인자child_work()
③ 몇 개를 동시에 돌리나running < MAXPARrunning
④ 결과를 보고 다음에 무엇을 하나waitpid, 종료 코드, 재시도waitpid(-1)

①–③은 fork 할 때 정하고, ④는 waitpid로 거둔 뒤에 정합니다. 무슨 일을 할지는 fork 순간의 메모리 복사본으로 자식에게 전해지고, 자식이 부모에게 알려 주는 것은 종료 코드(0–255)뿐이며 이것을 waitpid가 받아 옵니다. 그 사이, 곧 자식이 도는 동안에는 부모가 끼어들지 않고 기다립니다. 도는 중에 끼어들려면 시그널이 필요하고, 그것이 2부의 내용입니다.

일 배정: fork 순간의 값이 자식의 일이 된다

fork(2) 매뉴얼은 자식이 PID 등 몇 가지를 빼고 부모의 정확한 복제본이라고 설명합니다. fork는 부모의 메모리를 복제하므로(COW), fork 직전의 변수 값이 곧 자식의 일감이 됩니다. 부모의 id가 3일 때 fork 하면 자식도 id = 3인 복사본을 가지고 child_work(3)을 실행한 뒤 0 또는 1로 종료합니다. forkpool은 exec를 쓰지 않고 자식 안에서 함수를 바로 부릅니다.

이 전달은 한 방향입니다. 자식이 가진 것은 복사본이므로 자식이 id를 바꿔도 부모의 id는 그대로이고, 부모는 자식이 변수를 바꾼 사실을 알 수 없습니다. 결과가 돌아오는 길은 종료 코드 하나뿐입니다. 또 exec를 함께 쓰는 경우에는 exec 뒤에 변수가 남지 않으므로, 변수 대신 argv와 환경 변수로 일을 넘깁니다(1·2차시).

forkpool에서 작업이 6개라면 부모는 id를 0부터 5까지 바꿔 가며 fork를 여섯 번 합니다. 작업 i는 (i % 3 + 1) × 200 ms 동안 일하므로 작업 0–5의 길이는 차례로 200, 400, 600, 200, 400, 600 ms입니다. 재시도를 보여 주기 위해 작업 3은 첫 시도에서 실패하도록 만들어 두었습니다.

종료 코드는 자식의 결과 보고서

자식이 끝난 방식은 부모의 waitpid가 받아 온 status를 매크로로 판정해서 알아냅니다.

자식부모의 waitpid → 매크로판정
exit(0)WIFEXITED 참, WEXITSTATUS = 0성공 → done
exit(1)WIFEXITED 참, WEXITSTATUS = 1실패 보고 → 재시도할지 결정
시그널로 죽음 (예: kill -9)WIFSIGNALED 참, WTERMSIG = 9비정상 → 재시도할지 결정

이 판정은 2차시 runcmd에서 본 셸 규칙(127, 128+n)과 같은 것입니다. exit(3)의 설명대로 부모에게 전달되는 값은 status & 0377, 곧 0–255의 한 바이트뿐입니다. 그보다 큰 결과를 돌려받으려면 파이프(12주차), 파일, 공유 메모리(11주차) 같은 다른 통로를 써야 합니다.

누구를 기다릴까: waitpid(-1)과 waitpid(pid)

waitpid의 첫 인자에 따라 기다리는 대상이 달라집니다.

  • waitpid(pid, &st, 0)은 정한 자식 하나만 기다립니다. 예를 들어 600 ms짜리 0번을 먼저 기다리면, 그 사이에 200 ms 만에 끝난 1번은 거두어지지 못하고 좀비로 대기합니다. 결과를 만든 순서대로 모아야 할 때 쓰는 방식이며, 대신 먼저 끝난 쪽이 기다리게 됩니다.
  • waitpid(-1, &st, 0)의 -1은 "아무 자식이나"라는 뜻입니다(waitpid(2): "pid == -1: wait for any child process"). 먼저 끝난 자식부터 돌려주므로 빈 자리가 생긴 것을 가장 빨리 알 수 있습니다. 빈 자리를 바로 채워야 하는 forkpool이 이 방식을 씁니다.

2차시 multiwait에서 본 것과 같은 차이입니다. wait()는 끝난 순서로, waitpid(pid)는 만든 순서로 자식을 거둡니다.

waitpid(-1)을 쓰면 한 가지 일이 더 생깁니다. 반환값은 끝난 자식의 PID뿐이어서, 그 자식이 몇 번 작업을 하고 있었는지는 부모가 따로 알아내야 합니다. forkpool은 fork 할 때마다 jobs[i].pid에 PID를 적어 두고, job_of 함수가 이 표에서 PID에 해당하는 작업 번호를 찾습니다.

동시 실행 수 제한: MAXPAR

forkpool은 동시에 도는 자식 수를 MAXPAR 이하로 유지합니다. 자리가 MAXPAR개 있다고 생각하면 됩니다. 어떤 자식이 끝나는 순간 그 자리에 다음 일이 들어갑니다. waitpid(-1)이 돌아오면 running--으로 자리를 비우고, 빈 자리만큼 start()를 부릅니다.

MAXPAR가 2일 때의 실제 시간표를 보면 두 자리가 다음과 같이 채워집니다. 한 자리에서는 job 0, job 2, job 4가 이어서 돌고, 다른 자리에서는 job 1, 실패한 job 3, job 3의 재시도, job 5가 이어서 돕니다. 전체는 약 1400 ms에 끝납니다.

자리 수를 늘리면 전체 시간은 줄지만 CPU와 메모리 사용도 함께 늘어납니다. make -j N의 N이 바로 이 값입니다.

판정과 재시도: 실패하면 한 번 더

자식 하나를 거둔 뒤 부모가 하는 판정은 다음 순서입니다.

  1. waitpid(-1)이 PID를 돌려주면 running--을 하고 id = job_of(pid)로 작업 번호를 찾습니다.
  2. 정상 exit이고 코드가 0이면 done으로 처리하고 finished++을 합니다.
  3. 그렇지 않고 tries < MAXTRIES(2)이면 retry입니다. start(id)로 같은 작업을 다시 시작하고 running++을 합니다.
  4. 시도 횟수를 다 썼으면 give up입니다. finished++과 failed++을 합니다.

여기에 담긴 규칙은 세 가지입니다. 첫째, 성공 조건은 "정상 exit 그리고 코드 0" 하나뿐이고, 시그널로 죽은 경우를 포함해 그 밖은 모두 실패로 묶습니다. 둘째, 재시도 횟수에는 상한(MAXTRIES 2)을 둡니다. 무한히 재시도하면 영원히 끝나지 않을 수 있기 때문입니다. 셋째, 하나라도 포기한 작업이 있으면 부모 자신의 종료 코드를 1로 합니다. 그래야 부모를 부른 셸이나 스크립트가 같은 방식으로 다시 판정할 수 있습니다.

재시도는 방금 비운 자리(running 수)를 그대로 다시 쓰므로 동시 실행 상한을 넘지 않습니다.

forkpool의 흐름과 코드

사용법은 ./forkpool NJOBS MAXPAR입니다. 프로그램은 세 부분으로 이루어집니다.

  • main: 인자를 확인하고 시작 시각 t0을 기록합니다. 그다음 빈 자리만큼 start(next++)를 부르고, waitpid(-1)로 하나를 거두어 running--을 한 뒤, job_of로 작업을 찾아 결과를 판정합니다. finished < njobs인 동안 이것을 반복합니다.
  • start(id): tries++, fflush(stdout), fork() 순서입니다. 자식은 child_work로 들어가 _exit하고, 부모는 jobs[id].pid에 PID를 적고 시작 줄을 출력합니다.
  • child_work: (id % 3 + 1) × 200 ms 동안 잠을 잔 뒤, 작업 3의 첫 시도이면 _exit(1), 아니면 _exit(0)을 합니다. 자식은 이 함수에서 돌아오지 않습니다.

자식이 하는 일은 다음 몇 줄이 전부입니다. 정해진 시간만큼 잠을 자고 성공 또는 실패를 종료 코드로 보고합니다.

    struct timespec d = { 0, (id % 3 + 1) * 200000000L };
    nanosleep(&d, NULL);
    if (id == FAIL_JOB && attempt == 1)
        _exit(1);  /* 첫 시도는 실패로 보고 */
    _exit(0);  /* 성공 */

start()에서 눈여겨볼 것은 fork 직전의 fflush입니다. 출력 버퍼에 내용이 남은 채로 fork 하면 그 버퍼도 자식에게 복사되어 같은 출력이 두 번 찍힐 수 있으므로, 버퍼를 비우고 fork 합니다.

    jobs[id].tries++;
    fflush(stdout);  /* 버퍼를 비우고 fork */
    pid_t pid = fork();
    if (pid < 0) { perror("fork"); exit(1); }
    if (pid == 0)
        child_work(id, jobs[id].tries); /* 돌아오지 않는다 */
    jobs[id].pid = pid;

main의 반복문 앞부분이 "빈 자리 채우기"와 "아무 자식이나 기다리기"입니다. running < maxpar이고 남은 작업이 있으면 start(next++)를 부릅니다. waitpid가 실패했을 때 errno가 EINTR이면 다시 시도하고, 그 밖의 오류이면 종료합니다.

    while (finished < njobs) {
        while (running < maxpar && next < njobs) {  /* 빈 자리만큼 시작 */
            start(next++);
            running++;
        }
        int status;
        pid_t pid = waitpid(-1, &status, 0);  /* 아무 자식이나 */
        if (pid < 0) {
            if (errno == EINTR) continue;
            perror("waitpid");
            return 1;
        }
        running--;
        int id = job_of(pid, njobs);

이어지는 뒷부분이 앞에서 설명한 판정입니다. 성공이면 done, 시도 횟수가 남았으면 출력 후 start(id)와 running++, 아니면 give up입니다. 반복문이 끝나면 요약 줄을 출력하고 실패가 하나라도 있으면 1을 돌려줍니다.

        if (WIFEXITED(status) && WEXITSTATUS(status) == 0) {
            printf("%5ld ms  done  job %d  pid %d\n", ms(), id, (int)pid);
            finished++;
        } else if (jobs[id].tries < MAXTRIES) {
            printf("%5ld ms  FAIL  job %d  pid %d (exit %d) -> retry\n",
                   ms(), id, (int)pid, WEXITSTATUS(status));
            start(id);
            running++;
        } else {
            printf("%5ld ms  give up job %d\n", ms(), id);
            finished++;
            failed++;
        }
    }
    printf("%5ld ms  all %d jobs finished, %d failed\n", ms(), njobs, failed);
    return failed ? 1 : 0;

실행 결과: forkpool 6 2

강의에서는 Ubuntu 24.04 컨테이너(Docker, aarch64)에서 ./forkpool 6 2를 실행한 화면을 보았습니다. 두 자리로 여섯 작업을 처리한 결과에서 확인할 점은 세 가지입니다.

  • 끝나면 바로 채웁니다. 206 ms에 job 0이 끝나자 207 ms에 job 2가 시작됩니다. 동시에 도는 자식은 늘 2개 이하입니다.
  • 실패하면 재시도합니다. 615 ms에 job 3이 exit 1로 끝나자 같은 순간에 try 2가 시작되고, 816 ms에 성공합니다.
  • 자식은 7개입니다. 작업 6개에 재시도 1개가 더해져 PID 444–450의 일곱 프로세스가 만들어졌고, 약 1.4초에 모두 끝났습니다.

MAXPAR 1은 작업을 차례로 하나씩 실행하는 것이므로 전체 시간이 작업 시간의 합(재시도를 포함해 200+400+600+200+200+400+600 = 2600 ms)에 가깝습니다. MAXPAR 6은 한꺼번에 모두 실행하는 것이므로 가장 긴 작업의 600 ms가 전체 시간이 됩니다. 실패 후 재시도까지 합쳐 400 ms가 걸리는 작업 3도 그보다 짧습니다. 2에서 3으로 늘렸을 때는 1414 ms에서 1207 ms로 조금만 줄어듭니다. 자리를 늘려도 긴 작업이 전체 시간을 정하기 때문입니다.

이 실험에서 자식은 잠만 자므로 CPU 수(실행 환경은 10개)와 상관없이 작업들이 겹쳐 실행됩니다. 실제로 계산을 하는 작업이라면 CPU 수가 상한이 됩니다.

1부 정리

fork와 waitpid만으로 할 수 있는 것은 네 가지였습니다.

  • 일 배정: fork 전의 변수 값이 자식의 일감이 됩니다.
  • 동시 실행 제한: running < MAXPAR를 지키고, 끝나면 바로 채웁니다.
  • 결과 판정: waitpid(-1)로 거두고 WIFEXITED이면서 코드 0인지 봅니다.
  • 재시도: 같은 자리를 다시 쓰고 횟수에 상한을 둡니다.

반대로 할 수 없는 것도 분명합니다. 도는 중인 자식을 멈추거나, 다시 돌리거나, 일찍 끝내거나, 상태를 묻는 일은 할 수 없으며 이것은 2부의 시그널이 맡습니다. 0–255보다 큰 결과를 받는 일도 할 수 없으며 이것은 11주차의 mmap과 12주차의 파이프에서 다룹니다.

2부. 시그널로 제어하기

2부에서는 부모가 kill로 시그널을 보내 도는 중인 자식을 멈추고, 다시 돌리고, 상태를 묻고, 끝냅니다. 자식에게 일어난 변화는 waitpid로 확인합니다. 예제는 sigctl입니다.

부모가 보낼 수 있는 다섯 시그널

시그널기본 동작핸들러로 바꾸기sigctl에서의 쓰임
SIGSTOP멈춤 (Stopped)불가 — 항상 멈춘다일시 정지
SIGCONT멈춘 프로세스를 다시 실행핸들러는 가능, 재개 자체는 항상 일어남재개
SIGUSR1종료가능 — 의미는 약속으로 정한다"상태를 보고하라"
SIGTERM종료가능 — 정리할 기회"정리하고 끝내라"
SIGKILL종료불가 — 항상 즉시 종료강제 종료 (최후 수단)

SIGSTOP과 SIGKILL은 잡을 수도, 막을(block) 수도, 무시할 수도 없습니다. 자식이 어떻게 만들어졌든 거부할 수 없으므로 이 둘이 부모의 마지막 손잡이입니다. SIGUSR1은 정해진 의미가 없어서 부모와 자식이 약속한 뜻으로 쓰며, 약속이 없다면 기본 동작은 종료라는 점을 기억해 두어야 합니다. 참고로 셸에서 Ctrl+Z를 누르면 전달되는 것은 SIGSTOP이 아니라 잡을 수 있는 SIGTSTP입니다.

자식의 상태와 waitpid가 알려 주는 것

시그널에 따라 자식은 다음과 같이 상태가 바뀌고, 부모의 waitpid는 그 변화를 서로 다른 매크로로 알려 줍니다.

보낸 시그널자식의 변화waitpid의 보고
SIGSTOP실행 중 → 멈춤 (ps의 STAT 열에 T)WIFSTOPPED, WSTOPSIG = 19
SIGCONT멈춤 → 실행 중WIFCONTINUED
SIGTERM핸들러 → exit(0)로 종료 (정리함)WIFEXITED, 코드 0
SIGKILL (실행 중이든 멈춤이든)시그널로 종료 (정리 못 함)WIFSIGNALED, 9

waitpid는 종료만 알려 주는 함수가 아닙니다. 멈춤도 "상태 변화"이므로 WUNTRACED 옵션을 주면 waitpid가 멈춤도 보고하고, WCONTINUED(Linux 2.6.10부터)를 주면 SIGCONT로 다시 돌기 시작한 것도 보고합니다. exit와 시그널에 의한 종료는 옵션 없이도 늘 보고됩니다.

보내기는 kill, 확인은 waitpid

제어는 두 단계로 이루어집니다. 부모가 kill(pid, SIGSTOP)을 부르면 자식이 멈추고, 부모는 waitpid로 WIFSTOPPED를 확인합니다. 이어서 kill(pid, SIGCONT)를 부르면 자식이 다시 실행되고, 부모는 waitpid로 WIFCONTINUED를 확인합니다.

두 단계가 필요한 이유는 kill이 보내기만 하기 때문입니다. kill이 0을 돌려주었다는 것은 커널이 시그널을 맡았다는 뜻이지 자식이 그것을 처리했다는 뜻이 아닙니다. 실제로 상태가 바뀌었는지는 waitpid로 확인합니다. waitpid는 멈춤, 재개, 종료 가운데 하나가 일어날 때까지 기다렸다가 돌아옵니다.

다만 SIGUSR1처럼 자식의 상태를 바꾸지 않는 시그널은 waitpid로 확인할 수 없습니다. 보고를 요청하는 시그널은 보내 두고 자식의 출력을 볼 수 있을 뿐입니다. sigctl의 send(pid, sig, name, wait) 함수가 이 두 단계를 하나로 묶고, 마지막 인자로 확인 단계를 할지 말지를 정합니다.

자식 쪽: 핸들러는 깃발만 세운다

자식은 100 ms씩 잠을 자며 한 칸씩 일하는 루프를 돕니다. nanosleep(100 ms) 뒤 ticks++을 하고, want_report가 서 있으면 보고를 출력하고, want_quit가 서 있으면 루프를 나옵니다. 루프를 나오면 "cleanup" 메시지를 출력하고 fflush 한 뒤 _exit(0)으로 끝납니다.

두 깃발은 volatile sig_atomic_t 형이고, 핸들러는 9주차에서 배운 대로 깃발을 1로 세우기만 합니다. SIGUSR1의 핸들러는 want_report = 1, SIGTERM의 핸들러는 want_quit = 1이 전부입니다. printf는 signal-safety(7)가 정한 async-signal-safe 함수가 아니므로 핸들러 안에서 부르지 않습니다. 출력, 정리, exit 같은 실제 일은 메인 루프가 깃발을 보고 안전한 곳에서 합니다.

깃발 방식이면 반응이 늦을 것 같지만 그렇지 않습니다. nanosleep 중에 시그널이 오면 잠이 깨져 일찍 돌아오기 때문입니다(nanosleep(2)의 EINTR: "The pause has been interrupted by a signal handler"). 그래서 루프가 곧바로 깃발을 확인하게 됩니다.

핸들러는 fork 전에: 늦게 설치하면 죽는다

핸들러 설정, 곧 시그널을 어떻게 처리할지에 대한 설정은 fork로 자식에게 복사됩니다. sigctl의 term 모드와 kill 모드는 이 성질을 이용합니다. 부모가 fork 전에 SIGUSR1과 SIGTERM의 핸들러를 sigaction으로 설치해 두면, 자식은 태어날 때 이미 핸들러를 가지고 있으므로 SIGUSR1이 도착하면 바로 보고할 수 있습니다.

late 모드는 일부러 반대로 합니다. 자식이 fork 뒤 300 ms가 지나서야 핸들러를 설치하는데, 부모는 50 ms에 SIGUSR1을 보냅니다. 핸들러가 설치되기 전의 구간에서는 기본 동작이 적용되고 SIGUSR1의 기본 동작은 종료이므로, 자식은 핸들러를 갖기도 전에 SIGUSR1을 받아 죽습니다. 부모의 waitpid는 다음과 같이 보고합니다.

killed by signal 10 (User defined signal 1)

SIGUSR1의 번호 10은 x86-64와 aarch64 리눅스 기준입니다.

따라서 시그널을 보내기 전에 받을 쪽의 핸들러가 먼저 설치되어 있어야 하고, 그렇지 않으면 기본 동작이 일어납니다. 해결 방법은 두 가지입니다. fork 전에 핸들러를 설치하거나, fork 전에 sigprocmask로 시그널을 막아 두었다가 자식이 핸들러를 설치한 뒤에 푸는 것입니다(9주차 2차시).

fork와 달리 exec는 핸들러를 되돌립니다. execve(2)의 설명대로 잡고 있던 시그널의 처리 방식은 exec 뒤에 기본값으로 돌아가며, 무시 설정은 유지됩니다.

멈춘 자식에게 보낸 시그널은 어떻게 되나

SIGSTOP으로 멈춘 자식에게 다른 시그널을 보내면 시그널의 종류에 따라 결과가 다릅니다.

멈춘 자식에게바로 일어나는 일SIGCONT 뒤실측
SIGTERM보류(pending) — ShdPnd 0x4000 (15번 비트)처리 → 종료$? = 143 (128 + 15)
SIGUSR1 (핸들러 있음)보류 — 핸들러도 실행되지 않는다핸들러 실행 → 보고—
SIGKILL즉시 종료 (멈춤과 상관없이)—$? = 137 (128 + 9)

멈춘 프로세스는 실행되지 않으므로 SIGTERM이나 SIGUSR1은 도착해도 보류된 채 남아 있다가, SIGCONT로 다시 돌기 시작한 뒤에 처리됩니다. SIGKILL만은 멈춘 상태에서도 즉시 프로세스를 끝냅니다. 셸에서 직접 확인할 수 있습니다. 보류 중인 시그널은 /proc/PID/status의 ShdPnd 항목에 비트로 나타납니다.

$ sleep 100 & P=$!; kill -STOP $P; kill -TERM $P; grep -E "State|ShdPnd" /proc/$P/status
State:  T (stopped)
ShdPnd: 0000000000004000          # 15번(SIGTERM)이 보류 중
$ kill -CONT $P; wait $P; echo $?   → 143

이 실험에서 SIGCONT를 따로 보내야 했다는 점도 눈여겨볼 만합니다. 셸의 kill 명령은 멈춘 작업에 SIGCONT를 따로 보내 주지 않습니다.

sigctl의 흐름: 부모의 제어 순서

사용법은 ./sigctl [term|kill|late]입니다. 기본인 term 모드에서 부모는 대략 다음 시각에 시그널을 보냅니다(시각은 sleep_ms 기준의 대략값입니다).

시각(ms)부모가 하는 일결과
0fork자식이 실행되며 틱이 증가
350SIGUSR1보고 요청
450SIGSTOPstopped — 멈춘 동안 틱 없음 (STAT T)
950SIGCONTcontinued — 다시 실행
1200SIGUSR1보고 요청
1300SIGTERMexited 0 — 끝

세 모드의 차이는 마지막 부분에 있습니다.

  • term: 마지막에 SIGTERM을 보냅니다. 자식이 정리하고 exit 0으로 끝납니다.
  • kill: 마지막에 SIGKILL을 보냅니다. 자식은 정리 없이 signal 9로 죽습니다.
  • late: 자식이 핸들러를 300 ms 뒤에 설치합니다. 부모가 50 ms에 보낸 SIGUSR1에 자식이 죽습니다.

sigctl의 코드

맨 앞에는 깃발 두 개와 그것을 세우는 핸들러가 있습니다. 핸들러의 본문은 대입 한 줄뿐입니다.

static volatile sig_atomic_t want_report = 0, want_quit = 0;
static void on_usr1(int sig) { (void)sig; want_report = 1; }
static void on_term(int sig) { (void)sig; want_quit = 1; }

install 함수는 sigaction으로 핸들러를 설치합니다. sa_mask는 비우고 flags는 0으로 둡니다. sleep_ms는 부모가 시각을 맞추는 데 쓰는 함수로, nanosleep이 시그널 때문에 일찍 깨면 남은 시간만큼 다시 잡니다.

    while (nanosleep(&d, &d) < 0)  /* 시그널로 깨면 남은 시간만큼 */
        ;

자식의 일은 worker 함수입니다. late 모드일 때만 300 ms를 잔 뒤에야 핸들러를 설치하며, 그 전에는 기본 동작이 적용됩니다. 그다음이 일 루프입니다. 여기서는 sleep_ms와 달리 nanosleep을 한 번만 부르므로 시그널이 오면 일찍 깨어 깃발을 확인합니다. want_report가 서 있으면 깃발을 내리고 보고합니다. want_quit로 루프를 나오면 정리 메시지를 출력하고 fflush 합니다.

    while (!want_quit) {
        nanosleep(&tick, NULL);  /* 시그널이 오면 일찍 깰 수 있다 */
        ticks++;
        if (want_report) {
            want_report = 0;
            printf("    [child %d] report: %ld ticks\n", (int)getpid(), ticks);
            fflush(stdout);
        }
    }
    printf("    [child %d] got SIGTERM: cleanup, exit 0 (%ld ticks)\n",
           (int)getpid(), ticks);
    fflush(stdout);

부모 쪽의 send는 "보내기는 kill, 확인은 waitpid"를 그대로 옮긴 함수입니다. 무엇을 보내는지 출력한 뒤 kill(pid, sig)를 부르고, 실패하면 종료합니다. wait이 0이면 거기서 끝나는데, SIGUSR1처럼 상태가 바뀌지 않는 시그널이 이 경우입니다. wait이 참이면 WUNTRACED | WCONTINUED로 멈춤, 재개, 종료를 기다린 뒤 show로 결과를 출력합니다.

    if (kill(pid, sig) < 0) { perror("kill"); exit(1); }
    if (!wait) return;
    int status;
    if (waitpid(pid, &status, WUNTRACED | WCONTINUED) < 0) {
        perror("waitpid");
        exit(1);
    }
    show(pid, status);

main에서는 핸들러를 설치하는 시점과 제어 순서를 봅니다. term과 kill 모드는 fork 전에 설치하므로 자식이 핸들러를 물려받습니다. late 모드에서는 부모가 50 ms 뒤에 SIGUSR1을 보내고 그 결과를 본 뒤 끝납니다. 그 밖의 모드에서는 보고 → 멈춤 → 재개 → 보고 → TERM 또는 KILL의 순서로 진행합니다.

    if (!late) {  /* fork 전에 설치 → 자식이 물려받는다 */
        install(SIGUSR1, on_usr1);
        install(SIGTERM, on_term);
    }
    pid_t pid = fork();
    if (pid < 0) { perror("fork"); return 1; }
    if (pid == 0) worker(late);

    printf("parent: started worker %d (mode %s)\n", (int)pid, mode);
    if (late) {  /* 자식이 설치하기 전에 보낸다 */
        sleep_ms(50);
        send(pid, SIGUSR1, "SIGUSR1", 1);
        return 0;
    }
    sleep_ms(350);  send(pid, SIGUSR1, "SIGUSR1", 0);
    sleep_ms(100);  send(pid, SIGSTOP, "SIGSTOP", 1);
    sleep_ms(500);  /* 멈춘 동안 자식은 일하지 않는다 */
    send(pid, SIGCONT, "SIGCONT", 1);
    sleep_ms(250);  send(pid, SIGUSR1, "SIGUSR1", 0);
    sleep_ms(100);
    if (strcmp(mode, "kill") == 0) send(pid, SIGKILL, "SIGKILL", 1);

실행 결과: 멈춤 · 재개 · 보고 · 정리 종료

강의에서는 같은 컨테이너 환경에서 ./sigctl을 실행한 화면을 보았습니다. 확인할 점은 세 가지입니다.

  • 보고된 틱은 4에서 9로 늘었습니다. 멈추지 않았다면 두 번째 보고에서 약 12틱이었을 것입니다. 멈춘 0.5초 동안 자식은 일하지 않았습니다.
  • stopped와 continued가 모두 출력됩니다. WUNTRACED와 WCONTINUED 덕분에 부모가 두 변화를 모두 받았습니다.
  • 정리 후 exit 0으로 끝납니다. SIGTERM은 핸들러가 받아 루프를 끝냈고, 부모는 exited with 0을 출력합니다.

틱 수는 실행마다 1–2씩 다를 수 있습니다. 시그널이 nanosleep을 일찍 깨우면 한 틱이 더해지기 때문입니다.

실행 결과: kill 모드와 late 모드

  • kill 모드에는 정리가 없습니다. 출력에 "cleanup" 줄이 나오지 않습니다. SIGKILL은 핸들러를 설치할 수 없는 시그널이어서 자식에게 정리할 기회가 없습니다.
  • late 모드의 자식은 10번 시그널에 죽습니다. 핸들러 설치 전에 도착한 SIGUSR1에는 기본 동작인 종료가 적용됩니다.
  • 부모는 두 경우를 모두 압니다. waitpid의 결과가 WIFSIGNALED이고, 시그널 번호와 이름을 strsignal로 출력합니다.

실행 결과: 멈춘 자식은 ps에서 T

sigctl이 도는 동안 0.45–0.95초 구간에 ps를 찍어 보면 자식의 STAT 열이 T입니다. ps(1)의 PROCESS STATE CODES에서 T는 작업 제어 시그널로 멈춘 상태(stopped by job control signal)이고, 자식은 SIGSTOP을 받아 멈춰 있는 것입니다. 같은 화면에서 부모의 STAT는 S(interruptible sleep)입니다. 부모는 waitpid와 sleep_ms에서 잠든 채로 기다리고 있습니다. 이 관찰은 로그와도 일치하여, 같은 순간 부모의 로그에는 "stopped by signal 19"가 찍혀 있습니다.

2부 정리: 시그널 제어의 규칙 다섯

  1. 보내기는 kill, 확인은 waitpid(WUNTRACED | WCONTINUED)입니다.
  2. 자식의 핸들러는 깃발만 세웁니다. 출력과 정리는 메인 루프에서 합니다.
  3. 핸들러는 fork 전에 설치합니다. 늦으면 기본 동작(SIGUSR1은 종료)이 일어납니다.
  4. 멈춘 자식에게 보낸 SIGTERM은 SIGCONT 뒤에 처리되고, SIGKILL은 즉시 처리됩니다.
  5. 끝낼 때는 먼저 SIGTERM으로 정리할 기회를 주고, 그래도 끝나지 않으면 SIGKILL을 보냅니다.

다섯째 규칙의 순서(SIGTERM → 기다림 → SIGKILL)는 docker stop과 systemd의 서비스 중지도 그대로 따릅니다.

두 방법은 어느 한쪽을 고르는 것이 아니라 함께 쓰입니다. 셸이 좋은 예입니다. 명령 실행은 fork · exec · waitpid로 하고, 작업 제어(Ctrl+Z, fg, kill)는 시그널로 합니다.

실습 과제

과제는 세 가지이며, 두 예제를 고쳐 보는 것입니다.

  1. forkpool 시간 제한. 작업이 1초를 넘으면 부모가 kill(pid, SIGKILL)로 끝내고 실패로 처리합니다. 방법은 둘 중 하나를 고릅니다. 하나는 WNOHANG 폴링에 작업별 시작 시각 기록을 더하는 것이고, 다른 하나는 alarm과 SIGALRM을 쓰는 것입니다.
  2. 재시도 정책. WIFSIGNALED인 작업, 곧 시그널로 죽은 작업은 재시도하지 않게 바꿉니다. 확인하려면 ./forkpool 6 1을 실행하는 동안 다른 창에서 kill -9 <job PID>를 보냅니다.
  3. sigctl 속도 전환. SIGUSR2를 "속도 바꾸기"로 약속하고 틱 간격을 100 ms와 50 ms 사이에서 바꿉니다. 깃발 want_speed와 핸들러 on_usr2가 필요하고, 핸들러는 fork 전에 설치하며, 부모가 실행 도중에 시그널을 보내게 합니다.

정리

  • 부모는 fork 순간의 값으로 자식에게 일을 나눠 주고, waitpid로 거두며, 종료 코드(0–255)로 결과를 판정합니다.
  • waitpid(-1)은 먼저 끝난 자식부터 돌려줍니다. 빈 자리를 바로 채우는 작업 풀(동시 실행 수 제한, 재시도)의 핵심입니다.
  • 도는 중인 자식에게는 kill로 시그널을 보내 끼어듭니다. SIGSTOP · SIGCONT는 멈춤과 재개, SIGUSR1은 약속한 요청, SIGTERM은 정리 종료, SIGKILL은 강제 종료입니다.
  • 변화의 확인은 waitpid(WUNTRACED | WCONTINUED)로 합니다. kill의 성공은 "보냈다"일 뿐입니다.
  • 핸들러는 깃발만 세우고, fork 전에 설치합니다. 늦으면 기본 동작(SIGUSR1은 종료)이 먼저 일어납니다.
