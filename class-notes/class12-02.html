지난 시간에는 파이프의 규칙을 배웠습니다. 쓰기 끝이 모두 닫혀야 EOF가 오고, 65536바이트가 차면 write가 잠듭니다. 이번 시간에는 새 함수를 배우지 않습니다. 같은 규칙을 더 어려운 세 상황에 적용합니다. 서로 묻고 답할 때(1부), 명령을 셋·넷·다섯 개씩 이을 때(2부), 따로 실행된 여러 프로그램의 요청을 받을 때(3부)입니다. 이 과정에서 프로그램을 일부러 여러 번 멈추게 하고, 왜 멈췄는지 찾는 연습을 합니다. 전체를 꿰는 한 문장은 "멈췄으면 누가 누구를 기다리는지 그린다"입니다.

도입: 1차시에서 이어지는 질문

1차시에 한 문장씩만 하고 넘어간 것이 셋 있습니다. 양방향 통신은 파이프 두 개가 필요하고 교착을 조심해야 한다는 것, pipe2 예제는 명령 둘만 이었다는 것(파이프 하나), recv는 send 하나를 받고 끝났으며 답도 돌려주지 못했다는 것입니다. 이번 시간의 세 부는 이 셋을 하나씩 끝까지 따라갑니다. 1부에서는 끝점 여덟 개를 정리하고 교착 세 가지를 직접 만들고, 2부에서는 명령 N개를 반복문 하나로 잇고(파이프 N−1개), 3부에서는 여러 클라이언트를 계속 받으면서 각자에게 답을 돌려줍니다.

규칙 네 줄은 그대로, 달라지는 것은 끝점의 개수

규칙은 새로 생기지 않습니다. 1차시의 네 줄이 전부입니다.

호출상황결과
read비었고 쓰기 끝이 남아 있다잠든다
read비었고 쓰기 끝이 0개다0 (EOF)
write65536바이트가 찼다잠든다
write읽기 끝이 0개다SIGPIPE (무시하면 EPIPE)

달라지는 것은 끝점의 개수입니다. 파이프 하나에 프로세스 둘이면 끝점이 넷이었는데, 이번에는 여덟 개, 그리고 2N개를 다룹니다. 개수가 늘면 하나쯤 닫는 것을 잊기 쉽고, 그 하나가 프로그램을 멈춥니다. 멈춘 프로그램을 들여다볼 도구는 세 가지입니다. ps의 STAT 열, ls -l /proc/PID/fd, strace -p PID입니다.

입문 예제 pipe_two: 한 번 묻고 한 번 답한다

pipe_two는 가장 작은 양방향 프로그램입니다. 부모가 ping이라고 묻고 자식이 pong이라고 답하는 것이 전부이며, 교착이 없는 가장 단순한 경우입니다. 프로그램은 pipe를 두 번 불러 req(부모 → 자식)와 rep(자식 → 부모) 두 파이프를 만든 뒤 fork합니다. 그다음 자식과 부모가 하는 일은 서로 정반대입니다.

/* 자식 */
close(req[1]);              /* 자식은 req에 쓰지 않는다 */
close(rep[0]);              /* 자식은 rep에서 읽지 않는다 */
n = read(req[0], buf, sizeof buf);      /* 질문이 올 때까지 잠든다 */
...
if (write(rep[1], "pong\n", 5) == -1)   /* 반대 방향 파이프로 답한다 */

/* 부모 */
close(req[0]);                  /* 부모는 req에서 읽지 않는다 */
close(rep[1]);                  /* 부모는 rep에 쓰지 않는다 */
if (write(req[1], "ping\n", 5) == -1)       /* 먼저 묻는다 */
    perror("write");
n = read(rep[0], buf, sizeof buf);          /* 그다음에 답을 기다린다 */

자식은 req의 쓰기 끝과 rep의 읽기 끝을 닫고, 부모는 정확히 반대쪽 둘을 닫습니다. 그리고 자식은 read를 먼저 하고 write를 하며, 부모는 write를 먼저 하고 read를 합니다. "먼저 묻고, 그다음 기다린다"는 순서가 코드에 적혀 있고, 이 순서가 어긋나지 않기 때문에 프로그램이 끝납니다. 부모의 write와 read 두 줄을 바꾸면 부모는 답을 기다리고 자식은 질문을 기다려, 둘 다 read에서 영원히 잠듭니다. 1부에서 이것을 직접 만듭니다.

실행하면 첫 줄에 fd 번호 넷이 나옵니다. 3과 4가 req 파이프, 5와 6이 rep 파이프로, 0·1·2 다음의 빈 번호 넷입니다. 자식이 5바이트 ping을 받고 부모가 5바이트 pong을 받습니다. 질문과 답이 서로 다른 파이프를 지나갔고, 프로그램은 멈추지 않고 끝납니다. 당연해 보이지만, 이번 시간에는 이것이 당연하지 않게 되는 경우를 봅니다.

1부 양방향과 교착

파이프 두 개로 묻고 답하는 구조를 정리하고, 그 구조에서 양쪽이 서로를 기다리다 멈추는 교착 세 가지를 직접 만들어 본 뒤 푸는 방법을 익힙니다. 세 경우 모두 오류 메시지가 없습니다. 그냥 조용히 멈춥니다.

양방향은 파이프 두 개, 끝점은 여덟 개

파이프는 한 방향입니다. 그래서 방향이 둘이면 파이프도 둘입니다. fork를 하면 부모와 자식이 같은 fd를 똑같이 갖게 되므로 끝점은 파이프 2 × 끝 2 × 프로세스 2 = 8개가 됩니다. pipe_two의 실행 결과(req = 3,4 · rep = 5,6)로 적으면 다음과 같습니다.

fd끝점부모자식
3req 읽기닫음남김
4req 쓰기남김닫음
5rep 읽기남김닫음
6rep 쓰기닫음남김

부모는 req에 쓰고 rep에서 읽으니 4번과 5번만 필요하고, 자식은 반대로 3번과 6번만 필요합니다. 각자 "내가 쓰지 않는 끝" 둘을 닫는 것이며, 1차시의 규칙을 파이프마다 한 번씩 적용한 것입니다. 닫는 것은 모두 넷이고 부모와 자식이 서로 정반대쪽을 닫습니다. 한 가지 요령이 있습니다. fd[0], fd[1]이라는 이름으로는 헷갈리므로 req·rep, to·from처럼 방향이 보이는 이름을 붙입니다.

닫기 장부: 닫지 않으면 무슨 일이 생기나

닫아야 할 넷 각각에 대해, 닫지 않았을 때 무슨 일이 생기는지가 중요합니다.

끝점닫는 쪽안 닫으면
req 쓰기 끝 (자식의 4번)자식부모가 다 묻고 close해도 자식의 read가 0을 받지 못한다 → 자식이 끝나지 않는다 (1차시의 leak)
req 읽기 끝 (부모의 3번)부모자식이 죽어도 부모의 write가 SIGPIPE를 받지 못한다 → 가득 차면 영원히 잠든다
rep 쓰기 끝 (부모의 6번)부모자식이 죽어도 부모의 read가 0을 받지 못한다 → 부모가 끝나지 않는다
rep 읽기 끝 (자식의 5번)자식부모가 죽어도 자식의 write가 SIGPIPE를 받지 못한다 → 자식이 남는다

규칙은 하나입니다. EOF는 "그 파이프의 쓰기 끝이 0개"일 때, SIGPIPE는 "그 파이프의 읽기 끝이 0개"일 때 오며, 파이프마다 따로 셉니다. 쓰기 끝을 잊으면 "끝나지 않는다"가 되고, 읽기 끝을 잊으면 "상대가 죽은 것을 모른다"가 됩니다. 읽기 끝 두 줄은 정상 동작할 때는 티가 나지 않고 상대가 비정상으로 죽은 날에야 프로그램이 멈추므로 더 찾기 어렵습니다.

대화 규약: 차례 · 경계 · 끝

끝점을 정확히 닫아도 양방향 프로그램은 멈출 수 있습니다. 두 프로그램이 대화하는 방법을 약속하지 않았기 때문입니다. 이 약속을 규약(프로토콜)이라고 합니다. 커널은 바이트만 옮길 뿐이고, 그 뜻은 두 프로그램이 정합니다. 정할 것은 셋입니다.

  • 차례 — 누가 먼저 말하는가. 한쪽은 write → read, 다른 쪽은 read → write여야 합니다. 둘 다 read부터 하면 영원히 기다립니다.
  • 경계 — 한 마디는 어디까지인가. 파이프는 바이트 스트림이라 write 두 번이 read 한 번에 올 수 있습니다. 줄바꿈으로 끝내기, 길이를 먼저 보내기, 고정 길이로 정하기 중에서 고릅니다.
  • 끝 — 대화는 어떻게 끝나는가. 묻는 쪽이 쓰기 끝을 닫으면 답하는 쪽이 EOF를 보고 끝냅니다. 또는 "종료" 메시지를 따로 정합니다.

예제 pipetalk의 규약은 이렇습니다. 질문은 "A B\n", 답은 "합\n"입니다. 부모가 묻고 자식이 답하되 한 번에 하나씩 합니다. 부모가 쓰기 끝을 닫으면 자식이 EOF를 보고 끝냅니다. 번갈아 하면 답을 받기 전에는 다음 질문을 보내지 않으므로 파이프 안에는 늘 메시지가 하나뿐이고, 그래서 read 한 번에 메시지 하나가 옵니다. 이 약속을 지키지 않으면 아래의 교착이 됩니다.

교착 ①: 둘 다 read부터 한다

부모가 질문을 보내기 전에 read부터 합니다. 자식도 질문을 기다리며 read를 하고 있습니다. 부모는 자식의 답을 기다리고 자식은 부모의 질문을 기다립니다. 이렇게 서로가 상대의 다음 행동을 기다리는 고리가 교착(deadlock)입니다. "기다린다" 화살표가 한 바퀴 돌면 교착입니다.

이때 두 파이프는 비어 있고 쓰기 끝은 모두 열려 있습니다. 그래서 EOF도 오지 않습니다. 커널은 두 프로그램의 약속을 모르고, 쓰기 끝이 열려 있으니 "언젠가 누가 쓸 것"인 정상 상태로 봅니다. 오류도 없고 CPU도 쓰지 않으며, 그냥 끝나지 않습니다. 진단은 다음과 같이 합니다.

ps -o pid,ppid,stat,cmd     →  둘 다 S (잠듦)
strace -p PID               →  둘 다 read( 에서 괄호가 닫히지 않은 채 멈춤

푸는 법은 한쪽이 먼저 쓰도록 차례를 정하는 것입니다.

교착 ②: 쓰기만 하면 양쪽 파이프가 찬다

둘째 교착은 차례를 지켜도 생깁니다. 부모가 큰 데이터를 자식에게 보내고, 자식은 받은 것을 그대로 돌려보냅니다(메아리). 부모는 다 보낸 뒤에 읽을 생각이라 아직 read(rep)를 부르지 않았습니다. 자식이 돌려보낸 데이터는 rep 파이프에 쌓이고, 부모가 읽지 않으니 65536바이트에서 rep가 가득 차 자식이 write에서 잠듭니다. 자식이 잠들었으니 req를 읽을 프로세스가 없고, req도 65536바이트에서 가득 차 부모가 write에서 잠듭니다. 부모는 자식이 req를 비워 주기를, 자식은 부모가 rep를 비워 주기를 기다립니다. 또 고리입니다.

멈추는 지점은 대략 rep 65536 + 자식이 손에 든 4096 + req 65536 = 135168바이트입니다(Linux 기본 용량으로 계산한 값). 1차시에 직접 잰 65536이라는 숫자가 여기서 한계가 됩니다.

이 교착이 위험한 이유는 용량이 잘못을 숨기기 때문입니다. 13만 바이트까지는 버퍼가 받아 줘서 잘못된 순서가 드러나지 않습니다. 작은 입력으로 테스트하면 통과하고, 큰 입력을 만난 날 오류 없이 멈춥니다. popen으로 양방향을 하지 못하는 이유도 이것입니다.

교착 ③: 답을 썼는데 가지 않는다 — stdio 버퍼

셋째 교착은 가장 찾기 어렵습니다. 차례도 맞고 데이터도 작은데 멈춥니다. 자식이 답을 printf나 fprintf로 썼기 때문입니다. 4주차에 배운 대로 stdio는 출력을 바로 내보내지 않고 버퍼에 모으며, 내보내는 때는 stdout이 가리키는 곳에 따라 다릅니다.

stdout이 가리키는 곳버퍼링실제 write가 일어나는 때
터미널줄 버퍼줄바꿈을 만날 때마다
파이프 · 파일전체 버퍼버퍼가 찰 때 · fflush · fclose · 정상 종료
(참고) stderr버퍼 없음즉시

자식이 fprintf(fp, "3\n")로 답을 쓰면, 자식은 답을 썼다고 생각하고 다음 질문을 기다립니다. 그런데 답은 커널의 파이프가 아니라 자식의 메모리 안 stdio 버퍼에 있고, rep 파이프는 비어 있습니다. 부모는 read에서 답을 기다립니다. 고리입니다. 고치는 방법은 셋입니다.

  • 답 한 줄마다 fflush(fp)를 부른다.
  • setvbuf(fp, NULL, _IOLBF, 0)으로 줄 버퍼로 바꾼다.
  • stdio를 쓰지 않고 write를 직접 부른다.

이 문제가 고약한 이유는 터미널에서 혼자 실행하면 줄 버퍼라서 잘 된다는 것입니다. 파이프에 연결하는 순간 멈춥니다. 또 내가 만든 프로그램이 아니라 exec한 남의 필터가 이렇게 버퍼링한다면 밖에서 고치기 어렵습니다.

교착을 푸는 세 가지 방법

세 교착의 공통점은 기다림의 고리였습니다. 푸는 방법의 공통 원리는 고리에서 화살표 하나를 끊는 것입니다.

방법내용맞는 곳
① 번갈아 한다한 메시지를 쓰고, 그 답을 읽은 뒤 다음 메시지를 쓴다. 메시지는 파이프 용량보다 작게 하고 답마다 fflush한다.질문–답 구조
② 쓰는 프로세스를 따로fork를 한 번 더 해서 하나는 쓰기만, 하나는 읽기만 한다. 서로 기다리지 않는다. 셸의 파이프라인이 큰 데이터에도 멈추지 않는 것과 같은 원리다.큰 데이터 흘려보내기
③ 기다리지 않는 fdO_NONBLOCK + poll(2)로 지금 읽을 수 있는 쪽과 쓸 수 있는 쪽을 골라 처리한다. 프로세스 하나로 되지만 코드가 길어진다.이번 시간에는 이름만

예제는 ①(pipetalk ask)과 ②(pipetalk fix)를 씁니다. ③은 과제 ①의 선택 항목입니다.

예제 pipetalk: 다섯 모드

pipetalk에서는 부모가 덧셈 문제를 내고 자식이 답합니다. 그리고 일부러 세 번 멈춰 봅니다. 사용법은 ./pipetalk ask | both | mute | flood N | fix N입니다. 멈춘 모드는 Ctrl+C로 끝내거나 다른 터미널에서 pkill pipetalk로 끝냅니다.

모드자식의 역할부모가 하는 일결과
ask계산: "A B"를 받아 합을 답한다질문 → 답을 세 번 되풀이정상 종료
both계산질문보다 먼저 read를 부른다교착 ① 둘 다 read
mute계산, 단 fflush를 하지 않는다ask와 같다교착 ③ 답이 버퍼에

fix N메아리쓰는 자식을 따로 두고 자신은 읽는다정상 종료

자식의 역할은 둘입니다. 계산 역할은 숫자 둘을 받아 합을 답하고, 메아리 역할은 cat처럼 받은 바이트를 그대로 돌려보냅니다. 정상 모드와 멈추는 모드의 차이는 소스에서 각각 한두 줄입니다.

spawn — 끝점 여덟 개를 넷으로. 다섯 모드 모두 spawn()으로 시작합니다. 앞의 끝점 표가 그대로 코드가 된 함수입니다. 파이프 둘을 fork보다 먼저 만들고, 자식은 둘을 닫은 뒤 역할 함수로 들어가 돌아오지 않으며, 부모는 반대쪽 둘을 닫고 남은 둘을 to와 from이라는 이름으로 돌려줍니다.

    if (pid == 0) {
        close(req[1]);              /* 자식 ①: req의 쓰기 끝 */
        close(rep[0]);              /* 자식 ②: rep의 읽기 끝 */
        ...
    }
    close(req[0]);                  /* 부모 ①: req의 읽기 끝 */
    close(rep[1]);                  /* 부모 ②: rep의 쓰기 끝 */
    *to_child = req[1];
    *from_child = rep[0];

이 close 네 줄이 닫기 장부의 네 줄입니다. 함수 밖에서는 req, rep, 0, 1 같은 것을 볼 필요가 없고 보낼 곳과 받을 곳만 있습니다. 참고로 부모의 close(req[0])을 지워도 ask 모드는 멈추지 않습니다. 읽기 끝을 잊은 것이라 정상 동작에서는 드러나지 않기 때문입니다.

계산하는 자식. 자식은 fdopen(out, "w")로 fd를 FILE *로 감쌉니다. 이 순간부터 stdio 버퍼가 사이에 낍니다. 질문은 read 루프로 받는데, 번갈아 하는 규약이라 read 한 번에 질문 하나가 옵니다. read가 0이면 부모가 쓰기 끝을 닫았다는 뜻(EOF)입니다.

        fprintf(fp, "%d\n", a + b); /* 아직 fp의 버퍼 안에만 있다 */
        if (!mute)                  /* mute 모드는 다음 줄만 건너뛴다 */
            fflush(fp);             /* 버퍼를 비워야 파이프로 나간다 */

fprintf 직후의 답은 fp의 버퍼에 있고, fflush가 그것을 파이프로 내보냅니다. mute 모드는 이 한 줄만 건너뜁니다. 1차시의 leak 모드가 close 한 줄만 건너뛴 것과 같은 방식입니다. 루프를 나온 뒤의 fclose(fp)는 남은 버퍼를 비우지만, mute에서는 부모가 첫 답을 기다리느라 쓰기 끝을 닫지 않으므로 자식이 거기까지 가지 못합니다.

부모: 묻고, 기다린다. 정상 흐름은 질문 하나를 write 한 번으로 보내고 read로 답을 기다리는 것을 세 번 되풀이하는 것입니다. both 모드는 그 앞의 if로 들어가, 질문을 하나도 보내지 않은 채 read를 부르고 여기서 영원히 멈춥니다.

    if (read_first) {               /* both: 묻기 전에 답부터 기다린다 */
        ...
        n = read(from, buf, sizeof buf);        /* 영원히 돌아오지 않는다 */
    }
    for (int i = 0; i < 3; i++) {
        if (write(to, q[i], strlen(q[i])) == -1)    /* 질문 하나 = write 한 번 */
            die("write");
        ...
        n = read(from, buf, sizeof buf);        /* 답이 올 때까지 잠든다 */
        ...
    }
    close(to);                      /* 더 물을 것이 없다 → 자식이 EOF를 받는다 */

대화를 끝내는 것은 마지막 줄입니다. to를 닫으면 자식의 read가 0을 받고 자식이 끝납니다. 질문 셋을 먼저 다 쓰고 답 셋을 나중에 읽도록 바꾸면, 질문이 작아서 멈추지는 않지만 답 셋이 read 한 번에 붙어서 올 수 있어 경계를 직접 나눠야 합니다. 번갈아 하면 그 문제가 없습니다.

flood와 fix. 큰 데이터를 보내는 두 모드는 send_all()을 누가 부르느냐만 다릅니다. send_all()은 4096바이트씩 쓰고 32768바이트마다 진행을 표준 오류로 알립니다.

    if (fix) {                      /* fix: 쓰는 일을 다른 프로세스에 맡긴다 */
        writer = fork();
        ...
        if (writer == 0) {
            close(from);            /* 쓰는 자식은 읽지 않는다 */
            send_all(to, total);
            exit(0);                /* to가 닫힌다 */
        }
    } else {
        send_all(to, total);        /* flood: 다 쓴 뒤에야 읽으러 간다 */
    }
    close(to);
    while ((n = read(from, buf, sizeof buf)) > 0)   /* 쓰는 동안에도 읽는다 (fix) */
        got += n;

flood에서는 send_all이 N바이트를 다 쓸 때까지 돌아오지 않아 그 아래의 read 루프에 가지 못합니다. N이 크면 여기서 멈춥니다. fix에서는 fork를 한 번 더 해서 새 자식이 쓰기를 맡고, 부모는 바로 read 루프로 갑니다. 이때 프로세스는 셋이며 부모는 읽기만, 쓰는 자식은 쓰기만, 메아리 자식은 옮기기만 합니다. 셸의 파이프라인과 같은 모양입니다. 닫는 것 둘도 봐야 합니다. 쓰는 자식은 from을 닫고, 부모는 to를 닫습니다. 부모가 to를 쥐고 있으면 메아리 자식이 EOF를 받지 못해서 부모의 read 루프도 끝나지 않습니다.

pipetalk 실행 결과

ask. 질문 한 줄, 답 한 줄이 번갈아 나오고, 답을 받은 뒤에야 다음 질문이 나갑니다. 답이 바로바로 오는 것은 자식이 답마다 fflush를 했기 때문입니다. 부모가 to를 닫자 자식이 EOF를 보고 스스로 끝났고 종료 코드는 0입니다. 이 0은 자식이 kill이 아니라 EOF를 보고 정상으로 끝났다는 것, 곧 req의 쓰기 끝이 모두 닫혔다는 것을 확인해 줍니다.

both와 mute. 두 모드를 백그라운드로 실행하고 ps로 봅니다.

./pipetalk both &
ps -o pid,ppid,stat,command -p $(pgrep -d, pipetalk)
pkill pipetalk

both는 "먼저 읽는다" 한 줄만 나오고 조용해집니다. 프로세스가 둘이고 STAT이 둘 다 S, 곧 잠든 상태입니다. 실행 중(R)인 것이 하나도 없습니다. 이것이 교착의 겉모습입니다. mute는 아무 줄도 나오지 않고 ps는 똑같이 S, S입니다. 겉은 같지만 속이 다릅니다. both는 질문이 아예 가지 않았고, mute는 질문이 갔고 자식이 답도 썼는데 그 답이 자식의 버퍼 안에 있습니다. 2부 N단 파이프라인

셸의 A | B | C | …를 반복문 하나로 만듭니다. 1차시의 pipe2는 명령 둘을 이었는데, 이번에는 셋, 넷, 다섯 개를 잇습니다. 코드는 길어지지 않습니다. 단계가 늘어도 부모가 기억할 것은 fd 하나뿐입니다.

2단에서 N단으로: 프로세스 N개, 파이프 N−1개

cut -d: -f7 /etc/passwd | sort | uniq -c | head -3은 프로세스 넷, 파이프 셋입니다. cut은 0번이 터미널이고 1번이 파이프 1, sort는 0번이 파이프 1이고 1번이 파이프 2, uniq는 0번이 파이프 2이고 1번이 파이프 3, head는 0번이 파이프 3이고 1번이 터미널입니다.

단계바꿔 끼울 것dup2
첫 단계1번 → 새 파이프의 쓰기 끝한 번
가운데 단계0번 ← 앞 파이프, 1번 → 새 파이프두 번
마지막 단계0번 ← 앞 파이프의 읽기 끝한 번

새로운 것은 가운데 단계입니다. 입력도 출력도 파이프라서 dup2를 두 번 합니다. N = 2였던 pipe2에는 가운데 단계가 없었습니다. 사실 모든 단계는 "앞 파이프에서 읽고, 새 파이프에 쓴다"의 특수한 경우입니다. 첫 단계는 앞이 없고 마지막 단계는 뒤가 없을 뿐입니다. 이것을 손으로 쓰면 N이 바뀔 때마다 코드가 바뀌므로 반복문이 필요합니다.

반복문 하나로: 부모는 prev 하나만 들고 간다

2부에서 가장 중요한 내용입니다. 부모는 변수 하나 prev를 들고 다닙니다. prev는 앞 파이프의 읽기 끝이고, 처음에는 없으니 -1입니다.

prev = -1                    /* 앞 파이프의 읽기 끝 */
for (i = 0; i < N; i++) {

    fork()
    자식:  prev  → 0번
           fd[1] → 1번
           exec(cmd[i])
    부모:  close(prev)
           close(fd[1])
           prev = fd[0]
}

한 바퀴에서 자식은 prev를 0번에, 새 파이프의 쓰기 끝을 1번에 끼우고 exec합니다. 부모는 세 줄을 합니다. 방금 자식에게 넘겨준 읽기 끝 prev를 닫고, 새 파이프의 쓰기 끝을 닫고, 새 파이프의 읽기 끝을 prev에 넣습니다. 이것이 다음 바퀴 자식의 입력이 됩니다. 단계가 몇 개든 부모가 다음 바퀴로 들고 가는 fd는 prev 하나뿐입니다. N이 100이어도 부모가 동시에 열어 두는 파이프 fd는 prev와 방금 만든 파이프의 둘, 많아야 셋입니다.

가운데 단계의 자식: dup2 두 번, close 세 번

둘째 바퀴의 자식을 예로 들면, fork 직후에는 0·1·2가 터미널이고 3번이 파이프 1의 읽기 끝(prev), 4번과 5번이 파이프 2의 읽기 끝(fd[0])과 쓰기 끝(fd[1])입니다. 자식이 할 일은 순서대로 다음과 같습니다.

① close(fd[0])   다음 단계가 쓸 읽기 끝
② dup2(prev, 0)  →  close(prev)
③ dup2(fd[1], 1)  →  close(fd[1])
④ execvp(cmd[i][0], cmd[i])

새 파이프의 읽기 끝은 다음 단계의 것이지 내 것이 아니므로 쥐고 있지 않고 먼저 닫습니다. dup2 뒤에 원래 번호를 닫는 것은 0번(또는 1번)이 이미 같은 파이프를 가리키고 있어 원래 번호가 필요 없기 때문입니다. dup2(prev, 0) 뒤에 close(prev)를 하지 않으면 같은 파이프의 읽기 끝이 0번과 3번 두 개가 되어, exec한 명령이 0번을 닫아도 3번이 남고 앞 단계가 SIGPIPE를 받지 못합니다. exec 직전에는 0번이 파이프 1의 읽기 끝, 1번이 파이프 2의 쓰기 끝, 2번이 터미널이고 3·4·5번은 닫혀 있어야 합니다. exec한 명령은 0·1·2만 압니다. 3번 이상이 남아 있다면 그것이 leak입니다.

부모가 안 닫으면 뒤에 태어나는 자식이 물려받는다

1차시 pipe2 -k에서는 부모가 쓰기 끝을 쥐고 있어서 뒤 명령이 끝나지 않았습니다. N단에서는 문제가 더 커집니다. 부모가 첫 바퀴에 파이프 1 = (3, 4)의 쓰기 끝 4번을 닫지 않았다고 합시다. fork는 그 순간 부모가 가진 fd를 전부 복사하므로, 둘째 바퀴의 fork에서 2단계 자식이 4를 물려받고, 셋째 바퀴의 fork에서 3단계 자식이 4와 6을 물려받습니다. echo | cat | ls 모양의 파이프라인이라면 파이프 1의 쓰기 끝은 다음과 같이 퍼집니다.

echo가 끝나도 쓰기 끝이 셋 남으므로 2단계 cat은 EOF를 받지 못합니다. 특히 cat은 자기가 읽는 파이프의 쓰기 끝을 자기가 쥐고 있어 영원히 EOF를 받지 못합니다. 2단에서는 부모만 쥐었지만 N단에서는 뒤의 자식들도 쥔다는 것이 1차시와의 차이입니다. 부모가 반복문이 끝난 뒤에 한꺼번에 닫아도 소용이 없습니다. 그 사이에 태어난 자식들이 이미 복사본을 갖고 있고, 자식의 복사본은 부모가 닫을 수 없기 때문입니다. 교훈은 한 줄입니다. 필요 없어진 fd는 다음 fork 전에 닫습니다.

찾을 때는 ls -l /proc/PID/fd에서 0·1·2 말고 남은 pipe를 찾습니다. 예방책으로는 pipe2(fd, O_CLOEXEC)가 있습니다. 이렇게 만든 fd는 exec할 때 저절로 닫힙니다.

ls | grep zzz0 · 11
yes | head -2 | wc -lSIGPIPE(13) · 0 · 00

첫 줄에서 false는 1로 끝나지만 마지막 true가 0이라 전체는 0입니다. 앞 단계의 실패는 종료 코드에 나타나지 않습니다. 그래서 백업 스크립트에 tar ... | gzip > backup.gz라고 쓰면 tar가 실패해도 스크립트는 성공으로 끝납니다. 둘째 줄은 grep이 마지막이고 찾지 못해 1이니 전체가 1입니다. 셋째 줄에서 yes는 SIGPIPE로 죽지만 전체는 0입니다. head가 먼저 끝나서 yes가 죽는 것은 파이프라인이 끝나는 정상적인 방법입니다. 시그널로 죽은 경우 셸은 128 + 번호로 보여 줍니다(141 = 128 + 13).

bash에서 단계별 상태를 모두 보려면 echo "${PIPESTATUS[@]}"를 쓰고, set -o pipefail을 켜면 0이 아닌 마지막 상태가 전체의 값이 됩니다. 파이프라인을 만드는 부모가 할 일은 둘입니다. 자식 N개를 모두 wait하고(하나라도 안 거두면 좀비가 남습니다, 10주차), 마지막 자식의 상태를 자신의 종료 코드로 돌려줍니다.

동시에 돈다: 모두 띄운 뒤에 모두 기다린다

파이프라인의 명령들은 차례로 실행되지 않고 동시에 실행됩니다. sleep 1을 셋 이으면 3초가 아니라 1초가 걸립니다. 코드에서는 이것이 순서로 나타납니다. 옳은 순서는 fork를 N번 다 한 뒤에 wait을 N번 하는 것입니다. fork하고 바로 wait하기를 N번 되풀이하면 두 가지가 잘못됩니다. 첫째, 3초가 걸립니다. 둘째가 더 심각한데, 앞 명령의 출력이 65536바이트를 넘으면 읽어 줄 다음 명령이 아직 태어나지 않았으므로 앞 명령은 write에서, 부모는 wait에서 영원히 잠듭니다. 1부의 교착 ②와 같은 모양입니다.

동시에 돌기 때문에 생기는 성질도 있습니다. 뒤 단계가 느리면 파이프가 차서 앞 단계가 잠들고, 그래서 속도가 저절로 맞습니다(흐름 제어). 중간 결과를 통째로 저장하지 않고 파이프 하나에 65536바이트만 있으면 됩니다. 끝나는 순서는 보통 앞에서부터지만 yes | head처럼 뒤가 먼저일 수도 있습니다. cat 큰파일 | head -1이 큰 파일을 끝까지 읽지 않는 것도, head가 한 줄을 받고 끝나면 cat이 SIGPIPE로 죽기 때문입니다.

예제 pipeline

pipeline은 셸의 CMD1 | CMD2 | … | CMDN을 반복문 하나로 만듭니다. 사용법은 ./pipeline [-v] [-k] CMD [ARG...] -- CMD [ARG...] [-- ...]로, 1차시 pipe2처럼 명령과 명령 사이를 --로 나누되 몇 개든 받습니다. -v는 바퀴마다 fd 번호를 보여 주고, -k는 부모가 쓰기 끝을 닫지 않게 합니다.

전체 흐름은 이렇습니다. 부모는 인자를 "--"에서 잘라 cmd[0] … cmd[N-1]을 만들고, pipe(fd)(마지막 단계에서는 건너뜀) → fork() → close(prev) · close(fd[1]) · prev = fd[0]을 N번 되풀이한 뒤, waitpid를 N번 하고 마지막 상태를 return합니다. 자식은 prev·fd[0]·fd[1]을 물려받고 태어나 close(fd[0]) · dup2(prev, 0) · dup2(fd[1], 1)을 한 뒤 execvp(cmd[i])를 부르며, 실패하면 perror 뒤 _exit(127)(셸의 "명령을 찾을 수 없음" 코드, 10주차)로 끝납니다. 반복문 안의 세 줄(close · close · prev =)이 이 프로그램의 핵심입니다.

자식 run_stage. 인자는 실행할 명령, 입력으로 쓸 fd, 출력으로 쓸 fd, 닫아야 할 fd 넷이고, 없으면 -1이 옵니다.

static void run_stage(char **cmd, int in, int out, int unused)
{
    if (unused != -1)               /* 새 파이프의 읽기 끝: 다음 단계의 것이다 */
        close(unused);
    if (in != -1) {                 /* 첫 단계가 아니면 입력을 앞 파이프로 */
        if (dup2(in, 0) == -1)
            die("dup2");
        close(in);                  /* 0번이 가리키니 원래 번호는 닫는다 */
    }
    if (out != -1) {                /* 마지막 단계가 아니면 출력을 새 파이프로 */
        if (dup2(out, 1) == -1)
            die("dup2");
        close(out);
    }
    execvp(cmd[0], cmd);            /* 성공하면 돌아오지 않는다 */
    ...

첫 단계는 부모의 prev가 처음에 -1이라 in이 -1로 와서 입력 부분을 건너뛰고(0번은 터미널 그대로), 마지막 단계는 out이 -1이라 출력 부분을 건너뜁니다. 가운데 단계는 둘 다 합니다. if 둘로 세 경우를 모두 처리합니다.

부모의 반복문. 앞의 뼈대가 실제 코드가 된 부분입니다.

    int prev = -1;                  /* 앞 파이프의 읽기 끝. 첫 단계는 없다 */
    for (i = 0; i < n; i++) {
        int fd[2] = { -1, -1 };     /* 이 단계와 다음 단계를 잇는 파이프 */

        if (i < n - 1 && pipe(fd) == -1)
            die("pipe");
        pid[i] = fork();
        ...
        if (pid[i] == 0)
            run_stage(cmd[i], prev, fd[1], fd[0]);
        ...
        if (prev != -1)
            close(prev);            /* 방금 자식에게 넘겨준 읽기 끝 */
        if (fd[1] != -1 && !keep)   /* -k는 다음 줄만 건너뛴다 */
            close(fd[1]);
        prev = fd[0];               /* 다음 바퀴의 입력이 된다 */
    }

바퀴마다 fd를 -1, -1로 시작하므로, pipe를 부르지 않는 마지막 단계에서는 -1이 그대로 남습니다. 자식은 run_stage에 입력 prev, 출력 fd[1], 닫을 것 fd[0]을 넘기고 돌아오지 않습니다. 마지막 바퀴에서는 fd[0]이 -1이라 prev도 -1이 됩니다. 따라서 반복문이 끝났을 때 부모가 열어 둔 파이프 fd는 0개이고, 반복문 뒤에 따로 닫을 것이 없습니다. -k 옵션은 쓰기 끝을 닫는 한 줄만 건너뜁니다.

기다리고, 마지막 것을 return. 반복문이 끝난 뒤 별도의 for가 waitpid(pid[i], &st, 0)으로 자식을 차례로 기다립니다. 이 for가 fork의 반복문 밖에 있다는 것이 중요합니다. 그래서 명령들이 동시에 돕니다. 각 자식에 대해 정상 종료(WIFEXITED)와 시그널 종료를 구분해 표준 오류로 보고합니다. 표준 출력은 마지막 명령의 것이기 때문에 보고는 표준 오류로 나갑니다.

        last = WIFEXITED(st) ? WEXITSTATUS(st) : 128 + WTERMSIG(st);
    }
    return last;                    /* 셸처럼 마지막 명령의 상태를 돌려준다 */

last는 매번 덮어쓰므로 마지막 자식의 값이 남고, 시그널로 죽었으면 셸의 관례대로 128을 더합니다.

pipeline 실행 결과

5단도 셸과 같은 결과.

cut -d: -f7 /etc/passwd | sort | uniq -c | sort -rn | head -3
./pipeline cut -d: -f7 /etc/passwd -- sort -- uniq -c -- sort -rn -- head -3

/etc/passwd에서 일곱째 칸을 잘라 정렬하고, 세고, 많은 순으로 다시 정렬해 위 셋을 냅니다. 명령이 다섯, 파이프가 넷이고 결과 세 줄이 셸과 같습니다. 그 사이에 섞여 보이는 대괄호 줄은 프로그램이 표준 오류로 낸 단계별 보고이며(결과만 보려면 뒤에 2>/dev/null을 붙입니다), 다섯 단계 모두 종료 코드 0입니다. 결과와 보고는 화면에서만 섞입니다. 코드는 2단일 때와 한 줄도 다르지 않고 반복문이 다섯 번 돌았을 뿐입니다.

-v: fd 번호를 따라간다.

./pipeline -v ls -l /dev/fd/ -- cat -- cat

맨 위 세 줄이 앞의 표입니다. 첫 바퀴에 파이프 3,4가, 둘째 바퀴에 4,5가 생겨 4번이 다시 쓰였습니다. 첫 단계의 ls -l /dev/fd/는 자기 자신이 열고 있는 fd를 보여 주는데, 줄 맨 앞 글자가 p인 것이 파이프입니다. 1번 하나뿐입니다. 표준 출력이 다음 단계로 이어져 있고, 0·1·2 밖에는 파이프가 없습니다. 부모가 넘겨준 것 말고는 물려받은 것이 없다는 뜻이므로 leak이 없습니다. 목록에 보이는 3번과 4번은 파이프(p)가 아니라 디렉터리(d)로, ls가 목록을 읽으려고 스스로 연 것입니다. Linux에서는 /dev/fd가 /proc/self/fd로 이어져 1 -> pipe:[번호]처럼 가리키는 대상까지 보입니다.

-k: 물려받은 쓰기 끝.

./pipeline -k echo hi -- cat -- ls -l /dev/fd/ &
ps -o pid,ppid,stat,command -p $(pgrep -d, "^(pipeline|cat)$")
pkill pipeline; pkill cat

이번에는 ls를 마지막 단계에 놓았습니다. 앞 단계의 출력을 읽는 자리이니 0번이 파이프인 것은 맞습니다. 그런데 4번과 6번에도 파이프가 있습니다. 부모가 닫지 않은 쓰기 끝 둘(4번이 파이프 1, 6번이 파이프 2의 쓰기 끝)을 물려받은 것입니다. 그리고 프로그램이 끝나지 않습니다. [1] echo 줄이 나와 echo는 끝났지만, ps를 보면 부모와 둘째 단계 cat이 S로 남아 있습니다. cat은 파이프 1의 EOF를 기다리는데 그 쓰기 끝을 부모와 cat 자신이 쥐고 있습니다. 앞에서 예측한 그대로입니다. 이 실행에서 hi가 출력되지 않는 것은, echo가 파이프 1에 쓰고 cat이 읽어 파이프 2에 썼지만 ls는 표준 입력을 읽지 않고 끝나 아무도 읽지 않았기 때문입니다.

종료 상태와 동시 실행.

./pipeline yes -- head -2 -- wc -l
./pipeline false -- cat -- true; echo "종료 코드 $?"
time ./pipeline sleep 1 -- sleep 1 -- sleep 1

첫 명령에서 yes는 y를 끝없이 내다가, head가 두 줄을 받고 끝나 읽기 끝이 0개가 된 뒤의 다음 write에서 시그널 13(SIGPIPE)으로 죽습니다. wc는 2를 셉니다. 둘째 명령은 false가 1로 끝났지만 마지막 true가 0이라 전체가 0입니다. 셋째 명령은 real이 1.0초로, sleep 1 셋이 동시에 돌았습니다.

3부 FIFO 서버

지금까지는 모두 부모와 자식 사이였습니다. 3부는 따로 실행된 프로그램들입니다. 서버 하나가 먼저 떠 있고 클라이언트 여럿이 와서 묻습니다. 도구는 1차시의 FIFO입니다. FIFO 하나로 요청을 받고 각자에게 답을 돌려주는 작은 서버를 만들며, 계속 받기 · 섞이지 않기 · 답 돌려주기의 세 문제를 차례로 풉니다.

1차시 recv의 한계: 한 번 받으면 끝난다

1차시의 recv는 mkfifo 뒤 open(읽기)에서 잠들었다가, send가 쓰기로 열고 한 줄을 쓰면 그것을 받고, send가 닫자 read가 0(EOF)을 돌려줘 unlink하고 끝났습니다. 서버란 먼저 떠서 기다리고, 요청에 답하고, 다시 기다리는 프로그램입니다. 그런 서버로 쓰기에는 문제가 셋입니다.

  • 문제 ① 계속 받기 — 클라이언트가 닫으면 EOF가 옵니다. 끝내거나, 끝내지 않으면 0만 되풀이해서 받습니다. 쓰기 끝이 0개인 동안 read는 기다리지 않고 0을 바로 돌려주므로 루프가 쉬지 않고 돌아 CPU를 100% 씁니다.
  • 문제 ② 섞이지 않기 — 여러 클라이언트가 동시에 쓰면 요청이 뒤섞이지 않는가.
  • 문제 ③ 답 돌려주기 — FIFO도 한 방향입니다. 답은 어느 길로, 누구에게 가는가.

EOF의 뜻은 쓰기 끝이 0개라는 것일 뿐이어서, 다음 클라이언트가 열면 다시 데이터가 옵니다. 세 문제의 답은 각각 쓰기 끝을 쥐는 것, 고정 길이 요청, 응답 FIFO입니다.

문제 ① 계속 받기: 서버가 쓰기 끝을 하나 쥔다

계속 받는 방법은 둘입니다.

방법 A: 닫고 다시 연다방법 B: 쓰기 끝을 쥔다
하는 일read가 0 → close → open(O_RDONLY)에서 다음 클라이언트를 기다린다in = open(fifo, O_RDONLY)
hold = open(fifo, O_WRONLY)
성질단순하다쓰기 끝이 0개가 되지 않는다 → read는 EOF 대신 다음 요청까지 잠든다
주의close하는 순간 이미 들어와 있던 요청이 버려질 수 있다EOF로 끝낼 수 없다. "종료 요청"을 따로 약속한다

방법 A는 1차시 과제 ③의 풀이였습니다. 닫는 순간에 이미 연결한 다른 클라이언트가 보낸 데이터가 있었다면 함께 버려진다는 점을 조심해야 합니다. 예제 fifosrv는 방법 B를 씁니다. 서버가 자기 FIFO를 쓰기로도 한 번 열되, 쓰지는 않고 쥐고만 있습니다. 그러면 클라이언트가 모두 떠나도 쓰기 끝이 하나 남고, "쓰기 끝 fd가 0개일 때만 EOF"라는 규칙에 따라 EOF가 오지 않습니다. 1차시에는 쓰기 끝을 쥐고 있는 것이 버그였는데, 같은 규칙을 이번에는 설계로 이용하는 것입니다. 이 두 번째 open은 잠들지 않습니다. 쓰기로 여는 open은 읽는 쪽이 있으면 바로 돌아오는데, 서버 자신이 이미 읽기로 열어 두었기 때문입니다.

문제 ② 섞이지 않기: PIPE_BUF 이하의 write는 원자적이다

여러 클라이언트가 한 FIFO에 동시에 쓸 때 적용되는 규칙이 있습니다.

write의 크기보장
PIPE_BUF 이하원자적: 다른 프로세스의 write와 섞이지 않는다
PIPE_BUF 초과섞일 수 있다

원자적이라는 것은 통째로 들어가거나, 자리가 날 때까지 기다리거나 둘 중 하나라는 뜻입니다. 중간에 다른 프로세스의 write가 끼어들지 않습니다. PIPE_BUF는 Linux에서 4096바이트이고, POSIX가 보장하는 최솟값은 512바이트입니다. 클라이언트 A·B·C가 각각 12바이트를 쓰면 요청이 통째로 줄을 서고, 서버는 12바이트씩 세 번 읽습니다. 반대로 PIPE_BUF를 넘는 write 둘이 동시에 일어나면 A의 앞부분, B의 앞부분, A의 뒷부분, B의 뒷부분처럼 조각이 번갈아 들어갈 수 있고, 읽는 쪽은 원래대로 나눌 수 없습니다.

그래서 조건이 둘입니다. 요청 하나가 PIPE_BUF 이하일 것, 그리고 요청 하나를 write 한 번으로 보낼 것. 요청을 나눠 쓰면 각 write는 원자적이어도 그 사이에 남의 요청이 낄 수 있습니다. 또 보장되는 것은 섞이지 않는다는 것뿐입니다. 누구의 요청이 먼저 들어갈지는 정해지지 않습니다.

요청의 형식: 고정 길이 구조체

요청들이 FIFO 안에 이어져 있으므로 서버는 어디서 끊어 읽을지 알아야 합니다. 1부에서 말한 경계 문제입니다. 경계를 정하는 방법 셋을 비교하면 다음과 같습니다.

경계를 정하는 법좋은 점주의할 점
줄바꿈으로 끝내기사람이 읽기 쉽다줄 끝을 직접 찾아야 한다
길이를 먼저 보내기길이가 달라도 된다read를 두 번 한다
고정 길이read 한 번에 하나길이가 정해진 자료만

fifosrv는 가장 간단한 고정 길이를 씁니다.

struct request {
    pid_t pid;   /* 보낸 클라이언트 */
    int a, b;    /* 더할 두 수 */
};

pid 4바이트, a 4바이트, b 4바이트로 요청 하나가 12바이트이고, 이것을 write 한 번으로 보냅니다. 서버는 read(in, &rq, sizeof rq)로 읽습니다. 쓰는 쪽도 읽는 쪽도 sizeof(struct request)를 쓰므로 언제나 요청이 정확히 하나 나옵니다. 12바이트는 PIPE_BUF(4096)보다 작으니 섞이지도 않습니다. pid가 0인 요청은 "서버 종료"로 약속합니다. 구조체를 그대로 보내도 되는 것은 서버와 클라이언트가 같은 컴퓨터에서 같은 프로그램으로 돌기 때문이며, 다른 컴퓨터끼리는 형식을 따로 정해야 합니다.

문제 ③ 답 돌려주기: 클라이언트마다 응답 FIFO

FIFO도 한 방향이니 답을 위한 FIFO가 따로 있어야 합니다. 1부에서 파이프를 둘 만든 것과 같습니다. 그런데 응답 FIFO를 하나만 두면 안 됩니다. 클라이언트 둘이 같은 FIFO에서 읽으면 A의 답을 B가 읽어 갈 수 있습니다. 한 번 읽은 바이트는 버퍼에서 사라지고, 읽는 쪽이 여럿이면 누가 먼저 가져갈지 정해지지 않기 때문입니다.

그래서 클라이언트마다 자기 응답 FIFO를 만듭니다. 이름은 서버 FIFO 이름 뒤에 자기 PID를 붙인 것입니다. 예를 들어 서버 FIFO가 /tmp/calc이면 PID 101인 클라이언트는 /tmp/calc.101, PID 102인 클라이언트는 /tmp/calc.102를 씁니다. PID는 겹치지 않으니 경로도 겹치지 않습니다. 요청 {pid, a, b} 안의 PID가 곧 주소여서, 서버는 "서버 FIFO 이름.PID"를 열어 답을 씁니다. 정리하면 서버 FIFO는 쓰는 쪽이 여럿이고 읽는 쪽이 하나이며, 응답 FIFO는 쓰는 쪽 하나(서버)와 읽는 쪽 하나(그 클라이언트)입니다. 응답 FIFO는 만든 쪽이 지웁니다. 클라이언트가 mkfifo하고 답을 받은 뒤 unlink합니다.

만남의 순서: 다섯 단계

요청 하나가 오가는 순서입니다.

클라이언트서버
① mkfifo(응답 FIFO)read(서버 FIFO)에서 잠들어 있다
② open(서버 FIFO, O_WRONLY)
③ write(요청 12바이트) · closeread → 요청을 받는다 → 더한다
④ open(응답 FIFO, O_RDONLY) — 잠듦open(응답 FIFO, O_WRONLY)
⑤ read(답) → unlink(응답 FIFO)write(답) · close → 다음 요청으로

FIFO의 open은 상대가 열 때까지 잠듭니다. ④에서 클라이언트의 open과 서버의 open이 서로를 깨웁니다. 어느 쪽이 먼저 부르든 상대가 열 때 함께 풀립니다. 순서에서 중요한 것은 ①이 ③보다 먼저여야 한다는 것입니다. 서버가 열 때 응답 FIFO가 이미 있어야 하기 때문입니다. 요청을 먼저 보내고 FIFO를 나중에 만들면, 빠른 서버가 아직 없는 FIFO를 열려다 ENOENT로 실패합니다.

서버가 조심할 것 네 가지

서버는 오래 떠 있고 남이 만든 클라이언트를 상대하므로 조심할 것이 있습니다.

  • SIGPIPE — 클라이언트가 답을 읽지 않고 죽으면 서버의 write가 서버를 죽입니다. 그래서 signal(SIGPIPE, SIG_IGN)으로 무시해 둡니다.
  • 사라진 클라이언트 — 요청만 보내고 죽으면 서버가 응답 FIFO의 open에서 영원히 잠듭니다. O_NONBLOCK으로 열고 ENXIO면 건너뛰는 방법으로 고칩니다. 예제는 이 부분에 약하며, 과제 ③이 이것을 고칩니다.
  • 정리 — 서버가 죽으면 FIFO 이름이 남습니다. 끝낼 때 unlink하고, 시작할 때는 EEXIST를 허용합니다.
  • 권한 — FIFO도 파일입니다. 0600으로 만들면 같은 사용자만 요청할 수 있습니다(5주차).

또 이 서버는 한 번에 한 요청만 처리합니다. 오래 걸리는 요청이 있으면 뒤의 클라이언트가 모두 기다립니다. 요청마다 fork해서 자식이 답하게 하면 되지만(10주차) 예제의 범위 밖입니다.

예제 fifosrv

fifosrv는 FIFO 하나로 여러 클라이언트의 덧셈 요청을 받는 서버입니다. 사용법은 ./fifosrv serve FIFO | ask FIFO A B | burst FIFO K | stop FIFO이며, serve는 한 터미널에서, 나머지는 다른 터미널에서 실행합니다.

클라이언트는 서버의 PID를 모릅니다. 서로 아는 것은 FIFO의 경로 하나뿐입니다. 세 클라이언트 모드 모두 서버 FIFO에 12바이트 구조체를 write 한 번으로 씁니다. burst는 맞는 답을 셉니다. 자식 i는 i + i×1000을 받아야 하므로, 남의 답을 받으면 바로 드러납니다.

serve: 열고, 쥔다.

    if (mkfifo(fifo, 0600) == -1 && errno != EEXIST)
        die("mkfifo");
    signal(SIGPIPE, SIG_IGN);
    ...
    int in = open(fifo, O_RDONLY);  /* 첫 클라이언트가 열 때까지 잠든다 */
    ...
    int hold = open(fifo, O_WRONLY);

FIFO를 0600으로 만들되 이미 있으면 그대로 쓰고, SIGPIPE를 무시합니다. 읽기 open은 첫 클라이언트가 열 때까지 잠듭니다. 그리고 같은 FIFO를 쓰기로 한 번 더 엽니다. hold는 이 뒤로 한 번도 쓰지 않고 쥐고만 있습니다. 이 한 줄이 서버를 계속 살려 둡니다. 이 줄을 지우면 첫 클라이언트가 닫는 순간 read가 0을 돌려주고 루프를 나와 끝나므로 1차시의 recv와 같아집니다.

serve: 읽고, 답한다.

    while ((n = read(in, &rq, sizeof rq)) == (ssize_t)sizeof rq) {
        if (rq.pid == 0)            /* stop이 보낸 종료 요청 */
            break;
        int sum = rq.a + rq.b;
        reply_path(path, sizeof path, fifo, rq.pid);
        int out = open(path, O_WRONLY);     /* 그 클라이언트의 응답 FIFO */
        if (out == -1) {
            perror(path);           /* 클라이언트가 사라졌다: 건너뛴다 */
            continue;
        }
        if (write(out, &sum, sizeof sum) == -1)
            perror("write");
        close(out);                 /* 클라이언트가 EOF를 받는다 */
        ...
    }
    close(hold);
    close(in);
    unlink(fifo);                   /* 이름을 지운다 */

루프는 12바이트씩 읽고, 요청이 없으면 잠듭니다. hold 덕분에 0은 오지 않습니다. pid가 0이면 종료 요청이니 루프를 나갑니다. 그렇지 않으면 PID로 응답 FIFO의 경로를 만들어 열고, 답을 쓰고, 닫습니다. 닫아야 클라이언트가 EOF를 받습니다. 응답 FIFO의 open이 실패하면(클라이언트가 응답 FIFO를 만들지 않았거나 이미 지운 경우) 서버는 죽지 않고 그 요청을 건너뜁니다. 한 번에 요청 하나를 끝까지 처리한 뒤 다음 요청을 읽으며, 루프를 나오면 쥐고 있던 것을 닫고 FIFO 이름을 지웁니다.

ask: 다섯 단계. 클라이언트 코드는 앞의 다섯 단계를 그대로 따릅니다. ① mkfifo(path, 0600)으로 응답 FIFO부터 만듭니다. ② open(fifo, O_WRONLY)로 서버 FIFO를 엽니다. 서버가 없으면 여기서 ENOENT로 실패하는데, 이때 만들어 둔 응답 FIFO를 unlink하고 끝냅니다. 실패 경로에서도 만든 것은 지워야 이름이 남지 않습니다. ③ 요청 구조체를 write 한 번으로 보내고 닫습니다. ④ open(path, O_RDONLY)로 응답 FIFO를 읽기로 열며, 서버가 열 때까지 잠듭니다. ⑤ 답을 읽고, 마지막에 자기 응답 FIFO를 unlink합니다.

fifosrv 실행 결과

# 터미널 1
./fifosrv serve /tmp/calc

# 터미널 2
ls -l /tmp/calc
./fifosrv ask /tmp/calc 3 4
./fifosrv ask /tmp/calc 100 -1

서버를 띄우면 FIFO가 생깁니다. ls -l의 맨 앞이 p이고 크기가 0입니다. FIFO이며 데이터는 디스크에 가지 않습니다. ask로 3 더하기 4를 물으면 서버가 첫 번째 요청을 처리하고 클라이언트가 7을 받습니다. 1차시와 다른 곳은 여기입니다. 첫 클라이언트가 끝났는데 서버는 끝나지 않았고, 두 번째 ask도 답을 받습니다. 두 클라이언트의 PID가 다르므로 응답 FIFO도 서로 달랐습니다. 응답 FIFO는 클라이언트가 답을 받은 직후 지우므로 요청이 처리되는 짧은 순간에만 존재합니다.

# 터미널 2
./fifosrv burst /tmp/calc 5
./fifosrv stop /tmp/calc
ls /tmp/calc*
./fifosrv ask /tmp/calc 1 2

burst로 다섯을 동시에 보내면 서버가 세 번째부터 일곱 번째까지 다섯 요청을 하나씩 처리합니다. 숫자가 깨진 줄이 없으므로 섞이지 않았고, 다섯이 모두 맞는 답을 받았으므로 자기 응답 FIFO에서 자기 답만 받았습니다. 다만 처리 순서는 실행할 때마다 같지 않을 수 있습니다. 자식들이 동시에 write하므로 FIFO에 들어가는 순서는 스케줄링에 따라 달라지고, 섞이지 않는 것만 보장됩니다. stop을 보내면 서버가 일곱 개를 처리했다고 알리고 끝납니다. FIFO가 지워졌고, 서버가 없는 상태에서 ask를 하면 파일이 없다는 오류(ENOENT)가 납니다.

파이프의 장점은 단순함입니다. read · write · close와 규칙 네 줄이 전부입니다. 오른쪽 열에 적힌 불편함을 다른 도구들이 어떻게 덜어 주는지는 13–14주차의 프로세스 간 통신에서 봅니다.

정리

  • 양방향은 파이프 두 개입니다. fork 뒤 끝점 여덟 개 중 부모와 자식이 각자 쓰지 않는 둘을 닫습니다.
  • 교착은 기다림의 고리입니다. 둘 다 read, 둘 다 write, 버퍼에 남은 답의 세 가지가 있습니다. 차례를 정하고, 답마다 fflush하고, 큰 데이터는 쓰는 프로세스를 따로 둡니다.
  • N단 파이프라인은 반복문 하나입니다. pipe → fork → 부모는 prev와 쓰기 끝을 닫고 prev를 바꿉니다. 다음 fork 전에 닫지 않으면 뒤의 자식이 물려받습니다.
  • 모두 띄운 뒤에 모두 기다립니다. 파이프라인의 종료 코드는 마지막 명령의 것입니다.
  • FIFO 서버는 쓰기 끝을 쥐어 EOF를 막고, PIPE_BUF 이하의 고정 길이 요청을 write 한 번으로 받고, 클라이언트마다 응답 FIFO로 답합니다.

파이프 프로그램이 오류 없이 멈춰 있으면 ps로 모두 S인지 보고, strace -p로 각자 어느 호출에서 멈췄는지 보고, ls -l /proc/PID/fd로 누가 어느 끝을 쥐고 있는지 본 다음, 누가 누구를 기다리는지 화살표로 그려 고리를 찾습니다.
