이번 차시의 주제는 메모리 매핑입니다. mmap은 파일 또는 익명 메모리를 프로세스의 가상 주소 범위에 연결하는 시스템 호출입니다. 먼저 메모리 구조를 복습한 뒤, 1부에서 주소 공간과 mmap의 기본을, 2부에서 공유·비공개·익명 매핑을, 3부에서 활용과 성능, 한계를 다룹니다. 입문 예제 mmap_basic과 본 예제 mapcat, mapmode, countnl이 각 부에 하나씩 연결됩니다.

메모리 구조 복습과 수업 지도

메모리를 보는 세 가지 좌표

메모리를 이야기할 때는 세 가지 좌표를 구분해야 합니다. 첫째는 프로세스의 가상 주소로, 포인터가 사용하는 좌표입니다. 둘째는 RAM, 곧 물리 메모리로, 실제 데이터가 놓이는 곳입니다. 셋째는 저장장치로, 파일 안의 바이트 위치(offset)가 여기에 해당합니다.

파일 매핑에서는 예를 들어 포인터 p = 0x70000000이 MMU의 주소 변환을 거쳐 페이지 캐시에 있는 파일 페이지를 가리키고, 그 페이지의 내용은 파일 I/O로 data.bin의 offset = 8192 위치에서 읽어 온 것입니다. 익명 매핑에서는 q = 0x71000000이 0으로 시작하는 익명 메모리를 가리키며, 여기에 대응하는 사용자 파일은 없습니다. 이 주소와 offset은 설명을 위한 예시입니다. 또한 실제 페이지 연결과 메모리 할당은 첫 접근까지 미뤄질 수 있습니다.

프로세스의 가상 주소 공간

프로세스의 주소 공간은 낮은 주소부터 text(기계어 코드, r-x), data·bss(전역 변수), 위로 자라는 heap(작은 malloc, brk), mmap 영역, 그리고 높은 주소에서 아래로 자라는 stack(지역 변수와 함수 호출)으로 배치됩니다. mmap 영역에는 libc.so.6, 파일 매핑, 익명 매핑, 큰 malloc이 놓이며, 이곳이 오늘 수업의 무대입니다.

이 주소들은 모두 가상 주소입니다. 프로세스마다 자기 주소 공간이 있으므로, 같은 주소라도 프로세스가 다르면 다른 물리 메모리를 가리킵니다. 주소 배치는 ASLR 때문에 실행할 때마다 달라집니다. 교안의 aarch64 컨테이너에서 실제로 본 주소는 실행 파일이 0xaaaa…, mmap 영역이 0xffff…였습니다. 이 배치는 /proc/PID/maps에서 직접 볼 수 있으며, 한 줄이 한 구간입니다.

C 코드의 변수는 어느 영역에 놓이는가

  • text·data·bss — 코드와 정적 수명의 객체. 함수의 기계어는 text에, int g = 7; 같은 초기화된 전역은 보통 data에, int z; 같은 0 초기화 전역은 bss에 놓입니다.
  • stack — 함수 호출과 자동 변수. 함수 안의 int x = 3;은 보통 스택에 놓입니다. 다만 최적화에 따라 레지스터에 남거나 없어질 수도 있습니다.
  • heap 또는 익명 매핑 — malloc이 얻는 공간. char *q = malloc(100);에서 q라는 포인터 변수와 q가 가리키는 할당 공간은 서로 다른 객체입니다.
  • 파일 매핑 — mmap이 반환한 주소가 가리키는 공간. char *p = mmap(...);에서 지역 변수 p는 보통 스택에, 파일 데이터는 별도의 매핑 영역에 놓입니다.

이것은 일반적인 Linux ELF·C 구현의 개념도입니다. const 객체, TLS, 최적화, 할당기 정책에 따라 실제 배치는 달라질 수 있습니다.

malloc·free에서 mmap·munmap으로

익숙한 malloc·free와 나란히 놓고 보면 mmap·munmap의 역할이 분명해집니다.

  • malloc(n)은 프로그램이 쓸 메모리 블록을 요청합니다. libc의 할당기가 n바이트를 사용할 포인터를 돌려주며, 일반 malloc 메모리의 초기값은 정해져 있지 않습니다.
  • free(q)는 할당기에 사용이 끝났다고 돌려줍니다. malloc 계열로 받은 포인터를 넘겨야 하며, free마다 곧바로 OS에 메모리를 반환하는 것은 아닙니다.
  • mmap(...)은 주소 범위와 연결 대상을 커널에 요청합니다. 파일 매핑은 파일 내용을, 익명 매핑은 0으로 시작하는 메모리를 연결합니다. malloc도 내부적으로 mmap을 쓸 수 있습니다.
  • munmap(p, len)은 프로세스의 주소 매핑을 해제합니다. 여기서 p는 물리 주소가 아니라 mmap이 반환한 가상 주소입니다. mmap으로 직접 만든 매핑은 free가 아니라 munmap으로 해제합니다.

페이지와 페이지 테이블

매핑, 보호, fault는 모두 페이지 단위로 일어납니다. 교안의 Ubuntu 24.04 컨테이너(aarch64)에서 getconf PAGESIZE는 4096, 곧 4 KiB였습니다. 그러나 일부 ARM 리눅스는 16 KiB나 64 KiB 페이지를 쓰므로, 코드에서는 값을 고정하지 말고 sysconf(_SC_PAGESIZE)로 얻어야 합니다.

페이지 테이블은 가상 페이지를 물리 프레임으로 번역하는 표입니다. CPU의 MMU가 이 표로 가상 주소를 물리 주소로 바꾸며, 표는 프로세스마다 따로 있습니다. 표에 빈 칸이 있는 것도 정상입니다. 아직 연결되지 않은 페이지에 접근하면 page fault가 일어나고, 커널이 프레임을 채워 연결합니다. 한 물리 프레임이 여러 곳에서 공유될 수도 있습니다.

프로세스가 달라도 같은 데이터를 볼 수 있는가

  • 기본 — 프로세스마다 자기 주소 공간. 다른 프로세스의 포인터 값을 받아도 바로 사용할 수 없습니다. 주소의 의미는 각자의 페이지 테이블에서 정해지기 때문입니다.
  • fork — 같은 값으로 시작하고 쓰기에서 갈라진다. 일반 전역·힙·스택은 부모와 자식이 독립적으로 바꿉니다. Linux는 보통 COW(copy-on-write)로 물리 페이지 복사를 늦춥니다.
  • 공유 매핑 — 서로 다른 주소가 같은 페이지를 가리킨다. MAP_SHARED로 같은 대상을 매핑하면 같은 데이터를 함께 볼 수 있습니다. 부모와 자식은 fork 전에 익명 공유 매핑을 만들어 둘 수 있습니다.

오늘 확인할 질문은 세 가지입니다. 파일을 포인터로 읽을 수 있는가, 쓴 내용은 누가 보는가, 첫 접근과 반복 접근에는 어떤 비용이 드는가입니다. 전역 변수와 공유 매핑의 차이는 mapmode anon에서 확인합니다.

read 경로와 mmap 경로

두 경로 모두 페이지 캐시를 거칩니다(O_DIRECT는 다루지 않습니다). read 경로에서는 디스크의 hello.txt가 커널 메모리인 페이지 캐시에 올라오고, 거기서 char buf[65536] 같은 사용자 버퍼로 복사됩니다. read를 부를 때마다 커널에서 사용자로 복사가 한 번 일어나고, 버퍼는 재사용하며, 오프셋은 커널이 관리합니다.

mmap 경로에서는 같은 페이지 캐시의 페이지를 페이지 테이블로 연결만 합니다. mmap으로 범위를 등록하고, page fault에서 페이지가 연결되며, 연결과 권한이 유효한 동안에는 CPU가 p[0] … p[len-1]에 직접 접근합니다. 두 경로는 같은 페이지 캐시를 쓰므로, 차이는 "복사하느냐, 연결하느냐"입니다.

OS 안에서 mmap이 놓이는 자리

  • 사용자 공간 — 프로그램과 libc. 프로그램이 mmap()을 호출하면 libc의 래퍼가 시스템 호출로 커널에 요청합니다.
  • 커널 — 가상 메모리 관리(MM). 주소 범위와 권한, 연결할 대상을 등록합니다. 파일 매핑은 VFS·파일시스템과 협력합니다.
  • 하드웨어 — CPU의 MMU와 TLB. p[i]는 CPU의 메모리 접근 명령입니다. MMU가 주소와 권한을 검사하고, 필요하면 예외를 냅니다.
  • 데이터 — RAM과 저장장치. 일반 파일은 페이지 캐시를 통해 연결됩니다. 저장장치 I/O는 데이터가 없을 때 필요해집니다.

이 수업의 범위는 Linux의 일반 파일 매핑과 익명 매핑입니다. 장치 매핑, DAX, MAP_POPULATE 등은 제외합니다.

VMA와 페이지 테이블은 서로 다른 정보다

VMA는 "이 주소 범위를 어떻게 사용할까"에 대한 기록입니다. 커널의 vm_area_struct에 범위, 권한, 공유 방식, 파일과 offset 등이 들어갑니다. 페이지 테이블은 "지금 어느 물리 페이지에 연결됐나"를 담습니다. 페이지별 연결과 하드웨어 권한이 여기에 있고, CPU는 TLB와 페이지 테이블로 주소를 변환합니다.

따라서 VMA는 있어도 페이지 연결은 없을 수 있습니다. 아직 접근하지 않은 파일 페이지는 보통 첫 접근에서 연결됩니다. maps에 보인다고 해서 그 내용이 RAM에 전부 있는 것은 아닙니다. 또 VMA의 쓰기 허용과 현재 페이지 테이블의 쓰기 허용은 다를 수 있는데, COW가 대표 사례입니다.

프로세스의 주소 공간은 mm_struct로 표현됩니다. 커널이 VMA들과 페이지 테이블을 관리하며, 같은 프로세스의 스레드들은 이 주소 공간을 공유합니다.

mmap 호출이 반환할 때까지

  1. 커널 진입과 검사. length, offset, flags와 fd의 접근 권한을 확인합니다. 잘못된 요청은 MAP_FAILED로 돌아옵니다.
  2. 가상 주소 범위 선택. addr가 NULL이면 빈 범위를 고릅니다. VMA를 만들거나 기존 VMA와 병합해 매핑 정보를 기록합니다.
  3. 파일 또는 익명 메모리와 연결. 파일 매핑은 파일 참조와 offset을 보관합니다. 익명 매핑은 파일 없이 0으로 시작하는 메모리를 제공합니다.
  4. 시작 주소 p 반환. 기본적인 지연 매핑에서는 이때 파일 전체를 읽지 않습니다. 각 페이지의 실제 준비는 접근할 때 진행될 수 있습니다.

mmap의 성공은 주소 범위의 매핑이 성공했다는 뜻입니다. 이후의 모든 메모리 접근이 성공한다는 보장은 아닙니다.

p[i]를 처음 읽을 때 커널이 하는 일

  1. CPU가 가상 주소 p+i를 읽는다. TLB에 변환이 없으면 페이지 테이블을 확인합니다. 페이지 연결이 없으면 page fault 예외로 커널에 진입합니다.
  2. 커널이 VMA와 접근 권한을 확인한다. 유효한 범위인지, 읽기가 허용되는지를 봅니다. 해결할 수 없는 범위·권한 위반이면 SIGSEGV를 전달합니다.
  3. 필요한 데이터를 준비한다. 일반 파일은 페이지 캐시를 찾고, 없으면 파일시스템을 통해 읽습니다. 익명 메모리는 0인 내용을 제공합니다.
  4. 페이지 테이블을 갱신하고 명령을 재개한다. 같은 load 명령을 다시 실행합니다. 변환과 권한이 유효한 동안 다음 접근은 사용자 모드에서 진행됩니다.

TLB miss만으로 커널에 진입하는 것은 아닙니다. 여기서는 하드웨어가 페이지 테이블을 탐색하는 일반적인 CPU를 가정합니다.

파일 매핑의 흐름: 등록에서 기록까지

  1. mmap — 가상 주소 범위를 파일 구간과 연결한다. 커널이 VMA에 권한, 공유 방식, 파일 offset을 기록합니다. 보통 이 시점에 파일 전체를 RAM으로 읽지는 않습니다.
  2. 첫 접근 — page fault에서 페이지를 준비한다. 페이지 캐시에 내용이 있으면 연결하고, 없으면 파일시스템을 통해 읽습니다. page fault는 CPU의 동기적 예외입니다.
  3. 읽기·쓰기 — 페이지를 통해 데이터를 사용한다. 유효한 연결은 CPU가 직접 사용합니다. SHARED 쓰기는 파일 페이지를 dirty로 만들고, PRIVATE 쓰기는 COW 사본으로 갑니다.
  4. 기록·해제 — 각 연산의 역할을 구분한다. 커널의 writeback이 공유 수정을 기록합니다. MS_SYNC는 기록 완료를 기다리고, close는 fd를, munmap은 매핑을 해제합니다.

주소·물리 메모리·파일 위치를 구분한다

구체적인 숫자로 세 좌표를 구분해 봅니다. p가 0x70000000이고 i가 5000이면 접근하는 가상 주소는 0x70001388입니다. 프로세스마다 주소 배치는 다릅니다. 파일 위치는 매핑 offset에 i를 더한 값이므로, offset이 8192라면 p[5000]은 파일의 13192바이트 위치에 대응합니다. 페이지 크기를 4096바이트로 가정하면 5000 = 4096 + 904이므로, 매핑의 두 번째 가상 페이지에서 904바이트째를 읽는 것입니다.

그 페이지가 놓인 RAM 위치, 곧 물리 프레임은 커널과 MMU가 연결하며, 가상 주소나 파일 offset과는 다른 값입니다. 페이지 캐시의 같은 페이지를 여럿이 함께 볼 수도 있습니다. 여기서 p의 주소와 페이지 크기는 설명용 가정이고, 파일 크기는 해당 접근을 포함할 만큼 충분하다고 가정했습니다.

파일 매핑과 익명 매핑의 실제 데이터

  • 파일 매핑 — 페이지 캐시가 파일 내용을 보관한다. 일반적인 read와 mmap은 같은 페이지 캐시를 이용합니다. 캐시는 RAM의 일부이며, 디스크와 별개의 하드웨어가 아닙니다.
  • 익명 매핑 — 사용자 파일이 없다. 처음에는 0을 읽습니다. 실제 페이지 할당은 지연될 수 있고, 필요할 때 swap으로 내보낼 수도 있습니다.
  • 메모리 회수 — 같은 주소, 달라질 수 있는 상주 상태. 깨끗한(clean) 파일 페이지는 버린 뒤 다시 읽을 수 있습니다. 수정한(dirty) 공유 파일 페이지는 writeback으로 파일에 기록합니다. 익명 메모리의 회수는 swap 설정 등에 영향을 받습니다.
  • 관찰 — 가상 크기와 RAM 사용량은 다르다. smaps의 Size는 매핑 크기, Rss는 현재 상주량입니다. 큰 매핑을 만들었다고 같은 크기의 RAM을 즉시 독점하는 것은 아닙니다.

mmap의 시그니처와 인자 여섯 개

#include <sys/mman.h>

void *mmap(void *addr, size_t length, int prot, int flags, int fd, off_t offset);
int munmap(void *addr, size_t length);      /* 성공 0, 실패 -1 */

mmap은 매핑의 시작 주소를 반환하고, 실패하면 MAP_FAILED((void *) -1)를 반환합니다.

인자묻는 것규칙

length몇 바이트0이면 EINVAL. 페이지 단위로 올림됩니다.
prot무엇을 허락할까PROT_READ · PROT_WRITE · PROT_EXEC · PROT_NONE
flags누구와 나눌까MAP_SHARED · MAP_PRIVATE, 여기에 MAP_ANONYMOUS
fd어느 파일open한 fd. 익명이면 -1입니다.
offset파일의 어디부터페이지 크기의 배수. 익명이면 0입니다.

prot과 flags 한눈에 보기

prot은 |로 묶고, flags는 MAP_SHARED와 MAP_PRIVATE 중 정확히 하나를 고른 뒤 필요하면 MAP_ANONYMOUS를 더합니다.

규칙 세 가지: 정렬 · MAP_FAILED · 수명

첫째, offset은 페이지 크기의 배수여야 합니다. mmap(…, fd, 1)은 실제로 EINVAL로 실패했고, mmap(…, fd, 4096)은 가능합니다. 파일 중간부터 보고 싶으면 offset을 페이지 경계로 내리고, 그 차이만큼 건너뛰어 읽습니다(실습 과제 ①이 이 내용입니다).

둘째, 실패는 MAP_FAILED로 검사합니다.

p = mmap(…);
if (p == MAP_FAILED)
    perror("mmap");

MAP_FAILED는 (void *) -1이므로, NULL과 비교하면 실패를 놓칩니다.

셋째, 매핑은 fd와 별개입니다.

p = mmap(…, fd, 0);
close(fd);   /* 괜찮다 */
putchar(p[0]);
munmap(p, len);

매핑이 파일을 따로 붙잡고 있으므로 close(fd) 뒤에도 p를 쓸 수 있습니다. 매핑은 munmap으로 해제하며, 프로세스가 종료하면 자동으로 해제됩니다.

mmap의 오류로는 EINVAL(length 0, offset 비정렬), EACCES(O_RDONLY로 연 fd에 SHARED+WRITE), ENODEV(파이프처럼 매핑할 수 없는 파일)가 있으며, 교안은 이 셋을 모두 컨테이너에서 확인했습니다.

매핑 범위와 파일 크기: EINVAL과 SIGBUS

23바이트 파일 hello.txt를 length 8192(2페이지)로 매핑했을 때의 실측 결과는 다음과 같습니다.

범위내용
0 – 22파일 내용
23 – 40950으로 채워짐. 읽어도, 쓰기만 해도 괜찮지만 파일에는 가지 않습니다. 여기까지가 파일 끝이 들어 있는 마지막 페이지(1페이지)입니다.
4096 – 8191뒤에 파일이 없는 페이지(2페이지). 접근하면 SIGBUS입니다.
 
p[22]   = 10      ('\n')
p[100]  = 0
p[4095] = 0
p[4096] → Bus error (SIGBUS)

매뉴얼은 SIGBUS의 조건을 "매핑된 파일의 끝을 넘어선 버퍼 페이지에 접근을 시도한 경우"로 적고 있습니다. 반대쪽 경계로, length가 0이면 EINVAL입니다. 빈 파일은 st_size가 0이므로 그대로 넘기면 mmap이 실패합니다. 그래서 mapcat은 fstat로 크기를 먼저 보고 0이면 매핑하지 않습니다. 또 매핑한 뒤 파일이 줄어들어도 같은 SIGBUS가 납니다. 다른 프로세스의 truncate를 막을 방법은 없습니다.

입문 예제: mmap_basic

mmap_basic은 파일 없이 정수 하나를 매핑하고, 42를 쓰고 읽는 예제입니다. 파일 처리와 fork 없이 mmap의 기본 사용법부터 확인하는 것이 목적입니다. 실행하고 나면 mmap으로 받은 주소를 일반 포인터처럼 사용할 수 있다는 점, 익명 매핑의 인자와 MAP_FAILED 검사, 매핑의 생성·사용·해제 순서를 이해하게 됩니다.

매핑을 만드는 부분은 다음과 같습니다. Linux에서 MAP_ANONYMOUS 선언을 쓰기 위해 소스 맨 위에 #define _GNU_SOURCE를 둡니다.

size_t len = sizeof(int);    /* 요청 길이. 실제 매핑은 페이지 단위 */

int *p = mmap(NULL, len,     /* 주소는 커널이 선택, 길이는 바이트 */
              PROT_READ | PROT_WRITE,   /* 읽기와 쓰기 허용 */
              MAP_PRIVATE | MAP_ANONYMOUS, /* 비공개, 파일 없음 */
              -1, 0);       /* 익명 매핑: fd는 -1, offset은 0 */

if (p == MAP_FAILED) {       /* 실패는 NULL이 아니라 MAP_FAILED */
    perror("mmap");
    return 1;
}

익명 매핑은 파일 없이 0으로 시작합니다. 그다음 일반 포인터처럼 값을 쓰고 읽은 뒤 해제합니다.

*p = 42;
printf("*p = %d\n", *p);     /* 같은 주소에서 값을 읽는다. */

if (munmap(p, len) == -1) {  /* 매핑 해제. 이후 p로 접근하지 않는다. */
    perror("munmap");
    return 1;
}

*p = 42는 매핑된 메모리에 쓰고, printf의 *p는 같은 값을 읽습니다. mmap으로 만든 매핑은 munmap으로 해제하며, munmap 이후에는 그 주소로 다시 접근하지 않습니다.

$ make mmap_basic
$ ./mmap_basic
*p = 42

이 출력은 mmap이 반환한 주소에 쓰고 같은 주소에서 읽었다는 것을 보여 줍니다. 파일도 자식 프로세스도 필요하지 않았습니다. 주소값은 출력하지 않으며, 성공하면 종료 코드는 0입니다. 다음 예제 mapcat에서는 이 주소 범위를 파일 내용에 연결합니다.

예제 ① mapcat: 무엇을 확인하는가

mapcat은 파일을 매핑하고 포인터로 내용을 출력합니다. 이 예제로 파일 데이터와 매핑된 주소 p의 관계를 설명하고, 파일 크기·빈 파일·매핑 실패를 구분해 처리하며, close(fd)와 munmap(p, len)의 역할을 구분할 수 있게 됩니다.

질문은 "read 없이 파일을 출력할 수 있을까"입니다. mmap이 돌려준 p를 파일 내용의 시작 주소처럼 사용하고, PROT_READ·MAP_PRIVATE로 읽기 전용 매핑을 만듭니다. 준비는 실습 폴더에서 빌드하고 작은 파일을 만드는 것입니다.

make
printf 'hello mmap\nsecond line\n' > hello.txt
./mapcat hello.txt

두 줄의 파일 내용이 그대로 출력됩니다. 파일 길이만큼을 write_all에 넘기므로 문자열 끝의 NUL 문자는 필요 없습니다. OS 관점에서 볼 지점은 fd와 매핑의 수명입니다. mmap 뒤 close(fd)를 해도 p는 남습니다. -p로 실행하면 출력 뒤 멈추므로 다른 터미널에서 maps를 확인할 수 있습니다.

mapcat의 흐름과 코드

사용법은 ./mapcat [-p] FILE입니다. 흐름은 open(path, O_RDONLY) → fstat로 정규 파일인지(S_ISREG)와 크기가 0인지 검사 → mmap(PROT_READ, MAP_PRIVATE) → close(fd)(매핑은 남는다) → write_all(1, p, len)으로 전부 출력 → -p면 PID를 알리고 Enter 대기 → munmap(p, len) → return 0입니다. write_all은 3주차의 부분 쓰기 루프입니다.

실패 경로도 단계마다 다릅니다. open이 ENOENT 등으로 실패하면 perror 뒤 1, 디렉터리면 1, 빈 파일이면 0, mmap이 MAP_FAILED면 perror 뒤 1로 끝납니다. 인자가 틀리면 usage를 stderr로 내고 2로 끝납니다. 실패는 모두 stderr와 0이 아닌 종료 코드로 알립니다.

크기 검사 부분에서 눈여겨볼 줄은 다음입니다.

if (!S_ISREG(st.st_mode)) {
    fprintf(stderr, "%s: not a regular file\n", path);
    return 1;
}
if (st.st_size == 0) {          /* length 0 은 mmap 이 EINVAL */
    fprintf(stderr, "%s: empty file, nothing to map\n", path);
    close(fd);
    return 0;
}

S_ISREG 검사는 디렉터리와 장치를 거릅니다. 이런 대상은 크기가 의미가 없기 때문입니다. 크기 0 검사는 mmap에 length 0을 넘기면 EINVAL이 되는 상황을 피하며, 빈 파일은 오류가 아니므로 성공 코드 0으로 끝냅니다.

매핑과 해제 부분의 핵심은 다음입니다.

size_t len = (size_t)st.st_size;
char *p = mmap(NULL, len, PROT_READ, MAP_PRIVATE, fd, 0);
if (p == MAP_FAILED) { perror("mmap"); return 1; }
close(fd);                      /* 매핑은 fd 와 별개로 남는다 */

if (write_all(STDOUT_FILENO, p, len) < 0) { perror("write"); return 1; }

이후 -p 옵션이 켜져 있으면 PID, 매핑한 바이트 수, 주소를 stderr로 알리고 getchar()로 Enter를 기다린 다음, munmap(p, len)으로 해제합니다.

mapcat 실행 결과

파일 출력. 23바이트가 그대로 나옵니다. ls -l의 크기와 wc -c의 결과가 같고, 매핑한 바이트가 그대로 출력됩니다. 데이터는 read 없이, open·mmap·close 뒤 주소 p로 읽혀 write로 나갔습니다. 인자 없이 실행하면 usage를 stderr로 내고 $?는 2입니다. 10주차에서 본 셸 관례입니다.

매핑은 maps에, fd는 이미 닫힘. -p로 멈춰 둔 상태에서 maps를 보면 hello.txt 한 줄이 r--p, offset 0, 1페이지(…3000–…4000)로 보입니다. 23바이트도 4 KiB를 차지합니다. mapcat 실행 파일 자신도 세 줄로 매핑되어 있습니다. r-xp 코드, r--p 상수, rw-p 데이터입니다. 반면 열린 fd는 0·1·2뿐입니다. hello.txt의 fd는 close(fd)에서 닫혔고, 매핑이 파일을 따로 붙잡고 있습니다. 교안은 이 관찰을 위해 sleep 60 |을 앞에 붙여 실행했는데, 이는 mapcat의 stdin을 열어 두어 Enter 대기(getchar)에서 멈추게 하는 장치입니다.

세 가지 오류 경로. 없는 파일은 open의 ENOENT를 perror로 알리고 1로 끝납니다. 디렉터리는 S_ISREG 검사에 걸려 1로 끝납니다. 빈 파일은 mmap 전에 걸러 EINVAL을 피하고 0으로 끝납니다.

mapcat 실행 결과를 코드와 연결한다

  • 파일 내용이 그대로 나왔다 — p와 len이 데이터 범위다. write_all(1, p, len)이 p부터 정확히 len바이트를 출력합니다. 파일 데이터에 NUL이 있어도 전체 바이트 수로 다룹니다.
  • close 뒤에도 출력된다 — 매핑은 파일 참조를 유지한다. fd는 파일을 여는 손잡이입니다. close는 그 손잡이를 닫고, munmap은 프로세스의 주소 연결을 해제합니다.
  • 빈 파일 — 오류 없이 출력할 내용이 없다. st_size == 0이면 안내 후 성공 코드 0으로 끝납니다.
  • 없는 파일·디렉터리 — 실패한 단계가 다르다. 없는 파일은 open에서 실패합니다. 디렉터리는 이 프로그램의 S_ISREG 검사에서 거절합니다. 둘 다 mmap의 오류와는 구분해야 합니다.

생각해 볼 질문: close(fd)를 지우면 출력 내용이 바뀔까요? munmap 뒤 p를 다시 사용하면 왜 안 될까요?

1부 정리: 파일 한 구간 → 주소 공간 한 구간

mmap은 파일(디스크·페이지 캐시)의 offset부터 length만큼의 구간을 프로세스 주소 공간의 p … p+length 구간에 붙이고, munmap이 이를 뗍니다.

  • 페이지 단위. 길이는 4096의 배수로 올림되고, offset은 4096의 배수여야 합니다. 23바이트도 1페이지입니다.
  • 크기 경계. length 0은 EINVAL입니다. 파일 끝이 들어 있는 페이지의 나머지는 0이고, 그다음 페이지는 SIGBUS입니다.
  • fd와 별개의 수명. close(fd) 뒤에도 매핑은 유지되고, munmap이나 종료로 해제됩니다. maps에서 확인할 수 있습니다.

2부 공유 · 비공개 · 익명 매핑

같은 파일을 MAP_SHARED와 MAP_PRIVATE로 매핑했을 때 수정이 어디까지 보이는지, 그리고 파일 없는 익명 매핑으로 fork한 프로세스끼리 메모리를 나누는 방법을 봅니다.

MAP_SHARED와 MAP_PRIVATE

MAP_SHARED에서는 프로세스 A와, 같은 파일을 매핑한 프로세스 B가 페이지 캐시의 한 페이지를 공유합니다. A가 p[0] = 'H'를 쓰면 그 쓰기가 페이지 캐시에 그대로 들어가므로, 파일 hello.txt도 "Hello…"가 되고 B에게도 보입니다. 매뉴얼의 표현으로는 매핑에 대한 갱신이 같은 영역을 매핑한 다른 프로세스에 보이고, 바탕 파일까지 전달됩니다.

MAP_PRIVATE에서는 A가 p[0] = 'H'를 쓰는 순간 A만의 사본 페이지가 만들어지고 거기에 "Hello…"가 들어갑니다. 페이지 캐시는 "hello…" 그대로이고 파일도 "hello…" 그대로입니다. 파일과 다른 프로세스는 이 수정을 모릅니다. 매뉴얼은 이를 copy-on-write 매핑이며 바탕 파일로 전달되지 않는다고 적습니다.

copy-on-write: 쓰는 순간에만 복사

  1. 매핑 직후. 내 페이지는 캐시 페이지를 가리키며, 쓰기 금지로 표시되어 있습니다.
  2. 쓰기 시도. p[0] = 'H'가 page fault를 일으킵니다.
  3. 커널이 복사. 새 페이지에 내용을 복사하고, 연결을 바꾼 뒤 쓰기를 다시 실행합니다.
  4. 이후. 그 페이지는 내 것이며, 다시 fault가 나지 않습니다.

복사되는 것은 쓴 페이지뿐입니다. 읽기만 하면 복사는 0번이고, 1000페이지 중 1페이지에 쓰면 1페이지만 복사됩니다. 이것은 10주차에서 본 fork와 같은 원리입니다. fork 뒤 부모와 자식은 페이지를 공유하다가 쓰는 순간 갈라집니다. 파일은 그대로 남습니다. mapmode private에서 매핑 안은 HELLO인데 파일은 hello인 것이 그 결과입니다. 사본은 익명 메모리이지만 maps에서는 여전히 파일 경로로 보입니다.

SHARED와 PRIVATE가 갈라지는 지점

  • 읽기 — 같은 파일 페이지를 볼 수 있다. 서로 다른 프로세스라도 같은 파일 페이지 캐시를 연결할 수 있습니다. 가상 주소가 같을 필요는 없습니다.
  • SHARED 쓰기 — 공유 파일 페이지를 수정한다. 페이지가 dirty 상태가 되고 파일에 기록할 대상이 됩니다. 다른 매핑과 데이터를 주고받을 때의 동기화는 별도로 필요합니다.
  • PRIVATE 쓰기 — COW 사본을 준비한다. 쓰기 fault에서 자기 사본으로 갈라집니다. 수정한 사본은 익명 메모리로 관리되며 원본 파일에 기록하지 않습니다.
  • 가시성과 디스크 반영은 다른 문제다. msync(MS_SYNC)는 파일 기록 완료를 기다릴 뿐입니다. 잠금이나 원자 연산의 역할을 대신하지 않고, PRIVATE 사본을 저장하지도 않습니다.

한 가지 주의할 점은 MAP_PRIVATE가 파일의 고정된 스냅샷을 보장하지 않는다는 것입니다. 매핑 뒤에 외부에서 파일이 바뀌었을 때 그것이 보일지는 보장되지 않습니다.

msync와 ftruncate: 반영 시점과 파일 크기

msync — 언제 디스크에 가는가. p[i] = …는 메모리 쓰기이고, 그 결과는 공유된 페이지 캐시에 들어갑니다(접근 순서의 동기화는 별도 문제입니다). 디스크에는 커널이 나중에 dirty 페이지를 기록합니다. msync(p, len, MS_SYNC)는 기록이 끝날 때까지 기다립니다. MS_ASYNC는 비동기 요청이며 현대 Linux에서는 no-op입니다. munmap이나 프로세스 종료는 동기 기록 완료를 보장하지 않습니다.

ftruncate — 파일 크기는 먼저 정한다. 23바이트 파일을 length 4096으로 매핑하면 23–4095 범위에도 쓸 수는 있지만 그 내용은 파일에 가지 않습니다. ftruncate(fd, 4096)으로 파일을 먼저 키운 뒤 mmap하면 4096바이트 모두가 파일에 반영됩니다. 파일보다 한 페이지 이상 넘어 접근하면 앞에서 본 SIGBUS입니다. 요컨대 mmap은 파일을 키우지 않습니다. 크기는 ftruncate나 write로 정합니다.

익명 매핑: 파일 없는 공유 메모리

shared = mmap(NULL, 4096, PROT_READ|PROT_WRITE, MAP_SHARED|MAP_ANONYMOUS, -1, 0);

MAP_ANONYMOUS 매핑은 어떤 파일에도 바탕을 두지 않으며 내용은 0으로 초기화됩니다. fd는 -1, offset은 0입니다. fork 뒤에도 매핑은 그대로 물려받습니다. 그래서 fork 뒤 전역 변수(global)의 페이지는 부모 것과 자식 사본으로 갈라지지만, shared 페이지는 하나를 둘이 같이 봅니다.

공유하려면 MAP_SHARED여야 합니다. MAP_ANONYMOUS|MAP_PRIVATE는 fork 뒤 COW로 갈라집니다(큰 malloc이 이 조합입니다). 또 익명 매핑은 이름이 없으므로, fork로 물려받은 관계 있는 프로세스끼리만 공유할 수 있습니다. 이름 있는 공유는 13–14주차에 다룹니다.

malloc도 큰 블록은 mmap으로 받는다

malloc(1000), malloc(100 KiB), malloc(200 KiB), free(200 KiB)를 차례로 하는 프로그램을 strace로 본 결과입니다(glibc 2.39 컨테이너 실측이며, 시작부에 나오는 동적 링커의 mmap 줄은 생략했습니다).

$ strace -e trace=brk,mmap,munmap ./malloctest
brk(NULL)                               = 0xaaaaff991000
brk(0xaaaaff9b2000)                     = 0xaaaaff9b2000
mmap(NULL, 208896, PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_ANONYMOUS, -1, 0) = 0xffff9f32d000
munmap(0xffff9f32d000, 208896)          = 0

malloc(1000)과 malloc(100 KiB)는 brk로 heap을 늘려(0x21000 = 132 KiB) 그 안에서 잘라 줍니다. 이런 블록은 free해도 heap에 남습니다. 반면 malloc(200 KiB)는 익명 PRIVATE mmap으로 208896바이트를 받고, free하면 munmap으로 커널에 바로 반납됩니다. 기준값은 M_MMAP_THRESHOLD로 기본 128 KiB이며 동적으로 조정됩니다. 익명 매핑은 우리 코드만의 것이 아닙니다. malloc, 스레드 스택, 동적 링커가 모두 씁니다.

권한 위반은 SIGSEGV, 권한 변경은 mprotect

mmap(PROT_READ)로 만든 매핑에 p[0] = 1처럼 쓰면 SIGSEGV(Segmentation fault)가 납니다. mprotect(p, 4096, READ|WRITE)로 권한을 바꾼 뒤에는 p[0] = 'X'가 성공합니다. mprotect도 페이지 단위로 동작하며, 주소는 페이지 경계여야 합니다.

SIGBUS(7)매핑은 있는데 그 페이지 뒤에 파일이 없음파일 끝 다음 페이지

오류가 발생한 단계로 원인을 찾는다

  • 매핑 요청 단계 — 함수가 실패한다. length 0과 offset 비정렬은 EINVAL, 공유 쓰기 권한 부족은 EACCES, 매핑을 지원하지 않는 대상은 ENODEV입니다. 반환값과 errno를 확인합니다.
  • 주소·권한 검사 단계 — SIGSEGV. 유효한 매핑이 없거나 읽기 전용 영역에 쓰는 경우입니다. 단, COW처럼 커널이 해결할 수 있는 쓰기 fault는 정상 처리됩니다.
  • 파일 페이지 준비 단계 — SIGBUS. 파일 끝을 완전히 넘어선 페이지에 접근하는 경우입니다. mmap이 성공한 뒤 파일이 잘려도 접근할 때 이 문제가 생길 수 있습니다.
  • 프로그램이 나눈 수명 — close와 munmap. close(fd)는 fd를 닫고 munmap은 주소 매핑을 해제합니다. 해제한 주소를 계속 쓰면 잘못된 메모리 접근이 됩니다.

이것은 이 시그널들의 모든 원인을 나열한 표가 아니라, 오늘의 일반 파일 매핑 예제에서 원인을 찾는 기준입니다.

예제 ② mapmode: 매핑과 파일을 따로 읽는다

mapmode는 같은 메모리에 쓴 값이 누구에게 보이는지를 비교합니다. PRIVATE·SHARED의 수정 결과를 파일 내용과 비교하고, fork 뒤 전역 변수와 익명 공유 매핑의 차이를 설명하며, 경쟁 상태를 관찰해 별도의 동기화가 필요한 이유를 말할 수 있게 되는 것이 목표입니다. 사용법은 ./mapmode private|shared FILE, ./mapmode anon, ./mapmode race NPROC LOOPS입니다.

먼저 같은 입력에서 두 파일 모드를 비교합니다.

printf 'hello mmap\nsecond line\n' > hello.txt
cp hello.txt p.txt
cp hello.txt s.txt
./mapmode private p.txt
./mapmode shared s.txt
  • private: mapping: HELLO MMAP, file (pread): hello mmap. 내 매핑의 수정은 파일로 돌아가지 않습니다.
  • shared: mapping: HELLO MMAP, file (pread): HELLO MMAP. 공유 수정이 파일 데이터에 반영됩니다. 이 모드는 s.txt를 실제로 수정합니다.

이 비교가 가능한 이유는 같은 코드를 쓰고 flags만 바꾸기 때문입니다. file_mode가 첫 줄만 대문자로 바꾸고, 매핑을 해제한 뒤 pread로 파일을 다시 읽어 두 결과를 구분합니다.

mapmode의 코드: 두 매핑 함수와 file_mode

main은 모드에 따라 file_mode(private · shared), anon_mode, race_mode를 부릅니다. 매핑을 만드는 함수는 둘입니다. map_file은 파일을 O_RDWR로 열고 크기를 확인한 뒤 읽기·쓰기 매핑을 만들며, 호출하는 쪽이 flags만 바꿔 부릅니다.

int fd = open(path, O_RDWR);
...
char *p = mmap(NULL, *len, PROT_READ | PROT_WRITE, flags, fd, 0);

O_RDWR로 여는 이유는 SHARED+WRITE 매핑에는 쓰기로 연 fd가 필요하기 때문입니다. 그렇지 않으면 EACCES가 납니다(실측). shared_int는 fd -1에 MAP_SHARED | MAP_ANONYMOUS로, 0으로 채워진 int 하나를 만듭니다.

int *p = mmap(NULL, sizeof(int), PROT_READ | PROT_WRITE,
              MAP_SHARED | MAP_ANONYMOUS, -1, 0);

file_mode의 핵심 흐름은 다음과 같습니다.

char *p = map_file(path, shared ? MAP_SHARED : MAP_PRIVATE, &len, &fd);

for (size_t i = 0; i < len && p[i] != '\n'; i++)   /* 첫 줄 대문자 */
    p[i] = (char)toupper((unsigned char)p[i]);
print_line("mapping:", p, len);

if (shared && msync(p, len, MS_SYNC) < 0) die("msync");
if (munmap(p, len) < 0) die("munmap");

char buf[256];                                     /* 파일을 다시 읽는다 */
ssize_t n = pread(fd, buf, sizeof buf, 0);

첫 줄만 toupper로 바꾸고 매핑 안의 내용을 바로 출력합니다. shared면 MS_SYNC로 기록을 기다린 뒤 해제합니다. 마지막으로 매핑이 아니라 파일을 pread로 다시 읽습니다. 이것이 파일에 실제로 무엇이 남았는지를 보여 주는 진짜 결과입니다.

mapmode anon: 전역 변수와 공유 정수를 비교한다

초기 상태는 global_value = 0, *shared = 0입니다. shared_int()가 MAP_SHARED|MAP_ANONYMOUS로 정수 하나를 만든 뒤 fork합니다. 파일은 사용하지 않습니다.

int *shared = shared_int();
pid_t pid = fork();
if (pid < 0) die("fork");
if (pid == 0) {                                    /* 자식 */
    global_value = 42;
    *shared = 42;
    printf("child : global=%d shared=%d\n", global_value, *shared);
    fflush(stdout);
    _exit(0);
}
if (waitpid(pid, NULL, 0) < 0) die("waitpid");
printf("parent: global=%d shared=%d\n", global_value, *shared);

자식은 두 곳 모두에 42를 저장하므로 child 출력은 global=42 shared=42가 됩니다. 자식은 fflush 뒤 _exit로 끝납니다(10주차). 부모는 waitpid로 순서를 맞춘 뒤 두 값을 읽고, 출력은 global=0 shared=42입니다. 전역 변수는 독립적이고 shared는 같은 데이터를 봅니다. 주소 공간으로 설명하면, 자식의 전역 변수 쓰기는 COW로 갈라져 사본에 쓰였으므로 부모는 모릅니다. 익명 공유 매핑은 fork 뒤에도 부모와 자식이 같은 공유 대상을 유지하므로, 페이지가 하나이고 부모도 그 값을 봅니다.

생각해 볼 질문: shared_int()를 fork 뒤에 각자 호출하면 두 프로세스가 같은 공유 정수를 얻을까요?

mapmode race: 같은 메모리만으로는 부족하다

./mapmode race 4 1000000은 자식 4개가 각각 공유 카운터를 100만 번 증가시킵니다. 목표 합계 expected는 4000000입니다.

volatile int *counter = shared_int();
for (int i = 0; i < nproc; i++) {
    pid_t pid = fork();
    if (pid < 0) die("fork");
    if (pid == 0) {
        for (long j = 0; j < loops; j++)
            (*counter)++;                          /* 읽기-더하기-쓰기 */
        _exit(0);
    }
}
while (wait(NULL) > 0)
    ;

핵심은 (*counter)++입니다. 이것은 일반적인 읽기·더하기·쓰기의 세 단계이며 원자적 증가가 아닙니다. 그 사이에 다른 자식이 끼어들 수 있어서, 두 자식이 같은 값을 읽고 같은 다음 값을 덮어쓸 수 있습니다. 그러면 증가 한 번이 사라집니다.

출력은 expected, actual, lost를 함께 읽습니다. lost는 expected - actual입니다. 실제 손실량은 실행마다 달라질 수 있고, 손실이 안 보인 실행이 있었다고 해서 원자성이 증명되는 것도 아닙니다.

volatile과 wait는 이 경쟁을 해결하지 않습니다. volatile은 매번 메모리에서 읽고 쓰게 할 뿐 원자성을 보장하지 않습니다. wait는 자식의 종료만 기다립니다. 공유 데이터를 갱신하려면 동기화 수단이 별도로 필요합니다. 수업에서는 ./mapmode race 1 1000000과 비교합니다.

mapmode 실행 결과

private와 shared — 파일은 누가 바꾸는가. private에서는 매핑 안만 HELLO MMAP이고, pread와 cat은 hello mmap을 보여 줍니다. 사본에만 썼기 때문입니다. shared에서는 pread와 cat 모두 HELLO입니다. 둘째 줄은 그대로인데, 바꾼 바이트만 반영되기 때문입니다. MAP_SHARED냐 MAP_PRIVATE냐, 플래그 하나의 차이가 결과를 가릅니다.

anon — 전역 변수는 갈라지고 공유 매핑은 하나. 자식 안에서는 두 변수 모두 42로 바뀌었습니다. 부모에서는 global=0, shared=42입니다.

race — 넷이 동시에 쓰면 값이 사라진다. 자식이 1개면 1000000 그대로 정확합니다. 혼자면 경쟁이 없기 때문입니다. 자식이 4개면 값이 사라집니다. 교안의 실행(CPU 10개)에서는 400만 중 129만~232만으로 기록되어 있고 실행마다 달랐습니다. CPU가 하나뿐인 환경에서는 손실이 거의 없을 수 있습니다. 동기화는 13–14주차에 다룹니다.

3부 활용 · 성능 · 한계

매핑한 페이지가 실제로 언제 올라오는지(page fault)와 그 비용을 재 보고, mmap이 맞는 곳과 맞지 않는 곳을 고릅니다.

demand paging: 닿을 때 올라온다

  1. mmap(…) — VMA에 범위와 권한을 등록합니다. 페이지 연결은 지연될 수 있습니다.
  2. c = p[i] — 처음 닿는 페이지에 접근합니다.
  3. page fault — CPU가 커널로 넘어갑니다.
  4. 커널이 연결 — 캐시에 있으면 연결만 하고, 없으면 디스크에서 읽고 연결합니다.
  5. 다시 실행 — 같은 명령을 다시 실행합니다. 이후에도 페이지 회수나 COW 등으로 다시 fault가 날 수 있습니다.

mmap은 보통 범위만 등록하고 페이지 준비는 미룹니다(선행 적재 옵션은 별도입니다). 그래서 접근이 곧 읽기가 됩니다. 프로그램은 이 과정을 모릅니다. fault는 투명하게 처리되며, 그 횟수는 getrusage의 ru_minflt·ru_majflt로 셉니다. 2부의 copy-on-write도 같은 page fault 장치를 씁니다.

minor fault와 major fault

minor fault는 처리에 저장장치 I/O가 필요 없는 fault입니다. 연결, 페이지 할당, COW 등을 처리하며 비용은 작업에 따라 다릅니다. 파일 캐시 페이지를 연결하는 경우, 익명 페이지의 첫 쓰기, PRIVATE 매핑의 COW가 그 예입니다.

major fault는 페이지가 캐시에 없는 경우입니다. 디스크에서 읽어 올 때까지 기다려야 하므로 느립니다. 부팅 뒤 처음 여는 큰 파일(cold)이나 스왑으로 나간 페이지가 그 예입니다.

커널에는 미리 읽기(readahead)가 있습니다. 순차 접근을 보면 다음 페이지들을 미리 캐시에 올립니다. 그래서 순차로 훑으면 major는 드물고 대부분 minor가 됩니다. 3부의 실측에서도 캐시를 비운 직후 247 MB를 mmap으로 훑었는데 majflt는 1이었습니다.

페이지 캐시: cold와 warm

첫 실행(cold)에서는 디스크에서 읽어 페이지 캐시를 채워야 하므로 디스크 읽기를 기다리게 되어 느립니다. 다시 실행(warm)하면 페이지 캐시에 이미 있으므로 디스크에 가지 않고 메모리에서 바로 읽어 빠릅니다. 파일 데이터는 프로세스가 끝나도 페이지 캐시에 남기 때문입니다.

$ ./countnl drop big.txt          # 이 파일의 캐시를 비운다
$ ./countnl read big.txt          # cold
$ ./countnl read big.txt          # warm

따라서 재기 전에 조건을 맞춰야 합니다. cold끼리, warm끼리 비교합니다. 섞으면 결론이 뒤집힙니다. countnl drop은 posix_fadvise의 POSIX_FADV_DONTNEED로 그 파일의 캐시만 비우며, root 없이 가능합니다. 교안의 컨테이너에서는 overlayfs 위 파일의 캐시가 비워지지 않아 실습 폴더를 ext4 볼륨에 두었습니다.

기존 예제로 OS의 세 층을 관찰한다

  • maps — 등록된 가상 주소 범위. ./mapcat -p hello.txt를 실행해 PID를 얻고, 다른 터미널에서 /proc/PID/maps의 파일 경로와 권한을 찾습니다.
  • smaps — 실제 상주한 페이지. /proc/PID/smaps에서 같은 매핑의 Size·Rss·Pss·Private_Dirty를 읽습니다. 전체 파일의 합계와 혼동하지 않습니다.
  • countnl — 접근하면서 발생한 fault. read·mmap·mmap seq 결과의 minflt와 majflt를 비교합니다. 캐시가 따뜻해도 페이지 연결을 위한 minor fault는 생길 수 있습니다.

관찰 시점에 주의합니다. mapcat -p는 출력한 뒤에 멈추므로, 그때는 이미 파일을 읽은 상태입니다. 첫 접근 전후를 비교하려면 대기 지점을 mmap 직후와 읽기 직후에 각각 두어야 합니다. 이 항목은 관찰 절차와 예상 해석이며, 권한이 있는 동일한 Linux 환경에서 비교합니다.

madvise: 접근 패턴을 커널에 알린다

조언뜻커널의 반응
MADV_NORMAL특별한 패턴 없음(기본)보통 크기로 미리 읽기
MADV_SEQUENTIAL앞에서부터 차례로 읽는다미리 읽기를 늘리고, 지나간 페이지는 빨리 놓아 준다
MADV_RANDOM여기저기 띄엄띄엄 읽는다미리 읽기를 줄인다(낭비 방지)
MADV_WILLNEED곧 이 범위를 쓴다지금 미리 읽어 둔다
MADV_DONTNEED당분간 안 쓴다페이지를 놓는다 — 다음 접근 때 파일에서 다시 읽는다(익명이면 0)

조언은 힌트일 뿐이어서 결과가 크게 바뀌지 않을 수도 있습니다. 넣기 전과 후를 재서 확인해야 합니다. fd 기반 I/O에서는 posix_fadvise가 같은 역할을 합니다. countnl은 seq 인자를 주면 MADV_SEQUENTIAL을 줍니다.

mmap이 맞는 경우, 맞지 않는 경우

맞는 경우

  • 큰 파일을 여기저기 읽는 임의 접근. lseek + read를 반복하는 대신 p[off]로 접근합니다.
  • 같은 파일을 여러 프로세스가 읽는 경우. 페이지 캐시 한 벌을 공유합니다.
  • 파일을 자료구조처럼 다루는 경우. 구조체 배열이나 인덱스 파일이 그 예입니다.
  • fork한 프로세스끼리 메모리를 나누는 경우.

맞지 않는 경우

  • 작은 파일. 매핑과 fault 비용이 복사보다 큽니다.
  • 파이프 · 소켓 · 터미널. 매핑할 수 없어 ENODEV가 납니다.
  • 다른 프로세스가 크기를 바꾸는 파일. 줄어들면 SIGBUS입니다.
  • 한 번 처음부터 끝까지 훑기. read와 비슷합니다.

예제 ③ countnl: 무엇을 같게 하고 비교하는가

countnl은 같은 파일을 read와 mmap으로 읽고 비용을 비교합니다. 같은 개행 수를 세어 비교 조건을 맞추고, 시간·minor fault·major fault의 의미를 해석하며, 캐시 상태를 구분해 측정하고 성능 결론의 범위를 정하는 것이 목표입니다. 사용법은 ./countnl read|mmap FILE [seq]와 ./countnl drop FILE입니다.

같게 하는 것은 파일과 개행 세기 함수입니다. 두 방식 모두 같은 count_buf로 개행 문자 \n의 수를 셉니다. 세는 것은 개행이므로, 마지막 줄에 개행이 없으면 줄 수와 다를 수 있습니다. 바꾸는 것은 데이터가 들어오는 경로입니다. read 방식은 64 KiB 버퍼를 반복해서 사용하고, mmap 방식은 파일 전체를 매핑하고 매핑 범위에서 개행을 찾습니다.

작은 입력으로 결과부터 확인합니다.

printf 'a\nb\nlast' > tiny.txt
./countnl read tiny.txt
./countnl mmap tiny.txt

두 방식 모두 lines=2가 나와야 합니다. 같은 답이 나오는지 먼저 본 뒤 큰 파일에서 시간과 fault를 비교합니다. tiny.txt는 성능 결론을 내릴 입력이 아닙니다.

countnl의 흐름과 코드

흐름은 open·fstat → 모드 분기(drop이면 posix_fadvise(DONTNEED) 뒤 끝) → 측정 시작(getrusage, clock_gettime) → count_read 또는 count_mmap → 측정 끝(ms · minflt · majflt 출력)입니다. count_buf는 memchr로 \n을 셉니다. 세는 코드는 하나이고, 바뀌는 것은 "데이터가 버퍼로 복사되어 오느냐, 매핑으로 연결되느냐"뿐입니다. 그래서 시간과 fault의 차이는 데이터 경로의 차이로 읽을 수 있습니다.

static long count_read(int fd)
{
    static char buf[BUFSZ];
    long c = 0;
    ssize_t n;
    while ((n = read(fd, buf, sizeof buf)) > 0)
        c += count_buf(buf, (size_t)n);
    if (n < 0) die("read");
    return c;
}

static long count_mmap(int fd, size_t len, int advice)
{
    if (len == 0) return 0;
    char *p = mmap(NULL, len, PROT_READ, MAP_PRIVATE, fd, 0);
    if (p == MAP_FAILED) die("mmap");
    if (advice != MADV_NORMAL && madvise(p, len, advice) < 0) die("madvise");
    long c = count_buf(p, len);
    munmap(p, len);
    return c;
}

read 방식은 64 KiB 버퍼 하나를 재사용하며 read마다 복사가 일어납니다. mmap 방식은 파일 전체를 한 번 매핑하고 같은 count_buf로 셉니다. seq를 주면 madvise로 MADV_SEQUENTIAL 힌트를 줍니다.

측정 도구는 둘입니다. 하나는 CLOCK_MONOTONIC으로, 시계가 바뀌어도 거꾸로 가지 않는 경과 시간입니다. 다른 하나는 getrusage(RUSAGE_SELF)의 ru_minflt·ru_majflt 증가분입니다. 세기 전후에 각각 값을 얻어 차이를 출력합니다.

printf("%-4s%-4s lines=%ld  %8.1f ms  minflt=%ld  majflt=%ld\n",
       mode, tag, lines, t1 - t0,
       r1.ru_minflt - r0.ru_minflt, r1.ru_majflt - r0.ru_majflt);

countnl 실행 결과: read와 mmap, 캐시를 비운 직후와 다시

  • 시간은 비슷하다. 다시 실행(warm)했을 때 read는 272 ms, mmap은 267 ms였습니다. 한 번 훑기에는 mmap이 특별히 빠르지 않습니다.
  • fault는 19 대 533. read는 버퍼 한 개만 쓰기 때문입니다. mmap은 63,206페이지를 533번의 fault로 연결했습니다.
  • major는 1번. 캐시를 비운 직후에도 majflt=1이었습니다. 나머지는 미리 읽기 덕분에 minor가 되었습니다.

이 측정은 ext4 볼륨에 둔 실습 폴더에서 한 것이며, Mac 호스트 캐시 때문에 cold(360 ms)와 warm(272 ms)의 차이가 실제 디스크보다 작게 나왔습니다.

countnl의 숫자를 읽고 결론을 제한한다

  • lines — 먼저 두 방식의 결과가 같은지 본다. 개행 수가 다르면 시간 비교를 중단하고 입력 파일과 실행 조건을 확인합니다. 출력된 lines는 바이트 수가 아닙니다.
  • ms — 측정 구간의 경과 시간. 측정은 open·fstat 뒤에 시작합니다. mmap 방식은 매핑·탐색·해제를, read 방식은 읽기 반복·탐색을 포함합니다.
  • minflt·majflt — 측정 전후의 누적값 차이. minor는 I/O 없이 해결한 fault, major는 I/O가 필요한 fault입니다. fault 수는 바이트 수나 디스크 읽기 횟수가 아닙니다.
  • cold·warm·seq — 조건을 맞춰 비교한다. drop은 캐시 제거 요청이며 완전한 cold를 보장하지 않습니다. seq는 힌트입니다. warm끼리 비교하고 여러 번 측정합니다.

실행 화면의 시간은 그 환경의 측정값입니다. mmap이 항상 빠르다는 결론으로 일반화하지 않습니다.

IPC 지도에서 mmap의 자리

  • 9주차 시그널 — 사건이 있었다는 것만 알립니다(데이터 없음).
  • 11주차 mmap — 같은 메모리를 봅니다. 크고 빠르지만 동기화는 따로 해야 합니다.
  • 12주차 파이프 — 바이트가 흐릅니다. 순서와 대기를 커널이 맡습니다.
  • 13–14주차 IPC — 메시지 큐, 세마포어, shm_open(이름 있는 공유).

오늘의 race가 보여 준 것처럼 공유 메모리에는 "누가 언제 쓰나"를 정하는 장치가 없으며, 이것이 13–14주차의 세마포어로 이어집니다. IPC를 고르는 기준은 관계(부모·자식인가), 데이터량, 동기화, 수명(누가 언제 지우나)이며, 13–14주차에 완성합니다. 다음 주(12주차)에는 pipe와 dup2로, 10주차 미니 셸의 다음 단계인 ls | wc를 다룹니다.

정리

  • mmap은 파일(또는 0으로 채운 익명 메모리)의 한 구간을 주소 공간에 붙입니다. 단위는 페이지이고, 실패는 MAP_FAILED, 길이 0은 EINVAL, 파일 끝 다음 페이지는 SIGBUS입니다.
  • MAP_SHARED는 수정이 페이지 캐시를 거쳐 파일과 다른 프로세스로 가고, MAP_PRIVATE는 쓰는 순간 복사(COW)되어 나만 봅니다.
  • MAP_SHARED|MAP_ANONYMOUS를 fork 전에 만들면 부모와 자식이 같은 메모리를 봅니다. 그리고 동시에 쓰면 값이 사라집니다.
  • 커널은 VMA에 정책을 등록하고 page fault에서 페이지를 준비합니다. CPU는 페이지 테이블로 주소를 변환합니다. minor fault는 I/O 없이 해결되고, major fault는 I/O가 필요합니다.
  • mmap이 항상 빠르지는 않습니다. 한 번 순차로 훑는 일은 read와 비슷했습니다. 재서 고릅니다.
