이번 차시의 주제는 "함께 보고, 때를 맞춘다"입니다. 여러 프로세스가 같은 메모리를 복사 없이 함께 보는 방법(POSIX 공유 메모리)과, 함께 쓰는 데이터를 망가뜨리지 않도록 순서를 맞추는 방법(세마포어, 뮤텍스, 조건 변수)을 예제 일곱 개로 확인합니다. 각 부는 설명 → 예제 → 코드 → 실행 → 정리 순서로 진행합니다.

오늘의 지도와 예제 일곱 개

수업은 네 부로 나뉩니다. 1부는 이름 있는 메모리를 만들어 함께 보는 POSIX 공유 메모리, 2부는 한 번에 하나만 들어가게 지키는 세마포어, 3부는 둘을 합쳐 큐를 직접 만드는 생산자–소비자, 4부는 같은 문제를 스레드에서 푸는 뮤텍스 · 조건 변수 · 세마포어입니다. 본론에 들어가기 전에 입문 예제 shmhello로 공유 메모리가 무엇인지부터 봅니다.

예제 이름은 줄임말로 읽으면 됩니다. shm은 shared memory, sem은 semaphore, th는 thread, ring은 ring buffer(원형 버퍼)입니다.

미리 보기: 오늘 쓰는 기술 여섯 가지

본론에 앞서 오늘 등장하는 기술 여섯 가지를 한 번씩 훑어봅니다. 자세한 설명은 각 부에서 다시 하므로, 여기서는 각각이 무엇이고 어느 예제에서 쓰이는지만 잡아 두면 됩니다.

① 공유 메모리: 같은 메모리를 함께 본다

프로세스는 원래 서로의 메모리를 볼 수 없습니다. 공유 메모리는 그 벽에 낸 창입니다. 같은 물리 메모리를 여러 프로세스의 주소 공간에 붙여서, A가 쓰면 B에게 바로 보이게 합니다. A가 붙인 주소 p와 B가 붙인 주소 q는 서로 달라도 됩니다. 쓰는 순서는 shm_open(이름으로 연다) → ftruncate(크기를 정한다) → mmap(붙인다) → 포인터로 읽고 쓴다 → shm_unlink(이름을 지운다)입니다.

  • 복사가 없습니다. 파이프와 메시지 큐는 커널이 데이터를 복사하지만, 공유 메모리에서는 바로 봅니다.
  • 이름으로 만납니다. 부모–자식 사이가 아니어도 같은 이름을 열면 같은 메모리입니다.
  • 지울 때까지 남습니다. 프로세스가 끝나도 shm_unlink 전까지 /dev/shm에 남습니다.

커널이 끼어들지 않아 가장 빠르지만, 그 대신 순서는 프로그램이 직접 맞춰야 합니다.

② 경쟁 조건: 값이 사라지는 이유

경쟁 조건은 도구가 아니라 풀어야 할 문제입니다. count++는 읽고 · 더하고 · 쓰는 세 단계이고, 그 사이에 다른 흐름이 끼어들 수 있습니다. count가 5일 때 흐름 A가 6을 쓰기 전에 흐름 B가 5를 읽으면, 둘 다 6을 써서 7이어야 할 값이 6이 됩니다. 한 번이 사라진 것입니다. 결과가 실행 순서에 달려 있어 실행할 때마다 다른 값이 나오는데, 이것이 경쟁 조건입니다. 혼자 실행하면 나타나지 않고, 프로세스에서도 스레드에서도 똑같이 생깁니다.

답은 상호 배제입니다. 한 번에 하나만 실행해야 하는 구간을 임계 구역이라 하고(여기서는 count++ 한 줄), 임계 구역에 하나만 들어가게 하는 것을 상호 배제라 합니다. 그 도구가 세마포어와 뮤텍스입니다.

③ 세마포어: 정수 하나로 때를 맞춘다

세마포어는 정수 하나와 두 연산입니다. sem_wait는 값이 0보다 크면 1을 빼고 지나가고, 값이 0이면 올라갈 때까지 잠듭니다. sem_post는 값에 1을 더하고, 잠든 쪽이 있으면 하나를 깨웁니다. "확인하고 빼기"는 쪼개지지 않아서 그 사이에는 아무도 끼어들지 못합니다.

처음 값이 1인 세마포어로 두 흐름이 임계 구역에 들어가는 과정은 다음과 같습니다.

차례일어난 일값결과
1A가 sem_wait1 → 0A가 지나간다 — 임계 구역 안
2B가 sem_wait0B는 잠든다
3A가 sem_post0 → 1임계 구역을 나오며 B를 깨운다
4B가 깨어난다1 → 0B가 지나간다

처음 값이 쓰임을 정합니다. 처음 값이 1이면 한 번에 하나만 들어가는 잠금(이진 세마포어)이고, 임계 구역을 wait와 post로 감쌉니다(예제 semcount). 처음 값이 N이면 한 번에 N개까지 들어가는 자리의 수(계수 세마포어)입니다(예제 thlimit). 다만 값을 치릅니다. 잠그면 느려지고(실측으로 잠금 없이 0.006초이던 것이 세마포어로 0.407초), 잠근 채 죽으면 아무도 들어가지 못합니다.

④ 생산자–소비자와 원형 버퍼

넣는 쪽(생산자)과 꺼내는 쪽(소비자)이 고정 크기 버퍼를 함께 씁니다. 규칙은 세 가지입니다. 가득 차면 생산자가 기다리고, 비면 소비자가 기다리고, 버퍼를 고칠 때는 하나만 고칩니다. 버퍼는 8칸 배열이고 head는 다음에 꺼낼 자리, tail은 다음에 넣을 자리입니다. 7번 칸 다음은 0번 칸이라서 tail = (tail + 1) % 8로 옮기며, 그래서 원형(ring)이라 부릅니다.

프로세스 사이에서는 세마포어 셋으로 지킵니다. 빈 칸의 수(처음 8, 0이면 가득 찬 것이므로 생산자가 잠든다), 든 칸의 수(처음 0, 0이면 빈 것이므로 소비자가 잠든다), 그리고 head · tail · 칸을 고치는 동안 하나만 들어가게 하는 잠금(처음 1)입니다(예제 ringbuf). 스레드 사이에서는 뮤텍스와 조건 변수 둘로 합니다(예제 thqueue). 공유(버퍼)에 동기화(세마포어 셋)를 더하면 1차시의 메시지 큐가 커널 안에서 하던 일이 됩니다.

⑤ 스레드와 뮤텍스: 잠근 쪽이 푼다

스레드는 한 프로세스 안의 실행 흐름이고, 전역 변수와 힙을 처음부터 함께 씁니다. 그래서 경쟁 조건이 기본으로 따라옵니다. 뮤텍스는 스레드의 잠금 전용 도구로, lock과 unlock 사이는 한 스레드만 실행합니다.

pthread_mutex_lock(&m);    // 잠근다
count++;                   // 임계 구역
pthread_mutex_unlock(&m);  // 푼다
뮤텍스세마포어 (값 1)
푸는 쪽잠근 스레드만누구나 post 한다
쓰임잠금 전용잠금 · 수 세기
기다리기조건 변수와 짝값이 0이면 잠든다

정리하면 프로세스 사이에서는 공유 메모리 + 세마포어, 스레드 사이에서는 전역 변수 + 뮤텍스를 씁니다. 예제 thcount의 실측으로는 뮤텍스가 0.335초, 세마포어가 0.441초였습니다.

⑥ 조건 변수: 될 때까지 기다린다

뮤텍스는 "한 번에 하나"만 지킬 뿐, "값이 들어올 때까지" 같은 기다림은 맡지 못합니다. 조건 변수는 어떤 조건이 될 때까지 뮤텍스를 풀고 잠들게 해 줍니다.

pthread_mutex_lock(&lock);
while (used == 0)            // 비었으면
    pthread_cond_wait(&not_empty, &lock);
… 하나 꺼낸다 …
pthread_mutex_unlock(&lock);

pthread_cond_wait 한 번이 하는 일은 세 가지입니다. ① 뮤텍스를 풀고 잠든다, ② signal을 받으면 깨어난다, ③ 뮤텍스를 다시 잠그고 돌아온다. 깨우는 쪽은 pthread_cond_signal로 기다리는 스레드 하나를 깨우거나, pthread_cond_broadcast로 모두 깨웁니다. broadcast는 끝났음을 알릴 때 씁니다.

두 가지를 기억해야 합니다. 깨어났다고 조건이 참인 것은 아니므로 if가 아니라 while로 다시 확인합니다. 그리고 signal은 기억되지 않아서, 기다리는 스레드가 없으면 그냥 사라집니다.

본론에 앞서: 왜 공유 메모리인가

1차시에서 남겨 둔 두 자리

1차시에서 프로세스가 함께 일하려면 세 가지가 필요하다고 했습니다. ① 건넨다(전달), ② 함께 본다(공유), ③ 때를 맞춘다(동기화)입니다. 1차시에 배운 메시지 큐와 파이프는 ①에 해당하고, 커널이 데이터를 복사하면서 순서와 기다림까지 맡아 줬습니다. 오늘 1부의 공유 메모리가 ②, 2부의 세마포어가 ③입니다.

공유에서는 복사 없이 같은 메모리를 보지만 커널이 끼어들지 않습니다. 그래서 순서와 기다림을 프로그램이 직접 맞춰야 하고, 세마포어가 그 도구입니다. 11주차의 실험을 떠올리면 됩니다. 공유 매핑에서 넷이 동시에 100만 번씩 ++를 했더니 기대한 400만이 아니라 130만~230만이 나왔습니다. "공유는 빠르지만 순서는 직접 맞춰야 한다"는 것이 그때의 결론이었고, 오늘 그 방법을 배웁니다. 그리고 ②와 ③을 합치면 ①을 직접 만들 수 있는데, 그것이 3부의 생산자–소비자입니다.

전달로는 아쉬운 때

1차시의 "무엇을 고를까" 질문 가운데 "데이터가 크거나 여럿이 함께 고치는가"에 해당하면 공유 메모리 + 세마포어를 고릅니다. 상황별로 비교하면 다음과 같습니다.

OS 안에서 공유 메모리가 놓이는 자리

11주차에 본 "OS 안에서 mmap이 놓이는 자리"와 같은 구조입니다. 다른 점은 디스크 파일 대신 이름 있는 메모리 객체를 쓴다는 것입니다. 커널에는 물리 페이지 하나(예: "hello shm"이 든 메모리 파일 /dev/shm/w13_hello)가 있고, 프로세스 A의 페이지 테이블과 B의 페이지 테이블이 그 같은 물리 페이지를 가리킵니다. A가 포인터 p로 p[0] = 'h'를 쓰면 B는 포인터 q로 q[0]에서 'h'를 읽습니다. 같은 물리 페이지를 두 주소 공간에 붙인 것이므로 복사는 한 번도 일어나지 않습니다.

  • 주소는 달라도 됩니다. A와 B가 붙인 주소는 서로 다르지만(예: 0xffff9c6c9000과 0xffff8efb2000) 가리키는 곳이 같습니다.
  • 디스크가 아닙니다. /dev/shm은 메모리에만 있는 파일 시스템이라 재부팅하면 사라집니다.
  • 한 번 붙이면 끝입니다. 그 뒤의 읽기 · 쓰기에는 시스템 호출이 없습니다. 커널은 그 접근을 모릅니다.

입문 예제 shmhello: 끝난 프로세스가 남긴 글

shmhello는 한 프로세스가 써 둔 글을 나중에 온 다른 프로세스가 읽는 예제입니다. 서로 모르는 두 프로세스가 이름 하나로 같은 메모리를 보는지 직접 확인하려고 실행합니다. 사용법은 ./shmhello write TEXT | read | rm이고, 명령마다 새 프로세스입니다.

쓰는 쪽은 세 단계로 공유 메모리를 만듭니다.

int fd = shm_open(NAME, O_CREAT | O_RDWR, 0600);   /* ① 이름으로 연다 */
if (ftruncate(fd, SIZE) == -1) { perror("ftruncate"); return 1; }  /* ② */
char *p = mmap(NULL, SIZE, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
close(fd);                      /* 붙인 뒤에는 fd가 필요 없다 */
snprintf(p, SIZE, "%s", argv[2]);       /* 그냥 메모리에 쓴다 */

shm_open은 fd를 돌려줍니다. 새로 만든 객체의 크기는 0이라서 ftruncate로 늘려야 합니다. mmap에 MAP_SHARED를 주어 붙이고 나면 fd는 닫아도 되고, 쓰기는 평범한 snprintf입니다. 읽는 쪽은 같은 이름을 읽기용으로 열어 붙이기만 합니다.

int fd = shm_open(NAME, O_RDONLY, 0);
char *p = mmap(NULL, SIZE, PROT_READ, MAP_SHARED, fd, 0);

읽는 쪽은 ftruncate를 하지 않고, 읽기도 그냥 포인터로 합니다. rm은 shm_unlink(NAME)으로 이름을 지웁니다.

실행에서 확인할 것은 세 가지입니다.

  • 쓴 프로세스는 이미 끝났습니다. 글을 쓴 프로세스는 이미 없는데도 글은 커널의 객체에 남아 있어서, 나중에 실행한 프로세스가 읽습니다.
  • 주소가 매번 다릅니다. 프로세스마다 출력하는 주소가 다릅니다. 같은 메모리를 다른 주소로 보는 것입니다.
  • 파일로도 보입니다. 객체는 /dev/shm/w13_hello라는 파일로 보이고 head · cat · rm이 됩니다. 크기는 ftruncate한 값입니다.

1부 POSIX 공유 메모리

이름으로 열고, 크기를 정하고, 주소 공간에 붙입니다. 그 안에 구조체를 놓는 법과 수명을 보고, 잠금 없이 여럿이 쓰면 어떻게 되는지 확인합니다.

만들고 쓰고 지우는 순서

전체 흐름은 shm_open(이름 → fd) → ftruncate(크기를 정한다) → mmap(주소 공간에 붙인다) → p[i] = …(그냥 읽고 쓴다) → munmap(뗀다) → shm_unlink(이름을 지운다)입니다. 헤더는 <sys/mman.h>와 <fcntl.h>이고, glibc 2.34 이전에는 -lrt로 링크해야 합니다. ftruncate는 만드는 쪽만 하고, 붙이는 쪽은 shm_open과 mmap만 합니다.

구조체를 올린다 — 포인터는 올리지 않는다

공유 메모리를 쓰는 데는 캐스팅 한 번이면 됩니다. mmap이 준 주소를 구조체 포인터로 받으면 그 뒤는 평범한 C입니다.

struct shared {
    sem_t lock;
    volatile long count;
};
struct shared *s = mmap(...);
s->count++;

반대로 다음처럼 포인터를 넣으면 안 됩니다.

struct bad {
    char *name;   /* A의 주소 */
    struct bad *next;
};
/* B에게 그 주소는
   전혀 다른 곳이다 */

붙인 주소가 프로세스마다 다르기 때문에 A가 넣은 포인터 값은 B에게 뜻이 없습니다. 게다가 malloc으로 받은 메모리는 아예 공유되지 않습니다. 규칙은 "그 프로세스 안에서만 뜻이 있는 값은 공유 메모리에 넣지 않는다"입니다.

  • 넣어도 되는 것: 정수 · 실수 · 문자 배열 · 그것들의 구조체 · sem_t
  • 넣으면 안 되는 것: 포인터, malloc으로 받은 주소, FILE *, fd 번호
  • 가리켜야 하면: 시작에서의 거리(오프셋)나 배열의 인덱스를 씁니다. 3부의 head · tail이 그 예입니다.

양쪽 프로그램은 같은 헤더(counter.h · ring.h)를 포함해 구조체의 모양을 맞춥니다. 1차시의 proto.h와 같은 역할입니다.

수명: 무엇을 하면 무엇이 사라지나

IPC 객체의 수명은 세 가지로 나뉩니다. 파이프와 익명 공유 매핑은 프로세스 수명이라서 쓰던 프로세스가 모두 끝나면 사라집니다. 공유 메모리는 커널 수명(kernel persistence)입니다. 객체의 주인이 프로세스가 아니라 커널이어서, 만든 프로세스가 끝나도 커널이 갖고 있고 누가 지우거나 재부팅할 때까지 남습니다. 디스크의 파일은 파일 시스템 수명이라 재부팅해도 남습니다.

count++는 한 동작이 아니다

aarch64에서 s->count++는 ldr(읽기) · add(더하기) · str(쓰기) 세 명령입니다. ① 레지스터로 count를 읽고, ② 레지스터에 1을 더하고, ③ 레지스터 값을 count에 씁니다. 단계 사이에 다른 프로세스가 낄 수 있고, 코어가 여러 개면 정말로 동시에 실행됩니다.

3② ③ 6을 쓴다6
4② ③ 6을 쓴다6

두 번 올렸는데 6입니다. B는 A가 고치기 전의 값으로 계산했습니다. 둘 다 5를 읽으면 둘 다 6을 쓰고, 갱신 한 번이 없어집니다. 결과가 실행 순서에 달려 있어 매번 다른 값이 나오는 것, 이것이 경쟁 조건입니다. 한 프로세스만 돌리면 절대 나타나지 않기 때문에, 시험해 보고 "잘 된다"고 믿기 쉽다는 점이 위험합니다.

예제 shmrace: 혼자면 맞고 넷이면 틀린다

shmrace는 공유 메모리의 값을 여러 프로세스가 잠금 없이 올리는 예제입니다. 잠금이 왜 필요한지 듣기 전에, 없으면 어떻게 되는지를 먼저 겪어 보려는 것입니다. 사용법은 ./shmrace init | add N | show | rm입니다.

공용 헤더 counter.h에는 공유 메모리의 맨 앞에 놓이는 구조체와, 이름으로 열어 붙이는 함수 attach가 있습니다.

struct shared {                 /* 공유 메모리의 맨 앞에 이 구조체가 놓인다 */
    sem_t lock;                 /* 2부에서 쓴다: 이진 세마포어 (1 = 열림) */
    volatile long count;        /* 여러 프로세스가 함께 올리는 값 */
};

attach(create)는 만들 때는 O_CREAT | O_EXCL | O_RDWR로 열고 ftruncate(fd, sizeof(struct shared))로 크기를 정하며, 붙이기만 할 때는 O_RDWR로 shm_open만 합니다. 그다음 mmap의 결과를 struct shared *로 받고 fd는 바로 닫습니다. 매핑은 fd를 닫아도 남기 때문입니다.

init은 공유 메모리를 만들고 세마포어를 1로(sem_init(&s->lock, 1, 1)), 값을 0으로 둡니다. add는 붙여서 N번 올리는데, 잠금은 없습니다.

struct shared *s = attach(0);
long n = atol(argv[2]);
for (long i = 0; i < n; i++)
    s->count++;                 /* 읽고 · 더하고 · 쓴다: 세 단계 */

show는 붙여서 값을 읽고, rm은 shm_unlink로 이름을 지웁니다.

10코어 기계에서 실행한 결과는 다음과 같았습니다.

  • 혼자면 정확합니다. 100만 번 올리면 100만입니다. 코드에는 잘못이 없어 보입니다.
  • 넷이면 사라집니다. 네 프로세스가 400만을 더했는데 196만만 늘었습니다. 절반이 없어졌습니다.
  • 매번 다릅니다. 둘째 실행에서는 209만이 늘었습니다. 같은 프로그램, 같은 입력인데 결과가 다릅니다.

1부 정리: 빠르지만 지켜 주는 것이 없다

  • 얻은 것: 복사가 없습니다. 붙인 뒤에는 시스템 호출이 없습니다. 큰 데이터도 그대로 둡니다.
  • 조심할 것: 포인터 · fd는 넣지 않습니다. 프로세스가 끝나도 내용이 남습니다. 만든 쪽이 지웁니다.
  • 남은 문제: 동시에 고치면 값이 사라집니다. 커널은 끼어들지 않으므로 순서를 직접 맞춰야 합니다.

메시지 큐는 커널이 줄을 세워 줬지만, 공유 메모리에서는 줄을 우리가 세웁니다. 2부는 shmrace의 s->count++ 한 줄을 지키는 법입니다.

2부 세마포어

한 번에 한 프로세스만 값을 고치게 지킵니다. 세마포어가 무엇인지, 어떻게 잠그고 푸는지, 그리고 잠금에 드는 값과 함정을 봅니다.

임계 구역: 한 번에 하나만

임계 구역(critical section)은 함께 쓰는 데이터를 읽고 고치는 코드 구간입니다. 여기서는 s->count++;(읽고 · 더하고 · 쓴다)입니다. 상호 배제(mutual exclusion)는 그 구간에 한 번에 한 프로세스만 들어가고 나머지는 기다리게 하는 것입니다. 운영체제 과목의 용어를 실제 함수로 만나는 셈입니다.

문이 하나 달린 방으로 생각하면 됩니다. 들어갈 때는 비어 있으면 들어가서 문을 잠그고, 누가 있으면 잠들어 기다립니다. 나올 때는 문을 풀고, 기다리던 프로세스 하나를 깨웁니다. "세 단계 사이에 아무도 끼어들지 못하게" 하면 count++는 다시 한 동작처럼 됩니다.

재우고 깨우는 일은 커널이 합니다. 기다리는 쪽은 CPU를 쓰지 않고 자다가 풀리면 깨어납니다. 그리고 임계 구역은 짧을수록 좋습니다.

세마포어: 정수 하나와 두 연산

세마포어는 Dijkstra(1965)의 P · V 연산에서 왔습니다. sem_wait = P = down = 잠근다, sem_post = V = up = 푼다 로 대응합니다.

  • sem_wait(&s): 값이 0보다 크면 1을 빼고 지나갑니다. 값이 0이면 잠듭니다.
  • sem_post(&s): 값에 1을 더하고, 잠든 프로세스 하나를 깨웁니다.

값은 "남은 입장권"이라고 생각하면 됩니다. 0보다 크면 들어갈 수 있고 0이면 기다리며, 음수가 되지 않습니다. 중요한 것은 두 연산이 쪼개지지 않는다는 점입니다. 확인과 빼기 사이에 아무도 끼지 못하며, 이것을 커널과 CPU가 보장합니다. "확인하고 빼는" 두 걸음을 한 걸음으로 만들어 주는 것, 바로 우리가 count++에서 하지 못하던 일입니다.

처음 값이 쓰임을 정합니다. 처음 값이 1이면 잠금(이진 세마포어)이어서 wait … 임계 구역 … post로 쓰고 한 번에 하나만 들어갑니다. 처음 값이 N이면 자리 수(계수 세마포어)입니다. 빈 칸이 N개인 버퍼처럼 N번까지는 기다리지 않습니다. 3부에서 둘 다 씁니다.

POSIX 세마포어의 함수

헤더는 <semaphore.h>이고 -pthread로 링크합니다. 이름 없는 세마포어를 프로세스 사이에서 쓰려면 sem_t가 공유 메모리 안에 있어야 합니다.

예제 semcount: 정확해졌다, 그리고 느려졌다

semcount는 같은 값을 세마포어로 잠그고 올립니다. 같은 실험에 두 줄만 더해, 세마포어로 얻는 것과 치르는 값을 숫자로 재려는 예제입니다. 사용법은 ./semcount add N | hold SEC | try | value이고, shmrace init으로 만든 공유 메모리를 그대로 씁니다.

add는 shmrace의 반복문에 wait와 post 두 줄을 더한 것입니다.

for (long i = 0; i < n; i++) {
    sem_wait(&s->lock);         /* 1 → 0. 이미 0이면 여기서 잔다 */
    s->count++;                 /* 임계 구역: 한 번에 한 프로세스만 */
    sem_post(&s->lock);         /* 0 → 1. 기다리던 프로세스를 깨운다 */
}

hold는 잠근 채로 주어진 초만큼 sleep한 뒤 풉니다. 이 사이에 프로세스가 죽으면 sem_post는 영영 실행되지 않고 세마포어는 잠긴 채로 남습니다. 이 상황을 만들어 보려고 둔 명령입니다.

try는 마감 시각까지만 기다립니다. 1차시의 mq_timedreceive와 같은 방식으로, 지금 시각에 2초를 더해 마감 시각을 만듭니다.

struct timespec until;
clock_gettime(CLOCK_REALTIME, &until);
until.tv_sec += 2;              /* 마감 시각 = 지금 + 2초 */
if (sem_timedwait(&s->lock, &until) == -1) {
    perror("잠글 수 없다: sem_timedwait");
    return 1;
}

그때까지 잠그지 못하면 -1과 ETIMEDOUT으로 돌아오므로, 포기하고 알릴 수 있습니다. value는 sem_getvalue로 지금 값을 읽어 "열림"인지 "잠김"인지 보여 주는 진단용 명령입니다.

첫 번째 실행에서는 네 프로세스가 100만 번씩 올려 정확히 400만이 되었습니다. 하나도 사라지지 않았고, 끝난 뒤 세마포어 값은 1(열림)이었습니다. 대신 시간이 0.006초에서 0.407초로 늘었습니다. 잠그면 약 70배 느린 것이고, 이것이 맞는 답의 값입니다. 여기서 "임계 구역은 짧게"라는 규칙이 나옵니다. 잠금 안에서 오래 걸리는 일을 하면 모두가 그만큼 기다립니다.

두 번째 실행에서는 잠근 프로세스를 죽여 봅니다.

  • 죽어도 풀리지 않습니다. 커널은 누가 잠갔는지 기억하지 않습니다. 값 0만 남습니다.
  • 시간 제한이 없었다면 영원히 멈췄을 것입니다. try 대신 add였다면 끝나지 않고, 오류도 나지 않습니다.
  • 고치는 길은 통째로 지우고 다시 만들거나, 죽을 때 풀리는 잠금을 쓰는 것입니다.

2부 정리: wait와 post 사이

sem_wait(&s->lock);    /* 잠근다 — 0이면 잔다 */
s->count++;            /* 임계 구역 */
sem_post(&s->lock);    /* 푼다 — 하나를 깨운다 */

세마포어는 처음 값 1로 공유 메모리 안에 두고, sem_init(&s->lock, 1, 1)의 둘째 인자 1로 프로세스 사이에서 쓴다고 알립니다.

  • 얻은 것: 넷이 100만 번씩 올려 정확히 400만. 읽기–고치기–쓰기가 한 동작처럼 됩니다.
  • 낸 값: 0.006초 → 0.407초. 임계 구역은 짧게, 잠그는 횟수는 적게 합니다.
  • 남은 위험: 잠근 채 죽으면 풀리지 않습니다. 잠금이 둘이면 순서를 지킵니다. 기다림에는 시간 제한을 둡니다.

세마포어는 "한 번에 하나"를 보장할 뿐, "누가 먼저"와 "죽으면 풀기"는 보장하지 않습니다.

3부 생산자–소비자

공유 메모리 위에 작은 큐를 놓고 세마포어 셋으로 지킵니다. 넣는 쪽과 꺼내는 쪽의 속도가 달라도 잃거나 겹치지 않게 만듭니다. 2부에서 "잠금"으로만 쓴 세마포어를 여기서는 "잠금"과 "자리 세기" 두 가지로 함께 씁니다.

문제: 넣는 쪽과 꺼내는 쪽의 속도가 다르다

생산자–소비자(유한 버퍼) 문제입니다. 생산자 여럿이 put으로 공유 메모리의 8칸 버퍼에 값을 넣고, 소비자가 get으로 꺼냅니다. 지켜야 할 것은 세 가지입니다.

  1. 가득 차면 생산자가 잠듭니다(빈 칸이 생길 때까지). 가득 찼는데 더 넣으면 아직 꺼내지 않은 값을 덮어쓰기 때문입니다.
  2. 비면 소비자가 잠듭니다(값이 들어올 때까지). 꺼낼 것이 없기 때문입니다.
  3. 고칠 때는 한 번에 한 프로세스만 고칩니다(상호 배제). 둘이 같은 칸에 쓰면 하나가 사라집니다. 1부의 문제 그대로입니다.

①과 ②는 "자리의 수를 세는" 세마포어가, ③은 "잠금" 세마포어가 맡습니다. 12주차에 본 파이프의 "차면 write가 잠들고 비면 read가 잠든다"와 같은 규칙입니다.

원형 버퍼: 배열과 인덱스 둘

버퍼는 struct ring 안의 long buf[8]이고 공유 메모리에 놓입니다. head는 다음에 꺼낼 자리, tail은 다음에 넣을 자리입니다. 먼저 넣은 것이 먼저 나옵니다(FIFO).

넣기:    buf[tail] = v;    tail = (tail + 1) % 8;
꺼내기:  v = buf[head];    head = (head + 1) % 8;
  • 포인터가 아니라 인덱스입니다. head와 tail은 정수입니다. 1부의 규칙대로 주소는 넣지 않습니다.
  • 끝에서 처음으로 돌아갑니다. % 8로 돌아가므로 배열을 옮기지 않고 계속 씁니다.
  • 넣기와 꺼내기는 다른 끝에서 일어납니다. 생산자는 tail만, 소비자는 head만 옮깁니다. 그래도 잠금은 필요합니다.

이 네 줄이 임계 구역입니다. 두 프로세스가 동시에 tail을 읽으면 같은 칸에 쓰게 됩니다. 한편 든 칸의 수와 빈 칸의 수는 head · tail이 아니라 세마포어 값이 알려 줍니다.

세마포어 셋의 역할

  • slots — 빈 칸의 수(처음 8). 0이면 가득 찬 것이므로 생산자가 잡니다.
  • items — 든 칸의 수(처음 0). 0이면 빈 것이므로 소비자가 잡니다.
  • mutex — 잠금(처음 1). 버퍼 · head · tail을 고칠 때 씁니다.
put (생산자)
sem_wait(&r->slots);    빈 칸을 하나 얻는다
sem_wait(&r->mutex);    잠근다
buf[tail] = v; tail++   넣는다
sem_post(&r->mutex);    푼다
sem_post(&r->items);    든 칸 +1

get (소비자)
sem_wait(&r->items);    든 칸을 하나 얻는다
sem_wait(&r->mutex);    잠근다
v = buf[head]; head++   꺼낸다
sem_post(&r->mutex);    푼다
sem_post(&r->slots);    빈 칸 +1

생산자가 올린 items를 소비자가 내리고, 소비자가 올린 slots를 생산자가 내립니다. 내가 내린 세마포어를 상대가 올리는, 서로를 깨우는 구조입니다. 그래서 slots + items = 8이 언제나 유지됩니다.

잠그는 순서가 틀리면 멈춘다

옳은 순서는 자리를 먼저, 잠금을 나중에 얻는 것입니다.

sem_wait(&r->slots);
sem_wait(&r->mutex);

버퍼가 가득 찼을 때 이 순서라면 ① 생산자는 slots가 0이라 잠들지만 mutex는 쥐지 않았고, ② 소비자가 mutex를 얻어 하나 꺼내고, ③ 소비자가 slots를 올리고, ④ 생산자가 깨어나 넣습니다.

두 줄의 순서를 바꿔 잠금을 먼저 잡으면 이렇게 됩니다.

sem_wait(&r->mutex);
sem_wait(&r->slots);

버퍼가 가득 찼을 때 ① 생산자가 mutex를 얻고, ② slots가 0이라 mutex를 쥔 채 잠들고, ③ 소비자는 mutex를 얻지 못해 잠들고, ④ slots를 올려 줄 프로세스가 없습니다. 교착입니다. 두 줄의 순서만 바꿨는데 버퍼가 가득 차는 순간 프로그램 전체가 멈춥니다.

규칙은 "오래 기다릴 수 있는 것(자리)을 먼저, 짧게 쥐는 것(잠금)을 나중에", 그리고 "잠금을 쥔 채로 잠들지 않는다"입니다.

예제 ringbuf: 공유 메모리의 원형 버퍼와 세마포어 셋

ringbuf는 공유와 동기화를 합치면 1차시의 큐가 된다는 것을 직접 만들어 확인하는 예제입니다. 사용법은 ./ringbuf init | put START COUNT [MS] | get COUNT [MS] | stat | rm이고, 공용 헤더는 ring.h입니다.

#define RING_NAME "/w13_ring"
#define RING_SIZE 8

struct ring {
    sem_t slots;                /* 빈 칸의 수: 처음에 RING_SIZE */
    sem_t items;                /* 든 칸의 수: 처음에 0 */
    sem_t mutex;                /* head · tail · buf를 지키는 잠금: 처음에 1 */
    int   head;                 /* 다음에 꺼낼 자리 */
    int   tail;                 /* 다음에 넣을 자리 */
    long  buf[RING_SIZE];
};

세마포어 셋이 모두 공유 메모리 안에 있고, head와 tail은 포인터가 아니라 인덱스이며, 버퍼는 long 8개입니다. 구조체 전체가 168바이트입니다.

put과 get은 앞에서 본 틀 그대로입니다. put은 slots를 먼저 내리고(가득 찼으면 여기서 잡니다) 그다음에 mutex를 잠근 뒤, 값을 넣고 tail을 옮기고 풀고, items를 올려 소비자를 깨웁니다. get은 그 거울입니다. items를 내리고 잠그고 꺼내고 풀고 slots를 올립니다.

init은 세 세마포어의 처음 값을 정합니다. 둘째 인자 1은 프로세스 사이에서 공유한다는 뜻입니다.

sem_init(&r->slots, 1, RING_SIZE);  /* 둘째 인자 1: 프로세스 사이 공유 */
sem_init(&r->items, 1, 0);
sem_init(&r->mutex, 1, 1);
r->head = r->tail = 0;

put START COUNT [MS]는 공유 메모리에 붙어서 START부터 COUNT개를 넣습니다. 기다림은 put 함수 안에서 일어나고, 넣은 뒤에 한 줄을 출력합니다. MS를 주면 그만큼 쉬어 속도를 늦춥니다.

첫 번째 실행에서는 생산자가 1부터 10개를 넣으려 했지만 8개에서 멈췄습니다. 빈 칸이 0이 되자 slots에서 잠든 것입니다. 소비자를 실행해 꺼내자 소비자가 slots를 올렸고, 생산자가 깨어나 9와 10을 넣었습니다. 꺼낸 값의 합은 1부터 10까지의 합인 55로, 하나도 빠지거나 겹치지 않았습니다.

두 번째 실행은 생산자 둘과 소비자 하나입니다. 한 생산자는 100~104를, 다른 생산자는 200~204를 넣습니다. 소비자가 느려서(50 ms) 여덟 칸이 차자 생산자가 기다렸고, 204는 101이 나간 뒤에야 들어갔습니다. 먼저 들어간 100~104가 먼저 나왔습니다. 원형 버퍼는 FIFO이기 때문입니다. 합은 510 + 1010 = 1520으로, 열 개가 한 번씩 빠짐없이 왔습니다.

3부 정리: 공유 + 동기화 = 전달

공유 메모리(원형 버퍼 · head · tail)에 세마포어 셋(slots · items · mutex)을 더하면, 차면 기다리고 비면 기다리는 큐가 됩니다.

  • 세마포어의 두 쓰임: 잠금은 내가 내리고 내가 올립니다(처음 값 1). 자리 세기는 내가 내리고 상대가 올립니다(처음 값 N · 0).
  • 지킬 규칙: 자리를 먼저, 잠금을 나중에 얻습니다. 잠금을 쥔 채 잠들지 않습니다. 공유 데이터에 손대는 코드는 한 함수에 모읍니다.
  • 고르는 기준: 대부분의 경우에는 메시지 큐 · 파이프 · 소켓을 씁니다. 아주 잦거나 큰 데이터일 때 공유 메모리 + 세마포어를 씁니다.

파이프와 메시지 큐가 커널 안에서 해 주던 일을 직접 만들어 본 것입니다.

4부 스레드의 동기화

같은 문제를 한 프로세스 안의 스레드에서 다시 봅니다. 뮤텍스로 잠그고, 조건 변수로 기다리고, 세마포어로 수를 셉니다.

스레드: 처음부터 메모리를 함께 쓴다

1~3부의 프로세스 둘은 각자의 주소 공간을 갖고 있어서 공유 메모리를 만들어 붙여야 했습니다. 스레드는 한 프로세스 안의 실행 흐름 여럿이고 주소 공간이 하나입니다. 전역 변수 · 힙 · 열린 파일(fd)을 모든 스레드가 이미 함께 쓰므로 shm_open도 mmap도 필요 없습니다. 스택만 각자 갖습니다. 지역 변수는 스레드마다 따로이고, 나머지는 모두 조심해야 합니다.

pthread_t t;
pthread_create(&t, NULL, worker, arg);  /* 새 스레드: worker(arg) */
pthread_join(t, &result);               /* 끝나기를 기다린다 */

헤더는 <pthread.h>이고 gcc -pthread로 컴파일합니다. fork와 wait에 해당하는 것이 pthread_create와 pthread_join입니다. 공유 메모리를 만들 필요가 없다는 것은, 그만큼 동기화가 더 자주 필요하다는 뜻입니다.

pthread_mutex_trylock(&m)기다리지 않는다 — 잠겨 있으면 EBUSY
pthread_mutex_unlock(&m)푼다. 잠근 스레드만 불러야 한다
pthread_mutex_destroy(&m)끝낸다 (pthread_mutex_init으로 만든 것)

처음 값 1인 세마포어와 다른 점은 세 가지입니다.

  1. 소유자가 있습니다. 잠근 스레드만 풀 수 있고, "누가 쥐고 있나"를 따질 수 있습니다.
  2. 값이 없습니다. post를 두 번 해서 둘이 들어가는 실수가 없습니다. 잠금 전용이어서 수를 세는 일은 하지 않습니다.
  3. 실패하면 -1이 아니라 오류 번호를 돌려줍니다(errno를 쓰지 않습니다). 반환값이 0이면 성공이고 아니면 EBUSY · EINVAL 같은 오류 번호이므로, perror 대신 strerror(반환값)을 씁니다.

임계 구역을 짧게 하라는 2부의 규칙은 그대로입니다. 잠근 채 오래 걸리는 일을 하지 않습니다.

예제 thcount: 스레드에서도 사라지고, 잠그면 맞는다

thcount는 스레드 넷이 전역 변수 하나를 세 가지 방법(잠금 없이 · 뮤텍스 · 세마포어)으로 올립니다. 스레드에서도 1부와 같은 문제가 생기고 뮤텍스가 그 답이라는 것을 확인하려는 예제입니다. 사용법은 ./thcount none | mutex | sem [THREADS [N]]이고 기본값은 4개 × 100만 번입니다.

count는 전역 변수라서 모든 스레드가 같은 것을 봅니다. 공유 메모리를 만들지 않았습니다. 각 스레드가 실행하는 worker는 방식에 따라 다음 셋 중 하나를 반복합니다.

if (mode == 'm') {
    pthread_mutex_lock(&lock);      /* 잠근 스레드가 */
    count++;
    pthread_mutex_unlock(&lock);    /* 직접 푼다 */
} else if (mode == 's') {
    sem_wait(&sem);
    count++;
    sem_post(&sem);
} else {
    count++;                        /* 읽고 · 더하고 · 쓴다 */
}

세마포어는 sem_init(&sem, 0, 1)로 만듭니다. 둘째 인자가 0이면 한 프로세스의 스레드 사이에서 쓴다는 뜻입니다. main은 pthread_create로 스레드마다 worker를 실행시키는데, fork와 달리 메모리를 복사하지 않습니다. 그다음 pthread_join으로 모두 끝나기를 기다린 뒤에 값을 읽습니다. pthread_join은 스레드의 wait입니다.

10코어 기계에서 실행한 결과입니다.

  • 잠금 없이는 절반도 안 됩니다. 400만 중 188만, 160만이 나왔습니다. 프로세스 때와 같은 경쟁 조건입니다.
  • 잠그면 정확합니다. 뮤텍스도 세마포어도 400만입니다. 대신 0.006초가 0.3~0.4초가 됩니다.
  • 뮤텍스가 조금 빠릅니다. 0.335초 대 0.441초입니다. 다만 이 기계, 이 실행의 값이고 차이는 크지 않습니다.

조건 변수: 뮤텍스만으로는 기다릴 수 없다

버퍼가 비었으면 소비자는 값이 올 때까지 기다려야 합니다. 그런데 뮤텍스는 잠그고 푸는 것뿐이어서 "조건이 될 때까지"를 표현할 수 없습니다. 세 가지 방법을 비교해 봅니다.

① 잠근 채 기다리면 교착입니다. 넣는 쪽이 잠그지 못하므로 조건은 영원히 바뀌지 않습니다.

lock(&m);
while (used == 0)
    ;  /* 영원히 */
v = buf[head];
unlock(&m);

② 풀고 잠그며 돌면 동작은 하지만 바쁜 대기여서 CPU를 태웁니다.

for (;;) {
    lock(&m);
    if (used > 0) break;
    unlock(&m);
}

③ 조건 변수로 잠들면 CPU를 쓰지 않고 자고, 넣는 쪽이 깨워 줍니다.

lock(&m);
while (used == 0)
    cond_wait(&c, &m);
v = buf[head];
unlock(&m);

pthread_cond_wait(&c, &m)는 한 번에 ① m을 풀고 → ② 잠들고 → ③ 깨어나면 m을 다시 잠급니다. ①과 ②는 쪼개지지 않기 때문에 그 사이의 signal을 놓치지 않습니다. 3부의 규칙 "잠금을 쥔 채 잠들지 않는다"를 pthread_cond_wait가 대신 지켜 주는 것입니다. 뮤텍스는 "누가 들어가나"를, 조건 변수는 "언제 들어가나"를 맡습니다.

조건 변수를 쓰는 틀

기다리는 쪽과 알리는 쪽은 각각 정해진 틀을 따릅니다.

/* 기다리는 쪽 */
pthread_mutex_lock(&m);
while (!조건)                 /* if가 아니다 */
    pthread_cond_wait(&c, &m);
/* 조건이 참이다: 일을 한다 */
pthread_mutex_unlock(&m);

/* 알리는 쪽 */
pthread_mutex_lock(&m);
/* 조건을 바꾼다: used++ */
pthread_cond_signal(&c);      /* 하나를 깨운다 */
pthread_mutex_unlock(&m);
  • 왜 while인가. 깨어난 사이에 다른 스레드가 먼저 가져갔을 수 있습니다. 이유 없이 깨는 일도 있습니다. 그래서 깨면 다시 확인합니다.
  • 왜 뮤텍스와 함께인가. 조건(used)은 공유 데이터입니다. 확인과 잠들기 사이에 바뀌면 신호를 놓칩니다.
  • signal과 broadcast. signal은 하나를, broadcast는 모두를 깨웁니다. "끝났다"처럼 모두가 알아야 하면 broadcast를 씁니다.

조건 변수는 값을 기억하지 않습니다. 기다리는 스레드가 없을 때의 signal은 그냥 사라집니다. 마감 시각까지만 기다리는 pthread_cond_timedwait도 있습니다.

예제 thqueue: 뮤텍스 하나와 조건 변수 둘

thqueue는 뮤텍스만으로는 못 하는 "조건이 될 때까지 기다리기"를 조건 변수로 해 보는 생산자–소비자 예제입니다. 3부의 ringbuf와 같은 문제를 다른 도구로 풀어 둘을 비교합니다. 사용법은 ./thqueue P C N [MS]로, 생산자 P개가 N개씩 넣고 소비자 C개가 꺼냅니다.

도구는 뮤텍스 하나와 조건 변수 둘(가득 차지 않음 not_full · 비지 않음 not_empty)입니다. put은 가득 찼으면 기다립니다.

pthread_mutex_lock(&lock);
while (used == SIZE) {              /* if가 아니라 while: 깨면 다시 본다 */
    full_waits++;
    pthread_cond_wait(&not_full, &lock);    /* 잠금을 풀고 잠든다 */
}                                   /* 돌아왔을 때는 다시 잠근 상태다 */
buf[tail] = v;
tail = (tail + 1) % SIZE;
used++;
pthread_cond_signal(&not_empty);    /* 기다리는 소비자 하나를 깨운다 */
pthread_mutex_unlock(&lock);

get은 비었으면 기다리는데, 조건이 둘입니다. 비었고, 아직 끝이 아닐 때만 기다립니다. 조건식은 이렇게 마음대로 쓸 수 있습니다.

while (used == 0 && !done) {
    empty_waits++;
    pthread_cond_wait(&not_empty, &lock);
}
if (used == 0) {                    /* 비었고, 더 올 것도 없다 */
    pthread_mutex_unlock(&lock);
    return -1;
}

비었는데 반복문을 빠져나왔다면 더 올 것이 없다는 뜻이므로 뮤텍스를 풀고 -1을 돌려줍니다. 그렇지 않으면 값을 꺼내고 used를 내린 뒤 pthread_cond_signal(&not_full)로 기다리는 생산자 하나를 깨웁니다.

main은 소비자와 생산자 스레드를 만들면서 번호를 인자로 넘기고, 먼저 생산자가 모두 끝나기를 기다립니다. 그다음 끝을 알립니다.

pthread_mutex_lock(&lock);
done = 1;                           /* 조건이 바뀌었으니 */
pthread_cond_broadcast(&not_empty); /* 기다리는 소비자를 모두 깨운다 */
pthread_mutex_unlock(&lock);

기다리던 소비자가 모두 깨어나 끝을 확인합니다. 마지막으로 pthread_join(c[i], &sum)이 각 소비자 스레드의 반환값(꺼낸 값의 합)을 받습니다. wait가 종료 상태를 받는 것과 같습니다.

실행에서는 든 칸의 수가 8이 되면 생산자가 멈추는 것을 봅니다. 202를 넣자 8칸이 찼고, 그 뒤로는 하나 꺼내야 하나 넣습니다. 값은 넣은 순서대로(100~104, 200~204) 나오고, 합 1520은 3부의 ringbuf와 같습니다. 생산자 넷 · 소비자 둘로 40만 개를 돌려도 합이 기대와 같았고, 기다림은 약 15만 번 일어났습니다.

스레드 사이의 세마포어: 수를 센다

뮤텍스는 "하나만"입니다. "K개까지"는 세마포어가 합니다. 동시에 여는 연결의 수나 동시에 돌리는 작업의 수를 제한할 때 이렇게 씁니다. 3부의 slots · items도 같은 "수 세기"였습니다.

sem_init(&room, 0, 2);       /* 0: 스레드 사이 · 2: 자리 수 */
sem_wait(&room);   /* 일을 한다 */   sem_post(&room);
  • 처음 값이 자리 수입니다. 2로 두면 둘까지 지나가고 셋째부터 잠듭니다. 하나가 나오면 다음이 들어갑니다. 스레드 여섯 개라면 둘이 안에 있는 동안 나머지 넷은 문 앞에서 잡니다.
  • 둘째 인자가 0입니다. sem_init(&s, 0, 값). 공유 메모리가 필요 없고 전역 변수면 됩니다.
  • 소유자가 없습니다. 들어간 스레드와 다른 스레드가 post해도 됩니다. 뮤텍스와 다른 점입니다.

예제 thlimit: 안에는 언제나 둘까지

thlimit는 계수 세마포어로 스레드 여섯 개 가운데 한 번에 둘만 들어가게 합니다. 세마포어가 잠금이 아니라 "수를 세는 도구"로 쓰이는 경우를 확인하는 예제입니다. 사용법은 ./thlimit THREADS K이고, 예를 들면 ./thlimit 6 2입니다.

각 스레드는 자리를 얻고, 일하고, 자리를 돌려줍니다.

sem_wait(&room);                    /* 자리가 없으면 여기서 잔다 */

pthread_mutex_lock(&lock);          /* inside · peak는 뮤텍스가 지킨다 */
inside++;
if (inside > peak) peak = inside;
printf("[스레드 %ld] 들어감 (안에 %d개)\n", id, inside);
pthread_mutex_unlock(&lock);

usleep(100 * 1000);                 /* 안에서 0.1초 동안 일한다 */
…
sem_post(&room);                    /* 자리 +1: 기다리던 스레드가 들어온다 */

room의 처음 값은 K로 정해 두었고, 0이면 sem_wait에서 잠듭니다. 눈여겨볼 것은 뮤텍스도 함께 쓴다는 점입니다. 안에 있는 스레드 수 inside와 최댓값 peak는 공유 데이터이므로 뮤텍스가 지킵니다. 세는 일은 세마포어, 공유 변수를 지키는 일은 뮤텍스로 나눠 맡깁니다. 세는 것과 지키는 것은 다른 일입니다.

실행 결과에서 확인할 것은 다음과 같습니다.

  • 안에 2개를 넘지 않습니다. 셋째 스레드는 첫째가 나온 뒤에야 들어갔고, 끝까지 최대 2개입니다.
  • 나오면 곧 들어옵니다. "1 나옴" 바로 다음이 "3 들어감"입니다. post가 깨운 것입니다.
  • 순서는 보장하지 않습니다. 누가 먼저 들어갈지는 실행마다 다를 수 있습니다. 세마포어는 수만 지킵니다.

같은 큐, 두 가지 방법: ringbuf와 thqueue

둘 다 같은 입력에서 합 1520을 냈습니다. 도구가 달라도 지키는 것은 같습니다.

ringbuf (3부) — 세마포어 셋thqueue (4부) — 뮤텍스 + 조건 변수
누가 함께 쓰나서로 다른 프로세스 (공유 메모리)한 프로세스의 스레드 (전역 변수)
가득 찼을 때sem_wait(slots)에서 잠든다while (used == SIZE) cond_wait(not_full)
비었을 때sem_wait(items)에서 잠든다while (used == 0) cond_wait(not_empty)
버퍼 지키기sem_wait(mutex) … sem_post(mutex)pthread_mutex_lock … unlock
든 칸의 수세마포어 값이 기억한다변수 used를 직접 둔다
순서를 틀리면잠금을 먼저 잡으면 교착wait가 잠금을 풀어 주므로 그 실수가 없다
조건을 바꾸려면세마포어를 더 만든다while의 조건식만 고친다 (예: && !done)

조건이 "수 하나"면 세마포어가 짧고, 조건이 복잡하면 뮤텍스 + 조건 변수가 낫습니다.

4부 정리: 잠그고, 기다리고, 센다

  • 뮤텍스 — 잠근다. pthread_mutex_lock(&m); 임계 구역 pthread_mutex_unlock(&m); 잠근 스레드가 풉니다. (예제 thcount)
  • 조건 변수 — 기다린다. while (!조건) pthread_cond_wait(&c, &m); 조건을 바꾼 쪽이 signal · broadcast 합니다. 늘 뮤텍스와 함께, 늘 while입니다. (예제 thqueue)
  • 세마포어 — 센다. sem_init(&s, 0, K); sem_wait(&s); sem_post(&s); K개까지 들어가고 누구나 올립니다. (예제 thlimit)

이 도구들을 프로세스 사이에서 쓰려면, 세마포어는 sem_init의 둘째 인자를 1로 하고 공유 메모리 안에 둡니다(2 · 3부). 뮤텍스와 조건 변수도 공유 메모리 안에 두고 PTHREAD_PROCESS_SHARED 속성을 주면 됩니다. 프로세스든 스레드든 규칙은 같습니다. 함께 쓰는 데이터는 한 번에 하나만, 기다릴 때는 잠금을 놓고 기다립니다.

실습 과제: 예제를 넓힌다

  1. 잠금 줄이기 — ./semcount batch 1000000을 만듭니다. 100번은 자기 변수에 세고, 한 번 잠가 한꺼번에 더합니다. 결과는 여전히 정확해야 합니다. time으로 add와 비교하고, 묶음 크기를 10 · 100 · 1000으로 바꿔 표를 만듭니다.

  • 공유 메모리는 같은 물리 메모리를 여러 주소 공간에 붙입니다(shm_open → ftruncate → mmap). 복사도 시스템 호출도 없어 가장 빠릅니다.
  • 붙인 주소가 프로세스마다 달라 포인터는 넣지 않습니다. 프로세스가 끝나도 내용이 남으므로(커널 수명) 만든 쪽이 지웁니다.
  • count++는 세 단계라서 여럿이 잠금 없이 하면 값이 사라집니다. 세마포어의 wait · post로 임계 구역을 지키면 정확해지지만 느려지고, 잠근 채 죽으면 풀리지 않습니다.
  • 공유 메모리 + 세마포어 셋 = 큐입니다. 자리를 먼저 얻고 잠금을 나중에 얻습니다.
  • 스레드는 처음부터 메모리를 함께 씁니다. 뮤텍스로 잠그고, 조건 변수로 기다리고(늘 while), 세마포어로 수를 셉니다.
