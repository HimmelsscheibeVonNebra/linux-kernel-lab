이번 시간의 질문은 "새 프로세스(fork)와 새 프로그램(exec)은 어떻게 다른가"입니다. 1부에서 exec 가족으로 프로그램을 교체하고 fork로 프로세스를 복제한 뒤 둘을 합치고, 2부에서 프로세스가 끝나는 과정(exit, _exit, atexit)을, 3부에서 부모가 자식의 끝을 기다리고 회수하는 방법(wait, waitpid, status 매크로)을 봅니다. 수업 내내 반복하는 동작은 하나입니다. 프로그램이 printf로 스스로 보고한 값을 ps, strace, $?가 밖에서 보여 주는 값과 맞춰 보는 것입니다. PID 같은 값은 실행할 때마다 달라집니다.

들어가기

지난 시간과의 연결

9주차의 exit_how, chld_reap, usr_round는 fork, waitpid, pipe를 "관찰 도구"로만 썼습니다. 그때 설명 없이 지나간 것들이 오늘 정식으로 다뤄집니다.

  • 원시 status 값에서 상위 바이트가 종료 코드이고 하위 7비트가 시그널이라는 배치는 3부에서 정식 계약으로 다룹니다.
  • SIGCHLD가 오면 waitpid(WNOHANG) 루프로 자식을 수거했습니다. 왜 WNOHANG이어야 하는지의 답이 오늘 나옵니다.
  • exec 뒤의 시그널 처분은 SIG_IGN은 유지되고 핸들러는 초기화된다고 했습니다. 이것은 "exec가 무엇을 바꾸고 무엇을 남기는가"라는 더 큰 규칙의 한 줄입니다.

새 프로그램 실행과 새 프로세스 생성

새로운 프로세스를 실행하는 방법은 크게 두 가지, 새 프로그램 실행과 새 프로세스 생성입니다. 둘은 이름이 비슷하지만 바뀌는 것이 정반대입니다.

  • exec = 교체. 같은 PID 안에서 프로그램만 바뀝니다. 프로세스 A가 execlp("ls")를 부르면 PID는 그대로인 채 프로그램이 ls가 되고, 기존 코드는 더 실행되지 않습니다. 결과는 "같은 PID, 다른 프로그램"입니다.
  • fork = 복제. 부모의 사본이 새 PID로 생깁니다. 부모와 자식은 독립적으로 같은 코드를 이어 갑니다. 결과는 "다른 PID, 같은 프로그램"입니다.

둘을 합치면, fork로 자식을 만들고 자식만 exec를 해서 "내 일을 계속하면서 다른 프로그램도 돌리는" 구조가 됩니다. 셸이 ls를 실행하는 구조가 바로 이것입니다.

1부 생성과 실행

exec: 바이너리를 읽어 내 메모리에 덮어쓴다

execlp("ls", …)를 부르면 결국 execve 시스템 호출이 일어나고, 커널이 ls 바이너리를 읽어 지금 프로세스의 메모리에 적재합니다. 코드, 데이터, 힙, 스택이 모두 새로 만들어지고(스택에는 새 argv와 envp가 놓입니다), 기존 프로그램은 거기서 멈춥니다.

그래서 exec는 성공하면 돌아오지 않습니다. exec 다음 줄에 써 둔 "After exec" 출력은 새 프로그램 어디에도 없으므로 영원히 찍히지 않습니다. exec가 돌아오는 경우는 실패뿐이며, 이때 -1을 반환하고 errno에 ENOENT, EACCES, E2BIG 같은 원인이 들어갑니다.

무엇이 남고 무엇이 새로 만들어지는지는 다음과 같이 나뉩니다.

  • 유지되는 것: PID와 PPID, 열린 fd 표, 현재 작업 디렉터리(cwd), umask, 환경, SIG_IGN 처분. 9주차에 본 "SIG_IGN은 유지"가 이 목록의 한 항목입니다.
  • 새로 만드는 것: 코드, 데이터, 힙, 스택. 시그널 핸들러는 SIG_DFL로 돌아가고(핸들러 함수가 있던 코드가 사라졌기 때문입니다), stdio 버퍼도 사라집니다. exec 전에 버퍼에 "--> Before …"가 들어 있었더라도 교체 뒤의 버퍼는 비어 있습니다. 이 마지막 항목이 뒤에서 보는 "사라진 줄"의 원인입니다.

exec 가족 여섯: l·v, p, e

함수인자 전달찾기환경
execl(path, arg0, …, NULL)나열경로상속
execlp(file, arg0, …, NULL)나열PATH상속
execle(path, arg0, …, NULL, envp)나열경로envp
execv(path, argv)배열경로상속
execvp(file, argv)배열PATH상속
execvpe(file, argv, envp)배열PATHenvp

이름은 규칙대로 읽으면 됩니다. l은 list, v는 vector, p는 PATH 검색, e는 envp 지정입니다.

  • l과 v: l은 인자를 하나씩 나열하고 마지막에 (char *)NULL을 둡니다. v는 char *argv[] 배열로 넘깁니다.
  • p: 경로 대신 파일 이름을 받아, 셸처럼 PATH의 디렉터리를 차례로 찾습니다. 뒤의 strace 관찰에서 이 탐색이 실제로 보입니다.
  • e: envp로 환경을 직접 넘깁니다. e가 없으면 현재의 environ을 그대로 물려줍니다.

여섯 개는 모두 라이브러리 함수이고, 시스템 호출은 execve(path, argv, envp) 하나입니다. 여섯 모두 결국 이 한 호출로 모입니다. execvpe는 GNU 확장이라 _GNU_SOURCE가 필요합니다.

execlp.c와 execv.c: 같은 ls -a, 두 가지 호출

execlp와 execv는 둘 다 ls -a가 되는 프로그램이고, 인자를 전달하는 방식만 다릅니다.

/* execlp.c */
printf("--> Before exec function\n");
if (execlp("ls", "ls", "-a", (char *)NULL) == -1) {
    perror("execlp");
    exit(1);
}
printf("--> After exec function\n");   /* 도달하지 못한다 */

/* execv.c */
char *argv[3];
argv[0] = "ls"; argv[1] = "-a"; argv[2] = NULL;
if (execv("/bin/ls", argv) == -1) {
    perror("execv");
    exit(1);
}
  • ls를 두 번 쓰는 이유: 첫 "ls"는 PATH에서 찾을 파일이고, 둘째 "ls"는 새 프로그램이 받을 argv[0], 곧 프로그램 이름입니다.
  • NULL 종결: 인자가 어디서 끝나는지 알리는 표시입니다. 빠뜨리면 미정의 동작입니다. 배열로 넘기는 execv에서도 끝 표시는 똑같이 NULL입니다.
  • -1 검사: exec는 실패했을 때만 돌아오므로, == -1 검사와 그 안의 perror, exit가 실패 경로의 전부입니다.
  • execv에는 p가 없으므로 /bin/ls라는 전체 경로를 주어야 하고, e가 없으므로 환경은 현재 것을 물려줍니다.

실행하면 "Before" 줄 다음에 ls -a의 결과가 나오고 "After"는 없습니다. printf 다음의 execlp가 성공해 프로세스가 ls가 됐기 때문입니다. 화면에 보이는 파일 목록은 우리 프로그램의 출력이 아니라 ls가 같은 PID에서 찍은 것이고, 두 프로그램 모두 ls의 종료 상태 0으로 끝납니다.

exec의 두 경계: 파이프에서 사라진 줄, 실패 시 반환

같은 printf가 터미널, 파이프, 실패 경로에서 서로 다르게 보입니다.

  • 파이프(./execlp | head -3): "Before" 줄이 사라집니다. 출력이 파이프로 가면 완전 버퍼링이 되어 그 줄은 버퍼에만 있었고, exec가 버퍼째 버렸습니다.
  • 실패(PATH=/nonexistent ./execlp): ls를 찾지 못해 execlp가 -1로 돌아옵니다. perror 뒤 exit(1)로 끝나므로 종료 상태는 1입니다. 그리고 이번에는 "Before"가 보입니다. exec가 실패해 프로세스가 살아남았고, exit(1)이 버퍼를 비웠기 때문입니다.

왜 "Before" 줄이 사라졌나: stdio 버퍼와 exec

printf는 곧바로 화면에 쓰지 않고 먼저 사용자 공간의 stdio 버퍼에 넣습니다. 그 버퍼가 언제 write로 나가는지는 출력 대상에 따라 다릅니다. stdout은 터미널이면 줄 버퍼, 아니면 완전 버퍼(기본 4096바이트)입니다.

  • 터미널(줄 버퍼): "Before\n"의 \n에서 즉시 write되어 화면에 나옵니다. execve가 일어날 때 버퍼는 이미 비어 있었습니다.
  • 파이프·파일(완전 버퍼): 버퍼가 가득 차거나 프로그램이 종료할 때 write합니다. "Before\n"은 4096바이트를 채우지 못해 버퍼에만 머물렀고, 그 상태에서 execve가 일어났습니다. exec는 사용자 공간을 통째로 바꾸므로 아직 write되지 않은 버퍼도 함께 없어집니다. 화면에는 아무것도 남지 않습니다.

exec가 실패한 경로에서는 프로세스가 살아서 exit에 도달하고, exit가 버퍼를 flush하므로 그제야 "Before"가 보입니다. stderr는 버퍼가 없어서, perror의 메시지가 "Before"보다 먼저 보이는 것도 같은 이유로 설명됩니다.

여기서 규칙이 나옵니다. fork·exec 직전에 fflush(NULL)을 하거나, setvbuf(stdout, NULL, _IONBF, 0)으로 버퍼링을 끕니다. 9주차 exit_how가 flush를 했던 것이 바로 이 이유였습니다. 같은 규칙이 fork에도 적용되는데, 그쪽에서는 버퍼가 사라지는 것이 아니라 복제되어 자식이 exit할 때 또 비워지는 문제가 됩니다. 2부의 끝에서 다룹니다.

fork: 한 번 호출, 두 번 반환

pid = fork();를 부르면 커널이 자식의 PCB를 만들고 메모리 사본을 준비하고 자식 PID를 배정합니다. 그 뒤 같은 호출이 부모와 자식 두 프로세스에서 각각 반환되고, 반환값이 역할을 나눕니다.

  • 0보다 크면 부모입니다. 값은 자식의 PID입니다.
  • 0이면 자식입니다.
  • -1이면 실패입니다. 자식은 생기지 않았고 부모에게만 -1이 돌아오며 errno(EAGAIN, ENOMEM)가 설정됩니다.

같은 코드가 두 프로세스에서 이어지고 반환값만 다릅니다. fork 다음 줄부터는 둘 다 실행하므로, 분기 밖에 있는 "End of fork" 출력은 두 번 찍힙니다. 자식은 반환값으로 0을 받을 뿐 부모의 PID를 받지 못하므로, 부모가 누구인지는 getppid()로 알아냅니다.

복제되는 것, 새로 받는 것, 공유하는 것

"메모리에 있는 정보는 복사되고, 프로세스를 관리하는 정보는 복사되지 않는다"는 것이 큰 줄기입니다.

stdio 버퍼와 atexit 등록이 "복제된다" 쪽에 들어 있다는 점을 기억해 두십시오. 2부의 함정이 여기서 나옵니다.

fork.c: switch (pid = fork()) 세 갈래

fork 예제는 대입과 분기를 한 줄에 쓴 switch (pid = fork())로 세 갈래를 나눕니다. 반환값이 세 갈래의 열쇠입니다.

switch (pid = fork()) {
    case -1 :  /* fork failed */
        perror("fork");
        exit(1);
    case 0 :   /* child process */
        printf("Child Process - My PID:%d, My Parent's PID:%d\n",
               (int)getpid(), (int)getppid());
        break;
    default :  /* parent process */
        printf("Parent process - My PID:%d, My Parent's PID:%d, "
               "My Child's PID:%d\n",
               (int)getpid(), (int)getppid(), (int)pid);
        break;
}
printf("End of fork\n");
  • -1 (실패): perror 뒤 exit(1)입니다. 자식은 생기지 않았고 부모만 이 가지로 옵니다. 원본 소스에는 exit(1) 뒤에 break가 있는데, exit 뒤라 닿지 않는 관습적인 줄입니다.
  • 0 (자식): 자기 PID와, getppid()로 얻은 부모 PID를 찍습니다.
  • 양수 (부모): 반환값을 담은 pid 변수가 곧 자식의 PID입니다. 자기 부모(셸)의 PID도 함께 찍어 사슬을 보여 줍니다.
  • (int) 캐스팅은 pid_t의 크기가 구현마다 달라서 %d에 맞추는 관습입니다. pid_t는 sys/types.h에, fork·getpid·getppid는 unistd.h에 있습니다.
  • "End of fork"는 switch 밖이라 두 프로세스가 모두 실행합니다.

fork 실행: PID 사슬과 두 번의 End of fork

강의의 실행 화면에서는 셸(206)이 fork로 220을 만들고, 220이 fork로 221을 만들었습니다. 부모가 찍은 PPID는 셸에서 echo $$로 본 값과 같습니다. 같은 프로그램을 두 번 실행했더니 자식이 찍은 PPID가 달랐습니다.

  • 첫 실행의 PPID는 1: 자식이 getppid()를 부르기 전에 부모가 먼저 끝나서, 자식이 PID 1에게 입양된 뒤였습니다(7주차의 고아 프로세스).
  • 둘째 실행의 PPID는 222: 이번에는 자식이 실행될 때 부모가 살아 있었습니다.

"End of fork"는 매번 두 번 나옵니다. 두 결과는 모두 정상입니다.

실행 순서는 스케줄러가 정한다

fork 직후 두 프로세스는 같은 실행 큐에 놓이고, 누가 먼저 CPU를 받을지는 정해진 바가 없습니다. 코어가 여럿이면 동시에 실행됩니다. 둘은 서로 독립적으로, 동시에 실행된다고 보아야 합니다.

  • 부모가 먼저 끝난 경우(첫 실행): 부모 220이 "Parent process"와 "End of fork"를 찍고 종료 → 자식 221의 getppid()는 입양된 뒤라 1 → 자식의 "End of fork".
  • 자식이 먼저 실행된 경우(둘째 실행): 자식 223의 getppid()는 222(부모가 살아 있음) → 자식의 "End of fork" → 부모 222의 "Parent process"와 "End of fork".

출력이 섞이는 이유는 두 프로세스의 write가 한 터미널로 모이기 때문이며, 9주차 usr_round에서도 본 현상입니다. 순서가 필요하면 부모가 wait로 자식의 끝을 기다리거나(3부), 파이프나 시그널로 신호를 주고받아야 합니다.

fork + exec: 셸이 명령을 실행하는 방법

"내 것을 하는 중에 잠깐 다른 프로그램을 실행하고 싶다"면 fork 뒤 자식에서 exec를 합니다. 부모는 자기 코드를 이어 가고 자식만 새 프로그램이 됩니다. 셸은 이것을 반복하는 fork·exec·wait 루프입니다. ls -a라는 명령을 읽으면 bash가 fork하고, 자식이 (설정 단계를 거쳐) execvp("ls", argv)를 하고, bash는 waitpid(pid, &st, 0)으로 기다립니다. 자식이 끝나면 그 종료 상태가 $?(= WEXITSTATUS)가 되고 프롬프트가 다시 나옵니다.

  • forkNexec.c = fork + (자식) execlp — wait가 없어서 부모가 먼저 끝날 수 있습니다.
  • bash = fork + (자식) execvp + waitpid — 자식이 끝나야 프롬프트가 나옵니다.

정리하면 새 프로세스(fork) + 새 프로그램(exec) + 끝 기다리기(wait) = 명령 실행입니다.

forkNexec.c: 자식만 ls가 된다

forkNexec는 fork.c와 같은 switch로 역할을 나누고, 자식 가지에서만 exec를 합니다.

case 0 :    /* child process */
    printf("--> Child Process\n");
    if (execlp("ls", "ls", "-a", (char *)NULL) == -1) {
        perror("execlp");
        exit(1);
    }
    exit(0);       /* exec가 성공하면 도달하지 않는다 */
default :   /* parent process */
    printf("--> Parent process - My PID:%d\n", (int)getpid());
    break;
}
return 0;          /* 부모는 기다리지 않고 끝난다 */
  • 자식 가지: printf 뒤 execlp입니다. 실패하면 perror와 exit(1), 성공하면 그 아래 줄은 영영 실행되지 않습니다.
  • exit(0)이 있는 이유: exec가 성공하면 도달할 수 없는 줄이지만, 실패 경로의 자식이 switch를 빠져나가 부모 코드로 흘러가지 않게 막는 울타리입니다.
  • 부모 가지: PID를 찍고 return합니다. 이 소스에는 sys/wait.h조차 없습니다. 기다리지 않으니 부모가 자식보다 먼저 끝날 수 있고, 그러면 자식은 고아가 됩니다.

실제 실행에서 그 결과가 보입니다. 첫 실행에서는 부모가 PID를 찍고 끝나 프롬프트가 먼저 나왔고, ls의 출력이 그 뒤에 찍혔습니다. 프롬프트 뒤에 찍힌 목록은 고아가 된 ls의 출력입니다. 부모 없이 남은 자식은 PID 1에게 입양되어 끝까지 실행하고, 셸은 그 존재를 모릅니다. Enter를 치면 프롬프트가 다시 나옵니다. 또 출력을 | head로 파이프에 연결하면 "--> Child Process" 줄이 사라지는데, 앞에서 본 버퍼 규칙 그대로입니다.

strace로 본 fork·exec: clone과 네 번의 execve

strace -f -e trace=%process로 forkNexec를 추적하면 프로세스 관리 호출(clone, execve, wait4, exit_group)만 볼 수 있습니다. -f는 자식까지 추적하라는 옵션입니다.

  • clone(… SIGCHLD): fork는 리눅스에서 clone 호출로 나타납니다. 반환값으로 자식의 PID를 돌려받습니다.
  • execve 네 번: execlp의 p가 하는 일입니다. PATH의 디렉터리를 차례로 execve해 보다가 /usr/bin/ls에서 성공(= 0)했습니다.
  • exit_group 순서: 부모(270)가 먼저 exit_group을 했고, 자식(271)은 ls를 다 마치고 나중에 끝났습니다. 프롬프트가 먼저 돌아온 관찰과 같은 사실입니다.

왜 fork와 exec는 둘로 나뉘어 있나

fork 뒤, exec 전의 자식은 아직 부모의 코드를 실행하고 있습니다. 이 틈이 자식 설정 단계입니다. 자식은 부모가 써 둔 평범한 C 코드로 자기 환경을 자기 손으로 바꾼 다음 exec를 합니다.

  • open + dup2: 출력 리다이렉션
  • 시그널 처분 복원 (SIG_IGN → SIG_DFL)
  • chdir, umask, nice(우선순위)
  • 물려줄 필요 없는 fd 닫기 (FD_CLOEXEC)

exec된 프로그램은 "누가 어떻게 준비했는지" 몰라도 됩니다. ls > out.txt를 실행하면 셸은 자식에서 open과 dup2를 한 뒤 exec하고, ls는 자기 stdout이 파일인지 터미널인지 신경 쓰지 않습니다. exec가 열린 fd 표를 유지한다는 규칙이 여기서 쓰입니다.

대안도 있습니다. posix_spawn(&pid, path, file_actions, attrp, argv, envp)은 한 호출에 설정 목록을 넘깁니다. 다만 그 설정은 미리 정해진 옵션 목록이고, fork + 설정 + exec에서는 설정이 평범한 C 코드라 어떤 조합도 가능합니다. 유연함은 fork+exec 쪽이 큽니다. 둘로 나뉜 덕에 셸의 리다이렉션과 파이프(12주차)가 자식 설정 단계의 몇 줄로 끝납니다.

2부 프로세스의 종료

exit status: 자식이 부모에게 남기는 한 바이트

자식이 exit(2)로 끝나면 커널이 종료 상태를 보관하고, 부모가 wait(&status)로 그것을 받아 WEXITSTATUS(status)로 2를 꺼냅니다. 커널이 보관하는 값은 0x0200 = (2 & 0377) << 8의 꼴입니다.

  • 하위 8비트만 전달됩니다(status & 0377). 값의 범위는 0~255이고, exit(256)은 0, exit(-1)은 255가 됩니다.
  • 커널이 보관합니다. 자식은 사라져도 종료 상태는 부모가 가져갈 때까지 남습니다. 이것이 3부의 좀비입니다.
  • $?도 같은 값입니다. 부모가 셸이면 bash가 waitpid로 받은 값을 $?로 보여 줍니다.
  • main에서 return n은 exit(n)과 같고, main의 끝에 도달하는 것은 return 0과 같습니다.

./wait; echo $?가 0으로 나오는 이유도 이 길을 따라가면 풀립니다. 셸이 받은 것은 자기 자식인 wait.c 부모의 return 0이고, 자식의 2는 그 부모가 받았습니다. 종료 상태는 바로 위 부모에게만 갑니다.

셸의 관례는 0이 성공, 1~125는 프로그램이 정한 실패, 126은 실행 불가, 127은 못 찾음, 128+n은 시그널 n으로 종료(9주차)입니다.

exit의 네 단계: 등록 함수 → flush → 임시 파일 → _exit

exit(3)는 라이브러리 함수이고 _exit(2)는 시스템 호출입니다. exit(status)는 사용자 공간(glibc)에서 다음 순서로 정리한 뒤 커널로 들어갑니다.

  1. atexit로 등록한 함수를 역순으로 호출합니다.
  2. 열린 stdio 스트림을 모두 flush하고 close합니다.
  3. tmpfile(3)로 만든 임시 파일을 삭제합니다.
  4. _exit(status) 시스템 호출을 합니다.

1~3단계는 사용자 공간의 정리이고, main에서 return해도 같은 길을 갑니다. _exit부터가 커널의 몫입니다. 커널은 열린 fd를 모두 닫고(파일, 파이프, 소켓), 종료 상태를 보관하고(좀비 상태), 부모에게 SIGCHLD를 보내고(9주차), 내 자식들을 PID 1(init)에 입양시키고, 메모리와 자원을 반납합니다. 좀비 한 칸만 남깁니다.

_exit를 직접 부르면 정리 없이 즉시 커널로 갑니다. 1~3단계를 건너뛰는 것입니다. abort와 시그널에 의한 종료도 1~3단계를 건너뜁니다. 9주차 exit_how에서 _exit(3)이 "정리 없이 즉시"였던 이유가 4단계의 위치에 있고, 자식의 실패 경로에 _exit를 쓰는 이유도 여기에 있습니다.

atexit.c: 종료 처리기 등록

atexit 예제는 "Cleanup 1 is called."와 "Cleanup 2 is called."를 찍는 함수 두 개를 등록하고 exit(0)을 부릅니다.

int main(void) {
    atexit(cleanup1);
    atexit(cleanup2);

    exit(0);
}
  • 함수 포인터: atexit가 받는 것은 void (*func)(void)입니다. 인자도 반환값도 없는 함수만 등록할 수 있습니다. atexit 자체는 성공하면 0, 실패하면 0이 아닌 값을 반환하고, 최소 32개의 등록이 보장됩니다(ATEXIT_MAX).
  • 역순 호출: 나중에 등록한 cleanup2가 먼저 불립니다. 스택처럼 동작합니다.
  • exit(0): 등록 함수(2 → 1) → flush → _exit의 순서로 진행합니다. return 0이어도 같습니다. _exit(0)으로 바꾸면 두 함수 모두 불리지 않습니다(실습 5).

실행하면 "Cleanup 2" 다음에 "Cleanup 1"이 나옵니다. 등록의 역순이고, 자원을 얻은 순서의 반대로 놓는 관습과 맞습니다. 이어서 echo $?는 0입니다. exit(0)의 0이 앞에서 본 길을 따라 셸까지 온 것입니다. 종료 처리기는 임시 파일 삭제, 로그 닫기, 터미널 모드 복원처럼 "죽을 때 할 일"에 씁니다.

자식의 실패 경로는 _exit: 두 번 실행되는 함정

fork가 stdio 버퍼와 atexit 등록까지 복제한다는 점에서 함정이 생깁니다.

printf("hello");    /* 줄바꿈 없음 → 파이프·파일이면 버퍼에만 */
pid = fork();

fork 시점에 버퍼에 "hello"가 남아 있으면 부모와 자식이 각각 그 사본을 가집니다. 부모가 exit하면 flush되어 "hello"가 나가고, 자식이 execlp에 실패해 exit하면 자식의 사본이 또 flush되어 "hello"가 한 번 더 나갑니다. 출력은 hellohello입니다. 한 번만 찍은 줄이 두 번 나오고, 대상이 로그 파일이면 조용히 중복됩니다. 처리기도 사본이라, 자식이 exit하면 부모가 등록한 정리 함수가 자식에서 또 실행되어 결국 두 번 돕니다.

  • 해법 1: 자식의 실패 경로는 _exit(127)로 끝냅니다. 처리기 호출과 flush를 건너뛰고 커널로 바로 갑니다. 셸은 이때 127(못 찾음)이나 126(실행 불가)을 씁니다.
  • 해법 2: fork 직전에 fflush(NULL)로 복제될 버퍼를 비워 둡니다. 9주차 exit_how가 한 일입니다.

규칙으로 줄이면 이렇습니다. 자식은 exec에 성공하거나 _exit로 끝납니다. exit와 return은 부모의 것입니다. 자식은 상속된 버퍼를 다시 처리하지 않습니다.

3부 자식과의 동기화

종료와 회수는 다른 사건이다: 좀비

프로세스가 끝나는 것과 프로세스 표에서 사라지는 것은 별개의 사건입니다. 자식이 먼저 끝나는 보통의 경우, 실행 중(R/S)이던 자식이 exit → _exit로 끝나면 상태만 남긴 좀비(Z)가 되고, 부모가 wait(&st)로 상태를 가져가는 순간 프로세스 표에서 제거되어 소멸합니다.

  • 좀비 = 죽었지만 안 치워진 프로세스. 메모리와 fd는 이미 반납했고 종료 상태 한 칸만 남았습니다. 부모가 exit status를 얻어 갈 때까지 그 상태로 있습니다. ps의 STAT가 Z이고 <defunct>로 표시됩니다.
  • 치우는 사람은 부모입니다. wait나 waitpid가 상태를 가져가는 순간 사라집니다.
  • 부모가 먼저 죽으면 실행 중인 자식은 고아(orphan)가 되어 PPID가 1이 됩니다. 그 자식이 나중에 exit하면 잠깐 좀비가 되지만 init(PID 1)이 wait해서 대신 회수합니다. fork 실행에서 PPID가 1로 찍힌 것이 이 입양이었습니다.

ps의 STAT 문자는 R 실행, S 잠듦, Z 좀비, T 정지입니다(7주차 state_show에서 본 그 상태입니다).

좀비는 메모리는 없지만 PID 한 칸을 차지합니다. 오래 쌓이면 PID가 고갈되어 fork가 EAGAIN으로 실패할 수 있습니다. 또 좀비는 kill로 죽일 수 없습니다. 이미 죽었기 때문입니다. 해결은 부모를 고쳐 wait하게 하거나, 부모를 끝내 좀비를 init에 넘기는 것입니다.

좀비 관찰: 부모가 wait하지 않는 동안

C 코드 없이 셸의 exec(프로그램 교체)만으로 "wait하지 않는 부모"를 만들 수 있습니다.

(sleep 1 & exec sleep 4) & sleep 2; ps -o pid,ppid,stat,cmd; wait
  • (sleep 1 & exec sleep 4): 서브셸이 sleep 1을 백그라운드로 띄운 뒤 자기 자신은 sleep 4로 교체됩니다. 셸이었던 프로세스가 sleep이 되면서 wait할 코드가 사라졌습니다.
  • [sleep] <defunct>, STAT Z: 1초 뒤 끝난 자식이 좀비로 남습니다. 그 좀비의 PPID가 sleep 4의 PID이므로 책임자가 누구인지 ps에서 보입니다.
  • 4초 뒤 사라집니다. sleep 4가 끝나면 좀비는 PID 1에게 넘어가 회수됩니다. 부모가 할 일을 init이 하는 것입니다.

wait(2): 아무 자식이나 하나, 끝날 때까지

pid_t wait(int *status);         /* <sys/wait.h> — 자식 하나가 끝날 때까지 블록 */
  • 블록: 끝난 자식이 없으면 부모는 잠듭니다(S). 자식이 exit(2)로 끝나 종료 상태와 SIGCHLD가 전달되면 깨어납니다. 이미 끝난(좀비) 자식이 있으면 즉시 돌아옵니다.
  • 누가 끝났나: 반환값이 끝난 자식의 PID입니다. 자식이 여럿이면 가장 빨리 종료된 자식의 상태를 받습니다. 끝난 순서가 fork한 순서와 같다는 보장은 없습니다.
  • -1과 ECHILD: 기다릴 자식이 없다는 뜻입니다. 9주차 chld_reap이 이 값으로 루프를 끝냈습니다.
  • -1과 EINTR: 잡은 시그널 때문에 깨어난 경우입니다(9주차의 EINTR 패턴).
  • status에 NULL을 주면 상태는 버립니다. wait(&s)는 waitpid(-1, &s, 0)과 같습니다.

status의 비트와 매크로

glibc(Linux)에서 status는 비트 15~8에 종료 코드, 비트 6~0에 시그널 번호, 그 사이의 한 비트에 코어 덤프 여부를 담습니다. 실제 값으로 보면 다음과 같습니다.

status판정값어디서 봤나
0x0200WIFEXITEDWEXITSTATUS = 2wait.c (Status: 512, 200)
0x0300WIFEXITEDWEXITSTATUS = 3waitpid.c · 9주차 exit_how exit
0x000fWIFSIGNALEDWTERMSIG = 15 (TERM)9주차 exit_how term
0x0086WIFSIGNALEDWTERMSIG = 6, WCOREDUMP9주차 exit_how abort
0x137fWIFSTOPPEDWSTOPSIG = 19 (STOP)9주차 exit_how wait (WUNTRACED)
0xffffWIFCONTINUED9주차 exit_how wait (WCONTINUED)

이 배치는 glibc의 것이고, POSIX는 매크로만 약속합니다. 구성은 시스템마다 다를 수 있으므로 status >> 8 같은 직접 연산은 이식성이 없습니다. 그래서 비트를 직접 읽지 않고 매크로로 묻습니다. 순서는 판정 먼저, 값은 다음입니다.

  • 정상 종료: WIFEXITED(s)가 참이면 WEXITSTATUS(s)가 exit의 값(0~255)입니다.
  • 시그널 종료: WIFSIGNALED(s)가 참이면 WTERMSIG(s)가 시그널 번호, WCOREDUMP(s)가 코어 덤프 여부입니다.
  • 정지·재개: WIFSTOPPED(s)가 참이면 WSTOPSIG(s), 그리고 WIFCONTINUED(s).

wait.c: 자식 exit(2)를 부모가 받는다

wait 예제에서 자식은 "--> Child Process"를 찍고 exit(2)로 끝나고, 부모는 그 상태를 받아 원시 값과 매크로 값을 함께 보여 줍니다.

default :  /* parent process */
    while (wait(&status) != pid)
        continue;
    printf("--> Parent process\n");
    printf("Status: %d, %x\n", status, status);
    printf("Child process Exit Status:%d\n",
            WEXITSTATUS(status));
  • while (wait(&status) != pid): wait는 아무 자식이나 돌려주므로 다른 자식이 먼저 끝났을 수 있습니다. 그래서 내 자식의 PID가 올 때까지 반복합니다. status는 종료 상태를 받을 int이고 wait에는 그 주소를 넘깁니다. wait와 WEXITSTATUS는 sys/wait.h에 있습니다.
  • Status: 512, 200: 512와 0x200은 같은 값의 두 표기이고, 16진수가 바이트 경계를 보여 줍니다. 512 = 2 << 8, 곧 상위 바이트에 2가 실려 있습니다. 하위 바이트가 0이라는 것은 시그널도 없고 코어도 없다는 뜻입니다.
  • WEXITSTATUS: 상위 바이트를 꺼내 2를 줍니다. 직접 >> 8을 하지 않는 이유는 앞에서 본 이식성입니다.

실행하면 Child 줄이 먼저 나옵니다. 부모가 wait에서 자고 있었기 때문이고, fork.c와 달리 이번에는 순서가 보장됩니다. echo $?는 0입니다. 부모의 return 0이 셸에 전달된 것이고, 자식의 2는 부모가 받고 끝났습니다.

strace로 본 wait: wait4와 SIGCHLD

  • wait4(-1, …): wait(&status)는 wait4(-1, &status, 0, NULL)로 나타납니다. -1은 아무 자식이나 기다린다는 뜻입니다.
  • exit_group(2): 자식 249가 2로 끝나자 wait4가 그 결과를 들고 249를 반환했습니다. strace는 status를 매크로 식으로 풀어 [{WIFEXITED(s) && WEXITSTATUS(s) == 2}]처럼 보여 줍니다.
  • SIGCHLD: 회수와는 별개로 커널이 부모에게 SIGCHLD도 보냈습니다. 여기에도 si_status=2가 실려 있습니다(9주차의 재료).

반환값은 자식의 PID, 0(WNOHANG인데 아직 안 끝남), -1(ECHILD, EINTR) 중 하나입니다.

  • pid로 콕 집습니다. 자식이 여럿일 때 특정 자식(예를 들어 두 번째, 세 번째 자식)의 상태만 가져올 수 있습니다.
  • WNOHANG: 자식이 종료 전이라도 기다리지 않고 0으로 돌아옵니다. "끝났니?" 하고 찔러 보는 폴링입니다. 9주차의 관용구 while (waitpid(-1, &st, WNOHANG) > 0)은 끝난 자식을 있는 만큼 회수하고, 더 없으면 잠들지 않고 빠져나옵니다. 수거 루프가 WNOHANG이었던 이유입니다.
  • WUNTRACED: 9주차 exit_how가 STOP·CONT 보고를 받던 옵션입니다. 같은 함수입니다.

waitpid.c: WNOHANG으로 1초마다 찔러 본다

waitpid 예제는 switch 대신 if를 쓰지만 같은 세 갈래입니다(< 0 실패, == 0 자식, 나머지 부모). 자식은 "--> Child process"를 찍고 3초 잔 뒤 exit(3)을 합니다. 이 3초가 부모가 폴링할 시간을 벌어 줍니다.

printf("--> Parent process\n");
while (waitpid(pid, &status, WNOHANG) == 0) {
    printf("Parent still wait...\n");
    sleep(1);
}
printf("Child Exit Status : %d\n", WEXITSTATUS(status));
  • == 0이면 아직입니다. WNOHANG이라 자식이 살아 있으면 0이 돌아옵니다. 메시지를 찍고 1초 잔 뒤 다시 묻습니다.
  • 반환값이 pid가 되면 루프가 끝나고 WEXITSTATUS는 3입니다. status는 루프의 마지막 waitpid가 채웠습니다.

강의의 실행에서는 "Parent still wait..."가 세 번 나왔습니다. 0·1·2초의 세 질문에는 0이 돌아왔고, 3초째 질문에서 pid가 돌아와 3을 받았습니다. 영상의 실행에서는 네 번이었는데, 폴링 시점과 자식의 종료 시점이 겹치면 횟수가 달라집니다. 폴링 중에 ps를 보면 bash → 부모 → 자식의 사슬이 보이고 둘 다 S(잠듦)입니다. 부모는 sleep(1), 자식은 sleep(3) 안에 있기 때문입니다. 끝나면 셸이 [1]+ Done을 알립니다. 셸도 같은 일을 하는 것입니다. 백그라운드 작업을 waitpid로 회수하고 Done을 알립니다.

이것으로 할 수 있는 일

  • 미니 셸 1단계: 한 줄 읽기 → 토큰 나누기 → fork → 자식 execvp → 부모 waitpid → $? 표시. 조별 캡스톤의 출발점이고, 2차시에서 한 줄을 읽어 실행하는 셸을 만듭니다.
  • 명령 실행기: PATH를 검색해 실행하고, 못 찾으면 127("command not found"), 시그널 종료는 128+n으로 구분합니다.
  • 병렬 작업 분배: 자식 n개에 일을 나누고 waitpid로 종료 코드를 모읍니다. 11주차 mmap, 12주차 파이프로 확장됩니다.
  • 서비스 프로세스: fork 뒤 부모가 종료하면 고아가 된 자식이 배경에서 삽니다. nohup, setsid와 함께 2차시에서 다룹니다.

정리

  • fork: 한 번 호출, 두 번 반환. 메모리는 사본(COW), 열린 파일 설명은 공유, PID와 PPID는 새로 받습니다.
  • exec: 같은 PID에 새 프로그램. 성공하면 돌아오지 않고 stdio 버퍼도 함께 사라집니다.
  • fork + exec + wait가 셸의 명령 실행입니다. 설정 단계가 둘 사이에 있어 리다이렉션이 쉽습니다.
  • exit는 처리기(역순) → flush → _exit의 순서입니다. 자식의 실패 경로는 _exit로 끝냅니다.
  • 종료와 회수는 다른 사건입니다. 좀비는 부모의 wait가 치우고, 고아는 init이 맡습니다.
  • status는 매크로로 읽습니다: WIFEXITED → WEXITSTATUS, WIFSIGNALED → WTERMSIG.
