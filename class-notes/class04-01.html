지난 시간에는 파일을 열고 바이트를 읽고 쓰는 프로그램을 다뤘습니다. 이번 시간에는 범위를 넓혀, 그 파일에 붙은 이름과 속성, 그리고 파일을 찾아가는 경로와 디렉토리를 살펴봅니다. 시작하기 전에 질문 하나를 기억해 둡니다. 파일 이름을 지웠는데도 그 파일의 내용을 읽을 수 있을까요? 하드 링크와 열린 파일 디스크립터를 배우고 나면 이 질문에 이유를 붙여 답할 수 있습니다.

실습 프로그램은 두 개입니다. mystat은 파일 하나의 속성을 보여 주고, mini_ls는 디렉토리 안의 이름과 속성을 보여 줍니다. 출력만 따라 적지 말고, 어떤 API가 그 값을 얻었는지를 함께 찾아보는 것이 목표입니다.

1부 파일과 경로

파일을 세 부분으로 나누어 생각합니다. 우리가 입력하는 이름, 파일의 속성을 관리하는 inode, 그리고 실제 내용입니다. 이름 → inode → 내용이라는 관계를 이해하면 뒤에 나오는 링크와 삭제가 자연스럽게 이어집니다. 다만 이것은 일반 파일을 설명하기 위한 개념 모델이며, 실제 디스크 배치를 그린 것은 아닙니다.

파일 이름, inode와 데이터

note.txt라는 문자열은 디렉토리가 관리하는 이름입니다. 디렉토리 엔트리는 그 이름과 inode 번호를 연결합니다. inode에는 파일 종류, 권한, 소유자 같은 정보가 들어 있고, 일반 파일의 내용은 파일시스템이 관리하는 바이트입니다. 중요한 점은 파일 이름이 inode의 필드가 아니라는 것입니다. 이름은 디렉토리 쪽에 있습니다.

이름과 파일을 하나로 생각하면 뒤에서 혼동하기 쉽습니다. 하나의 파일에 이름을 두 개 붙일 수 있고, 두 이름이 같은 inode를 가리킨다면 내용도 하나를 공유합니다. 이름을 바꾸는 일이 파일을 복사하는 일과 다른 이유도 여기에 있습니다.

inode 번호는 같은 파일시스템 안에서만 고유합니다. 서로 다른 파일시스템에서는 번호가 겹칠 수 있으므로, 프로그램에서 두 파일이 같은 파일인지 확인할 때는 st_dev와 st_ino를 함께 봅니다.

두 가지 오해를 미리 정리해 둡니다. 첫째, 내용이 똑같은 파일 두 개가 반드시 같은 inode인 것은 아닙니다. 따로 만들었거나 복사한 파일은 내용이 같아도 다른 파일일 수 있으므로, 내용 비교와 파일의 동일성은 구분해야 합니다. 둘째, 빈 파일이라고 inode가 없는 것이 아닙니다. 0바이트 파일도 존재하며 속성을 가집니다.

Linux의 파일 종류

ls -l 출력의 첫 글자는 파일 종류를 나타냅니다.

문자종류설명
-일반 파일텍스트, 이미지, 실행 파일
d디렉토리파일 이름과 대상을 연결
l심볼릭 링크다른 대상을 가리키는 경로
c / b문자 장치와 블록 장치
p / sFIFO와 소켓

이번 시간에 집중할 것은 일반 파일, 디렉토리, 심볼릭 링크입니다. 장치, FIFO, 소켓도 파일 인터페이스로 다루지만 일반 파일과는 동작이 다르며, 지금은 종류를 구별할 수 있으면 충분합니다.

파일 이름의 확장자와 이 종류는 별개입니다. 확장자는 이름의 일부일 뿐이어서 파일 종류 비트를 바꾸지 않습니다. 이름을 .txt로 바꿨다고 내용의 바이트가 변환되지도 않습니다. 예를 들어 소스 파일 mystat.c와 실행 파일 mystat은 둘 다 일반 파일입니다. 서로 다른 것은 실행 권한과 내용의 형식입니다.

절대 경로와 상대 경로

  • 절대 경로는 /에서 시작합니다.
  • 상대 경로는 현재 작업 디렉토리 등을 기준으로 해석합니다. 일반적인 셸 명령에서는 현재 작업 디렉토리가 그 기준입니다.
  • 특수 이름 .은 현재 디렉토리, ..은 부모 디렉토리입니다.
/home/student/work/note.txt

# 현재 위치: /home/student/work
./note.txt
../work/note.txt

pwd
ls -ld . ..
ls -l ./note.txt

현재 작업 디렉토리가 /home/student/work라는 조건에서 위의 세 경로는 같은 파일을 가리킵니다. 문자열이 달라도 같은 파일을 찾을 수 있다는 뜻이며, ls -li로 두 표기의 inode 번호가 같은지 확인해 볼 수 있습니다. 반대로 같은 상대 경로 문자열이라도 현재 위치가 바뀌면 다른 대상을 찾을 수 있습니다. ../가 항상 /home/student를 뜻하는 것이 아니라, 그때그때 기준 위치의 부모 디렉토리를 뜻하기 때문입니다.

경로를 따라갈 때는 중간에 있는 디렉토리마다 검색 권한이 필요합니다. 또 openat 계열 함수에서는 현재 작업 디렉토리 대신 기준이 될 디렉토리의 FD를 지정할 수 있는데, 이 방식은 4부에서 다시 등장합니다.

2부 파일 속성과 권한

1부에서는 셸 명령으로 정보를 확인했습니다. 2부에서는 ls와 stat이 보여 주는 종류, 권한, 크기를 C 프로그램에서 어떻게 읽는지 살펴봅니다.

ls -l 출력 읽기

$ ls -l note.txt
-rw-r----- 2 student lab 4 Sep 21 10:00 note.txt

# 유형       -
# 권한       rw- r-- ---
# 링크 수    2
# 소유자     student
# 그룹       lab
# 크기       4 bytes
  • 종류와 권한: 첫 문자와 그다음 9개 문자를 나누어 읽습니다. 첫 글자 -는 일반 파일이고, 이어지는 아홉 글자가 권한입니다.
  • 링크 수: 권한 뒤의 2는 파일 크기가 아니라 하드 링크 수입니다.
  • 소유권: 사용자와 그룹별로 권한을 구분하므로 소유자와 그룹이 함께 표시됩니다.
  • 크기: 소유자와 그룹 다음의 4가 크기입니다. 일반 파일의 크기는 내용의 바이트 수입니다.

이 줄은 읽는 방법을 설명하기 위한 예시이며, 계정, 그룹, 시각은 실행 환경에 따라 달라집니다. 디렉토리를 볼 때는 두 가지를 주의합니다. 디렉토리 자체의 정보를 보려면 ls -ld 디렉토리처럼 -d를 붙여야 하고, 디렉토리의 크기 칸을 안에 든 파일 개수로 해석해서는 안 됩니다.

stat, lstat, fstat

세 함수는 모두 파일의 속성을 얻지만, 파일을 지정하는 방법이 다릅니다.

  • stat(path, &st): 경로가 가리키는 파일의 속성을 읽습니다. 마지막 심볼릭 링크를 따라갑니다.
  • lstat(path, &st): 마지막 경로 요소가 심볼릭 링크이면 링크 자체의 속성을 읽습니다.
  • fstat(fd, &st): 이미 열어 둔 파일 디스크립터로 속성을 읽습니다. open으로 받은 FD의 속성을 알고 싶을 때 씁니다.

공통 헤더는 <sys/stat.h>이고, 반환값은 성공 0, 실패 -1입니다. 실패하면 errno를 확인합니다. 먼저 성공했는지 검사하고, 성공한 경우에만 구조체의 필드를 사용해야 합니다.

stat과 lstat의 차이는 마지막 경로 요소가 심볼릭 링크일 때만 드러납니다. lstat도 경로 중간에 있는 심볼릭 링크는 해석합니다. 또 속성을 조회하는 데 파일 내용을 읽을 권한 자체가 필요한 것은 아니지만, 경로에 있는 디렉토리의 검색 권한은 필요합니다. 두 함수의 차이는 3부에서 깨진 링크로 직접 확인합니다.

struct stat의 주요 필드

필드의미
st_dev, st_ino파일시스템 식별 정보와 inode 번호
st_mode파일 종류와 접근 권한 비트
st_nlink하드 링크 수
st_uid, st_gid소유자
st_size일반 파일의 바이트 크기
st_atime / st_mtime / st_ctime접근 / 내용 수정 / 상태 변경 시각

모든 필드를 외울 필요는 없습니다. 이번 실습에서는 파일 식별, 종류와 권한, 링크 수, 크기에 집중합니다. st_mode 하나에 종류와 권한이 함께 들어 있다는 점, 그리고 앞의 ls -l 예시에서 본 “링크 수 2”와 “크기 4”가 각각 st_nlink와 st_size에서 나온다는 점을 연결해 두면 됩니다.

시각 필드에서는 한 가지를 정확히 구별해야 합니다. ctime은 생성 시각이 아니라 inode 상태 변경 시각입니다. 권한이나 링크 수처럼 inode의 상태가 바뀐 시각이고, 내용 수정은 mtime과 연결해서 봅니다. atime의 갱신은 마운트 옵션 등의 영향을 받으므로 파일을 읽을 때마다 반드시 바뀐다고 가정하면 안 됩니다. st_size의 의미도 파일 종류에 따라 다릅니다. 심볼릭 링크에서는 저장된 경로 문자열의 길이입니다.

mystat: 속성 조회와 파일 종류

struct stat st;
if (lstat(argv[1], &st) == -1) {
    perror(argv[1]);
    return 1;
}

if (S_ISREG(st.st_mode)) puts("regular");
else if (S_ISDIR(st.st_mode)) puts("directory");
else if (S_ISLNK(st.st_mode)) puts("symlink");

printf("inode=%ju links=%ju\n",
       (uintmax_t)st.st_ino,
       (uintmax_t)st.st_nlink);
  • 호출 결과: 조회에 성공한 뒤에만 st의 필드를 사용합니다. 실패하면 경로와 오류를 출력하고 프로그램을 끝냅니다.
  • 종류 판정: S_ISREG, S_ISDIR, S_ISLNK 매크로에 st_mode를 넘겨 판정합니다.
  • 출력 형식: 정수형을 uintmax_t로 변환해 %ju로 출력합니다. st_ino나 st_nlink 같은 필드의 원래 정수형 크기를 함부로 가정하지 않기 위해 변환과 형식 지정자를 맞춘 것입니다.

위 코드는 핵심 부분만 발췌한 것입니다. 완성된 mystat에는 인자 개수 검사와 필요한 헤더, 그 밖의 파일 종류 판정, 출력 오류 처리도 들어 있습니다. stat이 아니라 lstat을 사용하므로 심볼릭 링크 자체를 구별할 수 있다는 점이 뒤의 실습에서 중요해집니다.

함수의 반환값과 프로그램의 종료 상태는 별개입니다. lstat이 -1을 반환한다고 프로그램의 종료 상태가 -1이 되는 것이 아니며, 이 예제는 조회 실패 시 return 1, 사용법 오류에는 return 2를 사용합니다.

접근 권한 비트

소유자(u), 그룹(g), 기타 사용자(o) 세 묶음에 각각 rwx를 부여합니다. 일반 파일에서 r은 읽기, w는 쓰기, x는 실행 권한입니다. 한 묶음 안에서 r = 4, w = 2, x = 1을 더해 8진수 한 자리로 나타냅니다.

0640 = rw-r-----    0755 = rwxr-xr-x

640이면 소유자는 읽고 쓰며, 그룹은 읽기만 하고, 기타 사용자는 권한이 없습니다. 프로그램에서는 st_mode & 0777로 기본 rwx 비트만 추출합니다. st_mode에는 파일 종류도 함께 들어 있기 때문에 마스크로 권한 부분만 골라내는 것입니다.

여기서는 기본 rwx 비트에 집중합니다. set-user-ID, set-group-ID, sticky bit는 별도의 비트이며, ACL, capability, 읽기 전용 마운트도 실제 접근에 영향을 줍니다. 완성된 mystat.c는 이런 특별 권한 비트까지 표시할 수 있도록 07777을 마스크로 사용하지만, 이번 실습의 0640에서는 결과에 차이가 없습니다.

디렉토리의 r, w, x

같은 rwx 문자라도 디렉토리에서는 뜻하는 동작이 다릅니다.

  • r — 이름 목록 읽기: 디렉토리 안의 파일 이름을 나열할 수 있습니다.
  • x — 이름 검색과 경로 통과: 이미 아는 이름으로 내부 객체를 찾고 경로를 따라갈 수 있습니다. 디렉토리를 프로그램처럼 실행한다는 뜻이 아닙니다.
  • w — 디렉토리 엔트리 변경: 이름을 생성하거나 삭제하려면 일반적으로 디렉토리의 w와 x가 함께 필요합니다.

파일 내용에 쓰는 것과 디렉토리에서 이름을 바꾸는 것은 구분해야 합니다. 내용에 대한 접근은 파일의 권한이, 이름에 대한 변경은 부모 디렉토리의 권한이 결정합니다. 그래서 파일이 읽기 전용이어도 부모 디렉토리의 권한이 허용하면 그 이름을 삭제할 수 있습니다.

이 설명은 일반 사용자와 기본 권한을 기준으로 한 단순한 모델입니다. sticky bit, ACL, capability, 파일 속성 등 추가 조건이 있을 수 있습니다.

chmod와 umask

  • chmod: 기존 파일의 권한을 바꿉니다. 반환값을 확인합니다.
  • umask: 새 객체를 만들 때 허용하지 않을 비트를 제거합니다.
  • 8진수 표기: C의 0640과 십진수 640을 구분합니다. C 코드에서 권한을 쓸 때는 앞에 0을 붙여 8진수로 적어야 합니다.
# 기존 파일의 권한 변경
chmod 640 note.txt
ls -l note.txt

# C API: 성공 0, 실패 -1
if (chmod("note.txt", 0640) == -1)
    perror("chmod");

# 새 파일의 생성 권한 예시
0666 & ~0022 = 0644

위 블록은 셸 명령, C 코드, 계산식을 구분해 나란히 보여 주는 개념 예시이므로 통째로 터미널에 붙여 넣는 예제가 아닙니다.

생성 권한은 요청한 mode에서 umask의 비트를 제거한 값입니다. 요청 권한이 0666이고 umask가 0022이면 결과는 0644입니다. 숫자 뺄셈이 아니라 비트 연산이라는 점을 기억해야 합니다. 이 계산은 부모 디렉토리에 기본 ACL이 없는 경우에 해당합니다. 또 umask는 이미 존재하는 파일의 권한을 바꾸지 않습니다. umask를 바꾼다고 방금 만든 파일의 권한이 즉시 바뀌는 것이 아니며, 기존 파일의 권한을 바꾸는 것은 chmod의 역할입니다.

실습 1: 파일 속성 확인

RUN=$(mktemp -d)
printf 'ABC\n' > "$RUN/note.txt"
mkdir "$RUN/sub"

./mystat "$RUN/note.txt"
./mystat "$RUN/sub"
chmod 640 "$RUN/note.txt"
./mystat "$RUN/note.txt"
./mystat "$RUN/missing"

새 임시 폴더를 만들어 RUN에 담습니다. 이후 실습도 같은 셸의 RUN 디렉토리에서 이어서 진행하므로, 터미널을 닫거나 RUN을 다시 지정하지 않습니다. 확인할 것은 세 가지입니다.

  • 내용과 크기: ABC와 개행을 합쳐 4바이트인지 확인합니다. 세 글자만 세면 안 됩니다.
  • 종류와 권한: regular와 directory를 구별하고, chmod 전후의 권한을 비교합니다.
  • 실패 경로: 없는 경로를 주었을 때의 오류 메시지와 비정상 종료 상태를 확인합니다.
관찰 항목기대 결과
note.txt의 종류·크기type=regular, size=4
sub의 종류type=directory
chmod 후 권한mode=0640
missing오류 메시지, 바로 다음 echo $?는 1

종료 상태는 명령을 실행한 직후 echo $?로 확인합니다. 그 사이에 다른 명령을 실행하면 그 명령의 종료 상태가 나오므로 바로 이어서 실행해야 합니다. inode 번호의 실제 숫자는 환경마다 다르므로 다른 사람의 화면과 맞출 필요가 없습니다. 비교할 것은 각자 실행한 결과들 사이의 관계입니다. 없는 파일에서 오류가 출력되는 것도 이 실습에서는 기대한 동작입니다.

3부 하드 링크와 심볼릭 링크

1부에서 이름, inode, 내용을 나누어 보았습니다. 3부에서는 같은 파일에 이름을 하나 더 붙이는 하드 링크와, 경로를 저장하는 심볼릭 링크를 비교합니다. 한마디로 하드 링크는 “같은 inode”, 심볼릭 링크는 “대상 경로”입니다.

하드 링크

  • 같은 파일의 다른 이름: 여러 디렉토리 엔트리가 같은 inode를 가리킵니다.
  • 관찰할 값: 같은 파일시스템에서 st_ino가 같고, 하드 링크를 하나 추가하면 st_nlink가 증가합니다.
  • 생성 범위: 서로 다른 파일시스템 사이에는 만들 수 없습니다. 디렉토리에 대한 하드 링크는 일반적으로 제한합니다.
명령: ln old.txt new.txt
C API: link(oldpath, newpath)

하드 링크를 만드는 것은 파일 내용을 복사해 독립적인 파일을 하나 더 만드는 동작과 다릅니다. 두 하드 링크 사이에는 원본과 복사본의 구분이 없고, 이름 두 개가 같은 파일에 연결되어 있을 뿐입니다. 그래서 한 이름을 통해 내용을 수정하면 다른 이름으로 읽어도 같은 내용이 나옵니다. 그렇다면 한 이름만 없앴을 때 다른 이름은 어떻게 될지, 실습 2를 실행하기 전에 먼저 예측해 봅니다.

심볼릭 링크

  • 다른 경로를 저장하는 파일: 대상을 찾을 때 저장된 경로를 해석합니다. 대상과는 별도의 inode를 가집니다.
  • 대상과 수명이 분리됨: 대상이 없어도 링크는 존재할 수 있습니다. 디렉토리나 다른 파일시스템에 있는 대상도 가리킬 수 있습니다.
  • 상대 경로의 기준: 상대 대상 경로는 링크가 들어 있는 디렉토리를 기준으로 해석합니다.
명령: ln -s target.txt shortcut.txt
C API: symlink(target, linkpath)

ln -s TARGET LINK_NAME의 두 인자 순서에 주의합니다. 첫 번째가 저장할 대상 경로, 두 번째가 새로 만들 링크의 이름입니다. 대상 경로는 링크 안에 문자열 그대로 저장됩니다. 예를 들어 note.txt라는 상대 경로를 저장했다면, 링크가 들어 있는 디렉토리에서 note.txt를 찾습니다. 링크를 사용하는 사람의 현재 디렉토리가 기준이 아니므로, 사용자가 현재 위치를 바꿔도 찾는 곳은 달라지지 않습니다.

심볼릭 링크는 경로만 저장하므로, 링크를 만들어도 대상의 하드 링크 수는 늘어나지 않습니다.

심볼릭 링크에서 stat과 lstat

이제 stat과 lstat을 구분하는 이유가 분명해집니다. 대상 파일의 속성을 알고 싶은지, 링크 자체의 속성을 알고 싶은지에 따라 호출을 선택합니다.

  • stat: 대상 파일을 따라가므로 대상이 없으면 실패합니다.
  • lstat: 링크 자체를 조회합니다. S_ISLNK로 심볼릭 링크임을 판정할 수 있습니다.
# links.txt는 original.txt를 가리키는 symlink
stat("links.txt", &st);
/* original.txt의 속성 */

lstat("links.txt", &st);
/* links.txt 자체의 속성 */

# original.txt가 없어진 뒤
stat("links.txt", &st);   /* -1, ENOENT */
lstat("links.txt", &st);  /* 링크는 조회 가능 */

링크 파일은 남아 있으나 대상 경로를 해석할 수 없는 상태를 깨진 링크라고 합니다. 깨진 링크에 대해 stat은 대상을 찾지 못해 ENOENT로 실패하고, lstat은 남아 있는 링크 자체를 조사할 수 있습니다. 같은 경로에 대해 어떤 프로그램은 실패하고 다른 프로그램은 성공한다고 해서 모순이 아닙니다. 조사한 대상이 서로 다른 것입니다.

조건stat(링크)lstat(링크)
대상이 있고 경로 접근 가능대상의 속성링크 자체의 속성
링크는 남고 대상 이름은 없음실패, ENOENT링크 자체 조회 가능

위 코드는 두 호출의 차이를 보여 주는 개념 발췌이며, 그대로 컴파일되는 하나의 프로그램이 아닙니다. 또 다른 경로 접근 오류가 없는 실습 조건을 가정한 것입니다. 발췌에서 반환값 검사를 생략했다고 실제로도 생략해도 된다는 뜻은 아니며, 실제 코드에서는 모든 호출의 반환값을 검사합니다.

실습 2: 이름을 삭제한 뒤 비교

ln "$RUN/note.txt" "$RUN/hard.txt"
ln -s note.txt "$RUN/soft.txt"

ls -li "$RUN"
./mystat "$RUN/hard.txt"
./mystat "$RUN/soft.txt"

rm "$RUN/note.txt"
cat "$RUN/hard.txt"
cat "$RUN/soft.txt"
./mystat "$RUN/soft.txt"

실습 1에서 생성한 RUN 디렉토리 안에서만 실행합니다. 링크를 만든 뒤 바로 이름을 지우지 말고, 삭제 전의 값부터 기록합니다.

삭제 전에는 note.txt와 hard.txt의 inode와 링크 수를 비교합니다. 두 이름은 같은 device·inode를 보이고 둘 다 links=2입니다. soft.txt는 별도의 inode를 가지며 type=symlink로 나옵니다. 링크에 저장한 문자열 note.txt가 ASCII 8바이트이므로 이 실습에서 링크 자체의 size는 8입니다. 심볼릭 링크를 만든 것은 note.txt의 하드 링크 수를 늘리지 않습니다.

삭제 후의 결과는 다음과 같습니다. rm은 이 실습에서 만든 note.txt라는 이름 하나만 제거합니다.

관찰기대 결과이유
cat hard.txtABC 출력같은 파일을 가리키는 이름이 남아 있음
cat soft.txt오류, 종료 상태는 0이 아님저장된 note.txt 경로의 대상이 없음
mystat hard.txtlinks=1, size=4하드 링크 하나가 제거되어 2에서 1로 줄어듦
mystat soft.txttype=symlink, 조회 성공lstat은 링크 자체를 조사함

처음의 질문으로 돌아가면, 이름 하나가 없어져도 다른 하드 링크가 남아 있으면 내용을 읽을 수 있습니다. 반면 심볼릭 링크는 저장한 경로를 따라가므로 깨진 링크가 됩니다. 그래도 mystat은 lstat을 사용하므로 soft.txt 자체의 속성은 읽을 수 있습니다. 결과를 설명할 때는 “하드 링크는 살아 있고 심볼릭 링크는 깨졌다”에서 멈추지 말고, “같은 inode”와 “대상 경로”라는 표현을 넣어 이유까지 말할 수 있어야 합니다.

unlink와 열린 파일의 수명

이번에는 이름이 하나도 남지 않는 경우를 생각합니다.

  • unlink는 디렉토리에서 이름 하나를 제거합니다. C API로는 성공 0, 실패 -1입니다.
  • 다른 하드 링크가 남아 있으면 그 이름으로 계속 접근할 수 있습니다.
  • 마지막 이름을 지워도 이미 열린 FD로는 파일을 사용할 수 있습니다.
  • 마지막 하드 링크와 열린 참조가 모두 사라지면 저장 공간을 반환할 수 있습니다.

핵심은 이름을 찾아가는 경로와 이미 획득한 FD를 구분하는 것입니다. 이미 열어 둔 FD는 읽을 때마다 그 이름을 다시 찾는 것이 아니므로, 이름이 사라져도 영향을 받지 않습니다. 열린 참조가 파일의 수명을 유지하는 것입니다. 반대로 이름을 지운 뒤 같은 경로로 새로 open하면, 그 이름이 다시 만들어지지 않은 한 실패합니다.

이 순서는 셸에서도 확인할 수 있습니다. 서브셸에서 FD 3으로 파일을 먼저 열고, 이름을 지운 다음, 열린 FD로 읽습니다.

printf 'OPEN\n' > "$RUN/open-demo.txt"
(
    exec 3< "$RUN/open-demo.txt"
    rm "$RUN/open-demo.txt"
    cat <&3
    exec 3<&-
)

이름을 지운 뒤인데도 OPEN이 출력됩니다. 리다이렉션 문법을 외우는 것이 아니라 “먼저 열기 → 이름 삭제 → 열린 참조로 읽기”라는 순서를 보는 것이 목적입니다. 여기서 설명한 것은 일반적인 로컬 파일의 개념 모델이며, mmap 등의 참조도 파일의 수명에 영향을 줄 수 있습니다.

4부 디렉토리 탐색과 관리

지금까지는 파일 이름을 하나씩 직접 입력했습니다. 4부에서는 디렉토리에서 이름 목록을 읽고, 각 이름의 속성을 조회합니다. 이름 목록을 읽는 일과 속성을 읽는 일을 연결하면 작은 ls가 됩니다.

디렉토리 스트림

  • opendir(path): 디렉토리를 열어 DIR *를 얻습니다. 실패하면 NULL을 반환합니다.
  • readdir(dir): 다음 엔트리를 가리키는 struct dirent *를 얻습니다.
  • closedir(dir): 디렉토리 스트림을 닫습니다. 성공 0, 실패 -1입니다.

헤더는 <dirent.h>입니다. DIR *는 디렉토리 순회 상태를 관리하는 라이브러리 객체이므로 free로 해제하지 않고 closedir로 정리합니다. readdir가 돌려주는 d_name은 하위 항목의 이름이며 전체 경로가 아닙니다.

readdir의 반환값은 주의해서 봐야 합니다. 항목을 정상적으로 얻으면 포인터를 반환하지만, NULL은 더 읽을 항목이 없다는 뜻일 수도 있고 오류가 발생했다는 뜻일 수도 있습니다. NULL 하나만으로는 두 경우를 구분할 수 없습니다.

readdir의 끝과 오류 구분

for (;;) {
    errno = 0;
    struct dirent *ent = readdir(dir);
    if (ent == NULL) {
        if (errno != 0) {
            perror("readdir");
            status = 1;
        }
        break;
    }
    /* ent->d_name을 처리한다. */
}
if (closedir(dir) == -1) {
    perror("closedir"); status = 1;
}
  • 매번 초기화: readdir를 호출하기 직전에 errno를 0으로 만듭니다.
  • NULL 판별: 반환값이 NULL일 때 errno가 그대로 0이면 끝이고, 0이 아니면 오류입니다.
  • 정리: 반복문을 끝낸 뒤에는 closedir를 호출합니다.

초기화를 반복문 밖에서 처음 한 번만 해서는 안 됩니다. 반복문 안에서 호출한 다른 함수가 errno를 바꿔 놓았을 수 있기 때문입니다. 그렇게 되면 정상적으로 디렉토리 끝에 도달했는데도 이전에 남은 오류 값을 지금의 오류로 잘못 읽게 됩니다.

위 코드는 핵심 반복문만 발췌한 것으로, dir는 opendir에 성공한 뒤의 포인터이고 status는 0으로 초기화한 int입니다. 완성된 코드는 mini_ls에 있습니다.

디렉토리 엔트리 처리

  • d_name은 디렉토리 안의 이름이며 전체 경로가 아닙니다. 예를 들어 hard.txt라는 이름을 얻었다고 해서 현재 작업 디렉토리에 그 파일이 있다는 뜻이 아닙니다. 열어 둔 디렉토리의 항목입니다.
  • 반환된 정보는 라이브러리가 관리합니다. 필요한 이름과 정보는 다음 readdir 호출 전에 사용하거나 복사합니다.
  • 반환된 포인터를 free하지 않습니다.
  • d_type이 DT_UNKNOWN일 수 있습니다. 파일 종류가 언제나 확정된 값으로 오는 것이 아니므로 속성 조회를 준비해야 합니다.
  • 출력 순서는 정렬되어 있지 않을 수 있습니다. .과 ..을 어떻게 처리할지도 프로그램이 정책을 정해야 합니다.

이번 mini_ls는 .과 .. 두 이름만 생략합니다. 소스에서 두 strcmp 비교가 그 역할을 하며, 점으로 시작하는 이름을 모두 건너뛰는 것이 아니므로 .hidden 같은 숨김 파일 이름은 출력에 포함됩니다. 정렬을 따로 구현하지 않았으므로 출력 순서는 결과 비교의 기준이 될 수 없습니다. 재귀 순회는 이번 실습 범위 밖이며, 그렇게 확장하려면 심볼릭 링크를 따라갈지에 대한 정책과 순환 방지를 추가해야 합니다.

엔트리의 속성 조회

struct stat st;
int dfd = dirfd(dir);
if (dfd == -1) {
    perror("dirfd");
    closedir(dir); /* 정리 후 실패 반환 */
    return 1;
}

if (fstatat(dfd, ent->d_name, &st,
            AT_SYMLINK_NOFOLLOW) == -1) {
    perror(ent->d_name);
    status = 1;
    continue;
}
  • 기준 디렉토리: 열린 디렉토리의 FD를 기준으로 이름을 찾습니다. dirfd로 그 FD를 얻고, fstatat에 FD와 d_name을 함께 넘깁니다.
  • 링크 정책: AT_SYMLINK_NOFOLLOW로 마지막 심볼릭 링크 자체를 조회합니다.
  • 개별 실패: 실패한 이름을 기록하고 다음 엔트리를 읽습니다.

FD를 함께 넘기는 이유는 상대 이름을 어느 디렉토리에서 찾을지 분명히 하기 위해서입니다. stat(ent->d_name, &st)만 쓰면 프로세스의 현재 작업 디렉토리를 기준으로 이름을 찾게 되는데, 그곳은 지금 순회 중인 디렉토리와 다를 수 있습니다. AT_SYMLINK_NOFOLLOW를 지정했으므로 앞에서 깨진 soft.txt도 링크 자체의 정보를 출력할 수 있습니다.

항목 하나의 속성을 얻지 못하면 그 이름의 오류를 출력하고 다음 항목으로 넘어갑니다. 대신 status = 1을 남겨, 일부만 처리했는데 전체가 성공한 것처럼 보고하지 않도록 합니다. 디렉토리 자체를 열지 못한 경우와는 처리 위치가 다릅니다.

위 코드는 설명을 위해 두 구간을 함께 제시한 것입니다. dirfd는 반복 전에 한 번 호출하고 실패하면 closedir로 정리하며, fstatat은 readdir로 이름을 얻은 반복문 안에서 호출합니다. dirfd로 얻은 FD는 따로 닫지 않고 closedir로 스트림을 정리합니다. 실제 정리 경로는 mini_ls의 소스를 참고합니다. 한 가지 한계도 알아 둡니다. fstatat은 경로 문자열을 조합하는 일을 줄여 주지만, 순회하는 동안 일어나는 이름 변경 자체를 막아 주지는 않습니다.

디렉토리 생성과 삭제

  • mkdir(path, mode): 새 디렉토리를 만듭니다. 생성 권한에는 umask 등의 조건이 적용됩니다.
  • rmdir(path): 비어 있는 디렉토리를 삭제합니다. 안에 항목이 있으면 실패합니다.
  • 결과 확인: 두 함수 모두 성공 0, 실패 -1이며, errno로 실패 원인을 확인합니다.

헤더는 mkdir가 <sys/stat.h>, rmdir가 <unistd.h>입니다. 일반적인 실습에서 EEXIST는 이미 존재하는 이름, ENOTEMPTY는 비어 있지 않은 디렉토리를 뜻합니다. 이 두 경우는 정상적으로 예상해야 할 실패 입력입니다. 파일의 이름을 제거하는 unlink와 빈 디렉토리를 제거하는 rmdir는 구별해서 사용합니다.

셸에서는 다음 순서로 확인할 수 있습니다. 실습 3에서 쓸 sub는 그대로 두고 별도의 폴더를 사용합니다.

mkdir "$RUN/remove-demo"
printf 'x\n' > "$RUN/remove-demo/item.txt"
rmdir "$RUN/remove-demo"
echo $?
rm "$RUN/remove-demo/item.txt"
rmdir "$RUN/remove-demo"
echo $?

첫 번째 rmdir는 안에 항목이 있어 실패하고 종료 상태가 0이 아닙니다. 파일 이름을 제거한 뒤의 두 번째 rmdir는 성공하며 종료 상태는 0입니다. 여기서 “비어 있다”는 것은 일반적인 디렉토리에서 .과 .. 두 특수 항목 외에 다른 항목이 없는 상태를 말합니다.

현재 작업 디렉토리

  • getcwd: 현재 작업 디렉토리의 절대 경로를 얻습니다.
  • chdir: 현재 프로세스의 작업 디렉토리를 바꿉니다.
  • 영향 범위: 이후 상대 경로를 해석하는 기준이 바뀝니다. 부모 셸은 바뀌지 않습니다.
char cwd[4096];

if (getcwd(cwd, sizeof cwd) == NULL) {
    perror("getcwd");
    return 1;
}
puts(cwd);

if (chdir("sub") == -1) {
    perror("chdir");
    return 1;
}

헤더는 <unistd.h>입니다. 위 코드는 핵심 부분의 발췌입니다. 경로가 고정 크기 버퍼보다 길면 getcwd는 ERANGE로 실패할 수 있으므로, 4096을 모든 환경의 최대값으로 가정해서는 안 되며 버퍼가 부족한 경우도 오류로 처리합니다.

작업 디렉토리는 프로세스마다 가지는 상태입니다. 자식 프로그램 안에서 chdir를 호출해도 그 프로그램을 실행한 부모 셸의 위치는 바뀌지 않습니다. 어느 프로세스의 상태가 바뀌었는지 구별해야 합니다. 셸에서는 괄호로 만든 서브셸에서 같은 범위를 확인할 수 있습니다.

pwd
(cd "$RUN/sub" && pwd)
pwd

첫 번째와 마지막 출력은 같은 경로이고, 괄호 안의 출력만 sub 경로입니다.

실습 3: 작은 ls 실행

touch "$RUN/.hidden"
printf 'hello\n' > "$RUN/space name.txt"

./mini_ls "$RUN"
./mini_ls "$RUN/sub"
./mini_ls "$RUN/space name.txt"
./mini_ls "$RUN/missing"

# Ubuntu에서 시스템 호출 관찰
strace -e openat,getdents64,newfstatat,close \
  ./mini_ls "$RUN"

이번에는 정상적인 디렉토리만 검사하지 않고 세 종류의 입력을 차례로 넣습니다.

  • 정상 입력: 하위 이름, 종류, 크기를 출력하는지 확인합니다.
  • 경계 입력: 빈 디렉토리, 숨김 파일, 공백이 있는 이름을 확인합니다.
  • 실패 입력: 일반 파일과 없는 경로를 인자로 주어 오류를 확인합니다.

mini_ls는 정렬과 재귀 없이 한 디렉토리의 엔트리를 조회하며, 출력 열은 종류 inode 크기 이름 순서입니다. 앞의 실습을 그대로 따라왔다면 $RUN에는 .hidden, hard.txt, soft.txt, space name.txt, sub 다섯 항목이 보입니다. 출력 순서와 inode 번호는 환경에 따라 달라집니다. soft.txt는 종류가 l로 나오며, 깨진 심볼릭 링크여도 링크 자체의 속성 조회는 성공합니다. space name.txt의 크기는 6입니다.

입력기대 결과
빈 sub항목 출력 없음, 종료 상태 0
일반 파일 space name.txt디렉토리 열기 실패, 종료 상태 1
없는 missing디렉토리 열기 실패, 종료 상태 1

이 실습의 목표는 출력이 없는 것과 오류가 난 것을 구분하는 것입니다. 빈 폴더에서는 출력할 항목이 없지만 정상적으로 끝났고, 일반 파일이나 없는 경로는 opendir 단계에서 실패했습니다. 결과를 설명할 때는 출력 유무만 보지 말고 종료 상태와 실패한 위치를 함께 봅니다.

마지막의 strace 명령은 Ubuntu에서 시스템 호출을 관찰하기 위한 것입니다. readdir를 호출할 때마다 같은 이름의 시스템 호출이 한 번씩 발생하는 것은 아니며, libc가 엔트리를 묶어 읽을 수 있습니다. 구체적인 시스템 호출 이름은 libc와 아키텍처에 따라 다를 수 있습니다.

확인 퀴즈

명령을 다시 실행하기 전에 먼저 말로 설명해 봅니다. 답은 한두 문장이면 충분하지만 이유가 들어 있어야 합니다.

질문답주의할 오해
하드 링크 두 개는 inode와 파일 내용을 어떻게 공유하는가?같은 파일시스템의 같은 inode와 파일 내용을 공유합니다.복사한 두 파일이 아닙니다.
깨진 심볼릭 링크에 stat과 lstat을 호출하면 어떻게 다른가?대상이 없으면 stat은 ENOENT로 실패하고, lstat은 남아 있는 링크 자체를 조회할 수 있습니다.링크 자체의 존재와 대상의 존재를 구별합니다.
디렉토리의 x 권한은 어떤 동작에 필요한가?이름 검색과 경로 통과에 필요합니다.디렉토리를 프로그램처럼 실행한다는 뜻이 아닙니다.
readdir가 NULL을 반환했을 때 어떤 값을 더 확인해야 하는가?호출 직전에 0으로 만든 errno입니다. 0이면 끝, 아니면 오류입니다.오래 남아 있던 errno를 그대로 읽지 않습니다.
파일 이름을 삭제한 뒤에도 열린 FD로 읽을 수 있는 이유는?열린 참조가 파일의 수명을 유지하므로, 이름을 다시 찾지 않고 사용할 수 있습니다.삭제 뒤 같은 경로로 새로 open하는 경우와 구별합니다.

답이 흔들리는 부분이 있다면 이름, 속성, 내용, 열린 참조 가운데 무엇을 다루는 질문인지 다시 표시해 봅니다. 하드 링크는 이름과 inode의 관계이고, lstat은 링크 자체의 속성, readdir는 이름 목록, 열린 FD는 이미 확보한 참조입니다.

정리

  • mystat으로 종류, inode, 링크 수, 권한, 크기를 확인합니다.
  • 링크 생성 전후와 이름 삭제 전후의 결과를 비교합니다.
  • mini_ls에서 디렉토리의 끝과 오류를 구분합니다.
  • 코드와 실행 로그, 그리고 관찰한 차이를 설명하는 글을 제출합니다.

실행 로그에는 일반 파일과 디렉토리, 하드 링크와 심볼릭 링크, 깨진 링크, 없는 경로가 들어가야 하고, 설명에는 stat/lstat의 차이와 디렉토리의 x 권한이 포함되어야 합니다. inode 숫자를 다른 사람의 화면과 맞추는 것이 아니라, 자신의 실행 안에서 어떤 값이 같고 무엇이 달라졌는지를 보여 주는 것이 중요합니다. 추가 구현으로는 이름 정렬 또는 숨김 파일 옵션 가운데 하나를 선택해 볼 수 있습니다.

이번 시간의 내용은 파일 내용, 파일 속성, 파일 이름의 관계를 구분해 설명하는 것으로 모입니다. 파일 이름으로 대상을 찾고, 그 속성을 조사하고, 디렉토리에서 이름들을 얻는 흐름을 연결했습니다. 예를 들어 cat soft.txt는 실패했는데 mystat soft.txt는 성공한 이유를 한 문장으로 설명할 수 있다면 이 관계를 이해한 것입니다.
